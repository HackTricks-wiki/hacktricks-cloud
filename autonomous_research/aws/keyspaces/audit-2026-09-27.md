## Verified results

### Enumeration and `system*` authorization

1. `ListKeyspaces` initially returned only the four service system keyspaces.
2. After fixture creation, `ListKeyspaces`, `ListTables`, `GetTable`, `ListTagsForResource` and CQL `system_schema.tables` were tested under restrictive STS session policies.
3. `cassandra:Select` on the exact user-table ARN alone was insufficient. SDK calls failed on the service's internal `keyspaces`, `tables` or `tags` system tables, and a normal Cassandra driver could not initialize without system-table reads.
4. `cassandra:Select` on `arn:aws:cassandra:us-east-1:228478051196:/keyspace/system*` alone disclosed all user keyspace/table names, schema, comments and tags through the SDK and CQL. It did not permit `SELECT` from the user table.
5. Exact-table `Select` plus `system*` read the fixture row. `UPDATE` and `DELETE` were denied without `Modify`.

Conclusion: system-keyspace read access is an account-wide schema/configuration reconnaissance permission, not merely driver plumbing.

### CQL authentication

- SigV4 authentication with temporary assumed-role credentials worked through `cassandra.us-east-1.amazonaws.com:9142`.
- TLS was required. A connection without any authentication provider reached the endpoint but failed with `AuthenticationFailed: Remote end requires authentication`.
- The Python driver's default `LOCAL_ONE` consistency was rejected. `LOCAL_QUORUM` succeeded.
- An IAM user with `Select`/`Modify` on the fixture plus system-table `Select` received a service-specific credential for `cassandra.amazonaws.com`. After propagation, plaintext Cassandra authentication read and wrote the table. Marking the credential inactive prevented authentication. The credential, inline policy and IAM user were deleted.

### Blind mutation

- A session with exact-table `cassandra:Modify` and only system-keyspace `Select` successfully performed `INSERT` and `UPDATE` while a target-table `SELECT` was denied.
- This confirms that data poisoning/deletion is independently exploitable by a blind writer that knows the schema and keys.

### PITR and restore

- Exact-table `cassandra:Alter` alone disabled and re-enabled PITR. Re-enabling produced a new `earliestRestorableTimestamp`; the prior recovery window was not preserved.
- `RestoreTable` authorization was probed with restrictive sessions. It required `cassandra:Restore` on the target ARN as well as the source ARN, then required `cassandra:Select` on the source. Supplying `Select` only on the target and system keyspaces did not bypass the source read check.
- A tags override additionally required `cassandra:TagResource` on the target.

Conclusion: restore is operationally sensitive but is not a source-`Select` privilege-escalation bypass.

### Client-side timestamps

- Exact-table `cassandra:Alter` enabled client-side timestamps. The setting is irreversible for that table.
- A blind `Modify` session attempted a value one day in the future and received an error revealing the accepted timestamp range: about two days in the past through five minutes in the future.
- A value roughly four minutes in the future succeeded. A subsequent ordinary administrator update did not replace it. A corrective write using a timestamp one microsecond greater did.

Conclusion: timestamp precedence can briefly defeat normal writes and is worth mentioning as an integrity nuance, but the approximately five-minute future bound is too short to publish as a standalone persistence technique.

### CDC stream access

- Enabling CDC with exact-table `Alter` initially failed because the account lacked `AWSServiceRoleForAmazonKeyspacesCDC` and the session lacked `iam:CreateServiceLinkedRole`.
- Adding only the official, service-constrained permission for `cassandra-streams.amazonaws.com` allowed a `NEW_AND_OLD_IMAGES` stream to be enabled.
- `ListStreams` worked with `cassandra:ListStreams` on `Resource: "*"` and no system/table `Select`.
- A session containing only exact-stream `GetStream`, `GetShardIterator`, and `GetRecords` plus wildcard-resource `ListStreams` read a captured record. The record contained partition key, clustering key and plaintext `newImage.secret = CDC-EXFIL-DEMO`. The session had no `Select` permission on the user table or system keyspaces.

Conclusion: CDC is an independent future-data exfiltration path and a useful service-level persistence mechanism when an attacker can both enable and consume a stream.

### Replication and KMS probes

- A multi-Region update under `cassandra:*` constrained to the test keyspace/table, but without IAM permission, failed before mutation on `iam:CreateServiceLinkedRole`. The keyspace remained `SINGLE_REGION`; no replication service-linked role was created.
- Earlier narrower probing also showed that replication carries tag authorization dependencies.
- An encryption update to a deliberately nonexistent customer-managed key returned `ValidationException: Specified encryption key is invalid or not found`; the table remained on its AWS-owned key.
- No KMS key or replica was created. Documentation of their security consequences is based on the official service authorization and Keyspaces guides rather than claiming a successful mutation.

### Cross-account and resource policies

- The Keyspaces API has no resource-policy operations. Official IAM documentation states that Keyspaces does not support resource-based policies.
- Cross-account guidance uses an assumable role in the resource-owning account, including when VPC endpoints/subnets are shared. A VPC endpoint policy is an additional filter and not a cross-account resource grant by itself.

### CloudTrail observations

- `CreateKeyspace` and `CreateTable` appeared in Event history as management events from `cassandra.amazonaws.com`.
- `requestParameters.rawquery` contained the generated CQL, including schema, comment, capacity, PITR and tags. Both a failed early `CreateTable` attempt and the successful retry produced events.
- `SELECT`, `INSERT`, `UPDATE`, and `DELETE` were absent from ordinary Event history, as expected for data events.
- A temporary single-region trail selected only `AWS::Cassandra::Table` data events for the exact fixture table. The delivered file captured table DML and CDC access. `Insert` identified the table and column names but redacted primary-key values and omitted the inserted value. `GetShardIterator` and `GetRecords` contained both table and stream resource ARNs. `GetRecords` recorded the opaque iterator and limit, not returned change records. This demonstrates that exact-table selectors cover CDC reads whose event resources include that table.

## Rejected or bounded hypotheses

| Hypothesis | Result | Publication decision |
| --- | --- | --- |
| Unauthenticated access to system schema or rows | TLS connection succeeded but Cassandra required authentication before a session was established | No standalone unauthenticated page; negative result stays in ledger |
| PITR restore bypasses source `Select` | Rejected live; source `Select` and `Restore` on both source and target were enforced | Document the boundary, not a privesc technique |
| Resource policy enables direct public/cross-account table access | Rejected by API surface and official IAM documentation | Mention role-based cross-account model in enum page |
| Future CQL timestamp provides durable persistence | Bounded to roughly five minutes in the future | Mention only as integrity/post-exploitation nuance |
| Adding a replica Region exfiltrates cross-account | Replicas stay in the resource account and require multi-Region permissions plus a service-linked role | No privesc technique; document cost/availability risk only |
| Switching to an attacker KMS key reveals plaintext | KMS observes cryptographic operations, not table plaintext; the practical abuse is availability/control of decryptability | No exfiltration claim |
| Customer-managed KMS or live multi-Region validation | Avoided because creating a KMS key leaves a deletion window and replica changes complicate immediate cleanup | Retain as future isolated-account research |
