## Environment-credential findings

The built-in `CustomAwsService` blueprint could be enabled without provisioning roles. A manual environment created from it initially reported `DISABLED`, then became `ACTIVE` after the custom IAM role was associated.

The environment role:

- trusted `datazone.amazonaws.com` for `sts:AssumeRole` and `sts:TagSession` with `aws:SourceAccount`;
- allowed only `s3:ListAllMyBuckets` for the test;
- had no permissions boundary;
- was associated only after exact `iam:PassRole` succeeded.

Both owner and catalog-viewer sessions with only `datazone:GetEnvironmentCredentials` received credentials for this role. CloudTrail showed DataZone's injected session policy:

```json
{
  "Version": "2012-10-17",
  "Statement": {
    "Effect": "Allow",
    "NotAction": "sts:AssumeRole",
    "Resource": "*"
  }
}
```

The credentials were valid for 900 seconds and allowed the role's S3 inventory action. This aligns with the documented custom-environment model and the documentation that project members can access environments/read subscribed data. It is a dangerous expected capability/misconfiguration amplifier, not an AWS defect.

## CloudTrail observations

All observed DataZone operations were management events associated with the domain ARN. The account had no trail or event data store, but Event history was sufficient.

Key results:

- `GetEnvironmentCredentials`: `readOnly: true`, `managementEvent: true`, and `responseElements: null`; credentials were not recorded.
- STS `AssumeRole`: `userIdentity.type = AWSService`, `invokedBy = datazone.amazonaws.com`, role ARN, 900-second duration, profile/environment session name, injected session policy, and `dz`/`RedshiftDbUser` tags.
- `GetIamPortalLoginUrl`: `authCodeUrl` was redacted as `***`; `userProfileId` remained.
- `CreateAssetRevision`: request `name`, `description`, and `formsInput` were `***`, but the response contained the resulting form content, including the test poison marker.
- `SearchListings`: request contained search text and `additionalAttributes`; response contained the original test secret marker. The event unexpectedly classified the search as `readOnly: false`, but this is telemetry metadata rather than a security defect.
- `CreateProjectMembership`: retained project ID, user-profile ID, and designation for both the denied self-grant and successful owner grant.
- `AssociateEnvironmentRole`: retained the URL-encoded role ARN, domain, and environment.
- `PutEnvironmentBlueprintConfiguration`: retained provisioning/manage-access role ARNs, blueprint ID, domain, and enabled Regions.

Because catalog form values can be copied into CloudTrail response elements, CloudTrail readers and log destinations should be treated as additional recipients of published metadata. This reinforces the documented requirement not to place secrets in DataZone metadata.

## Useful book techniques accepted

1. Domain-wide extraction of published listing forms using `SearchListings --additional-attributes FORMS` without producing-project membership.
2. Project-member/private asset, environment, data-source, and subscription discovery, plus nonmember project-membership enumeration.
3. Custom environment-role credential extraction with `GetEnvironmentCredentials`, including catalog-viewer access, the 15-minute session, and the broad `NotAction: sts:AssumeRole` session policy.
4. `AssociateEnvironmentRole` plus exact `iam:PassRole` as a role-credential escalation/distribution path.
5. `PutEnvironmentBlueprintConfiguration` plus PassRole as a future provisioning/manage-access role substitution path (configuration verified; real infrastructure provisioning intentionally not launched).
6. Asset revision poisoning followed by listing publication under a trusted asset identity.
7. Durable attacker project membership and environment-role association as DataZone service-level persistence.

## Rejected, constrained, or deferred ideas

### Not promoted

- **Generic unauthenticated access:** unsigned APIs rejected authentication. The portal root exposed only the static application shell.
- **Simple IAM-only self-membership escalation:** DataZone's internal project ACL denied it.
- **Arbitrary environment-action phishing:** the service rejected a non-AWS-console URL.
- **Generic delete/update denial of service:** obvious write/delete permissions without a distinctive DataZone security primitive were omitted.
- **Portal auth-code disclosure through CloudTrail:** CloudTrail redacted the URL as `***`; no defect.
- **Catalog viewer credential vending as a zero-day:** the behavior is security-sensitive, but custom environments are documented as available to project members and administrators are explicitly told to make the role least-privileged.
- **CloudTrail catalog metadata as a zero-day:** forms are user-supplied catalog metadata and should not contain secrets; the log copying is documented/auditable service behavior.

### Deferred candidates

- Cross-account associated-domain/account-pool and RAM invitation acceptance/rejection in an AWS Organization with a disposable second account.
- Complete Glue/Lake Formation and Redshift subscription fulfillment with narrowly scoped roles, including revocation propagation and race conditions.
- Default Data Lake/Data Warehouse blueprint environment provisioning and CloudFormation template substitution. It was not launched because it would create several additional resources and was unnecessary to verify the PassRole boundary.
- Identity Center user/group synchronization, profile assignment/deactivation, and stale-group membership behavior in a domain with an existing IAM Identity Center instance.
- Data-source Redshift secret/role validation and whether update/run paths re-check `iam:PassRole` after a role was initially stored.
- Subscription request metadata forms and asset-scope filters across product/listing revisions.
- Custom CloudFormation blueprint template URL validation, same/cross-account S3 access-point behavior, and template replacement after approval.
