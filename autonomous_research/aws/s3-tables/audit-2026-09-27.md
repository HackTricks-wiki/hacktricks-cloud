# AWS S3 Tables security audit — 2026-09-27

## Scope and safety

- Service: Amazon S3 Tables (`s3tables`), Region `us-east-1`, authorized account `228478051196` through `hacktricks-training` and `ChackBotAdministratorRole`.
- Test assets used only the `ht-s3tables-audit-*` prefix, an empty Iceberg table, harmless self-grants to temporary IAM roles and a same-account empty replication destination.
- No real data, external principal, public policy, KMS key, Glue/Lake Formation integration, analytics compute or paid long-lived workflow was used.
- Replication was removed before its empty source had metadata to copy. Every table, namespace, bucket, policy and IAM role was deleted.
- No unexpected AWS security defect was confirmed. No `/home/tester/cloud_bb/aws` report was created.

## Baseline and current surface

- No existing HackTricks page mentioned `s3tables`, S3 table buckets or their distinct IAM prefix.
- AWS CLI: `2.34.45`, S3 Tables model `2018-05-10`.
- Current local model: 49 control-plane operations.
- Current AWS service-authorization data: 53 IAM actions. The four permission-only/optional-parameter actions absent as standalone control-plane APIs are `GetTableData`, `PutTableData`, `PutTableEncryption` and `PutTableStorageClass`.
- Resources: `TableBucket` (`...:bucket/<name>`) and `Table` (`...:bucket/<name>/table/<generated-id>`).
- Condition keys: request/resource/tag keys plus `s3tables:KMSKeyArn`, `s3tables:SSEAlgorithm`, `s3tables:StorageClass`, `s3tables:TableBucketTag/<key>`, `s3tables:namespace` and `s3tables:tableName`.
- Permission-management actions: `PutTableBucketPolicy`, `DeleteTableBucketPolicy`, `PutTablePolicy`, `DeleteTablePolicy`.
- Modern surfaces reviewed: bucket/table encryption and storage class, metrics, maintenance, record expiration, resource policies, table metadata pointer, Iceberg REST data plane, bucket/table replication and status.
- AWS managed policies observed on 2026-09-27:
  - `AmazonS3TablesReadOnlyAccess` v3: `s3tables:Get*`/`List*` on `*`.
  - `AmazonS3TablesFullAccess` v6: `s3tables:*` on `*`, plus `iam:PassRole` on `*` when passed to `replication.s3tables.amazonaws.com`.
  - `AmazonS3TablesLakeFormationServiceRole` v6 also exists for the Glue/Lake Formation integration.

## Initial inventory

`ListTableBuckets` returned zero table buckets. Therefore the authorized account initially had no namespaces, tables, policies, maintenance configurations or replication configurations to inspect. An unsigned `ListTableBuckets` call returned `MissingAuthenticationTokenException`.

## Live tests

### Disposable resource lifecycle

Created:

- table bucket `ht-s3tables-audit-20260927-01`;
- namespace `ht_audit`;
- empty Iceberg table `empty_table`;
- generated exact table ARN and warehouse location;
- later, empty destination bucket `ht-s3tables-audit-20260927-02`.

`GetTable` returned the generated table ID/ARN, warehouse, version token, owner, creator, timestamps and format. `GetTableMetadataLocation` returned the warehouse/version but no root metadata file because no Iceberg content was written.

### Table-policy self-escalation

Created a temporary role whose only S3 Tables permission was `s3tables:PutTablePolicy` on the exact generated table ARN.

1. `GetTable` was denied before the resource-policy write.
2. The role installed a table policy naming its own IAM role principal and granting only `GetTable` and `GetTableMetadataLocation` on that exact table.
3. The same assumed-role principal immediately succeeded with both reads.
4. An administrator deleted the policy.

Result: verified expected privilege escalation within the table boundary. No `Get*` permission is a prerequisite to `PutTablePolicy` when the bucket/name are already known.

### Table-bucket-policy self-escalation

Replaced the temporary role's identity policy with only `s3tables:PutTableBucketPolicy` on the exact table-bucket ARN.

1. `ListNamespaces` was denied before the resource-policy write.
2. The role installed a table-bucket policy granting itself `ListNamespaces` and `CreateNamespace` on that bucket.
3. It listed the existing namespace and created harmless `self_granted_ns`.
4. An administrator deleted the namespace and table-bucket policy.

Result: verified the broader bucket/namespace self-grant path. This does not escape S3 Tables or override explicit denies.

### Replication caller minimum and PassRole

Created a destination table bucket and a replication role trusting `replication.s3tables.amazonaws.com`. The role had exact source-table reads and destination-bucket/table writes documented for S3 Tables replication.

1. A caller with only `s3tables:PutTableReplication` on the exact source table was denied; the response identified missing authorization/PassRole.
2. Added only `iam:PassRole` on the exact replication role with `iam:PassedToService = replication.s3tables.amazonaws.com`.
3. `PutTableReplication` succeeded and returned a version token/status even though the caller did **not** have `GetTableReplication`.
4. Administrator `GetTableReplication` returned the exact role and destination configuration. The empty source had no metadata, so status contained no destination replica and the destination remained empty.
5. Deleted the configuration using its version token and verified `GetTableReplication` no longer succeeded before deleting resources.

Result: verified the exact caller minimum for table-level creation as `PutTableReplication` plus constrained `PassRole`. `GetTableReplication` is useful for viewing/updating/deleting later, but it was not a create-time dependent action in the live API.

The official cross-account workflow additionally requires a destination table-bucket policy. AWS documents that replication copies all data files, delete files, metadata and snapshot history, including future changes, to as many as five destination buckets.

### Public/unauthenticated boundary

- AWS documentation explicitly states that public table/table-bucket policies and presigned URLs are unsupported.
- S3 Tables Iceberg REST uses SigV4 with signing name `s3tables`.
- An unsigned control-plane request failed with `MissingAuthenticationTokenException`.

Result: no unauthenticated-access page. Authenticated cross-account resource-policy access belongs in persistence/post-exploitation coverage.

## CloudTrail observations

- S3 Tables uses `eventSource=s3tables.amazonaws.com` and management event category for its control plane.
- Live event history recorded create/get/delete calls, both denied and successful access checks, `PutTablePolicy` and `PutTableBucketPolicy`.
- Successful `GetTable`, `GetTableMetadataLocation`, policy writes and deletes had `responseElements: null`; create operations returned resource identifiers.
- Both denied and successful `PutTableReplication` calls and the successful `DeleteTableReplication` call appeared as management events. This confirms the newer replication APIs use the control-plane event category even though the public logging page's static action list lagged the current API model.
- Iceberg object reads/writes are CloudTrail **data events**, which are not recorded by default. Selectors must include `AWS::S3Tables::Table` and/or `AWS::S3Tables::TableBucket`. This is the most important detection gap for table exfiltration.
- Automatic compaction/snapshot expiration produces `TablesMaintenanceEvent` service events.

## Published expected techniques

1. Post-exploitation: load and extract an Iceberg table, including retained snapshot history, with exact table-scoped metadata/data actions.
2. Post-exploitation: poison the Iceberg root metadata with the supported data-write/update actions.
3. Privilege escalation: use table/table-bucket policy-write permission to self-grant otherwise denied S3 Tables actions.
4. Persistence: add an authenticated external principal through a table or table-bucket policy.
5. Persistence/exfiltration: configure continuous same/cross-account replication through a constrained passed role.

Every public technique documents impact or persistence scope, exact permissions/resources, detection/log events and stealth.

## Considered but not promoted

- Delete table/bucket/namespace and early record expiration: obvious destructive availability/data-retention effects, not a distinct attack primitive.
- Disable compaction/snapshot cleanup or metrics: operational/cost abuse with weak offensive value.
- Change KMS encryption or storage class: expected administrative behavior and mainly availability/cost impact; KMS policy remains a separate control.
- Rename a table: visible integrity/availability disruption without distinct escalation.
- `CreateTable` with initial metadata: requires `PutTableData` when metadata is supplied; no permission bypass found.
- Arbitrary metadata URI redirect: `UpdateTableMetadataLocation` restricts the root URI to the table's own warehouse and required suffix. The public technique is deliberately framed as in-warehouse metadata poisoning, not arbitrary cross-bucket redirect.
- Replication as arbitrary role execution: false. Passing a role lets the S3 Tables replication service use it only for replication; it is valuable when that role can read target tables/write an attacker-accessible destination, not as general code execution.
- Glue/Lake Formation integration: important additional authorization plane, but generic Glue/Lake Formation techniques should not be duplicated here without a distinct S3 Tables bypass.
- Public/anonymous access: unsupported and unsigned requests fail. No unauthenticated technique.
