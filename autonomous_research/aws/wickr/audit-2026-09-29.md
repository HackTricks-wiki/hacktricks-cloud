# AWS Wickr boundary audit — 2026-09-29

## Scope and inventory

- Allowed Regions checked: `us-east-1`, `eu-west-1`.
- No Wickr networks existed in either Region. The Wickr endpoint was usable in `us-east-1`; the
  `eu-west-1` endpoint was unavailable.
- No service resources were created or changed. Synthetic reads and IAM simulation were used to
  establish the reachable authorization boundary without provisioning a network.

## Publishable expected-functionality techniques

| Surface | Result | Preconditions / boundary | Public treatment |
| --- | --- | --- | --- |
| `GetOpentdfConfig` | Documented response directly contains `clientId`, `clientSecret`, `domain`, and `provider` | Known eight-digit network ID; OpenTDF configured; exact-network `wickr:GetOpentdfConfig` | Publish as credential disclosure. OpenTDF access remains bounded by client scopes and entitlements. |
| `GetOidcInfo` | Documented response contains distinct stored `clientSecret` and `secret` fields | Known network ID; OIDC configured; exact-network `wickr:GetOidcInfo` | Complete existing technique. Optional access/ID/refresh tokens additionally require caller-supplied valid OAuth parameters/code. |
| `ListUsers` | Preview response includes `inviteCode`, user status, invite expiry/validation state, groups, and administrator status | Known network ID; exact-network `wickr:ListUsers`; pending unexpired invitation | Publish as conditional Wickr foothold. The code is consumed through the client and the enrolling user sets the password. |
| `CreateDataRetentionBotChallenge` | Existing challenge-generation technique remains supported by current API and IAM model | Data retention enabled; exact-network action | Retrofit explicit minimum permission, impact, stealth, and telemetry. |

The current Service Authorization Reference scopes all four relevant actions to the Wickr `network`
resource type: `arn:${Partition}:wickr:${Region}:${Account}:network/${NetworkId}`. IAM simulation
allowed each action on the exact ARN and denied a mismatched network ARN.

## Telemetry observations

- A signed synthetic `GetOpentdfConfig` call reached Wickr and produced a read-only management event
  from `wickr.amazonaws.com`. The request recorded `networkId`; the not-found response was null.
- A `GetOidcInfo` sentinel request showed only `networkId` in CloudTrail. Optional URL/OAuth
  parameters were omitted from the observed request record, and the response was null.
- `ListUsers` generated a read-only management event with `networkId` and `maxResults`; the response
  was omitted.
- Successful secret-returning responses could not be inspected without a configured network, so the
  public page does not assert that successful secrets are or are not present in CloudTrail.

## Secure negatives and rejected claims

- Signed calls using a fake network ID were authorized to the service and returned the service-level
  failure rather than disclosing another network. Unsigned calls failed authentication.
- No resource-policy, cross-account, or unauthenticated Wickr management surface was identified.
- `GetOidcInfo` is not documented to mint a token from only the Wickr permission. A valid IdP flow,
  supplied parameters, and authorization code are still required where applicable.
