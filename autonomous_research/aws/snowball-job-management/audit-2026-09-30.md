# AWS Snowball Job Management audit (2026-09-30)

## Scope and model

- Snowball Job Management had no dedicated HackTricks Cloud page before this pass; it is distinct from the newer `snow-device-management` API.
- Reviewed the current API/Developer Guide, Service Authorization Reference, CLI model, IAM role/KMS requirements, shipping lifecycle and CloudTrail contract.
- Job types are `IMPORT`, `EXPORT` and `LOCAL_USE`. Export jobs use a selected IAM role to read selected S3 buckets/key ranges, copy the data onto one or more devices and ship them to an address.
- The service is closed to new customers but remains usable by existing customers.
- Snowball defines no resource ARN and no service-specific IAM condition key. Every action uses `Resource: "*"`.

## Wildcard-only job reads and credential model

Fresh STS sessions were restricted to `DescribeJob`, `GetJobManifest` and `GetJobUnlockCode` against a synthetic well-formed job ID:

- with `Resource: "*"`, all three actions reached service-level `InvalidResourceException`;
- with a synthetic job ARN, all three were denied because no session-policy statement applied;
- unsigned requests returned `MissingAuthenticationTokenException`.

This live behavior agrees with the authorization table: even a known-ID job read cannot be scoped to that job in IAM. For a real job, the two credential APIs work only in `WithCustomer`. The manifest URL lasts up to 60 minutes, and manifest/code credentials expire 360 days after job creation.

## `UpdateJob` existing-role pivot

Safe synthetic-job probes established:

- `snowball:UpdateJob` alone on wildcard resource, changing only `AddressId`, reached `InvalidResourceException` for the nonexistent job;
- a synthetic exact-job ARN policy was denied by IAM;
- adding `RoleARN` to the request while omitting PassRole failed specifically on `iam:PassRole`.

Therefore a request that omits `RoleARN` can update mutable fields without re-passing the existing job role. During a real export job's `New` window (normally about 60 minutes), changing `Resources` and `AddressId` can make the already trusted role read additional permitted S3 data and ship it to another valid address. This is a conditional physical exfiltration/role-escalation path; later appliance access still requires the job credentials and possession/reach.

## `CreateJob` PassRole boundary

A `CreateJob`-only STS session submitted a fully synthetic export request and failed specifically on `iam:PassRole` for the supplied role. Adding exact-role PassRole with `iam:PassedToService=importexport.amazonaws.com` passed that authorization gate.

No job was created. Subsequent requests were deliberately guaranteed invalid and exposed service/client availability drift:

- the current CLI/API model accepted `V3_5S`, but the live endpoint rejected it against an older enum;
- retired `EDGE_S` device/capacity variants were rejected as invalid or unavailable;
- every final `ListJobs` remained empty.

The documented successful primitive remains sound for an eligible existing customer: `CreateJob` plus exact-role PassRole selects data reachable by a Snow-trusting role, a physical destination and a supported device. A live successful order was intentionally not tested because it creates cost, an external shipment and a potentially weeks-long non-cleanable workflow.

## Telemetry

- CloudTrail source is `snowball.amazonaws.com`; all tested calls were management events.
- Read-only synthetic `DescribeJob`, `GetJobManifest` and `GetJobUnlockCode` events exposed caller/action/error but had null request parameters, response and resources.
- The safe `UpdateJob` failure retained the synthetic job ID and new address ID. The exact-ARN IAM denial and PassRole denial had null request parameters.
- Safe post-PassRole `CreateJob` validation failures retained the complete job type, S3 bucket/key range, address ID, role ARN, device/capacity, shipping and remote-management configuration.
- The create-only denial named the exact missing `iam:PassRole`; as usual, PassRole produced no standalone event.
- AWS documents read-only response omission, so unlock code, manifest URL, job metadata and address content should not be assumed to be duplicated into CloudTrail.

## Ideas considered but not promoted

- `GetSoftwareUpdates`: returns AWS-provided update content, not attacker-controlled code or a customer secret.
- `CreateReturnShippingLabel`: produces a label for returning the existing device to AWS; no destination-redirection primitive was established.
- `UpdateJobShipmentState`: potentially dangerous state tampering, but the caller model and actual carrier/workflow consequences were not established without a live shipment.
- Description/notification injection: no trusted renderer, code execution or meaningful authorization boundary was found.
- Device-type/client enum drift: operational defect only, with no security impact.
- `CancelJob`: retained as a bounded DoS in the public post-exploitation page because it can abort a weeks-long workflow, but only during `New`.

## Open hypotheses

1. Cross-account job/address IDOR caused by wildcard-only authorization combined with known foreign IDs.
2. Job-state race in which `UpdateJob` succeeds after preparation has begun and causes data/destination mismatch.
3. Address/resource partial-update desynchronization across export job parts.
4. Presigned manifest/report URL lifetime or scope bypass by query mutation, duplicate parameters or alternate endpoint/Region.
5. `UpdateJobShipmentState` accepting caller-selected state transitions that alter shipping or unlock eligibility without carrier evidence.
6. `CreateLongTermPricing` / `UpdateLongTermPricing` billing abuse, association confusion or irreversible renewal behavior.

These need a real authorized existing-customer fixture, physical logistics or a paid contract. No AWS vulnerability was demonstrated and no private report was created.

## Cleanup

- Final `ListJobs`, `ListLongTermPricing`, `DescribeAddresses` and Snowball usage remained zero/empty in the allowed Region.
- All test principals were expiring STS sessions; there are no persistent test resources or cleanup debt.
