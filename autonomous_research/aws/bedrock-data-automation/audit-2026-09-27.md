## Security model findings

- Resources are blueprints/versions/stages, projects, libraries/entities/ingestion jobs and runtime invocations.
- Current API shapes contain no caller-supplied role/service-role ARN. There is no BDA `iam:PassRole` pivot; runtime S3/KMS access is tied to caller/service authorization.
- No BDA resource-policy API exists. Bedrock documentation's resource-policy support applies to guardrails/inference profiles, not BDA resources. Cross-account data paths therefore require downstream S3/KMS policy and an authorized caller rather than a BDA project policy.
- Projects have mutable `LIVE` and `DEVELOPMENT` stages; DEVELOPMENT can be API-only. Blueprints contain natural-language prompts, and AWS explicitly warns that Bedrock does not validate prompt intent.
- Synchronous invocation can return extracted content inline; async/status returns S3 output. Results can include OCR, transcripts, summaries, PII detection/redaction and custom fields.
- Libraries ingest organization-specific entity manifests and write ingestion results beneath a job-specific S3 prefix.
- Native endpoints require SigV4. Unsigned `ListBlueprints` returned `MissingAuthenticationTokenException`; no unauthenticated/bearer page is warranted.

## Published techniques

- Enum: both APIs, stages, projects, blueprints, libraries, runtime status, IAM/S3/KMS/logging boundaries.
- Post-exploitation: read sensitive extraction/domain configuration; retrieve output location then use separately authorized S3/KMS access.
- Persistence: poison a LIVE blueprint/project so later legitimate invocations use altered extraction/redaction behavior.

## Exclusions

- No privilege-escalation page: BDA has no passed role and fixed extraction is not code execution. S3 read/write requires the caller/service path already authorized.
- No cross-account persistence page beyond downstream S3/KMS: no BDA resource policy exists.
- No unauthenticated page: SigV4 required.
- No invocation-as-exfil technique: invoking BDA cannot bypass S3/KMS authorization; it is useful transformation only after the caller can already access input and output paths.
- No destructive delete/cost abuse entries: obvious and low-value.
- Blueprint optimization, recommendation and library ingestion were not run because they may incur processing cost and add no distinct authorization primitive.
- No unexpected AWS defect was confirmed; no private report created.

## CloudTrail

The current CloudTrail data-event catalog explicitly exposes
`AWS::Bedrock::Blueprint`, `AWS::Bedrock::DataAutomationProject`,
`AWS::Bedrock::DataAutomationProfile`, and `AWS::Bedrock::DataAutomationInvocation`. Blueprint,
project and invocation activity therefore requires non-default data-event selectors for reliable
visibility. Other Bedrock control-plane operations follow management-event logging. S3 object
reads/writes are separate data events and KMS use is separate. Defenders should correlate
project/blueprint changes with later invocations and output writes.
