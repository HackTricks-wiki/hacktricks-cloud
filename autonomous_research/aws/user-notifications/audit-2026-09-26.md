## Live tests

### Exact-rule blind update

Created an EC2 state-change rule with the filter:

```json
{"detail":{"state":["terminated","stopping","stopped","shutting-down"]}}
```

A role with only `notifications:UpdateEventRule` on the exact rule ARN successfully replaced the filter with:

```json
{"detail":{"state":["terminated"]}}
```

`notifications:GetEventRule` was independently denied. The configuration and rule remained `ACTIVE`. This confirms a useful notification-blinding technique: a principal can make a security/operations rule much less likely to match without read/list permissions.

CloudTrail recorded the complete rule ARN, Region list, and full unredacted replacement event pattern.

### Channel association/disassociation boundary

A role with only `notifications:AssociateChannel` on the exact configuration successfully associated a syntactically valid **same-account but nonexistent** email-contact ARN. `ListChannels` then returned the dangling ARN. This means association itself does not validate current contact existence. It is not a security defect because the nonexistent channel cannot receive notifications.

The same call using a foreign-account-shaped contact ARN was denied:

```text
Calling account 228478051196 does not have permission to perform this action on the resource ...
```

No cross-account confused-deputy path was found. A real exfiltration path therefore requires an activated channel in the victim account (or another valid account-local email/chat/mobile channel) plus `AssociateChannel`.

A role with only `notifications:DisassociateChannel` on the exact configuration removed the dangling channel without any get/list permission. This establishes the delivery-suppression boundary safely.

CloudTrail recorded both configuration and URL-encoded channel ARNs. The foreign-account denial retained the target account/ARN in the event.

### Hub removal

`notifications:DeregisterNotificationHub` alone was sufficient to remove `us-east-1` while a second `us-east-2` hub was active. The removed Region stopped being a notification storage/replication hub. Attempting to remove the sole remaining hub returned the documented guard:

```text
ConflictException: Cannot deregister last ACTIVE notification hub
```

This restriction has a major testing consequence described below.

### Email delivery chain (documentation-confirmed, no outbound email test)

AWS documents the minimum chain:

1. `notifications-contacts:CreateEmailContact` creates a contact and sends an activation email.
2. `notifications-contacts:ActivateEmailContact` with the seven-character code activates it.
3. `notifications:AssociateChannel` attaches it to a user-created configuration.
4. `notifications:AssociateManagedNotificationAdditionalChannel` attaches an additional channel to an AWS-managed configuration; `notifications:SubscribeSensitiveEvents` is additionally required when subscribing it to sensitive managed events.

No mailbox was supplied for this authorized environment, so the audit did not create a contact or send an activation message. The service-side association permission and same-account boundary were tested separately as above.

## Publication decisions

Published:

- email-channel notification-feed disclosure and service-level persistence, with activation/same-account prerequisites;
- exact-rule filter narrowing and channel removal as notification suppression;
- regional hub removal with the last-hub limitation;
- expanded enumeration of rules, channels, contacts, and managed associations;
- an explicit warning not to activate the first hub for disposable testing.

Not promoted:

- dangling same-account channel ARN association, because it cannot deliver data;
- cross-account channel exfiltration, because AWS rejected the foreign account;
- hub removal as total service disablement, because the last active hub is protected;
- creation of many configurations/contacts for quota exhaustion, because it is noisy, quota-limited, and much less useful than direct rule/channel tampering.

## Cleanup and irreversible service state

Deleted and verified absent:

- exact event rule;
- exact notification configuration;
- all associated channels (`0` before configuration deletion);
- audit IAM role and inline policy;
- service-linked role `AWSServiceRoleForAWSUserNotifications` (it did not pre-exist and deletion task succeeded);
- temporary `us-east-2` notification hub;
- email contacts remained `0`.

Unavoidable residual account setting:

- one `us-east-1` notification hub remains `ACTIVE`.

The account started with zero hubs, but the API explicitly states that the last active hub cannot be deregistered. This guard still applied after all configurations, contacts, and the service-linked role were removed. There is no public reset/delete-service operation. The residual hub has no configuration, rule, contact, channel, stored test event, service-linked role, or additional charge; it is nevertheless an account-level setting created during this audit.

Future agents must **not** repeat first-hub activation in an account that still has zero hubs. If the account already has one legitimate hub, temporary additional hubs can be removed safely as long as the legitimate hub remains active.

## Potential defect / research backlog

- With a second authorized account and mailbox, verify that actual channel delivery never crosses account ownership even if a caller can guess an existing foreign ARN. The authorization guard observed here is expected to prevent it.
- Test whether an activated contact deleted after association is automatically removed or remains dangling, and whether recreation/ID reuse is possible.
- Audit `UpdateManagedNotificationChannelAssociation`, a newly exposed operation for toggling sensitive-event subscriptions, against the permission-only `SubscribeSensitiveEvents` action.
- Test managed AWS Health Security/Billing channel associations with a controlled email, including what exact event fields are redacted from delivery.
- Test organization-level notification configurations for unauthorized OU expansion and member-account event disclosure.
- Test event-pattern parser differences between User Notifications and its EventBridge managed rule for filters that are accepted but evaluated differently.
- Test Region removal/re-add behavior against the documented visibility restoration of retained notification events.
- Audit notification-event read APIs in every configured hub Region for pagination-token binding and cross-configuration access.
