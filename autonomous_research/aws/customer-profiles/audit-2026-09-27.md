# Amazon Connect Customer Profiles security audit — 2026-09-27

## Scope and safety controls

- Authorized account: `228478051196`.
- Entry: profile `hacktricks-training` through configured profile `ht-admin`, assuming `arn:aws:iam::228478051196:role/ChackBotAdministratorRole`.
- Region used for mutations: `us-east-1` only.
- Initial `us-east-1` state: no Customer Profiles domains and no Kinesis streams.
- The organization SCP explicitly denied Customer Profiles in `us-west-2`; no attempt was made to bypass it.
- Only synthetic names, addresses and marker values under reserved audit prefixes were used. No existing profiles or unrelated resources were read or changed.
- No Kinesis stream, S3 bucket, KMS customer key, AppFlow flow, SaaS connection, segment/recommender job, upload job or Connect campaign was created.
- Customer Profiles pricing charges daily utilization for profiles with imported data. The live fixture caused one synthetic profile to appear as metered. The published unit price is USD 0.005/profile/day before applicable free-tier treatment; no other paid infrastructure was used.

Existing book coverage for Customer Profiles was not found.

The installed AWS CLI was `2.34.45`, with the Customer Profiles `2020-08-15` service model. It did not yet expose every operation in the current API reference.

## Attack hypotheses and disposition

| Hypothesis | Class | Result |
| --- | --- | --- |
| Unsigned profile APIs allow discovery because the endpoint returns permissive CORS headers | Unauthenticated access | Rejected: both raw HTTPS and CLI no-sign requests returned `MissingAuthenticationTokenException` |
| Customer Profiles domains can be shared by native resource policies | Cross-account access | Rejected: no domain/profile resource-policy API; external service/resource policies remain the boundary |
| Exact domain IAM is sufficient for profile-object ingestion | Least privilege | Rejected: `PutProfileObject` required both domain and object-type ARNs |
| Exact domain ARN is sufficient for `ListDomains` | Least privilege | Rejected: live service authorized an undocumented collection ARN ending in `:domains` |
| `MergeProfiles` uses the documented domain resource | Least privilege | Rejected: live service evaluated a request-path ARN, not the documented domain ARN |
| A single action can irreversibly consolidate profiles | Post-exploitation | Confirmed with two synthetic profiles; source key resolved to the survivor afterward |
| `AddProfileKey` creates a durable lookup alias | Persistence | Confirmed with synthetic data |
| Object ingestion can attach attacker-controlled source JSON to a matched profile | Post-exploitation | Confirmed; manual source priority prevented the tested object from replacing the manually created first name |
| New batch ingestion uses the older `profile:PutProfileObject` IAM action | Least privilege/API drift | Rejected: the service required distinct `profile:BatchPutProfileObject` |
| `AssociateStreamForSegments` accepts a role without `iam:PassRole` because the published dependency table omits it | Privilege escalation/control | Rejected: live request failed specifically for missing `iam:PassRole` |
| `CreateIntegrationWorkflow` and `CreateSegmentSnapshot` provide generic role takeover | Privilege escalation | Rejected as overclaim; documented impact is bounded service use through a passed role |
| Real-time event streams directly target another account | Cross-account exfiltration | Rejected by API contract: event stream and domain must be in the same account and Region |

An unexpected security-sensitive result was handled under the task's private-report rule and is intentionally excluded from this repository ledger and all public pages.

## Live fixture 1: data and IAM behavior

Created:

- domain `ht-cp-audit-20260927`, one-day default expiry and audit tags;
- two synthetic profiles with `.invalid` email addresses;
- profile key `_account = HT-AUDIT-ALIAS`;
- temporary role `ht-cp-audit-probe`, trusted only by `ChackBotAdministratorRole`;
- object type `AuditRecord`, recreated only when required for isolated tests.

The object type used:

- `AllowProfileCreation = false`;
- one `_account` key carrying `PROFILE` and `UNIQUE` identifiers;
- simple `accountId`, `firstName` and synthetic marker fields;
- one-day expiration.

No external source, DLQ or customer-managed encryption key was configured.

### Exact domain access

A fresh probe session with only `profile:GetDomain` on:

```text
arn:aws:profile:us-east-1:228478051196:domains/ht-cp-audit-20260927
```

successfully retrieved that domain. The same session was denied for another domain, confirming domain resource isolation. A session with only `profile:SearchProfiles` on the exact domain found the synthetic alias.

The AWS-managed encryption configuration did not require caller-side KMS permissions. AWS documentation states that customer-managed KMS configurations require `kms:Decrypt` and `kms:GenerateDataKey` for entities using relevant profile APIs; that was not live-tested to avoid creating a billable customer key.

### `ListDomains` collection ARN

`profile:ListDomains` with the exact domain ARN failed. The authorization error named:

```text
arn:aws:profile:us-east-1:228478051196:domains
```

Granting the action on that collection ARN succeeded and returned the single test domain. The machine-readable service authorization catalog currently lists no resource type for the action, while the HTML action presentation is inconsistent. The exact collection ARN is an observed implementation detail, not a published resource type.

### `PutProfileObject` parent and child resources

A session policy granting `profile:PutProfileObject` only on the domain was denied on:

```text
arn:aws:profile:us-east-1:228478051196:domains/ht-cp-audit-20260927/object-types/AuditRecord
```

Adding both the exact domain and exact object-type ARNs succeeded. `ListProfileObjects` returned the exact serialized synthetic object. This confirms both resources are mandatory for this object operation.

The test object targeted `_profile.FirstName`, but the existing manually created value remained `Synthetic`. This matches AWS's documented priority protection for manually populated profile fields. Do not claim that any object mapping automatically overwrites all manual profile fields.

### `MergeProfiles` authorization drift and behavior

`profile:MergeProfiles` on the published domain ARN was denied. The error evaluated this resource:

```text
arn:aws:profile:us-east-1:228478051196:/domains/ht-cp-audit-20260927/profiles/objects/merge
```

An isolated session policy granting the action on that exact request-path ARN succeeded. After merging the second profile into the first, searching for the second profile's account key returned the first profile ID. CloudTrail recorded both profile IDs. This was a one-way operation, consistent with the identity-resolution documentation.

### New batch API and IAM action

The current API reference documents `BatchPutProfileObject`, but AWS CLI `2.34.45` did not expose it and the current public authorization catalog did not list an action. A SigV4-signed request was sent directly to:

```text
PUT /domains/<domain>/profiles/objects/batch-put-profile-object
```

A session with only `profile:PutProfileObject` was denied and the service explicitly required:

```text
profile:BatchPutProfileObject
```

Granting `profile:BatchPutProfileObject` on both the exact domain and object-type ARNs returned one successful item. This action should be used in current least-privilege policies even before the public authorization catalog/installed CLI catches up.

Batch ingestion is asynchronous. The returned object key was not immediately visible to `ListProfileObjects`, and an immediate object deletion returned not found. The object type and then the containing domain were deleted, removing queued/stored test data. Do not design cleanup that assumes immediate read-after-write consistency for this API.

## Live fixture 2: segment-stream PassRole enforcement

A second empty domain `ht-cp-role-audit-20260927` was created with:

- probe role `ht-cp-segment-probe`, allowed only `profile:AssociateStreamForSegments` on that domain;
- destination role `ht-cp-segment-destination`, trusting only `profile.amazonaws.com` and allowing the documented Kinesis producer actions only on a deliberately nonexistent audit stream.

No Kinesis stream was created. A raw signed `AssociateStreamForSegments` request supplied the destination role. The service returned HTTP 403 naming missing `iam:PassRole` on that exact role. This confirms PassRole enforcement before any usable stream association despite the missing dependency in the current service-authorization table.

Production policy should grant exact-role `iam:PassRole` and constrain `iam:PassedToService` to `profile.amazonaws.com`. The destination role needs only `kinesis:PutRecord`, `PutRecords`, `DescribeStream` and exact KMS permissions when applicable.

## Unauthenticated, cross-domain and cross-account findings

### Native endpoint

An unsigned `GET /domains?max-results=1` returned HTTP 403 with `MissingAuthenticationTokenException`. The endpoint sent `Access-Control-Allow-Origin: *` and allowed standard methods/headers, but this only permits browser clients to make signed/authorized requests; it did not expose data.

### Resource policies

No Customer Profiles domain/profile resource-policy APIs or IAM resource-policy resource types were found. Cross-account influence comes from:

- AppFlow/SaaS connector accounts;
- S3/KMS/SQS/Kinesis resource policies;
- a passed role's allowed destinations;
- cross-account Kinesis consumers after same-account Customer Profiles delivery.

### Same-account cross-domain behavior

AWS documents that the Amazon Connect service-linked role receives broad Customer Profiles access to all same-account/same-Region domains whose names start with `amazon-connect-`, with a list of explicit destructive/admin denies. This is not cross-account access, but it can violate assumed domain isolation. Use non-prefixed names or distinct Connect instances/authorization boundaries when domains require stronger separation.

## IAM model summary

### Resources

Published resource types are domains, object types, domain object types, calculated attributes, layouts, integrations, event streams/triggers, segment definitions, recommenders, recommender schemas and recommender filters.

Profiles, profile keys, individual profile objects, workflows and upload jobs have no distinct IAM resource types. They are primarily domain scoped. Object operations require the domain plus object-type resource where the catalog marks both required.

### Tag conditions

Most resources support `aws:ResourceTag/${TagKey}`. Create/put operations support `aws:RequestTag/${TagKey}` and `aws:TagKeys` on the new child resource. Requests that include tags also require `profile:TagResource` according to the operation dependency table.

### Role-bearing operations

- `CreateIntegrationWorkflow`: documented `iam:PassRole` to `profile.amazonaws.com`.
- `CreateSegmentSnapshot`: documented `iam:PassRole` to `profile.amazonaws.com`.
- `AssociateStreamForSegments`: live-confirmed `iam:PassRole`, absent from the published dependency table at test time.

These are bounded delegation. The service does not return credentials and does not supply arbitrary compute. Precise impact is integration resource creation, S3/KMS segment export or Kinesis/KMS event delivery.

## Persistence and post-exploitation surface

High-value read actions:

- `SearchProfiles`, `BatchGetProfile`;
- `ListProfileObjects` and history-record APIs;
- calculated attributes, identity-resolution matches, segment membership and recommendations;
- `GetUploadJobPath`, which returns a pre-signed upload URL and plaintext SSE-C client token for an existing job.

High-value integrity/destructive actions:

- direct profile create/update/delete;
- profile key add/delete;
- object type and object put/delete;
- bulk upload job create/path/start;
- irreversible manual merge and automatic matching/merging changes through `UpdateDomain`;
- integration/workflow creation or deletion;
- event trigger changes leading to outbound campaign actions;
- segment/recommender/calculated-attribute lifecycle changes.

Persistence primitives:

- durable attacker-known profile lookup aliases through `AddProfileKey`;
- real-time profile export through `CreateEventStream` to a same-account/Region Kinesis stream;
- domain-level segment event stream association and recurring segment subscriptions;
- recurring AppFlow-backed integration workflows;
- event triggers attached to integrations and downstream campaigns.

## CloudTrail observations safe for publication

All tested public calls appeared as management events with `eventSource = profile.amazonaws.com`.

| API | Observed logging behavior |
| --- | --- |
| `CreateDomain` | Domain name, retention and tags visible; response configuration visible |
| `GetDomain`, `SearchProfiles`, `ListProfileObjects` | Caller and target parameters visible; successful response omitted |
| `CreateProfile` | Domain and generated profile ID visible; supplied customer fields redacted as `***` |
| `AddProfileKey` | Profile ID/key name visible; key values redacted |
| `PutProfileObjectType` | Domain/type/retention visible; description, fields and keys redacted |
| `PutProfileObject` | Domain/type visible; serialized object redacted |
| `MergeProfiles` | Main and source profile IDs visible |
| Failed authorization | Error class/message and evaluated resource/action visible |

Kinesis records, S3 writes, KMS use, AppFlow executions and downstream campaign delivery require their own telemetry. Management Event History is not enough to prove what data a read returned or what a persistent stream consumer received.

## Ideas rejected or deliberately not live-tested

- **CORS as unauthenticated access:** rejected by SigV4 requirement.
- **Native cross-account domain policy:** no resource-policy API exists.
- **Connector credential extraction:** Customer Profiles integration output exposes topology/role/flow references, not SaaS secrets.
- **Generic PassRole takeover:** unsupported; service actions are bounded.
- **`PutIntegration` alone as PassRole escalation:** not established. It registers an existing flow/integration and does not itself prove role assumption.
- **Event stream to a foreign-account Kinesis stream:** contract prohibits it.
- **Paid Kinesis/AppFlow/KMS/segmentation fixtures:** not created. Official contracts plus the no-cost PassRole negative test were sufficient for the public guidance.
- **Upload-job live fixture:** not created because the API has no delete-job operation; this would violate the immediate-cleanup requirement.
