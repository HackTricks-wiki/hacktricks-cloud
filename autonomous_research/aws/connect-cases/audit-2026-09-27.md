# Amazon Connect Cases security audit — 2026-09-27

## Scope and disposition

- Service: Amazon Connect Cases (`connectcases` CLI, `cases` IAM prefix, `cases.amazonaws.com` CloudTrail source).
- Region tested: `us-east-1` in authorized account `228478051196`.
- Public outcome: enumeration, post-exploitation and conditional tag-pivot pages added.
- Private vulnerability outcome: none. Observed behavior agrees with the public API and Service Authorization Reference. The surprising domain-wide scope of `SearchAllRelatedItems` is an expected authorization design, not a zero-day.
- Persistence outcome: no service-native mechanism grants or preserves AWS access. Durable template/rule/event changes are workflow poisoning or defense evasion, not identity persistence, so no persistence page was added.
- Unauthenticated outcome: rejected. The API is SigV4-only and unsigned `ListDomains` returned `MissingAuthenticationTokenException`.

## Sources reviewed

- Current AWS CLI `connectcases` service model (`2022-10-03`) and all 43 exposed operations.
- AWS Service Authorization Reference for Amazon Connect Cases.
- Current API references for case search, related-item search, audit history, related-item mutation and event configuration.
- Administrator guidance for Cases, tag-based access control, event streams and Customer Profiles integration.
- EventBridge events reference (`source: aws.cases`, `detail-type: Amazon Connect Cases Change`).

## Verified results

### Enumeration and authentication

- `ListDomains` enforces a maximum `maxResults` of 10.
- A newly created domain exposes the system field IDs `assigned_queue`, `assigned_user`, `case_id`, `case_reason`, `created_by`, `customer_id`, `last_closed_datetime`, `last_reopened_datetime`, `created_datetime`, `last_updated_datetime`, `last_updated_user`, `next_sla_breach_datetime`, `reference_number`, `status`, `summary` and `title`.
- Unsigned `ListDomains` failed with `MissingAuthenticationTokenException`.
- No resource-policy API or account-sharing mechanism exists in the service model.

### Domain-wide related-item read

- A synthetic case was tagged `Classification=Restricted` and contained a comment body marker.
- A temporary IAM user had only `cases:SearchAllRelatedItems` on the exact domain ARN—no Case, RelatedItem, tag, Customer Profiles or Connect permissions.
- `SearchAllRelatedItems` returned the case ID, comment ID, comment body, content type and association time.
- Result: Case-level resource tags and Case/RelatedItem permissions do not narrow this domain-level API. This matches the Service Authorization Reference, which lists only Domain for the action.
- A separate exact-domain `SearchCases` test succeeded when no fields were requested. Requesting `customer_id`/other values failed until the same action was also permitted on each requested Field ARN. This is useful, more granular behavior and must not be confused with `SearchAllRelatedItems`.

### Case audit and attribution

- `GetCaseAuditEvents` returned case creation and comment creation events, complete field/comment values, timestamps and event IDs.
- Supplying `performedBy.customEntity=trusted-looking-automation` caused that label to appear in returned objects.
- The audit record also included the actual STS caller under `iamPrincipalArn`. CloudTrail separately identified the principal.
- Result: custom attribution can mislead a casual UI/API consumer but does not erase forensic attribution; this is documented as an operational integrity caveat, not a vulnerability.

### Event-stream control

- An exact-domain IAM user with only `cases:PutCaseEventConfiguration` successfully changed an enabled stream to `enabled=false`, empty fields and `includeContent=false`.
- The same single permission successfully enabled the stream with `relatedItemData.includeContent=true` and no selected case fields.
- No `events:*` permission was required for either operation.
- Adding `title` to the included case fields failed for the exact-domain-only user because authorization additionally evaluated `cases:PutCaseEventConfiguration` on the `.../field/title` ARN. AWS's tabular reference currently shows Domain for the action, while live enforcement adds selected Field resources. This is restrictive and has no security impact worth a private report.
- Result: disabling future events is a direct defense-evasion/workflow-disruption primitive. Enabling related-item content can expand data reaching pre-existing default-bus consumers but is not standalone exfiltration.

### CloudTrail

- All checked Cases operations appeared as management events with event source `cases.amazonaws.com`.
- Read events such as `SearchCases`, `SearchAllRelatedItems`, `GetCaseAuditEvents`, `GetCaseEventConfiguration` and `ListDomains` had `readOnly: true` and normally `responseElements: null`.
- `CreateCase` field values and `CreateRelatedItem` comment/`performedBy` content were redacted as `***` in `requestParameters`; resource IDs remained visible.
- `PutCaseEventConfiguration` recorded `enabled`, included field IDs and `includeContent` in clear request parameters.
- Failed authorization was recorded with the attempted field ARN and error response.

### Tag-conditioned permission pivot

- A minimum-permission IAM user was allowed `cases:TagResource` on one exact domain ARN and `cases:PutCaseEventConfiguration` on that ARN only when `aws:ResourceTag/Access` equaled `Operator`.
- The user set `Access=Operator` and then successfully called `PutCaseEventConfiguration` through the newly satisfied condition.
- No administrator, IAM policy mutation or EventBridge permission was available to the test principal.
- Result: the documented tag pivot is functional. Multi-resource case operations still require every evaluated Domain/Case/Field resource to be independently authorized; a Case tag alone is not a universal bypass.

## Attack idea matrix

| Idea | Minimum permissions / prerequisites | Result | Public disposition |
| --- | --- | --- | --- |
| Enumerate domains and data model | `ListDomains` on `*`; relevant List/Get on domain/children | Works; maps fields, templates, layouts, rules, tags and stream settings | Enumeration page |
| Bulk current field reads | `SearchCases` on domain plus each requested Field ARN | Works; values omitted from CloudTrail response | Post-exploitation |
| Bulk domain-wide related-item reads | `SearchAllRelatedItems` on exact Domain | Works without Case/RelatedItem access; returns comment/custom content | Post-exploitation, high-value IAM warning |
| Historical value recovery | `GetCaseAuditEvents` on Domain and Case | Works; full old/new values and real IAM caller | Post-exploitation |
| Follow Customer Profiles/contact/file references | Cases read plus separate `profile:*` / `connect:*` permissions | References are exposed; underlying data is separately authorized | Limitation noted, no standalone technique |
| Disable case events | `PutCaseEventConfiguration` on Domain | Works without EventBridge permission | Post-exploitation defense evasion |
| Expand event payload | Same on Domain for related-item content; additionally each Field ARN for case fields | Works; value depends on an existing readable/attacker-controlled consumer | Post-exploitation with prerequisite clearly stated |
| Redirect events directly to attacker bus | Cases event config only targets the same-account default bus | Not possible with Cases permission alone | Rejected |
| Case/related-item corruption | `UpdateCase` or related-item write/delete permissions on required resources | Expected and useful; status, assignment, notes and evidence can be changed | Post-exploitation |
| Field/template/layout/rule poisoning | Corresponding domain/model write permissions | Expected durable workflow disruption; not retained access | Post-exploitation, not persistence |
| Spoof `performedBy.customEntity` | Case/related-item write permission | Label is arbitrary, but audit history retains `iamPrincipalArn` | Caveat only, no vulnerability claim |
| ABAC tag pivot | `TagResource`/`UntagResource` plus a separate tag-conditioned allow | Works by normal IAM semantics | Privesc page with limited impact |
| Override propagated template tag at case creation | `CreateCase`, dependent `TagResource`, unconstrained request tags | Explicit case tag wins by documented design | Included as tag-boundary variant |
| Cross-account resource-policy abuse | Resource policy/share mechanism | No such Cases mechanism | Rejected |
| `iam:PassRole` / service-role pivot | Role-bearing API | No Cases API accepts a role ARN | Rejected |
| Unauthenticated discovery | Public/unsigned operation | Unsigned request rejected | Rejected |
| Native credential/access persistence | Access-bearing Cases resource | None found | Rejected |
| Contact/file IDOR | Valid foreign ARN plus Cases write/read calls | Documentation requires separate Connect authorization; no unvalidated cross-account access demonstrated | Rejected pending a concrete authorization bypass |
| Event delivery integrity/ordering abuse | Best-effort events and rapid updates | General asynchronous-delivery limitation, no security bypass demonstrated | Rejected as low-value/speculative |

## Cleanup proof

- Final `ListDomains`: `{"domains":[]}`.
- Every explicitly checked deleted Cases domain returned `ResourceNotFoundException`.
- Every explicitly checked temporary Customer Profiles domain returned `ResourceNotFoundException`.
- Every explicitly checked temporary IAM user returned `NoSuchEntity` after its access key and inline policy were removed.
- No `ht-cases-*`, `ht-case-read-*`, `ht-global-*`, `ht-disable-*`, `ht-content-*`, `ht-read-*` or `ht-cases-*-*` test asset was intentionally left behind.
