# AWS Ground Station audit — 2026-10-01

## Result

Published the previously missing Ground Station inventory and four material expected attack paths:

1. exact-contact `UpdateContact`/`CancelContact` can retarget or interrupt scheduled and active satellite passes;
2. wildcard-only `ReserveContact` can create antenna-time spend and availability denial;
3. exact config/mission-profile updates persistently poison future contact definitions; and
4. wildcard `CreateEphemeris` or exact `UpdateEphemeris` can install a higher-priority orbital payload that affects new availability calculations and tracking for already scheduled contacts.

These are expected consequences of explicit Ground Station permissions. No AWS zero-day or private report was created.

## Current control plane

- SDK/CLI service: `groundstation`; endpoint/signing name `groundstation`; API model `2019-05-23`.
- The current model exposes 40 operations, including new contact versioning, antenna/reservation inventory, V2 endpoint groups and Agent task-response URLs.
- Core resources: contacts, mission profiles, typed configs, dataflow endpoint groups, ephemerides, satellites, Ground Station locations and Agents.
- Direct CloudTrail source: `groundstation.amazonaws.com`; direct EventBridge source: `aws.groundstation`.
- Ground Station supports identity policies, temporary credentials, ABAC on several resource types and service-linked roles, but no Ground Station resource-based policies.

## Live inventory and authentication

The target account was queried with the authorized administrator role. `eu-west-1` contained zero satellites, configs, dataflow endpoint groups, mission profiles, contacts and minute usage. Most other modeled Regions were blocked by the account's Region-deny SCP; `af-south-1` was not usable with the regional token. No antenna contact was reserved and no satellite/ephemeris onboarding was attempted.

An unsigned `ListGroundStations` call returned `MissingAuthenticationTokenException`. No unauthenticated enumeration path was found.

## Authorization findings

The machine-readable and HTML service authorization references agree on the broad boundary:

- `ReserveContact`, all `Create*` calls and `RegisterAgent` require `Resource: "*"`;
- `CancelContact`, `UpdateContact`, object reads/updates/deletes and most tags support exact resource ARNs;
- list/minute-usage calls generally require `*`; and
- config/profile operations that accept a role can additionally authorize `iam:PassRole` with `iam:PassedToService = groundstation.amazonaws.com`.

A disposable IAM user was allowed `CancelContact` and `UpdateContact` only on one fake contact ARN. Both requests for that ID reached `ResourceNotFoundException`; the identical calls for a second UUID were IAM-denied on the different contact ARN. The same pattern held for `GetAgentConfiguration` and `UpdateAgentStatus` on an exact Agent ARN (`Invalid AgentID` versus IAM denial).

### `GetAgentTaskResponseUrl` resource discrepancy

The authorization reference marks `GetAgentTaskResponseUrl` as supporting the `Agent` resource type. In the live service, a policy allowing the documented exact Agent ARN was denied against:

```text
arn:aws:groundstation:eu-west-1:228478051196:/agentResponseUrl/<agent-id>/<task-id>
```

The request matching that undocumented path ARN was not IAM-denied, but it coincided with the service's transient new-key `UnrecognizedClientException`, so the custom-ARN workaround is not considered proven. `Resource: "*"` with `StringEquals` on `groundstation:AgentId` did correctly allow one fake agent ID while denying another. The AWS managed `AWSGroundStationAgentInstancePolicy` grants all four Agent APIs on `*`.

This is a service-authorization/documentation mismatch with a usable condition-key mitigation, not a demonstrated confidentiality/integrity break. Keep it as a hardening note and retest against a real disposable Agent before considering an AWS report.

## Reversible live mutation test

A no-contact fixture was created in `eu-west-1`:

- one `tracking` config (`PREFERRED`);
- one `antenna-downlink` config (2.2 GHz, 1 MHz, no polarization);
- one dataflow-endpoint config naming a nonexistent endpoint; and
- one mission profile joining the downlink and endpoint configs.

A disposable IAM user received only:

```text
groundstation:UpdateConfig         on the exact tracking config ARN
groundstation:UpdateMissionProfile on the exact mission-profile ARN
```

After normal IAM propagation delay, the user changed `autotrack` from `PREFERRED` to `REMOVED`, changed the config/profile names and changed minimum viable duration from 60 to 61 seconds. Administrator reads confirmed the replacement values. No list/get/create/delete, IAM, S3, Kinesis, EC2, KMS or `iam:PassRole` permission was present on the restricted user.

Ground Station briefly returned `UnrecognizedClientException` for newly issued IAM-user keys before accepting them. Bounded retries reached success on the third call; this was credential propagation behavior, not treated as a security issue.

The test also confirmed a model/service mismatch: the modeled `DataflowEdgeList` minimum is zero, but the service rejects `CreateMissionProfile` when `dataflowEdges` is empty.

## Lifecycle and impact boundaries

- `ReserveContact` snapshots its mission profile/configs. Later config/profile edits do not change already scheduled contacts.
- `UpdateContact` creates an immutable version and is accepted only for `SCHEDULED`, `PREPASS` or `PASS`. It cannot change time/profile and cannot be used with antenna downlink demod/decode profiles.
- `CancelContact` cancels before start or stops during `PASS`; stopping may still bill the entire original duration without a qualifying duplicate.
- TLE/OEM behavior is materially different from profile snapshots: the highest-priority enabled unexpired customer ephemeris is used for antenna tracking even for contacts reserved before it was uploaded. Their start/end stay fixed, but usable visibility can shrink.
- The Ephemeris API remains preview/approval-gated. Azimuth/elevation ephemerides are even more restricted, do not participate in priority, and must be selected explicitly on a contact.
- S3 recording buckets must be in the account and begin with `aws-groundstation`; telemetry Kinesis streams must be in the scheduling account/Region. Avoid claiming arbitrary cross-account exfiltration without a separate downstream trust path.

## Telemetry

AWS documentation states that all Ground Station API calls are CloudTrail events. Live events were default `AwsApiCall` management events:

- successful `UpdateConfig` logged the complete `configData`, including `autotrack: REMOVED`, config ID/type and name;
- `UpdateMissionProfile` logged supplied replacement fields and profile ID;
- `CancelContact`/`UpdateContact` logged contact ID and client token; failed events stored detail in `responseElements.message` with `errorMessage:null`;
- successful list/get calls had `responseElements:null`, so CloudTrail proves the query but not the returned inventory;
- Agent reads/status requests logged full agent/task IDs and component/aggregate status; and
- create/delete fixture events retained full RF/dataflow/profile definitions and returned resource IDs/ARNs.

Direct best-effort EventBridge events provide independent signals for contact, endpoint-group, ephemeris, S3-upload and endpoint-health changes. CloudWatch signal/pointing/tracking metrics, data-delivery evidence and minute/billing records expose runtime impact.

## Deferred high-value tests

Use a disposable, explicitly onboarded Ground Station digital-twin/Agent account before testing these:

1. create a V2 dataflow endpoint group, register an Agent, and determine whether another Agent role can read tasking or spoof status/log uploads for that agent under the AWS managed wildcard policy;
2. verify whether the undocumented `agentResponseUrl` ARN can be safely scoped for a real task and whether the presigned upload URL permits overwrite/replay;
3. test same-account versus cross-account capability ARNs in `RegisterAgent` and confirm deletion/expiry of all Agent state when the endpoint group is deleted;
4. upload a benign higher-priority TLE in the digital twin, observe selection for an already scheduled contact, then disable/delete it and verify full fallback;
5. test `CreateEphemeris` S3-object access with explicit caller/service/KMS denies for confused-deputy or validation-oracle behavior;
6. test ReserveContact tag guardrails, quota exhaustion behavior and exact CloudTrail fields only on digital-twin capacity; and
7. test S3/Kinesis/endpoint destination validation and cross-account rejection without sending satellite data.

Do not run production antenna reservations merely to validate billing/availability abuse.

## Cleanup

Every created mission profile and config was deleted after its test. All disposable IAM access keys, inline policies and users were deleted. Final `eu-west-1` inventory was zero configs, zero mission profiles, zero dataflow endpoint groups, zero contacts and zero usage; no Agent, ephemeris, S3 bucket, role, Kinesis stream, EC2/network object, service-linked role or antenna reservation was created.
