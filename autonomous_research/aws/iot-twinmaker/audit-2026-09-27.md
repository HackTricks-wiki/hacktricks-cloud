## Verified connector invocation boundary

The strongest live result used a scoped caller with:

```json
{
  "Effect": "Allow",
  "Action": [
    "iottwinmaker:CreateComponentType",
    "iottwinmaker:CreateEntity",
    "iottwinmaker:GetPropertyValueHistory",
    "iottwinmaker:GetEntity"
  ],
  "Resource": "*"
},
{
  "Effect": "Deny",
  "Action": ["lambda:InvokeFunction", "iam:PassRole"],
  "Resource": "*"
}
```

The workspace execution role had only the exact test bucket permissions and `lambda:InvokeFunction` on the exact test function. Direct invocation by the scoped caller failed. After it created a component type and entity, TwinMaker invoked the same Lambda through the workspace role and returned:

```json
{
  "propertyValues": [{
    "entityPropertyReference": {
      "componentName": "sensor",
      "entityId": "ht-entity",
      "propertyName": "reading"
    },
    "values": [{
      "value": {"doubleValue": 1337.0},
      "time": "2026-09-27T00:00:00Z"
    }]
  }]
}
```

This is expected delegation, not a zero-day. Impact is limited to the connector's implemented interface and side effects under its Lambda execution role. It does not expose workspace-role credentials or provide arbitrary execution as that role.

## CloudTrail observations

Event History contained scoped-attacker records for:

- `CreateComponentType`
- `CreateEntity`

It returned no records for:

## Useful book techniques accepted

1. Workspace, role, S3, component, entity, function, scene, sync and transfer-job enumeration.
2. Workspace-scoped `ExecuteQuery` as complete graph/topology reconnaissance.
3. Static value and connector configuration disclosure through entity/component reads.
4. High-stealth external property retrieval through configured readers.
5. Custom Lambda connector invocation without direct Lambda permission or PassRole, with narrowly stated impact.
6. Workspace role replacement only with `iam:PassRole`, followed by a supported connector/data-source operation.
7. Durable custom component/entity connector implant as service-level persistence.
8. Documentation-backed metadata export to S3, explicitly constrained by destination access and the durable job record.
9. Entity/relationship poisoning and the documented `BatchPutPropertyValues` data-writer route, without overstating the unsuccessful live data-writer probe.

## Rejected, constrained, or deferred ideas

- **Unauthenticated access:** unsigned API requests failed authentication; no public/resource-policy API exists for general TwinMaker resources.
- **Workspace S3 redirection:** `UpdateWorkspace` rejected changing the workspace bucket even though the original role could access both buckets.
- **Generic delete denial of service:** deleting entities, scenes, component types or workspaces is real but obvious destructive permission and did not justify a standalone technique.
- **Automatic workspace-role credential theft:** connector invocation does not expose the workspace-role session. The target Lambda runs with its own execution role.
- **Cross-account connector as automatic escalation:** cross-account Lambda invocation still needs workspace-role identity permission plus a target function resource policy. It is configuration-dependent expected behavior.
- **Metadata transfer live test:** the job record cannot be deleted, so creating it would violate the clean-test requirement.
- **Sync-job/PassRole live test:** no SiteWise fixture existed and creating a synchronized service graph was disproportionate. The documented PassRole dependency is recorded in enumeration.
- **Scene content hijack as persistence:** scene replacement is operational sabotage/defacement, not a reliable way to maintain AWS access, so no weak standalone technique was added.
- **`BatchPutPropertyValues` live writer claim:** the tested component returned `No dataWriter connector defined`; only AWS's documented connector semantics and logging gap are described.
