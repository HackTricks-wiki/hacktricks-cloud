# Amazon S3 Vectors security audit - 2026-09-27

## Scope and safety

- Service: Amazon S3 Vectors (`s3vectors`), current AWS CLI 2.34.45/API surface.
- Focus: enumeration, vector/metadata exfiltration, cross-account/resource policies, poisoning/deletion, persistence/privilege escalation, public access, encryption/KMS, resource scoping and CloudTrail stealth.
- Authorized account: `228478051196`, using `hacktricks-training` to assume `ChackBotAdministratorRole` in `us-east-1`.
- Fixtures contained only two-dimensional synthetic vectors and fake marker strings. No production/customer content or secret was read or written.
- No KMS key or billable provisioned capacity was created. Every vector bucket, index, policy and IAM probe role was deleted in the same test.

## Starting state and repository gap

Initial `ListVectorBuckets` returned zero resources. The repository had no `s3vectors`, vector-bucket or vector-index coverage.

The current API/IAM surface reviewed was:

| Scope | Actions |
| --- | --- |
| Account | `ListVectorBuckets` |
| Vector bucket | `CreateVectorBucket`, `GetVectorBucket`, `DeleteVectorBucket`, `ListIndexes`, `PutVectorBucketPolicy`, `GetVectorBucketPolicy`, `DeleteVectorBucketPolicy`, bucket tagging |
| Index control plane | `CreateIndex`, `GetIndex`, `DeleteIndex`, index tagging |
| Vector data plane | `PutVectors`, `GetVectors`, `ListVectors`, `QueryVectors`, `DeleteVectors` |

All actions except `ListVectorBuckets` support their documented exact bucket/index resource type. ARN forms:

```text
arn:aws:s3vectors:<region>:<account>:bucket/<bucket>
arn:aws:s3vectors:<region>:<account>:bucket/<bucket>/index/<index>
```

Relevant condition keys: `s3vectors:sseType`, `s3vectors:kmsKeyArn`, `aws:ResourceTag/${TagKey}`, `aws:RequestTag/${TagKey}`, `aws:TagKeys`, and `s3vectors:VectorBucketTag/${TagKey}`.

## Live tests

### 0. Aborted setup and cleanup validation

The first fixture, `ht-s3v-audit-927-1790484186`, created an empty vector bucket and then stopped before index creation because the host had an invalid global AWS CLI output setting. The cleanup trap deleted the bucket. CloudTrail later showed `CreateVectorBucket`, a harmless `DeleteIndex` `NotFoundException`, and successful `DeleteVectorBucket`. No role or index existed.

This local configuration issue was corrected by explicitly setting `AWS_DEFAULT_OUTPUT=json`; it is not an AWS finding.

### 1. Resource-policy self-grant and cross-principal read

Fixture:

- Bucket: `ht-s3v-audit-927-1790484271`.
- Index: `audit-index`, dimension 2, cosine distance, SSE-S3.
- Two synthetic vectors: `doc-a` and `doc-b`; metadata included filterable tenant/marker fields and a non-filterable `text` field.
- Policy probe role: `ht-s3v-policy-927` with only `s3vectors:PutVectorBucketPolicy` on the exact bucket ARN.

Results:

1. `QueryVectors` before the policy returned `AccessDeniedException` because the role had no query identity permission.
2. The same role wrote a bucket policy granting its IAM role ARN `QueryVectors`, `ListVectors` and `GetVectors` on the exact index ARN.
3. Without changing the role's identity policy, the same assumed role immediately queried keys/distances and listed complete embedding arrays plus all metadata.
4. The returned metadata included the non-filterable `text` values, confirming that non-filterable means only "not usable in a filter," not "not retrievable."

Conclusion: `PutVectorBucketPolicy` is a direct same-account self-escalation primitive and a documented cross-account persistence primitive. One exact bucket-level permission can grant data-plane access on its child indexes. KMS remains a separate boundary.

CloudTrail recorded successful `PutVectorBucketPolicy` management events at `04:44:56Z` and `04:45:01Z`; request parameter keys included both `policy` and `vectorBucketName`.

### 2. Mandatory Block Public Access / no anonymous path

The administrator attempted to replace the synthetic bucket policy with:

- `Principal: "*"`;
- `s3vectors:QueryVectors`;
- the exact synthetic index ARN.

`PutVectorBucketPolicy` returned:

```text
ValidationException: The specified policy allows public access
```

CloudTrail recorded the failed management event at `04:44:59Z`. AWS documentation independently states that all S3 Block Public Access settings are always enabled for vector buckets and cannot be disabled, and that requests require AWS authentication.

Conclusion: no unauthenticated/public vector access technique exists in the current service. Named authenticated cross-account principals are supported.

### 3. Exact-index `PutVectors` poisoning without read permission

Role `ht-s3v-put-927` had only `s3vectors:PutVectors` on the exact synthetic index ARN.

- `GetVectors(doc-a)` failed with `AccessDeniedException` for missing `s3vectors:GetVectors`.
- `PutVectors` using the already-existing key `doc-a` succeeded.
- Administrator retrieval showed the vector changed from `[1.0, 0.0]` to approximately `[0.7, 0.7]`, and metadata changed to `marker=poisoned` / `text=attacker replacement context`.

Conclusion: `PutVectors` is an upsert and needs no read/list permission or old value. Predictable/known keys enable blind, strongly consistent RAG/semantic-corpus poisoning.

### 4. Exact-index `DeleteVectors` without read permission

Role `ht-s3v-delete-927` had only `s3vectors:DeleteVectors` on the exact synthetic index ARN.

- `GetVectors(doc-b)` failed for missing `GetVectors`.
- `DeleteVectors(doc-b)` succeeded.
- Administrator `ListVectors` then returned only `doc-a`.

Conclusion: known/predictable keys can be deleted blindly. `ListVectors` is discovery convenience, not a dependent permission.

### 5. Conditional read permission boundaries

Second fixture:

- Bucket: `ht-s3v-boundary-927-1790484420`.
- Index: `boundary-index`, dimension 2, Euclidean distance.
- Role: `ht-s3v-query-927` with only exact-index `QueryVectors` and `ListVectors`.

Results:

| Request | Result |
| --- | --- |
| Query without metadata, with distance | Success; returned key and distance |
| List without data/metadata | Success; returned key |
| Query with `returnMetadata=true` | Denied specifically for missing `s3vectors:GetVectors` |
| Query using a metadata filter | Denied specifically for missing `s3vectors:GetVectors` |
| List with `returnMetadata=true` | Denied specifically for missing `s3vectors:GetVectors` |
| List with `returnData=true` | Denied specifically for missing `s3vectors:GetVectors` |

Conclusion: AWS enforces the documented conditional `GetVectors` boundary. Query/list-only permissions still leak keys and similarity distance but not raw embeddings/metadata.

### 6. CloudTrail behavior

Live Event History contained management events for bucket/index creation, listing, policy writes, public-policy rejection and cleanup. `PutVectors`, `GetVectors`, `ListVectors`, `QueryVectors` and `DeleteVectors` did not appear in Event History; an explicit `PutVectors` lookup returned zero.

This matches the AWS logging contract:

- control-plane bucket/index/policy actions are management events logged by default;
- vector operations are CloudTrail data events and require selectors for `AWS::S3Vectors::VectorBucket` or `AWS::S3Vectors::Index`.

## Cleanup proof

Both live scripts had exact-resource cleanup traps. Final authorized inventory:

```text
all_vector_buckets=0
audit_vector_buckets=0
audit_roles=0
```

CloudTrail additionally recorded successful `DeleteIndex` and `DeleteVectorBucket` for both completed fixtures, plus `DeleteVectorBucketPolicy` for the policy fixture. No S3 Vectors or IAM test asset remains.

## Retained high-value techniques

| Technique | Classification | Reason retained |
| --- | --- | --- |
| List/Get complete vectors and metadata | Post-exploitation | Direct bulk disclosure of embeddings and commonly sensitive RAG source/context metadata |
| Query-only semantic/membership probing | Post-exploitation | Exact permission boundary still returns keys/distances; useful without full data read |
| Blind vector upsert | Post-exploitation / application persistence | One exact action replaces trusted RAG context without read permission; data operations are not logged by default |
| Blind known-key deletion / index deletion | Post-exploitation | Targeted corruption or complete availability loss with clear minimum actions |
| External principal in vector-bucket policy | Service-level persistence | Durable authenticated cross-account access to current/future indexes under the chosen resource pattern |
| Self-grant through `PutVectorBucketPolicy` | Privilege escalation | Live verified escalation from one exact permissions-management action to vector data access |

## Rejected, excluded or ledger-only ideas

- **Anonymous/public bucket policy:** rejected by mandatory S3 Block Public Access in a live test; all requests require AWS credentials. No unauthenticated page was created.
- **KMS bypass through bucket policy:** no bypass. AWS documents `kms:Decrypt` for every vector-level operation on SSE-KMS indexes and cross-account key-policy requirements.
- **Live SSE-KMS boundary fixture:** not run because creating a dedicated customer-managed key would leave a seven-day pending-deletion resource, conflicting with strict zero-residue requirements. Official documentation is explicit enough for the public KMS boundary.
- **Index encryption downgrade:** indexes may intentionally override bucket encryption with immutable SSE-S3 or SSE-KMS. This is expected configuration behavior, not access by itself. Defenders should constrain `CreateIndex` with `s3vectors:sseType`/`s3vectors:kmsKeyArn`; no standalone attack page.
- **Delete/recreate index with the same name:** destructive replacement can change dimension, metadata configuration and encryption, but needs broad delete/create/write access and is noisier than direct `PutVectors`; retained in the future queue rather than duplicated as a technique.
- **Tag-based ABAC manipulation:** `TagResource` can matter if a separate policy grants data access based on mutable `aws:ResourceTag` or `s3vectors:VectorBucketTag`. This generic two-permission ABAC composition is documented as a review point, not promoted as a distinct S3 Vectors attack without a concrete victim policy.
- **VPC endpoint policy:** it is only an additional network authorization layer. Changing one requires EC2 permissions and does not independently grant S3 Vectors access.
- **Bedrock/OpenSearch integrations:** those services can consume/export S3 vector indexes, but no distinct `s3vectors` credential-vending or role-passing API exists in the current service surface. Integration-specific attacks belong on their service pages.
- **Vector extraction/inversion certainty:** raw embeddings and similarity oracles can support model-specific inference research, but deterministic recovery of original text is not guaranteed. Public wording avoids overstating it.
- **Vector-bucket policy lockout:** replacing the policy can add explicit denies or remove other grants, but this is already covered by the stronger self-grant/persistence primitive and ordinary policy precedence.

## Unexpected-defect assessment

No unexpected AWS vulnerability was confirmed:

- public policies were rejected;
- conditional `GetVectors` authorization was enforced for data, metadata and filters;
- exact index scoping was honored in all probe policies;
- SSE-KMS remains an independent documented authorization boundary;
- the self-grant, upsert and blind-delete behaviors are documented/expected permission semantics.

No private bug-bounty report was created.
