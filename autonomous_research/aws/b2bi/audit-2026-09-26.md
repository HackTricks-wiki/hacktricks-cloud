## Verified results worth documenting

### Sensitive metadata reads

Exact-resource `GetProfile`, `GetTransformer`, `GetCapability`, and `GetPartnership` succeeded without any list permission. Returned data included fake contact PII, a complete EDI sample document, S3 buckets/prefixes, instruction-document key, transformer/capability links, and trading-partner ID.

### Update response read oracle

With all matching `Get*` operations explicitly denied, exact-resource updates that re-supplied one known current field returned the complete object:

- `UpdateProfile`: email, phone, business name, logging state.
- `UpdateTransformer`: complete sample document/configuration.
- `UpdateCapability --name`: full S3 paths, instruction document, transformer ID.
- `UpdatePartnership --name`: email/phone, profile, capabilities, trading-partner ID.

This is expected API behavior rather than an AWS authorization defect, but it is an important permission-review trap.

### Persistent transformer replacement

- Created and activated an inert replacement transformer.
- A caller with `b2bi:UpdateCapability` on exactly the capability and replacement transformer changed the capability's `transformerId` without `GetCapability`/`GetTransformer`.
- Restored the original transformer immediately.
- Input/output locations are immutable: a tested output-prefix replacement was rejected with `EDI Capability outputLocation cannot be changed`.
- Active transformers cannot return to inactive, and mapping changes on an active transformer are rejected. A malicious mapping must be finalized before activation.
- Tagged creation additionally enforced `b2bi:TagResource`. In this account it also walked the vended-log setup chain: `logs:DescribeLogGroups`, `logs:ListLogDeliveries`, then `logs:CreateLogDelivery`.

### S3 boundary

- `StartTransformerJob` with only the B2BI action and explicit `Deny s3:*` failed while getting input object attributes.
- `TestParsing` behaved the same even when the bucket policy trusted `b2bi.amazonaws.com`.
- `TestParsing` is authorized against the synthetic `arn:aws:b2bi:REGION:ACCOUNT:transformer/*`, despite accepting no transformer ID.
- Giving the caller input/output S3 permissions was not sufficient for successful service writes until the service principal also had a bucket policy. This confirms two distinct checks: invoker identity access and service-principal resource access.
- A deliberately incomplete output policy produced a failed job after partial ACK/parsed objects were generated. Every generated object was removed.
- No `iam:PassRole` dependency was observed. KMS relies on key policies for `b2bi.amazonaws.com`.

### CloudTrail observations

- `eventSource` is `b2bi.amazonaws.com`.
- Read events normally recorded the ID with `responseElements: null`.
- Profile/partnership PII and transformer mapping/sample contents were redacted as `HIDDEN_DUE_TO_SECURITY_REASONS`.
- `UpdateCapability` masked S3 paths in `requestParameters` but returned those paths unmasked in `responseElements`.
- Event History returned no `StartTransformerJob`, `GetTransformerJob`, `TestParsing`, or `TestMapping` records while contemporaneous management events were present. AWS's CloudTrail reference classifies B2BI transformer operations such as `StartTransformerJob` and `GetTransformerJob` as data events on `AWS::B2BI::Transformer`. Data events are not in Event History and are not enabled in trails by default. This is expected behavior, not a logging defect, but it creates a high-stealth path in accounts that collect only management events.
- Delete management events appeared after the normal delivery delay and contained the expected target IDs.

## Candidate vulnerabilities tested and rejected

- **XSLT local-file/SSRF primitive:** `document('file:///etc/hostname')` was rejected with `External URI resolution is not permitted`.
- **XXE:** a `DOCTYPE`/external entity in mapping input was rejected.
- **S3 read/write proxy:** both job and test parsing APIs enforced caller S3 access; no privilege escalation.
- **Cross-account resource access:** B2BI exposes no resource-policy API and documents identity-only resource access. No cross-account path was found.
- **Arbitrary output redirection:** capability S3 locations cannot be changed after creation.
- **Active transformer mutation:** active-to-inactive and active mapping changes were rejected.
- **Instruction-document path changes:** possible on an owned bucket but considered low value by itself; omitted from the book.
- **Tag-only persistence/ABAC bypass:** no useful bypass found; standard request/resource tag keys were enforced.
