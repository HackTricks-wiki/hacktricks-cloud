## Prior documentation review

The existing PR page had useful high-level ideas but was based only on inactive-account setup errors. It also needed four corrections:

1. `UpdateSettings` only changes defaults for future assessments; an existing assessment's report destination is changed with exact-resource `UpdateAssessment`.
2. Cross-account report publication still needs S3/KMS authorization. An Audit Manager destination change does not bypass the bucket, identity, or key policies.
3. `DisassociateAssessmentReportEvidenceFolder` changes the report selection but does not delete raw evidence.
4. Audit Manager's CloudTrail schema redacts report destinations and other sensitive request bodies as `***`; the prior claim that the new destination was logged in clear text was incorrect.

The revised page adds direct evidence/report disclosure, existing-assessment redirection, Evidence Finder export redirection, delegation, manual-evidence poisoning, false review status, report-selection suppression, and irreversible Evidence Finder deletion.

## Live authorization design

The temporary role trusted only `ChackBotAdministratorRole`. Its base policy allowed `auditmanager:*` only so each fresh `AssumeRole` session could be intersected with a one-action session policy and an exact resource. This avoided inline-policy propagation ambiguity while preserving a true single-action test boundary.

Every resource test used non-existent identifiers:

```text
assessment: 00000000-0000-4000-8000-000000000000
control set: ht-am-set
```

A call was treated as authorized only when it reached Audit Manager's account-state error, `Please complete AWS Audit Manager setup ...`, rather than IAM's `not authorized` response. No authorized probe could mutate state because the service rejected the call before resource processing.

## Strong expected attack paths

### Evidence and report disclosure

- `GetEvidence` returns account/resource identifiers, event and configuration attributes, compliance results, and other collected evidence.
- `GetAssessmentReportUrl` returns a pre-signed URL object. This is the cleanest report-theft primitive because it does not require granting the caller direct `s3:GetObject` on the report bucket.
- Practical discovery additionally needs list/get/folder permissions unless identifiers are known from logs or another compromise.

### Cross-account S3 destination redirection

- AWS officially supports cross-account assessment-report buckets with CLI/SDK even though the console does not.
- `UpdateSettings` changes the default assessment-report destination for new assessments and the default Evidence Finder CSV export destination.
- `UpdateAssessment` changes an existing assessment's destination. AWS documents that assessment edits take effect at 00:00 UTC the next day.
- Publication is performed with the assessment/report owner's permissions. The compromised identity must have the required S3/KMS authorization, and the cross-account bucket policy must trust that principal. This is an expected exfiltration chain, not a bucket-policy bypass.

### Delegation as evidence access and tampering

- Delegation gives the chosen role Audit Manager permissions over the selected control set: evidence reads, manual evidence import, control/comment updates, and control-set review submission.
- Live IAM evaluation proved the creator needs the action on both assessment and control-set ARNs.
- The AWS-managed administrator policy contains no `iam:PassRole`; this is resource-level Audit Manager delegation, not service role assumption.
- Arbitrary external-account acceptance was not claimed. Official UI documentation describes selecting users/roles and can span supported in-scope accounts, but the inactive account prevented recipient validation.

### Evidence poisoning and report suppression

- `BatchImportEvidenceToAssessmentControl` accepts one of `textResponse`, `s3ResourcePath`, or `evidenceFileName` and can inject false manual evidence.
- `UpdateAssessmentControl` can add comments and set `REVIEWED`.
- `BatchDisassociateAssessmentReportEvidence` and `DisassociateAssessmentReportEvidenceFolder` omit records from the next report without removing the underlying evidence.
- `UpdateAssessmentStatus INACTIVE` stops future collection while retaining existing evidence.

### Destruction and crypto availability

- AWS states that `DeleteAssessment` permanently removes an assessment and all evidence that it collected.
- `DeleteAssessmentReport` attempts S3-object and metadata deletion. If S3 returns 403/404, it still deletes Audit Manager metadata and leaves the object.
- `UpdateSettings --no-evidence-finder-enabled` deletes the Audit Manager CloudTrail Lake event data store. It cannot be re-enabled normally; the customer must deregister and re-register the service.
- Changing the Audit Manager KMS setting and later disabling/deleting the selected customer key can make content unrecoverable, but that chain requires the relevant KMS authorization and was not tested destructively.

CloudTrail Event History captured every tested Audit Manager call under `auditmanager.amazonaws.com`, including reads and failed calls.

| `BatchCreateDelegationByAssessment` | Assessment ID visible; `createDelegationRequests` redacted as `***` |
| `UpdateSettings` | Setting name visible; `defaultAssessmentReportsDestination` redacted as `***` |
| `StartAssessmentFrameworkShare` | Framework ID, destination account/Region, and comment visible |
| `CreateAssessmentReport` | Assessment ID and supplied report name visible; error response contained the setup message |

The current AWS user guide's sample `CreateAssessment` CloudTrail record likewise redacts name, description, scope accounts, roles, tags, destination, and response assessment. Detection must alert on the action and actor rather than parse the new destination or delegation role from the event.

All techniques are management events and therefore visible in Event History. Reads are medium stealth because their responses are not logged; account-level settings changes and destructive writes are low stealth/rare.

## Lower-value or rejected ideas

- **Framework sharing as evidence exfiltration:** `StartAssessmentFrameworkShare` copies a custom framework and its custom controls, not assessments or collected evidence. It can leak sensitive control text if customers put secrets there, but AWS already warns not to share sensitive framework content. Retain as a cross-account governance check, not a primary attack technique.
- **Custom-control rewrite as immediate assessment poisoning:** custom controls/frameworks are important integrity objects, but updating a library object is not clearly equivalent to silently rewriting controls already instantiated in an active assessment. Do not overclaim without an active customer fixture.
- **SNS redirection as secret exfiltration:** notifications can expose workflow metadata, but no external SNS destination was created and the expected impact is weaker than evidence/report theft. Monitor `UpdateSettings` and approved topic policies.
- **`GetEvidenceFileUploadUrl` as arbitrary S3 write:** the API returns a managed upload URL for manual evidence. No evidence supports arbitrary key selection or a write outside the intended upload workflow.
- **Availability change bypass:** no attempt was made to invoke `RegisterAccount` on the inactive post-cutoff account. Activating a closed-to-new-customers service solely for research could leave irrecoverable customer state and was unnecessary for the authorization audit.
