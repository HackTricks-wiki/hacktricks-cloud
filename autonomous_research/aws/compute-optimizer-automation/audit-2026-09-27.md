# AWS Compute Optimizer Automation audit — 2026-09-27

## Scope and outcome

Audited the new `compute-optimizer-automation` CLI / `aco-automation` IAM surface, including recommendation reads, one-time execution, scheduled account/organization rules, enrollment, service-linked-role permissions, resource scoping, cross-account behavior, rollback, unauthenticated access and CloudTrail.

Public coverage was added because active rules provide a durable organization-scale mutation path, and `StartAutomationEvent` can apply EBS changes without direct EC2 write permission. Claims are bounded to current expected functionality; no vulnerability was found.

## Current action and authorization model

Current recommendation types are only:

- snapshot and delete an EBS volume observed unattached for at least 32 days;
- upgrade an eligible previous-generation EBS volume type.

Automation uses `AWSServiceRoleForComputeOptimizerAutomation`, trusted by `aco-automation.amazonaws.com`. Its managed policy can describe EBS state, create snapshots and volumes, modify/delete volumes and tag resources. Modify/delete excludes resources carrying the documented `exclude-from-compute-optimizer-automation` tag. There is no caller-selected role, PassRole, arbitrary API/command input, resource policy or credential return.

Only existing-rule get/update/delete/tag operations support the global rule ARN `arn:aws:compute-optimizer::ACCOUNT:automation-rule/RULE_ID`. Create/list/enrollment/event/ recommendation/account-association/on-demand/rollback actions require `Resource:"*"`. Recommendation and rule-preview lists additionally depend on `ec2:DescribeVolumes`.

## Retained techniques

1. Enumerate global rules, recommendations, event history and—when operating as a management/ delegated administrator—associated member recommendations.
2. Use `StartAutomationEvent` to make the fixed service role implement a known recommendation without direct EC2 write actions.
3. Create or update an active no-criteria account rule to apply future recommendations across all supported Regions.
4. From a management/delegated-admin account, associate members (automatic enablement and `AnyAllowed`) and apply an organization rule to up to 50 accounts.

The recurring rules are documented as persistence of malicious automation/state, not credential or login persistence.

## Rejected and bounded ideas

| Idea | Decision |
| --- | --- |
| Delete/modify any arbitrary EBS volume | Rejected. `StartAutomationEvent` accepts only a 16-character AWS-generated recommendation ID; the current recommendation set is constrained. |
| Arbitrary execution as the service-linked role | Rejected. No role selector, script, command, URL, destination or general API input exists. |
| Read EBS data through recommendation APIs | Rejected. They return configuration, tags and savings—not blocks, snapshots or credentials. |
| Snapshot action directly exfiltrates data | Rejected. The snapshot stays in the resource account with its existing encryption/access boundaries. Separate EC2/KMS permissions are required to use it. |
| Organization action from an ordinary member | Rejected. Association and organization rules have service-side management/delegated-admin and trusted-access checks. |
| Unauthenticated enumeration | Rejected by live unsigned request; no resource-policy API exists. |
| Disassociate/disable as standalone technique | Availability/governance only; retained as defensive context, not promoted. |
| Rollback as privilege escalation | Bounded corrective workflow for a previous event, subject to snapshot/current-state/time/EBS modification limits. |

## Telemetry

AWS documents every Automation API call as a CloudTrail management event. The event source is `aco-automation.amazonaws.com`; rules are global, so defenders should use a multi-Region trail and not assume changes occur in one fixed Region. Downstream snapshot/delete/modify/create operations use the service-linked role and appear in EC2 telemetry. Generated snapshots carry `aws:compute-optimizer:automation-event-id`.

## Cleanup proof

Final state remains base Compute Optimizer enrollment `Inactive`; Automation reads remain opt-in blocked; the Automation service-linked role and historical test role are absent.
