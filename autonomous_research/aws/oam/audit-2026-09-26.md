## Documentation review

OAM is a regional cross-account observability plane:

1. A monitoring account creates one sink per Region and attaches a resource policy permitting source accounts/organizations and resource types.
2. A source account creates a link to that sink and chooses resource types plus optional metric namespace / log-group filters.
3. The monitoring account obtains direct visibility into the shared metrics, logs, traces, Application Insights applications, Internet Monitor monitors, and Application Signals services/SLOs without assuming into the source.

Source identity permissions require more than `oam:CreateLink`/`UpdateLink`. Each telemetry family has a dependent `Link` action:

| Type | Action |
| --- | --- |
| Metrics | `cloudwatch:Link` |
| Logs | `logs:Link` |
| Traces | `xray:Link` |
| Application Insights | `applicationinsights:Link` |
| Internet Monitor | `internetmonitor:Link` |
| Application Signals service/SLO | `application-signals:Link` |

The sink policy and identity policy can constrain types with `oam:ResourceTypes`.

## Live authorization tests

### CreateLink resource evaluation

Created a sink and a sink policy permitting only account `228478051196` and `AWS::CloudWatch::Metric`. A caller with `oam:CreateLink` only on the exact sink ARN failed:

```text
not authorized to perform: oam:CreateLink on resource:
arn:aws:oam:us-east-1:228478051196:link/*
```

This confirms that a least-privilege identity policy for creation must cover both:

- the monitoring-account sink ARN; and
- the source-account `link/*` ARN pattern.

This nuance appears in the AWS user-guide example even though the Service Authorization Reference's action row emphasizes the sink resource type.

### Telemetry service actions are enforced

After allowing `oam:CreateLink` on both resources, the same request failed on:

```text
cloudwatch:Link on resource: *
```

After adding only `cloudwatch:Link`, authorization reached semantic validation and returned:

```text
InvalidParameterException: Cannot create a link to a sink in the same account
```

Thus the safe one-account test verified every source-side authorization layer without establishing a data path. The remaining external sink-policy and different-account requirements are explicit expected service behavior documented by AWS.

### PutSinkPolicy is an independent blind write

A role with only `oam:PutSinkPolicy` on the exact sink successfully replaced its policy and expanded accepted types from metrics to metrics plus log groups. `oam:GetSinkPolicy` was independently denied. The caller therefore does not need read access to overwrite a known sink policy.

This behavior is expected replacement semantics, not a vulnerability. Potential attack uses brainstormed:

- allow an attacker-controlled source account to attach and inject misleading external telemetry into a central monitoring view;
- remove legitimate source principals or types and break new link creation/update;
- use principal-validation success/error differences, which is already documented elsewhere.

The first two were not promoted as standalone book techniques: existing attached links are managed from their source accounts, and monitoring-account poisoning/disruption is less generally useful than the verified source-side disclosure/blinding paths.

## Published expected techniques

1. `oam:CreateLink` plus per-type `Link` actions can create a durable cross-account observability disclosure channel to a preauthorized external sink. No `iam:PassRole` is involved.
2. `oam:UpdateLink` can remove filters (`Filter: "*"`) or add resource types to broaden disclosure; it can also narrow types/filters while leaving the link present.
3. `oam:DeleteLink` can sever central monitoring from the source account.

Cross-account success itself was not executed because only one authorized account was available. The permission chain was verified live through the service's same-account guard, and the cross-account prerequisites are documented in the book rather than implied away.

| Event | Observed fields |
| --- | --- |
| `CreateSink` | Name and tags in request; full sink ARN/ID/name/tags in response. |
| `PutSinkPolicy` | Full unredacted policy and sink ARN in both request and response. |

AWS also emits best-effort direct EventBridge lifecycle events to the monitoring account: `Attached Link Created`, `Attached Link Updated`, and `Attached Link Deleted`.

## Potential defect backlog

- Test from a second authorized account whether `oam:ResourceTypes` is enforced identically by the source identity policy and sink resource policy for every current type.
- Test whether a source can request additional type strings by casing/duplicate/array-shape tricks that bypass either policy condition.
- Test UpdateLink concurrency and eventual-consistency races between a sink-policy restriction and source link expansion.
- Test whether filtering differences leak log-group or namespace existence to the monitoring account outside the configured filters.
- Test whether attached-link lifecycle EventBridge events contain enough policy/link detail for reliable prevention and whether any deletion/update path lacks the event.
- Compare CloudTrail visibility of actual linked telemetry reads in both source and monitoring accounts; identify blind spots but do not call expected account-local logging a defect.
- Test tag-condition enforcement for link creation because the API authorizes both a future `link/*` and a remote sink resource.
- Test Organizations sink policies for stale membership, suspended accounts, delegated administrators and organization moves.
