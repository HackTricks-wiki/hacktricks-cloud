# AWS Support Authorization audit — 2026-09-30

## Scope and model

- Audited the new `supportauthz` API model dated 2026-06-30 with AWS CLI 2.37.6, current API/user-guide/IAM contracts, and live read-only calls in `us-east-1` and `eu-west-1`.
- A permit authorizes AWS Support operators—not the permit creator—to perform catalogued actions against selected resources. It is signed through a customer-managed same-Region ECC P-384 signing key.
- `CreateSupportPermit` accepts the two broad unions `allActions` and `allResourcesInRegion`. Both time conditions and `supportCaseDisplayId` are optional, so proactive no-expiry authorization is explicit supported functionality.
- Permits are immutable except tags. Deletion revokes the authorization; disabling/revoking the KMS signing path can prevent new signatures but is eventually consistent and does not delete the permit.

## Live inventory and action catalog

- Both allowed Regions returned zero permits and zero pending permit requests.
- The service returned opaque continuation tokens across several empty internal pages. Manual traversal terminated after three permit pages and four request pages; this is a sparse-pagination behavior, not an infinite-loop defect.
- Neither Region had an existing customer-managed key with `KeySpec=ECC_NIST_P384` and `KeyUsage=SIGN_VERIFY`. No KMS key was created because KMS deletion cannot be completed immediately.
- `ListActions` returned no entries for sampled `ec2`, `eks`, `redshift`, `s3`, `lambda`, or `dynamodb` prefixes. The live `rds` catalog returned:
  - `rds:CustomerDataAccess` — diagnostics may access small amounts of customer content;
  - `rds:read-backup-data_run` — diagnostics access database backup data; and
  - `rds:read-volume-data_run` — diagnostics access database volume data.

Catalog results are dynamic. Public coverage tells operators to enumerate them rather than treating this sample as exhaustive.

## Authorization boundary probe

- Assumed `ChackBotAdministratorRole` from `hacktricks-training` with a session policy granting only `supportauthz:CreateSupportPermit` on `*`.
- Submitted a synthetic request named `HTAuthzProbe20260930` using `allActions`, `allResourcesInRegion`, no conditions, no case and an existing AWS-managed symmetric key.
- The request reached Support Authorization and failed on caller-side `kms:DescribeKey`. No permit was created.
- This verifies that `CreateSupportPermit` alone is insufficient and that Support Authorization uses a KMS forward access session. Current docs require `kms:DescribeKey` and `kms:CreateGrant` on a same-Region customer-managed ECC P-384 `SIGN_VERIFY` key, with strict service/grant conditions.
- A successful fixture was deliberately not created because no compatible key existed and a new KMS key would remain scheduled for deletion rather than being immediately removable.

## Telemetry

- `ListSupportPermits`, `ListSupportPermitRequests`, and `ListActions` were default read-only management events under `supportauthz.amazonaws.com`; responses were omitted. Pagination tokens were retained in request parameters.
- The failed `CreateSupportPermit` was a default write management event. It retained the exact `allActions`, `allResourcesInRegion`, name, description, signing-key ARN and generated client token. Its response retained the complete `kms:DescribeKey` authorization error and restricted session ARN.
- AWS documents `SupportPermitRequestCreated`, `RetrieveSupportPermit`, `StartSupportAction`, and `CancelSupportPermitRequest` as default `AwsServiceEvent` management events. `StartSupportAction` is emitted per permitted action/resource. The signing KMS key also logs grant/sign use.

## Public technique decision

- Publish foundational enumeration and no-expiry Support-access-plane persistence because broad, case-free, expiry-free authorization is durable and currently includes support actions that can access RDS customer/backup/volume data.
- Bound the impact strictly: the creator receives no credential, cannot assume the Support service-linked role, and cannot directly invoke the supported action. An AWS Support operator must retrieve and use the authorization. Separate `support:*` permissions and human interaction are required for an attacker-controlled case/social-engineering path.
- This is expected functionality, not an AWS vulnerability. No private report was created.

## Cleanup

- The failed create left no permit or KMS grant.
- Final permit inventories remain empty in both Regions.
- No KMS key, Support case, RDS resource, service-linked role, EventBridge rule or notification resource was created.

## Follow-up hypotheses

- Test whether case closure deactivation is prompt and fail-closed under concurrent `RetrieveSupportPermit` requests.

- Compare a proactive permit against a reactive request whose requested scope is narrower: confirm whether a covering broad permit accepts the request by design and which telemetry associates them.
