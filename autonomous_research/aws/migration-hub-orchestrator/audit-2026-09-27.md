## Execution chain

`CreateWorkflowStep` accepts a custom `AUTOMATED` step with:

```text
scriptLocationS3Bucket
scriptLocationS3Key.linux / .windows
command.linux / .windows
runEnvironment = AWS | ONPREMISE
targetType = SINGLE | ALL | NONE
stepTarget[]
```

The current service-linked role policy permits:

- `ssm:SendCommand`, `ssm:GetCommandInvocation`, and `ssm:CancelCommand` on
  `AWS-RunRemoteScript`, all EC2 instance ARNs, and matching Orchestrator bucket resources;
- `ssm:DescribeInstanceInformation` and `ssm:GetCommandInvocation` on `*`;
- `s3:GetObject` from `migrationhub-orchestrator-*` buckets.

There is no instance-tag condition in that managed policy. AWS Systems Manager documents that SSM
Agent normally executes with root permissions on Linux/macOS and SYSTEM on Windows. Consequently,
an actor allowed to mutate and start an existing workflow can cross from Orchestrator permissions
to operating-system command execution and then use the target's available role credentials and
network/data access.

## Minimum-permission model

Primary existing-workflow path:

```text
migrationhub-orchestrator:CreateWorkflowStep
migrationhub-orchestrator:StartWorkflow
s3:PutObject on arn:aws:s3:::migrationhub-orchestrator-<suffix>/<key>
```

The two Orchestrator actions scope to:

```text
arn:aws:migrationhub-orchestrator:REGION:ACCOUNT:workflow/WORKFLOW_ID
```

`CreateWorkflowStepGroup` is additionally required only if no suitable custom group exists. Direct
caller `ssm:SendCommand` and `iam:PassRole` are not required. The alternative existing-step path
uses `UpdateWorkflowStep` and, for a failed step, `RetryWorkflowStep` on the same exact workflow ARN.

Prerequisites intentionally kept in the public technique:

1. Existing-customer eligibility and a workflow in a compatible state.
2. The Orchestrator service-linked role.
3. A mutable custom group/step or permission to add one.
4. A selected AWS server registered as an SSM managed node, or a configured on-premises plugin path.
5. A correctly prefixed S3 script object readable by the service.

## IAM and logging notes

- Workflow ARN: `arn:aws:migrationhub-orchestrator:REGION:ACCOUNT:workflow/ID`.
- Template ARN: `arn:aws:migrationhub-orchestrator:REGION:ACCOUNT:template/ID`.
- Top-level `ListWorkflows`, `ListTemplates`, and `ListPlugins` are unscoped; nested workflow list
  calls and workflow mutation APIs use the exact workflow ARN.
- `CreateWorkflow` evaluates its source template ARN, but creating a workflow is not needed for the
  most direct existing-workflow technique.
- Orchestrator control-plane calls are CloudTrail management events under
  `migrationhub-orchestrator.amazonaws.com`.
- The AWS CloudTrail guide names workflow lifecycle events `CreateMigrationWorkflow`,
  `StartMigrationWorkflow`, etc., while step calls use the public API names.
- The service-linked role's downstream `ssm:SendCommand`, Run Command history, SSM Agent logs and
  optional S3/CloudWatch output form a second detection layer.
- S3 object reads require data-event logging or equivalent bucket telemetry for direct visibility.
