## Resource and IAM findings

```text
arn:aws:verifiedpermissions::<account>:policy-store/<id>
arn:aws:verifiedpermissions:<region>:<account>:policy-store-alias/<name>
```

- `ListPolicyStores`, `ListPolicyStoreAliases`, and `CreatePolicyStore` require `Resource: "*"`.
- Schema, policy, template, identity-source, decision, validation-setting, and tag operations authorize against the exact parent store ARN.
- Policies/templates/identity sources have no separate IAM ARN.
- `CreatePolicyStoreAlias` requires both the exact destination-store ARN and exact alias ARN.
- `GetPolicyStoreAlias` and `DeletePolicyStoreAlias` authorize against the exact alias ARN.
- Policy-store aliases are Regional, while the policy-store ARN format omits Region.
- Store-scoped actions support `aws:ResourceTag/<TagKey>`; create/tag paths also support request-tag keys.

## Alias propagation observations

The documented non-atomic alias behavior was reproduced:

1. Immediately after creating an alias, an authorization request through it briefly returned `ResourceNotFoundException` even though the control-plane create had succeeded.
2. Immediately recreating a just-deleted alias name returned `ConflictException` while the old deletion propagated.
3. Repeated create attempts continued producing visible management events.
4. The experiments were stopped before trying to exploit inconsistent decisions; all exact resources were deleted and final inventory returned zero.

This is expected eventual consistency documented by AWS, not a defect. It is operationally important because alias rebinding can create an indeterminate window of old/new/not-found authorization results.

## CloudTrail validation

Event History in `us-east-1` recorded the following as management events under `verifiedpermissions.amazonaws.com`:

- `CreatePolicyStore` / `DeletePolicyStore`
- `CreatePolicy`
- `ListPolicies` / `GetPolicy` / `BatchGetPolicy`
- `CreatePolicyStoreAlias` / `GetPolicyStoreAlias` / `DeletePolicyStoreAlias`
- `ListPolicyStores` / `ListPolicyStoreAliases`

`IsAuthorized` and `BatchIsAuthorized` did not appear in Event History. AWS documents authorization decisions as data events that must be explicitly enabled in a trail or event data store. This creates a material default detection gap for decision-oracle enumeration and later use of malicious policies.

The first failed local CloudTrail parsing command changed nothing. A corrected query confirmed `readOnly` and `managementEvent` classifications.

## Strong expected attack paths

| Technique | Required control | Result |
| --- | --- | --- |
| Read schema/policies/templates/identity sources | Exact-store read actions | Recover authorization and token-trust model |
| Decision oracle | `IsAuthorized`/token variant on exact store | Test principal/action/resource/context combinations without policy reads |
| Create/update permissive policy | Policy write on exact store | Application service privilege escalation |
| Update identity source | Identity-source write on exact store | Map attacker-controlled/less-trusted tokens into authorized principal types |
| Delete/recreate application alias | Exact alias delete plus alias+store create | Redirect alias-based authorization to a permissive store |
| Delete/corrupt store configuration | Exact store write/delete | Authorization outage; privilege gain only if application fails open |
| Persistent static/template policy | Exact store policy write | Service-level persistence after AWS session revocation |
| Persistent OIDC source | Exact store identity-source write | Durable attacker-issued application identities |
| Persistent alias mapping | Exact alias+store create | Durable selection of attacker-controlled authorization model |

No technique grants AWS IAM authority by itself. The impact is determined by what the consuming application delegates to a Verified Permissions decision.

## Rejected or constrained ideas

- **Unsigned store/decision access:** endpoints require SigV4 and IAM.
- **Public policy-store sharing:** no resource-policy API exists for stores.
- **Cognito cross-account source:** AWS requires the user pool in the same account.
- **OIDC token as AWS credential:** the token is evaluated only when an AWS-authorized caller invokes the token decision API.
- **Injected request entities as persistence:** `entities` and `context` affect only one decision request.
- **Permit overriding forbid:** Cedar forbid takes precedence.
- **Schema-only privilege escalation:** schema/validation changes can enable unsafe authoring but do not themselves produce an allow.
- **Alias as atomic traffic switch:** explicitly unsupported; propagation is asynchronous.
