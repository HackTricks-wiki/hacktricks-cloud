## Canonical IAM resource discovery

The first temporary role intentionally used the ARN interpretation suggested by naively inserting
the full API ID:

- `...:waba/waba-012345...`
- `...:phone-number-id/phone-number-id-012345...`

`ListLinkedWhatsAppBusinessAccounts` succeeded with `Resource: "*"`, while every resource action
was denied. The denials named the resources actually evaluated:

- `arn:aws:social-messaging:us-east-1:228478051196:waba/012345...`
- `arn:aws:social-messaging:us-east-1:228478051196:phone-number-id/012345...`

After changing only the policy resources to those canonical ARNs, the second role produced:

| API | Caller result | Interpretation |
| --- | --- | --- |
| `GetLinkedWhatsAppBusinessAccount` | `ResourceNotFoundException` | Exact WABA authorization passed |
| `GetLinkedWhatsAppBusinessAccountPhoneNumber` | `ResourceNotFoundException` | Exact phone authorization passed |
| `SendWhatsAppMessage` | `ResourceNotFoundException` | Exact send authorization passed; no message sent |
| `GetWhatsAppMessageMedia --metadata-only` | `ResourceNotFoundException` | Exact media-read authorization passed; no media copied |
| `CreateWhatsAppMessageTemplate` | `ResourceNotFoundException` | Exact WABA template-write authorization passed; no template created |
| `PutWhatsAppBusinessAccountEventDestinations --event-destinations []` | `InvalidParametersException: LinkedWhatsAppBusinessAccountId Not Found` | Exact destination-write authorization passed |
| `DisassociateWhatsAppBusinessAccount` | `ResourceNotFoundException` | Exact destructive authorization passed; nothing disassociated |

This live result is why the public page explicitly distinguishes API IDs from resource ARNs.

## Event-destination PassRole boundary

A third isolated test created:

- caller role `ht-social-caller-1790477989-2304350`;
- delivery role `ht-social-delivery-1790477989-2304350`, trusted only by
  `social-messaging.amazonaws.com`;
- no SNS topic.

The caller initially held only
`social-messaging:PutWhatsAppBusinessAccountEventDestinations` on the exact canonical fake WABA.
Supplying the delivery role and a nonexistent SNS ARN returned an explicit `iam:PassRole` denial.

The caller policy was then expanded with only:

```json
{
  "Effect": "Allow",
  "Action": "iam:PassRole",
  "Resource": "arn:aws:iam::228478051196:role/ht-social-delivery-1790477989-2304350",
  "Condition": {
    "StringEquals": {
      "iam:PassedToService": "social-messaging.amazonaws.com"
    }
  }
}
```

A fresh session reached
`InvalidParametersException: LinkedWhatsAppBusinessAccountId Not Found`. This confirms the useful
minimum: exact WABA write plus exact, service-constrained PassRole when `roleArn` is supplied.
Neither call changed service state.

## CloudTrail results

AWS documents list/get/configuration operations as management events and message/media APIs as data
events on `AWS::SocialMessaging::PhoneNumberId`.

Live Event History showed:

- successful `ListLinkedWhatsAppBusinessAccounts` management reads;
- `GetLinkedWhatsAppBusinessAccount` and phone-number get events with the exact
  `ResourceNotFoundException`;
- `CreateWhatsAppMessageTemplate`, destination update and disassociation write events with their
  exact service errors;
- no `SendWhatsAppMessage` or `GetWhatsAppMessageMedia` event, as expected because data events are
  not enabled in Event History.

An initial lookup occurred before the second probe's events were indexed and showed only the first
role's correct `AccessDenied` events. A unique admin-session replay and a later issuer-filtered
lookup proved there was no error-code misclassification. No private vulnerability report was
created.
