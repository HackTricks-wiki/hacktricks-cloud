## PassRole and stored-authority boundaries

- `CreateLocationS3` requires `iam:PassRole` when supplying `BucketAccessRoleArn`.
- `UpdateLocationS3` is listed with dependent PassRole, but a path-only update that omits `S3Config` reuses the stored role and does not perform a new PassRole check.
- Baseline `StartTaskExecution` reuses stored location roles and needs no PassRole.
- `StartTaskExecution` requires PassRole when the request supplies `ManifestConfig.Source.S3.BucketAccessRoleArn` or `TaskReportConfig.Destination.S3.BucketAccessRoleArn`; both were explicitly denied in the live test.
- A manifest is a file/object selection list. It does not replace the task source or destination and cannot escape the source location's effective path/permissions.
- A task report can disclose paths, statuses, versions and error details but does not contain transferred file contents. Treat report redirection as metadata disclosure, not full data exfiltration.
- `DescribeLocation*` responses reveal paths/hosts/identities and S3 role ARNs but redact passwords, object-storage secret keys, Kerberos material and SAS tokens.

## Cross-account findings

- S3 is the native cross-account policy bridge: a DataSync role in the task-owning account accesses a foreign bucket whose bucket/KMS policies authorize it. `iam:PassRole` does not pass a role from another account.
- AWS documents S3-to-S3 and S3-to/from-other-storage cross-account combinations directly.
- EFS/FSx-to-EFS/FSx across accounts is represented through NFS/SMB protocol locations and requires an agent/network path; a foreign native EFS/FSx ARN is not a generic direct substitute.
- A cross-account S3 destination can make `StartTaskExecution` or a planted schedule an exfiltration channel, but the destination bucket policy and location role still must authorize writes.

## Rejected, bounded and future-test ideas

| Idea | Finding | Decision |
| --- | --- | --- |
| Replace task source/destination with `UpdateTask` or execution overrides | Neither API accepts new location ARNs. Includes, excludes, manifests and options operate inside the stored locations. | Rejected as arbitrary-location redirection. |
| Bypass PassRole through task report or manifest overrides | Live calls failed explicitly on `iam:PassRole`; the Service Authorization Reference also lists it as dependent. | Rejected as a bypass; documented exact boundary. |
| Full data exfiltration through task reports | Reports contain summaries or per-item status/path/error metadata, not file contents. This can still leak names, versions, KMS/resource ARNs and failure details. | Not promoted as full exfiltration. |
| Direct cross-account EFS/FSx location ARN | Cross-account combinations without S3 require NFS/SMB exposure and an agent according to the supported-transfer matrix. | Rejected direct native-ARN assumption. |
| Redirect an existing SMB location and reuse its stored NTLM password | `UpdateLocationSmb` permits a new server hostname and credentials are not readable. It is plausible that an omitted password remains stored, which could coerce NTLM authentication to an attacker server, but AWS replacement guidance supplies the password again and no agent fixture existed to settle behavior. | High-priority future test; not added to book or reported as a vulnerability. |
| Redirect object-storage location and recover its secret | S3-compatible authentication transmits an access-key ID and request signature, not the raw secret key. A captured signature may support offline guessing of weak secrets but is not direct disclosure. | Not promoted. |
| Agent-based internal HTTP/TCP probing | Object-storage locations accept agent, hostname, HTTP/HTTPS and a configurable port; NFS/SMB/HDFS locations also direct agents to network targets. Error/timing differences may form a network reachability oracle. | Future test requiring a disposable agent; no claim yet. |
| Secrets Manager custom-role coercion | Several location APIs accept a secret ARN and `SecretAccessRoleArn`, with PassRole enforced. Coercing secret-derived SMB/object credentials to an attacker endpoint may be valuable but needs an agent and protocol capture to prove exactly what leaves the appliance. | Future test; no zero-day report. |
| Agent activation-key theft | This is expected, documented functionality rather than an AWS malfunction. The risk exists only while the unactivated agent's port 80 is reachable, and the key expires after 30 minutes. | Strong misconfiguration technique; added to unauthenticated access. |
| Delete/cancel/update-execution actions | `DeleteTask`, `DeleteLocation`, `DeleteAgent`, `CancelTaskExecution` and bandwidth throttling are straightforward disruption, not privilege escalation, persistence or sensitive-data access. | Tracked but not promoted. |
| Tag-based ABAC self-tagging | Conditional on a separately unsafe victim IAM policy and generic to AWS ABAC. | Not promoted. |

## Telemetry conclusions

- DataSync API calls are CloudTrail management events by default, including `CreateAgent`, `CreateLocation*`, `UpdateLocation*`, `CreateTask`, `UpdateTask` and `StartTaskExecution`.
- Event History confirmed that successful `UpdateLocationS3` records the location ARN and `subdirectory: "/"`, while `UpdateTask` records the complete cron expression and enabled/disabled status.
- `iam:PassRole` is an authorization check and emits no standalone CloudTrail event; successful DataSync calls that accept a role can record it in their request parameters.
- In the two denied execution-override tests, CloudTrail stored `requestParameters: null` but the `errorMessage` still named the denied role ARN. Detections should inspect both fields rather than rely only on request parameters.
- S3 object operations are data events and absent from default Event History unless explicitly enabled. They are attributed to the DataSync location role, not the human/role that configured or started the transfer.
- DataSync metrics are automatically published to CloudWatch at five-minute intervals.
- Enhanced-mode tasks automatically use `/aws/datasync` logs. Basic-mode per-file/error logs require an allowed log group and a non-`OFF` log level.
- An activation-key HTTP GET is not an AWS API. If a foreign account claims the unactivated agent, `CreateAgent` and follow-on events appear in that account, not in the intended victim's CloudTrail.
