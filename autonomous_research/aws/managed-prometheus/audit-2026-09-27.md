## CloudTrail and detection results

- AMP control-plane calls were CloudTrail `Management` events.
- `CreateAlertManagerDefinition`, `CreateRuleGroupsNamespace` and `PutRuleGroupsNamespace` included the **complete base64 YAML** in `requestParameters.data`. This is encoding, not redaction.
- `PutResourcePolicy` included the complete JSON document, including principal and actions, in `requestParameters.policyDocument`.
- Describe calls recorded workspace/name but had `responseElements: null`; the returned definition bodies were not copied into the event.
- No Event history records were found for `RemoteWrite`, `QueryMetrics`, `GetLabels`, `GetSeries`, `CreateAlertManagerAlerts` or `PutAlertManagerSilences` after successful live calls.
- Query logging is optional and QSP-threshold based. AMP usage/ingestion metrics give aggregate visibility but are not principal-level audit trails.

## Negative, bounded and unresolved checks

### Logging delete least-privilege discrepancy

Rules/alert and query logging configurations were created successfully with administrator permissions. AWS's service authorization reference lists `DeleteLoggingConfiguration` and `DeleteQueryLoggingConfiguration` as supporting the workspace ARN.

A session policy allowing only both delete actions on the exact workspace nevertheless received:

```text
AccessDeniedException: IAM policy permission denied
```

for `DeleteLoggingConfiguration`. The administrator cleanup then asynchronously removed both configurations. Because the exact cause could be an undocumented CloudWatch Logs dependency or an authorization-reference mismatch, this is **not** treated as a security vulnerability and no unverified minimum-permission claim was published. Follow-up should independently compare:

1. exact workspace plus CloudWatch Logs delivery-management permissions;
2. `Resource: "*"` for the AMP delete action;
3. exact workspace after all configuration states are fully ACTIVE.

### Cross-account sharing

Resource-policy delegation was verified with a same-account principal that had no identity policy. AWS documentation states that cross-account access is supported for Prometheus-compatible APIs and requires an identity-policy allow in the trusted account as well as the workspace policy. The available external `chack-bot` user did not have a known independent AMP identity allow, so cross-account data access was not labeled live-tested.

### Alert delivery/exfiltration

An Alertmanager definition pointing to a same-account SNS topic became ACTIVE, and direct alert injection worked. An SNS subscription/topic policy was intentionally not added, so end-to-end alert delivery was not tested. Documentation confirms AMP requires the topic policy to allow `aps.amazonaws.com`; the configuration writer does not automatically obtain `sns:Publish`.

### Ideas intentionally not promoted

- Prometheus templates are formatting logic, not shell execution. No RCE claim.
- Managed scrapers accept structured EKS/network sources, not arbitrary URLs. No generic SSRF claim.
- Workspace alias changes were judged too low impact.
- `DeleteWorkspace` is obvious destructive access and did not merit a standalone technique.
- Anomaly detectors were not exercised because no stronger privilege or data boundary was identified.
- KMS grant/policy denial is primarily an availability path and would require extra infrastructure; authoritative boundaries are documented without a destructive live test.

## Future research queue

- Reproduce the logging-delete authorization discrepancy in a fresh workspace with one permission/dependency changed at a time.
- Use a second authorized AWS account with an explicit `aps:QueryMetrics` identity allow to live-test external resource-policy access, KMS grants and organization conditions.
- Test SNS alert delivery into a disposable SQS subscription to characterize exact message contents and topic-policy source conditions.
- Add a temporary CloudTrail Lake selector only if AWS later documents AMP data-event support; current AMP documentation describes control-plane management events only.
- Explore query-cost limits, label-set limits and whether a constrained writer can cause economically meaningful cardinality pressure below safety limits.
- Audit managed scraper `iam:PassRole`, EKS access-entry and VPC endpoint dependencies when a pre-existing cheap test cluster is available.
