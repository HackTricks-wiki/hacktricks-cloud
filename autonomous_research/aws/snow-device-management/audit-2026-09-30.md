# AWS Snow Device Management audit (2026-09-30)

## Scope and model

- AWS Snow Device Management (SDM) had no dedicated public HackTricks Cloud coverage before this pass.
- Reviewed the current Developer Guide, CLI/API model, Service Authorization Reference and Snowball CloudTrail documentation.
- The current service surface is small: device/task/execution/resource enumeration, device/task tagging, exact-task cancellation, and task creation.
- `CreateTask` is a tagged union with only `unlock` and `reboot`; it accepts one to ten managed-device IDs, and only one task executes on a device at a time.
- AWS no longer accepts new Snowball Edge customers. Existing-customer devices and legacy permissions remain a practical security surface.

## Read-only inventory and safe probes

In account `228478051196`:

- `ListDevices` and `ListTasks` in `us-east-1` reached the service and returned `AccessDeniedException: No devices found in this region`.
- `us-west-2` was unavailable because the organization SCP explicitly denies the Region.
- An unsigned `ListDevices` request returned `MissingAuthenticationToken`, confirming there is no unauthenticated inventory path.
- No SDM device/task resource, Snow job, IAM fixture, local-device session, network connection or billable infrastructure was created.

## Authorization boundary probe

Two fresh STS sessions called `CreateTask` with the nonexistent target `smd-htnonexistent0001` and command `unlock`:

1. one session allowed only `snow-device-management:CreateTask` on `Resource: "*"`;
2. one session allowed the same action only on the synthetic exact ARN `arn:aws:snow-device-management:us-east-1:228478051196:managed-device/smd-htnonexistent0001`.

Both requests reached the same account-level empty-inventory preflight and returned `AccessDeniedException: No devices found in this region`. Because that preflight occurs before useful action authorization in an account with no devices, the live environment could not distinguish the two policies. The public minimum therefore follows the authoritative current Service Authorization Reference: `CreateTask` has no resource type and must use wildcard resource scope. This is a documented-model result, not a claimed live exact-resource proof.

## High-value expected technique

`CreateTask` is worth public coverage despite the service's narrow command surface:

- **Unlock:** remote AWS IAM authorization replaces the normal local manifest plus 29-character unlock-code ceremony. This can enable a foothold for an attacker who separately has physical/local-network reach, but it does not itself return device credentials or grant local S3/EC2-compatible service access.
- **Reboot:** stops running EC2-compatible instances, interrupts device S3 writes, takes roughly ten minutes to recover, and requires a later unlock. This is a direct availability attack rather than privilege escalation.
- Both effects require activated remote management and a powered/networked device able to reach its device-order Region endpoint.
- Neither command is arbitrary execution, and no PassRole/downstream cloud-service permission is involved.

## Telemetry

- The Snowball documentation says its API calls integrate with CloudTrail and that read-only response bodies are omitted.
- A live `ListTasks` empty-account failure appeared in Event History under `snow-device-management.amazonaws.com` with `readOnly:true`, the requested `maxResults`, null response/resources and the access-denied error.
- Neither wildcard nor exact-ARN `CreateTask` empty-account failure appeared in recent Event History after propagation checks. Therefore the public page does not claim that every SDM preflight failure is captured.
- No accepted task could be observed without a real device. The public logs table treats successful write logging as the documented control-plane expectation and tells defenders to verify exact successful-event fields in their own trail.
- Task/execution inventory and physical/device/network behavior provide additional high-signal evidence for accepted unlock/reboot operations.

## Ideas considered but not promoted

- Task-description/tag phishing or injection: no security-relevant renderer or downstream trust path was identified.
- Tag-only persistence: changing device/task tags does not retain access or execute behavior.
- Repeated reboot loops: this is merely repetition of the same availability primitive and does not deserve a separate technique.
- Brute-forcing managed-device IDs: IDs are not an unauthenticated oracle, and signed list/CloudTrail/configuration sources are more realistic discovery paths.
- Arbitrary commands, update installation, credential recovery and local service control through `CreateTask`: rejected by the current tagged-union model; only empty `unlock` or `reboot` structures are valid.

## Potential unexpected-defect hypotheses

These require one or more authorized real devices and remain untested hypotheses:

1. Cross-account or cross-Region device-ID authorization confusion during `CreateTask` or exact-device reads.
2. Duplicate-target/case/Unicode parser inconsistencies that cause authorization and execution to resolve different device IDs.
3. Cancellation/execution races that report a task cancelled while a device still executes it.
4. Idempotency-token confusion allowing a token to replay a different command or target set.
5. Remote-unlock activation-state desynchronization that permits a task after remote management is disabled.
6. Task/execution response leakage across accounts when a valid foreign task/device ID is supplied.

No AWS defect was demonstrated and no private vulnerability report was created.

## Cleanup

- The account had no managed devices or tasks and no test infrastructure was launched.
- Final state is identical to initial state; there is no SDM cleanup debt.
