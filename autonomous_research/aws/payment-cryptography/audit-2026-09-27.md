### CloudTrail observations

- Signed `ListKeys`, `ListAliases` and `GetDefaultKeyReplicationRegions` appeared as `eventCategory=Management`, `managementEvent=true`, `readOnly=true` events.
- Successful control-plane read events had `responseElements=null`; detections cannot depend on returned key metadata being present.
- Failed authorization was logged with `errorCode=AccessDenied`.
- Official behavior: all control-plane operations are management events, but data-plane operations require paid advanced data-event selectors. Both `AWS::PaymentCryptography::Key` and `AWS::PaymentCryptography::Alias` must be selected.

## Expected attack ideas retained for the book

| Idea | Confidence / status | Book location |
| --- | --- | --- |
| Data-plane key oracle: decrypt/re-encrypt, PIN/key translation, card/PIN/MAC/cryptogram generation or verification | High; expected service functionality and current API/IAM mappings verified from official references. No production/payment operation performed. | Post exploitation |
| Export an exportable target under attacker-controlled wrapping/certificate material | High; documented expected function. Requires `ExportKey`, compatible exchange material and immutable `Exportable=true`. | Post exploitation |
| Redirect an application alias to another key, including an incompatible or attacker-controlled key | High; AWS documents that `UpdateAlias` does not validate matching old/new attributes. | Post exploitation |
| Stop or schedule deletion of payment keys and primary replicas | High; documented lifecycle behavior. Not executed because no victim key existed and creating one would leave a pending-deletion asset. | Post exploitation |
| `PutResourcePolicy` same-account self-grant | High; AWS explicitly states that a same-account principal allowed by the resource policy needs no additional identity allow for the granted key operation. | Privilege escalation |
| Alias-policy pivot: retain an alias-scoped data permission while changing the alias target | High expected authorization behavior; key compatibility still limits the resulting operation. | Privilege escalation |
| External-account principal in key resource policy | High; documented two-sided authorization model. | Service-level persistence |

## Ideas rejected or deferred

| Idea | Decision |
| --- | --- |
| Public/anonymous key resource policy | Not a technique. AWS rejects policies granting public access and unsigned endpoints rejected both tested requests. |
| Default multi-Region replication as persistence | Omitted from the book: it creates a useful monitoring gap/future attack surface but does not itself grant a new principal access, and primary state/deletion propagates to replicas. |
| Root-certificate import bypassing MPA | No bypass attempted. MPA protects only `ImportKey` with `RootCertificatePublicKey`; disabling an existing association itself requires current-team approval. Retain for future negative testing in an organization-enabled disposable account. |
| Control-plane/data-plane cross-account documentation differences | Current CLI/API descriptions vary by operation and older client versions; treat as documentation/version drift, not a security issue, until tested with two authorized accounts. |

## Potential vulnerability tests for a future disposable-key account

These are private research leads, not confirmed vulnerabilities and are not described as defects in the public book:

1. **Coverage of newly added data operations in CloudTrail.** The current Data API includes `GenerateAs2805KekValidation`, `GenerateAuthRequestCryptogram`, `GenerateMacEmvPinChange` and `TranslateKeyMaterial`, while the Payment Cryptography CloudTrail page's enumerated event list omits them. Enable both key and alias advanced selectors, invoke each with synthetic compatible keys, and verify that an event is delivered and sensitive fields are redacted.
2. **Alias-selector completeness.** Invoke each data operation once by key ARN and once by alias while only one selector type is enabled, then verify the documented requirement and ensure no identifier form escapes both selectors.
3. **Cross-account matrix.** For every API whose current reference says cross-account is supported, test key-ARN and alias invocation with resource policy + external identity allow, explicit denies, replica keys and resource-policy conditions.
4. **Resource-policy privilege semantics.** Validate same-account user ARN, role ARN and role-session ARN grants under permissions boundaries and session policies, especially for `ExportKey`, `DeleteKey` and data-plane actions.
5. **Alias target authorization.** Prove whether `UpdateAlias` requires authorization on alias plus old/new key resources, and whether alias-scoped data access follows a newly selected key exactly as documented.
6. **Public policy rejection variants.** Verify rejection of `Principal:"*"`, organization-wide patterns, anonymous federated principals and policy-variable variants without disclosing or creating public access.
