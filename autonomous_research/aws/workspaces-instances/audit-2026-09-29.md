# WorkSpaces Instances attack audit — 2026-09-29

## Scope and hypotheses

The existing WorkSpaces enumeration page covered `ListWorkspaceInstances` and `GetWorkspaceInstance` but not the new launch primitive. The primary hypotheses were:

| Hypothesis | Security classification | Result |
| --- | --- | --- |
| `CreateWorkspaceInstance` + user data + a passed instance profile gives root execution as the profile role | Expected privilege escalation | Confirmed authorization path; public technique added |
| The service omits `iam:PassRole` because the current Service Authorization Reference does not list it | Potential AWS authorization vulnerability | Falsified: downstream EC2 `RunInstances` enforces PassRole |
| AWS's example IAM policy is sufficient as written | Documentation/minimum-permission check | Falsified: live create also required `ec2:DescribeImages` |

## Documentation and model evidence

`CreateWorkspaceInstance` accepts an arbitrary AMI, instance type, subnet, security groups, instance profile, metadata options, key pair, public-IP/network-interface configuration, and sensitive `UserData`. The billing mode defaults to hourly and can be set explicitly to `HOURLY`. The service-linked role manages lifecycle operations on EC2 resources whose managed-resource operator is `workspaces-instances.amazonaws.com`.

The Service Authorization Reference currently lists `CreateWorkspaceInstance` and optional `TagResource`, but no `iam:PassRole` dependency. The WorkSpaces Core IAM guide separately grants the caller `ec2:RunInstances` and related actions when `aws:CalledVia` is the WorkSpaces Instances service. This split made live PassRole verification necessary.

## Live authorization results

Authorized account: `228478051196`, Region `us-east-1`.

### Read-only preflight

- The account had no WorkSpaces Instances or `AWSServiceRoleForWorkSpacesInstances` role.
- `us-east-1` was supported and offered hourly shared Linux configurations, including `c5.large`.
- A default VPC, subnet and security group were available.
- The current public Amazon Linux 2023 AMI resolved successfully.

### Hidden `DescribeImages` prerequisite

A restricted caller with `workspaces-instances:CreateWorkspaceInstance`, the EC2 actions shown in AWS's example policy, KMS permissions, and an explicit PassRole deny failed with:

```text
AccessDeniedException: Insufficient permissions for WorkSpaces billing operations
```

CloudTrail independently recorded `ec2:DescribeImages` under the restricted caller at the same time. Adding `ec2:DescribeImages` let the same invalid-AMI probe reach field validation. The error text is therefore misleading, and the current AWS example policy omits a practical create-path permission.

### PassRole boundary

The decisive request used a real public AMI, `c5.large`, hourly billing, a disposable empty EC2 instance-profile role, IMDSv2-required metadata, benign user data, and a caller with an explicit identity-policy deny on `iam:PassRole`.

`CreateWorkspaceInstance` initially returned a new `wsinst-*` identifier, but asynchronous provisioning changed to `ERROR_ALLOCATING`. `GetWorkspaceInstance` returned an EC2 client error stating that the caller was explicitly denied `iam:PassRole` on the selected role. No backing EC2 instance or EBS volume was created. This falsifies the missing-PassRole vulnerability hypothesis; callers must not treat the initial HTTP 200 as successful code execution.

### Positive-path limit

A second caller allowed exact-role `iam:PassRole`, `ec2:DescribeImages`, and `ec2:RunInstances` only through the documented `aws:CalledVia` path. WorkSpaces accepted the create and invoked `RunInstances` with:

- `invokedBy=workspaces-instances.amazonaws.com`;
- the supplied AMI, subnet, security group, instance profile and redacted user data; and
- the caller's restricted role session as the principal.

The organization's service control policy then explicitly denied `ec2:RunInstances` on the prospective instance resource. That organization-level restriction cannot be bypassed from this authorized account, so no compute was launched. The request nevertheless verifies the documented forward-access-session and exact PassRole path. Per the testing limit for unavailable privileges, the expected technique is documented from the verified authorization chain and official API contract rather than misrepresented as an end-to-end launch.

## Telemetry

| Event | Observed details |
| --- | --- |
| `CreateWorkspaceInstance` | Management write under `workspaces-instances.amazonaws.com`; request records profile, AMI, network and hourly billing, with user data hidden |
| `DescribeImages` | Management read attributed to the initiating restricted caller |
| `RunInstances` | Management write under `ec2.amazonaws.com`, attributed to the caller and marked `invokedBy=workspaces-instances.amazonaws.com`; user data was removed as sensitive |
| `DeleteWorkspaceInstance` | Management write; repeated delete attempts against an already deleting object returned not found |
| `iam:PassRole` | No standalone event; the EC2 error and selected profile appear in the downstream event/state |

## Cleanup

Both failed provisioning records reached terminal `DEALLOCATED` state. WorkSpaces Instances keeps these terminal list records as tombstones even though `DeleteWorkspaceInstance` returns not found. Final checks showed:

- no backing EC2 instances;
- no EBS volumes;
- no disposable caller role, target role, or instance profile; and
- no `AWSServiceRoleForWorkSpacesInstances` role after successful asynchronous deletion.

No billable compute was ever launched. No unexpected security defect remained, so no report was created under `/home/tester/cloud_bb/aws`.
