# AWS AppConfig security audit — 2026-09-26

## Scope and baseline

- Region: `us-east-1`
- Authorized account: `228478051196`
- Administrative test identity: assumed `ChackBotAdministratorRole` from the `hacktricks-training` profile.
- Initial inventory: zero AppConfig applications. AWS-provided deployment strategies were present.
- Sources reviewed: current AppConfig API/CLI models, Service Authorization Reference, AppConfig external-source/retrieval-role documentation, extension action/payload documentation, agent deployment documentation, and CloudTrail integration documentation.
- Cost: only AppConfig, IAM, one Secrets Manager test secret, and one SNS topic were used; no compute was launched.

## Authorization and behavior findings

### Hosted configuration and deployment

- `CreateHostedConfigurationVersion` requires authorization on both the application and configuration-profile resources. It creates, rather than overwrites, a version and does not deploy it.
- `StartDeployment` requires application, configuration-profile, environment, and deployment-strategy resources.
- AWS-provided deployment strategies use the **customer account ID** in the IAM resource ARN. The exact tested ARN was `arn:aws:appconfig:us-east-1:228478051196:deploymentstrategy/AppConfig.AllAtOnce`; an otherwise identical ARN with `aws` in the account field was denied.
- An `AppConfig.AllAtOnce` deployment exposed content through AppConfig Data while the control-plane state was still `BAKING`. `COMPLETE` is not a confidentiality boundary.

### AppConfig Data

- Both `appconfig:StartConfigurationSession` and `appconfig:GetLatestConfiguration` support the configuration ARN:
  `arn:aws:appconfig:<region>:<account>:application/<app>/environment/<env>/configuration/<profile>`.
- Both are CloudTrail data events for `AWS::AppConfig::Configuration`, disabled by default and absent from Event History.
- The initial and next-poll tokens are single-use bearer values and must not be printed in book evidence.
- Official documentation states cross-account AppConfig Data retrieval is unsupported.

### External-source retrieval role: confirmed delegated secret read

The lab created a disposable Secrets Manager secret, AppConfig application/environment, AppConfig-trusted retrieval role, and a separate low-privilege actor role.

Phase 1 actor permissions:

- `appconfig:CreateConfigurationProfile` on the exact application ARN.
- `iam:PassRole` on the exact retrieval-role ARN, conditioned on `iam:PassedToService = appconfig.amazonaws.com`.

The actor successfully created a `secretsmanager://<secret-arn>` configuration profile. A first attempt included request tags and correctly failed because `appconfig:TagResource` was absent; omitting optional tags proved they are not required for the technique.

Phase 2 added:

- `appconfig:StartDeployment` on the exact application, generated profile, environment, and account-qualified `AppConfig.AllAtOnce` strategy ARNs.
- `appconfig:StartConfigurationSession` and `appconfig:GetLatestConfiguration` on the exact generated configuration ARN.

The actor had **no** `secretsmanager:GetSecretValue`. It deployed the known Secrets Manager version and received the marker `APPCONFIG_DELEGATED_SECRET_READ_CONFIRMED` through `GetLatestConfiguration`. This confirms a useful, expected `iam:PassRole` escalation into data readable by the retrieval role.

Boundaries:

- The source ARN and version must be known.
- The role must trust AppConfig and have source read permissions; customer-managed encryption can add KMS requirements.
- The attacker needs an application, environment, strategy, and the complete AppConfig create/deploy/data permission set.
- This is same-account expected behavior, not an AWS vulnerability.
- S3, Parameter Store, and SSM document sources should offer analogous delegated reads, but only Secrets Manager was live-tested in this pass.

### Extension association boundary: confirmed target-resource gap is expected IAM design

A separate lab created an existing application and hosted profile as administrator. The low-privilege actor had only:

- `appconfig:CreateExtension` and `appconfig:CreateExtensionAssociation` on `Resource: "*"` (neither action supports resource-level IAM authorization); and
- `iam:PassRole` on the exact AppConfig action-role ARN.

The actor had no permission on the target application or configuration-profile ARN. It nevertheless created an extension and associated it to the exact pre-existing profile. This confirms that association creation does not require an additional action on the target AppConfig resource.

Compatibility test:

- An SNS URI at `PRE_START_DEPLOYMENT` was rejected with: `Extension action URI type SNS does not support the extension action point PRE_START_DEPLOYMENT`.
- The same SNS URI at `ON_DEPLOYMENT_START` succeeded and the target association succeeded.
- Current official Lambda extension documentation proves that Lambda-backed `PRE_CREATE_HOSTED_CONFIGURATION_VERSION` and `PRE_START_DEPLOYMENT` payloads include base64 configuration content and that the Lambda response may replace it.

Security conclusion: a caller with both extension creation actions, a passable invocation role, and a compatible Lambda target can plant a delayed, service-level interception/transformation hook without AppConfig authorization on the chosen application/profile/environment. This is expected based on the published lack of resource-level support, not a zero-day.

### Agent endpoint

- Agent consumers retrieve configuration over ordinary HTTP on port 2772 with no SigV4 request from the consumer.
- EC2/on-premises default binding is localhost; ECS/EKS documented default is all interfaces.
- This is a workload post-exploitation/SSRF/sibling-container proxy surface, bounded by reachability, identifiers, and the agent role's AppConfig Data permissions.
- No compute was launched solely to repeat behavior already defined by the current official integration contract.

## Candidate matrix

| Candidate | Result | Book decision / reason |
| --- | --- | --- |
| Read old hosted versions with `GetHostedConfigurationVersion` | Documented behavior; useful | Keep; old versions can retain secrets and the API bypasses the deployment-token workflow |
| Read deployed bytes with the two AppConfig Data calls | Documented and exercised as part of the lab | Keep; data-event-only logging is an important stealth boundary |
| Query AppConfig Agent without caller AWS credentials | Strong documented workload-side primitive | Keep, explicitly not described as public unauthenticated cloud access |
| Create external profile + pass retrieval role + deploy/read | Live-confirmed end to end | Add as privilege escalation into source-readable data |
| Create hosted version only | Existing technique is useful but delayed | Keep with bounded consumer-dependent impact |
| `StartDeployment` only | Existing technique is useful when a dangerous version exists | Keep; no claim that it creates content or requires `PassRole` |
| Custom `PRE_*` extension + association | Target authorization boundary live-confirmed; content payload documented | Add as AppConfig service-level persistence/config supply-chain attack |
| SNS at a `PRE_*` point | Rejected live | Do not suggest; use Lambda for content-bearing `PRE_*` actions |
| SNS/SQS/EventBridge `ON_*` hook | Compatible notification primitive but lacks configuration contents | Mention only as an extension compatibility boundary, not a standalone high-impact attack |
| `UpdateConfigurationProfile` to redirect source | API cannot update `LocationUri`; it can change the retrieval role/validators/key only | Reject as a generic source-redirection claim |
| Delete application/profile/environment/version | Expected destructive DoS | Omit as low-quality/non-distinct |
| Stop deployment | Narrow availability/rollback behavior | Omit unless a concrete high-impact consumer case is demonstrated |
| Modify environment alarm monitors | May weaken automatic rollback and requires suitable monitor role/config | Track for future consumer-specific validation; not strong enough for this book update |
| Cross-account AppConfig Data retrieval | Officially unsupported | Reject as a normal cross-account technique; no bypass found |
| Public/anonymous AppConfig service API | No resource policy or unsigned service API found | No unauthenticated cloud technique |
| New AppConfig experiment APIs | Authorization surface observed in current Service Authorization Reference | Future audit item; no concrete privilege/persistence impact established in this pass |

## Telemetry conclusions

- All AppConfig control-plane calls are management events logged by default.
- `StartConfigurationSession` and `GetLatestConfiguration` are opt-in data events; this materially raises the stealth of direct and agent-mediated reads.
- `iam:PassRole` produces no standalone event. Detect it through the retrieval/action role embedded in AppConfig control-plane events and correlate with role sessions/source reads.
- Lambda `Invoke` is a data event and is not logged by default. Planting a custom extension is more observable than its later execution.

Post-test CloudTrail Event History inspection confirmed matching low-privilege-role events as follows:

| Event | Category / readOnly | Request fields present in the successful event |
| --- | --- | --- |
| `CreateConfigurationProfile` | Management / `false` | `applicationId`, `locationUri`, `name`, `retrievalRoleArn`, `type` |
| `StartDeployment` | Management / `false` | `applicationId`, `configurationProfileId`, `configurationVersion`, `deploymentStrategyId`, `environmentId` |
| `CreateExtension` | Management / `false` | `actions`, `description`, `name` |
| `CreateExtensionAssociation` | Management / `false` | `extensionIdentifier`, `extensionVersionNumber`, `resourceIdentifier` |

The same Event History lookup returned zero matching `StartConfigurationSession` and `GetLatestConfiguration` records, consistent with their documented data-event category and the account not collecting those data events into Event History.

## Cleanup record

The first cleanup attempt demonstrated that `DeleteApplication` does not cascade and that an active `BAKING` deployment blocks deletion. Cleanup was therefore completed explicitly in dependency order: stop active deployment, delete configuration profiles, delete environments, delete applications, delete extension associations/extensions, delete SNS topics, force-delete the disposable secret, remove inline policies, and delete IAM roles.

Final independent inventory returned:

- `[]` applications with the `ht-appconfig-` prefix;
- `[]` extensions with the `ht-audit-ext-` prefix;
- `[]` IAM roles with the `ht-appconfig-` prefix;
- `[]` SNS topics with the test prefix; and
- `[]` active Secrets Manager secrets with the test prefix.

No test infrastructure remains.

## Vulnerability assessment

No unexpected AWS security malfunction was found. The delegated retrieval and extension-association results are security-significant expected feature/authorization behavior and belong in HackTricks Cloud, not in the private AWS vulnerability-report folder.
