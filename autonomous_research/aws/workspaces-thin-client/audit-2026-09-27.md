# Amazon WorkSpaces Thin Client audit — 2026-09-27

## Scope

Reviewed WorkSpaces Thin Client enumeration, environment/provider mutation, device and user metadata, software-set validation/deployment, resource sharing, unsigned access, exact IAM resource scope and CloudTrail telemetry. Cross-service dependencies on WorkSpaces Personal, WorkSpaces Applications and WorkSpaces Secure Browser were also tested far enough to establish the compatibility boundary without leaving billable infrastructure.

## Service lifecycle and authorization model

- AWS stopped accepting new Thin Client customers on April 20, 2026 and will end support on March 31, 2027.
- Current documented control-plane Regions are `us-east-1`, `us-west-2`, `ap-south-1`, `eu-west-1`, `ca-central-1`, `eu-central-1`, and `eu-west-2`.
- Resource types are `environment`, `device`, and `softwareset`, with Regional/account-scoped ARNs.
- No resource-policy, ACL, RAM-sharing, provider-role attachment, stored IAM role, or cross-account association API exists. Direct cross-account use therefore requires credentials in the owning account.
- `GetDeviceDetails` and `ListDeviceSessions` are permission-only actions used by service/device flows; they are not public CLI control-plane operations.

## Inventory and authentication boundary

The authorized account SCP allows the Thin Client API in `us-east-1` and `eu-west-1`; it explicitly denies the other five documented Regions. Initial and final inventories in both allowed Regions were:

| Region | Environments | Devices | AWS-published software sets |
| --- | ---: | ---: | ---: |
| `us-east-1` | 0 | 0 | 3 |
| `eu-west-1` | 0 | 0 | 3 |

An unsigned `ListEnvironments` call in `us-east-1` returned `MissingAuthenticationTokenException`. No unauthenticated API or activation-code-only enumeration path was found. The activation code enrolls a physical device into an environment; it is not a general control-plane credential or a desktop-session credential.

## Enumeration findings

- `GetEnvironment` exposes activation code, desktop provider ARN, AppStream IdP endpoint, desired/pending software set, maintenance settings, device-creation tags and timestamps.
- `GetDevice` exposes serial/model, environment, enrollment state, current/desired/pending software sets, last connection/posture times and `lastUserId`.
- `GetSoftwareSet` exposes component names/versions, release/support times and account-local validation status.
- These are useful endpoint, identity and patch-posture reconnaissance but do not return desktop content, passwords, SAML assertions or bearer streaming URLs.
- The actual CloudTrail event source is `thinclient.amazonaws.com`; the previous combined WorkSpaces page incorrectly used `workspaces-thin-client.amazonaws.com`.
- The CLI paginator can surprise scripts that combine `--output text` with `--query 'softwareSets[0].id'`: it emitted one first element per page. JSON aggregation avoids treating multiple IDs as one CLI argument.

## Exact IAM tests

Disposable IAM users were created only for the live permission checks, given one inline policy, used after IAM propagation, and deleted with their access keys and policies.

### List actions accept resource-pattern scope

All of the following succeeded without `Resource:"*"`:

| Action | Allowed resource |
| --- | --- |
| `thinclient:ListEnvironments` | `arn:aws:thinclient:us-east-1:228478051196:environment/*` |
| `thinclient:ListDevices` | `arn:aws:thinclient:us-east-1:228478051196:device/*` |
| `thinclient:ListSoftwareSets` | `arn:aws:thinclient:us-east-1:228478051196:softwareset/*` |

This is narrower than the current Service Authorization Reference presentation, which does not attach resource types to the three actions. It is a useful least-privilege behavior, not a security vulnerability.

### Exact-resource writes

- `thinclient:UpdateSoftwareSet` on only `arn:aws:thinclient:us-east-1:228478051196:softwareset/67` successfully changed `NOT_VALIDATED` to `VALIDATED` with HTTP 204. The administrator immediately restored `NOT_VALIDATED`, and a final `GetSoftwareSet` confirmed the restoration.
- `thinclient:UpdateEnvironment` on only `arn:aws:thinclient:us-east-1:228478051196:environment/000000000` passed IAM evaluation. Because no environment existed, the service retried and returned `InternalServerException` rather than a not-found response. This establishes the exact ARN boundary but not an end-to-end device redirection.
- The authorization reference and API shape also scope `UpdateDevice` to one exact device ARN. No physical device existed, so no device update was sent.

## Provider-fixture tests

An actual environment requires a compatible pre-existing desktop provider; a syntactically valid ARN is not enough:

1. A nonexistent same-account WorkSpaces Applications stack was rejected with `ValidationException` stating that the stack did not exist.
2. Two disposable AppStream stacks were created. An unassociated stack was rejected as incompatible. An attempt to construct an associated zero-capacity fleet stopped before fleet creation because this account's pre-existing `AmazonAppStreamServiceAccess` role was invalid. The unrelated role was not modified.
3. A disposable WorkSpaces Secure Browser portal was rejected while `Incomplete`.
4. A second disposable portal with a compliant user-settings resource (copy, paste, upload, download and print disabled) was still rejected while `Incomplete`.

All temporary stacks, portals and user-settings objects were deleted. The first portal creation automatically created `AWSServiceRoleForAmazonWorkSpacesWeb`; its CloudTrail timestamp tied it to this audit, and it was also deleted after the portal fixtures were gone. No fleet instance, Thin Client environment or device was created. Creating a complete provider would have required unrelated directory/network/IdP infrastructure, so the live account boundary plus the documented API semantics were used for the retained environment-redirection technique.

## Retained techniques

### Environment/provider and AppStream IdP redirection

`UpdateEnvironment` can replace `desktopArn` and `desktopEndpoint`. AWS documents `desktopEndpoint` as the WorkSpaces Applications IdP login/logout URL used by Thin Client users. With a compatible destination, this is a durable user-redirection and credential-phishing primitive. It does not itself bypass the provider's authentication or grant AWS IAM authority.

### Software-set validation and deployment control

`UpdateSoftwareSet` can approve or unapprove an AWS-published release. `UpdateEnvironment` can select `USE_DESIRED`, a release ID and immediate/maintenance-window deployment for all registered devices; `UpdateDevice` can do the same for one device. This can temporarily pin a still-supported older release, remove newer security fixes or interrupt a session. It cannot upload arbitrary firmware, and the service forcibly updates expired sets.

These two techniques are documented in `aws-workspaces-thin-client-post-exploitation`. No separate privilege-escalation page was added because neither primitive automatically grants additional AWS IAM permissions. No persistence page was added because a durable device redirection does not preserve the attacker's AWS principal; its security impact is downstream user authentication and endpoint posture.

## Rejected or bounded ideas

| Idea | Result |
| --- | --- |
| Read APIs expose desktop files or session credentials | Rejected; they expose inventory, identity and posture metadata only. |
| Reassign a device to another environment with `UpdateDevice` | Rejected; the public update input has no environment field. |
| Upload or modify Thin Client firmware | Rejected; only AWS-published software-set IDs and validation state are writable. |
| Persist by attaching an IAM role or resource policy | Rejected; environments/devices expose neither mechanism. |
| Direct cross-account resource share | Rejected; there is no customer sharing/resource-policy API. |
| Activation code is an unauthenticated desktop credential | Rejected; it is part of physical-device enrollment and provider authentication is still required. |
| Deregister/delete as a book technique | Excluded as availability-only administration. |
| Tag/name changes as a technique | Excluded as low-value metadata tampering. |

## Telemetry

- `ListEnvironments`, `ListDevices` and `ListSoftwareSets` appeared as CloudTrail management events with `readOnly:true`.
- Successful `UpdateSoftwareSet` appeared after normal Event History propagation under `thinclient.amazonaws.com`, `managementEvent:true`, `readOnly:false`; the request contained the set ID and validation state. The HTTP 204 response has no body and CloudTrail `responseElements` is `null`.
- `UpdateEnvironment` was a write management event. The test request's `desktopEndpoint` was redacted to `***`, so detection should reconcile `GetEnvironment` state rather than rely on the request URL being visible in CloudTrail.
- Device-side `RegisterDevice` and `UpdateDeviceDetails` are separately documented CloudTrail data events and are not present in Event History unless the relevant data-event selector is enabled.

No unexpected vulnerability remained after verification, so this audit created no private bug-bounty report.

## Cleanup proof

Final checks confirmed:

- `0` Thin Client environments and `0` devices in both authorized Regions;
- all three `us-east-1` software sets restored to `NOT_VALIDATED`, matching the initial state;
- `0` IAM users with the `ht-tc-` test prefix;
- `0` AppStream fleets and `0` AppStream stacks with the `ht-tc-` prefix;
- `0` WorkSpaces Secure Browser portals and `0` user-settings resources;
- the audit-created `AWSServiceRoleForAmazonWorkSpacesWeb` service-linked role absent after successful deletion;
- no directory, VPC, subnet, security group, fleet instance, KMS key or physical-device resource was created.
