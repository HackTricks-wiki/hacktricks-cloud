# AWS Marketplace Metering audit — 2026-10-01

## Result

Added the missing Marketplace Metering plane to the existing Marketplace service and post-exploitation pages. Two expected-functionality attacks met the publication threshold:

1. a compromised seller metering principal can submit inflated SaaS quantities and, during a legacy-to-license migration, use AWS's documented dual-path condition to cause duplicate billing; and
2. a compromised supported buyer workload can win the first non-AgentCore `MeterUsage` slot for a dimension/hour with an inflated quantity that the legitimate process cannot later change.

Both are financial-integrity attacks with strong product, customer/license or platform prerequisites. Neither grants IAM privilege or lets an arbitrary AWS principal bill an arbitrary account. No valid usage record was submitted in the training account, no subscription or agreement was created, and no AWS defect was claimed.

## Surface and authorization model

- CLI client: `meteringmarketplace`.
- IAM prefix: `aws-marketplace`.
- CloudTrail source: `metering-marketplace.amazonaws.com`.
- All four actions are `Write`, require `Resource: "*"`, and have no service-specific condition keys:
  - `aws-marketplace:BatchMeterUsage`
  - `aws-marketplace:MeterUsage`
  - `aws-marketplace:RegisterUsage`
  - `aws-marketplace:ResolveCustomer`
- `BatchMeterUsage` is a seller-account SaaS API. It accepts up to 25 records and a quantity up to 2,147,483,647 per record. Records are accepted for less than 24 hours after the event, subject to the documented first-of-month grace period.
- `ResolveCustomer` is seller-account-only and redeems the buyer browser's short-lived, single-use registration token for account, license and product identifiers.
- `MeterUsage` is called from a buyer EC2 instance, ECS task, EKS pod or AgentCore runtime using the supported workload credential mechanism. The service rejects generic long-term keys and unsupported credential/platform combinations.
- `RegisterUsage` begins paid hourly container metering and returns a signed JWT, but only from a supported subscribed ECS/EKS/Fargate workload.

## Live safe validation

Disposable IAM users were given one action at a time on `*`. All calls used deliberately invalid identifiers, and `MeterUsage` used `DryRun=true` with quantity zero:

| Exact permission | Safe call result | Boundary established |
| --- | --- | --- |
| `BatchMeterUsage` | Legacy request: `InvalidProductCodeException`; current no-product-code request: `InvalidLicenseException` | IAM authorization passed both integration paths and product/license validation ran; no usage accepted |
| `ResolveCustomer` | `InvalidTokenException` for `ht-invalid-registration-token` | IAM authorization passed and token validation ran |
| `MeterUsage` | Combined unauthorized/unsupported-platform response | The API intentionally does not distinguish IAM denial from an unsupported caller platform; no metering occurred |
| `RegisterUsage` | `PlatformNotSupportedException` | Exact action passed IAM and the ECS/EKS platform gate ran |

An early policy-swap test briefly returned IAM denial for `ResolveCustomer`, consistent with inline-policy replacement propagation. A fresh user with only that action reached `InvalidTokenException` and is the result relied upon above.

A second fresh `BatchMeterUsage` user exercised the current Concurrent Agreements shape with a synthetic customer account and fake `LicenseArn`, without a request-level `ProductCode`. It reached `InvalidLicenseException: Provide valid, active LicenseArns for a single product and retry`, confirming both that the exact action authorizes the new request shape and that AWS rejects an inactive/nonexistent license before recording usage.

Marketplace inventory found no acceptor or proposer purchase agreements and no seller-owned container product. That prevented an end-to-end valid usage test without accepting external commercial terms or creating a billable relationship. The public attack semantics are instead bounded to the explicit API behavior and current AWS documentation.

## Published technique 1 — seller SaaS usage fraud

For Concurrent Agreements integrations introduced for new SaaS products on June 1, 2026, each record uses `CustomerAWSAccountId` and `LicenseArn`; the request omits `ProductCode`. Existing integrations use the legacy `CustomerIdentifier` plus request-level `ProductCode` path. AWS explicitly warns that sending through both paths for the same customer and hour causes duplicate billing during migration.

The service validates seller/product/customer/license/dimension/time relationships but necessarily trusts the seller's reported quantity. A principal with only `BatchMeterUsage` and harvested valid identifiers can therefore inflate a charge. `ResolveCustomer`, seller databases, entitlement output, configuration and metering logs/CloudTrail are possible identifier sources. Replaying an identical record through one path is idempotent and was not misrepresented as double charging.

Impact is fraudulent usage, customer overbilling and corrupted reconciliation, subject to later validation, dispute or refund. No buyer-account IAM permission is required, but the caller must be in the publishing seller account and the buyer must have the applicable active product/license.

## Published technique 2 — buyer workload first-write poisoning

For non-AgentCore products, `MeterUsage` rounds the timestamp down to the hour and permits only one quantity per dimension and workload (EC2 instance, ECS task or EKS pod). The quantity cannot be modified after it is recorded. A compromised runtime can submit an inflated record before the legitimate process; its later different value receives `DuplicateRequestException`.

AgentCore Runtime permits multiple records per hour when client tokens differ and aggregates duplicate timestamps. It therefore has an extra-record injection path, not the non-AgentCore first-write lockout.

The action remains platform-bound. AWS documents EC2 instance-role, ECS task-role, EKS IRSA and AgentCore runtime execution-role credentials. EKS Pod Identity, node roles and long-term access keys are not supported substitutes. The endpoint Region must match the workload. These restrictions were kept prominent so the page does not imply that a generic wildcard-IAM user can submit a buyer's usage.

## Telemetry

AWS documents all three metering operations as CloudTrail events:

- `BatchMeterUsage` is recorded in the seller account and retains product where applicable plus customer/account, dimension, timestamp and quantity; a success response contains status and metering-record ID.
- `MeterUsage` is recorded in the buyer account and retains workload identity, product, dimension, timestamp, quantity and `DryRun`; a success response contains the metering-record ID.
- `RegisterUsage` is recorded in the buyer account with product and public-key version. The current documentation example places the returned JWT signature in `responseElements`.

After the normal indexing delay, live Event History confirmed that all four operations were default `Management` writes with `readOnly:false` and `eventSource: metering-marketplace.amazonaws.com` in `us-east-1`:

- the rejected `BatchMeterUsage` event retained the complete fake record (timestamp, customer identifier, dimension and zero quantity), product code, `InvalidProductCodeException` and message;
- the authorized rejected `ResolveCustomer` event retained the submitted invalid registration token, `InvalidTokenException` and message; the earlier IAM-denied call had null request parameters;
- the `MeterUsage` event retained product, timestamp, dimension, zero quantity and `dryRun:true`, with an intentionally ambiguous `AccessDenied` / `An unknown error occurred` trail result; and
- the rejected `RegisterUsage` event retained product, public-key version and nonce plus `PlatformNotSupportedException` and message.

Successful response shapes were not exercised. The public success-field claims remain limited to AWS's explicit current examples.

## Negative and deferred candidates

| Candidate | Result | Disposition |
| --- | --- | --- |
| Bill arbitrary accounts with `BatchMeterUsage` | Customer/license must exist, match the seller/product, and be active | Secure service gate; excluded |
| Duplicate identical records | API is idempotent per documented key | Excluded; only the explicitly documented legacy-plus-license split remains |
| Call `MeterUsage` with generic IAM credentials | Platform/credential binding is enforced and deliberately masks the reason | Excluded |
| Use `RegisterUsage` off-platform | Live `PlatformNotSupportedException` with the exact action | Excluded |
| Extract a valid paid-container JWT from CloudTrail and replay it outside its task/pod | AWS's example logs the signature. The signed payload contains product, key version, nonce and issue time; AWS's sample verifier checks those request fields but no task/pod identity or expiry claim is documented. The nonce is optional and the JWT itself reveals it. There was no subscribed container fixture, and actual product enforcement/replay behavior is vendor-specific | Retained privately as a higher-priority test idea; no AWS report or public attack claim |
| Keep billing after unsubscribe using an existing task/pod | AWS explicitly documents that an already registered task/pod continues billing until it stops | Expected lifecycle behavior, low independent offensive value |
| Registration-token theft alone | Requires capture before the seller, exact seller-account action and a valid token; yields identifiers and burns the one-time token | Included only as a prerequisite/chain, not promoted as a standalone headline technique |

## Cleanup

Every disposable `ht-marketplace-metering-*`, `ht-marketplace-license-*` and `ht-marketplace-resolve-*` IAM user, inline policy and access key was deleted. Independent final IAM inventory returned an empty list for the `ht-marketplace-*` prefix. The account still had no buyer/seller agreements and no seller-owned container product. No usage record, registration, subscription, agreement, product, ECS/EKS/EC2 workload, role, bucket, log trail or other infrastructure was created.
