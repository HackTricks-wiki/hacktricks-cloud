# AWS IoT Wireless security audit — 2026-09-27

## Scope and safety

- Account `228478051196`, Region `us-east-1`.
- Administrator session assumed `ChackBotAdministratorRole` from `hacktricks-training`.
- Fixtures used synthetic onboarding values and no physical device, gateway, RF transmission, paid positioning request, FUOTA image, multicast session, or external recipient.
- Every run installed an exit trap that deleted wireless devices, destinations, device/service profiles, IAM policies and roles.

## Prior coverage

The existing service page documented `GetWirelessDevice` as sensitive for Sidewalk private keys. This audit verified that LoRaWAN OTAA keys are also returned, expanded inventory/CloudTrail guidance, and added useful post-exploitation and persistence pages.

## Fixtures

Successful runs used:

```text
LoRaWAN 1.0.x synthetic device
two MQTT-topic destinations (original and redirect)
one empty/default LoRaWAN device profile
one service profile
one destination delivery role trusted by iotwireless.amazonaws.com
one exact-resource caller role
```

No IoT rule was created. The delivery role allowed only `iot:Publish` to synthetic `ht/iotwireless/audit/*` topics.

## Verified results

### LoRaWAN onboarding keys are returned by `GetWirelessDevice`

The device was created with synthetic OTAA 1.0.x values. A read returned the `OtaaV1_0_x` object. Non-secret equality checks proved:

```text
AppKeyMatches=true
GenAppKeyMatches=true
AppEuiMatches=true
```

The values were not `***` or otherwise transformed. The action was then exercised through a caller policy scoped to the exact `WirelessDevice/<uuid>` ARN.

This confirms the read is credential access for LoRaWAN as well as Sidewalk. It is expected functionality, not a service defect.

### Destination reads expose the routing trust

`GetDestination` returned:

- `ExpressionType=MqttTopic`;
- the exact topic expression; and
- the destination service role ARN.

This provides the routing and trust context required to assess telemetry exfiltration or rule abuse.

### Device rebinding evaluates both resources

The first least-privilege caller had `UpdateWirelessDevice` only on the exact device ARN. A partial update containing a replacement destination failed with an authorization error naming:

```text
arn:aws:iotwireless:us-east-1:228478051196:Destination/ht-iotwireless-audit-20260927-redirect
```

The next caller policy granted the same action on the exact device and exact replacement destination ARNs. The update succeeded, and a follow-up read returned the replacement destination and supplied description.

No PassRole was needed during the device rebind because it referenced an already-created destination. Destination creation with `RoleArn` was performed by the administrator and follows the documented PassRole dependency.

### Exact-device downlink injection

The caller held `SendDataToWirelessDevice` only on the exact device ARN. A one-byte synthetic LoRaWAN FPort 1 payload with transmit mode 0 was accepted and returned a message ID.

No gateway existed and no RF delivery occurred. The result proves queue/API authorization, not behavior of a physical target.

### Profile-version validation

The first device-creation attempt combined the default LoRaWAN 1.0.3 profile with an OTAA 1.1 structure. AWS rejected it with:

```text
Validation error: the input profile version is not match macVersion defines in deviceProfile: 1.0.3
```

The trap removed both destinations, both profiles and both roles. A separate inventory returned empty before the corrected OTAA 1.0.x run began.

This was secure input validation, not a defect.

## CloudTrail observations

Observed IoT Wireless management events included create/get/update/delete operations.

| Event | Request/response behavior |
| --- | --- |
| `GetWirelessDevice` | Identifier/type visible; `responseElements: null`, so returned keys were absent |
| Successful `UpdateWirelessDevice` | Device ID, replacement destination and description visible; response null |
| Denied dependent-resource update | `AccessDenied` named destination ARN; request parameters null |
| `CreateWirelessDevice` | DevEUI and OTAA key fields redacted as `HIDDEN_DUE_TO_SECURITY_REASONS` |
| `CreateDestination` | Expression and role ARN redacted as `HIDDEN_DUE_TO_SECURITY_REASONS` |
| `SendDataToWirelessDevice` | Did not appear in Event History during the observation window |

Detection should alert on sensitive reads and all routing/task changes, maintain configuration snapshots outside CloudTrail, and use IoT Wireless/gateway/device/application telemetry for packet/downlink activity.

## Rejected or lower-value ideas

- **PassRole as generic escalation:** a destination role is used for the configured IoT rule/topic delivery path. No evidence suggests credentials or arbitrary AWS API access are returned to the caller. Document least privilege, not generic role takeover.
- **Unsigned API enumeration:** no public control-plane or data API was identified; resource IDs alone are not credentials.
- **Downlink equals guaranteed device compromise:** false. Firmware/application validation, FPort, radio availability, join/session state, replay protection and device behavior determine impact.
- **FUOTA/gateway task equals generic RCE:** compatible target/firmware configuration is required. Retain as a high-impact fleet-management technique, not an unconditional shell.
- **Position APIs:** potentially sensitive but no physical-device fixture existed, so no location request was made.
- **Network Analyzer:** may expose packet metadata, but no trace session against real devices was started.

## Cleanup proof

After each failed and successful run, final inventory showed:

```text
matching wireless devices: []
matching destinations: []
matching device profiles: []
matching service profiles: []
ht-iotwireless-audit-* IAM roles: absent
ht-iotwireless-caller-* IAM role: absent
```

No gateways, task definitions/tasks, FUOTA tasks, multicast groups, network-analyzer configurations, position configurations, IoT rules, topics, certificates, Things, S3 objects, Lambda functions, or paid resources were created.

Only immutable CloudTrail history remains. No unexpected authorization bypass, cross-account leak, or AWS zero-day was confirmed; no private report was created.
