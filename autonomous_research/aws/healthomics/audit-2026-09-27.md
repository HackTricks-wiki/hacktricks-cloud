# AWS HealthOmics research audit - 2026-09-27

## Scope and starting state

- Region/account: `us-east-1`, authorized training account `228478051196`.
- Service prefix/principal: `omics` / `omics.amazonaws.com`.
- Objective: sequence/reference data theft and poisoning, workflow/run PassRole paths, S3 access policies, analytics shares, bearer URLs, IAM boundaries and CloudTrail coverage.
- Initial inventories: no sequence/reference/variant/annotation stores, workflows, runs, run groups, run caches or shares.
- Cost controls: one 24-byte FASTQ, one 44-byte FASTA, one metadata-only WDL workflow; no workflow run, compute task, analytics data or large storage.

## Verified results

### Private workflow source export

- Created a harmless private WDL workflow and waited for `ACTIVE`.
- A minimum-permission role with only `omics:GetWorkflow` on the exact workflow ARN could call `GetWorkflow --export DEFINITION` while `ListWorkflows` remained denied.
- The response contained an S3 presigned URL with `X-Amz-Expires=600`.
- The URL downloaded the exact definition ZIP with no AWS credentials; its SHA-256 matched the workflow digest.
- CloudTrail recorded `GetWorkflow`, request ID/type/export and a `null` response. The presigned URL and retrieved source were omitted.
- `CreateWorkflow` with an inline ZIP logged the complete `definitionZip` as base64 in CloudTrail. This is important secondary exposure to principals that can read CloudTrail events/logs.

### Direct read-set upload IAM boundary

- Admin direct multipart create/upload/abort accepted the tiny gzip FASTQ and left no read set.
- Parent-only permission was denied and named `sequenceStore/ID/readSet/*`.
- Child-wildcard-only permission was denied and named the parent sequence-store ARN.
- Granting the multipart actions on **both** parent and child wildcard succeeded for create, upload and abort without list/read permissions.
- CloudTrail logged subject ID, sample ID, name, store/upload IDs, payload length and checksum, but not payload bytes.
- This supports a blind data-poisoning technique and a least-privilege warning; it is expected IAM behavior, not a service defect.

### Sequence-store S3 access policy

- `GetSequenceStore` returned an S3 alias URI and service-owned access-point ARN.
- The default policy granted the account root S3 object/list actions under exact store prefixes and required `omics:readSetStatus=ACTIVE` for object reads.
- A minimum-permission role with `Put/Get/DeleteS3AccessPolicy` on the exact parent sequence-store ARN successfully replaced the policy with a grant to that role. The legitimate default policy was immediately restored.
- The caller did not need S3/read-set permissions to mutate the resource policy. Actual reads still require identity-side S3 permission and, where applicable, KMS decrypt permission.
- CloudTrail recorded the complete policy string, including principal, actions, resource and conditions.

### Workflow/run and job privilege paths

- `StartRun` was reviewed against the current CLI/API/IAM documentation but not invoked because it creates billable compute/storage.
- Authoritative behavior: it requires `iam:PassRole`; task access to S3/ECR/other AWS services is governed by the passed service role. `VPC` networking can reach private/on-premises/internet destinations according to the chosen configuration, while default `RESTRICTED` networking is limited to same-Region S3/ECR.
- Read-set/reference import, read-set export and analytics import APIs likewise accept a caller-selected service role and require PassRole. They are constrained data-movement deputies rather than generic role-credential theft.
- A tiny reference import was submitted with a deliberately narrow role. It completed with failures because the role lacked additional permissions; no reference was created. The failed job was allowed to reach a terminal state before store deletion.

### Run caches and analytics

- Created an empty run cache backed by a private disposable S3 bucket. HealthOmics created a zero-byte cache-prefix object; cache deletion did not delete that S3 object, so it had to be removed explicitly before bucket deletion.
- `UpdateRunCache` cannot change the S3 location, only metadata/default cache behavior. AWS documents that reuse requires identical task definition, inputs and container. A generic cache-poisoning claim was rejected.
- `CreateVariantStore` and `CreateAnnotationStore` were rejected in this account. Current CLI/AWS documentation states both features are closed to new customers. Legacy analytics import/share paths were documented authoritatively but not claimed as live-tested here.
- Current `CreateShare` documentation also supports private workflows. Shared-workflow subscribers can run but cannot export the workflow definition; this was recorded as a bounded cross-account persistence mechanism, not source-code theft.

## Rejected or deferred hypotheses

- **Unsigned known-ID APIs:** service APIs require SigV4; exported workflow/S3 URLs are bearer URLs only after an authorized principal creates them.
- **Public sequence-store access from policy alone:** rejected. HealthOmics requires dual resource-policy and identity-policy authorization; the policy validator limits elements, actions, prefixes and condition keys.
- **Generic PassRole credential theft:** rejected. HealthOmics exercises the role through workflows/jobs and does not return credentials.
- **Arbitrary S3 writes through export/import:** rejected. Writes are workflow/job outputs using service-defined behavior, not arbitrary caller-controlled object bytes.
- **Run-cache poisoning by `UpdateRunCache`:** rejected because location is immutable and cache-hit identity binds definition, inputs and container.
- **Mutable base workflow code through `UpdateWorkflow`:** rejected. That action changes metadata/storage/README; new executable definitions use explicit workflow versions.
- **New analytics-store exploitation:** unavailable to this new-customer account. Existing-customer store/share paths remain documented.
- **Paid workflow RCE validation:** deferred intentionally; the documented role/network execution model is authoritative and a live run would add cost without changing the permission conclusion.
- **Zero-day candidates:** no unexpected security defect was confirmed; no private vulnerability report was created.
