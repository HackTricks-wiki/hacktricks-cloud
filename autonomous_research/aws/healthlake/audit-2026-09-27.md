## Ideas and results

| Idea | Result | Evidence / conclusion |
| --- | --- | --- |
| Read a known resource with only `ReadResource` | Worked | Exact datastore ARN; returned Patient. |
| Search with only `ReadResource` | Denied | Required `SearchWithGet`. |
| GET search with only `SearchWithGet` | Worked | Enumerated both synthetic Patient resources. |
| POST search with GET permission | Denied | Required the independent `SearchWithPost`; exact permission then worked. |
| IAM-scope access to one Patient/type | Not possible | Service authorization supports only the datastore ARN, not FHIR type/ID resources. |
| Blind overwrite with only `UpdateResource` | Worked | Known Patient moved from version 1 to 2 without read/search. |
| Upsert a new fixed ID with only `UpdateResource` | Worked | HTTP 201 for a previously absent Patient ID. Expected FHIR update semantics, important IAM consequence. |
| Batch-create with only `ProcessBundle` | Worked | A one-entry batch created a Patient without `CreateResource`. |
| Read current/old history | Authorization split verified; content inconclusive | `ReadResource` was denied on history/vread; exact `GetHistoryByResourceId` and `VersionReadResource` passed authorization, but this new datastore returned an empty history/404 during the short test. AWS documentation states history is enabled by default on new stores and retains creates/updates/deletes. Do not treat the short consistency result as a defect. |
| Bulk native export without FHIR read/search | Worked | `StartFHIRExportJob` plus exact `iam:PassRole` exported Patient NDJSON and a manifest to the selected S3 prefix. No `ReadResource`/`Search*` permission in the session. Without PassRole, submission was denied. |
| Import as an S3 read proxy | Worked | A session with only exact `StartFHIRImportJob` and conditioned exact `PassRole` submitted a 208-byte encrypted NDJSON input despite having no S3/KMS permission. Import-then-search is an expected cross-service read proxy if the service role is over-broad. |
| FHIR Subscription persistence | Partially live, rest authoritative | `CreateResource` alone created a valid `SubscriptionTopic` for Observation changes. AWS documents active EventBridge/REST-hook Subscriptions and `full-resource` payloads. An external callback was not activated to avoid unnecessary external effects. |
| Replace SMART authorizer | Authoritative | `UpdateFHIRDatastore` can replace the identity-provider metadata, authorization strategy and token-validation Lambda. Current AWS CLI build lacked this recently added subcommand, so no SMART fixture was created. |
| Unauthenticated clinical read/search | Denied | Known Patient read and search returned HTTP 401 without authorization. |
| Unauthenticated `/metadata` | Worked, low impact | A valid datastore ID returned a 609 KB CapabilityStatement without SigV4, while a random 128-bit ID returned not-found. This reveals supported resource types/operations and is inconsistent with the separately documented `GetCapabilities` action, but the datastore ID is high entropy and no PHI/configured secret was exposed. Considered too weak for the public attack book or an AWS security report. |
| Cross-account datastore resource policy | Not applicable | HealthLake documents resource-based policies as unsupported. Use role assumption or SMART flows. |
| CloudTrail coverage | Strong management-event coverage | `CreateResource`, `ReadResource`, both searches, history/vread, update, bundle, import/export and denied attempts appeared in Event History. Search values were `HIDDEN_DUE_TO_SECURITY_REASONS`; resource bodies were absent. |
| CloudTrail request header handling | Unexpected but no standalone exploit | FHIR events included `x-amz-security-token` in captured request headers. The signing secret/Authorization header was absent, so the token and logged access-key ID are insufficient to forge SigV4 requests. Recorded for regression research, not reported as a vulnerability. |

## Strong expected attacks added to the book

1. Datastore-wide PHI theft through independent read/search/history actions.
2. Full native or FHIR REST bulk export, emphasizing that export does not require FHIR read/search permission and that all variants need separate restriction.
3. S3 import-role proxy and mass clinical-data poisoning through import-then-search.
4. Blind update/upsert and bundle-based create/update/delete using their distinct permissions.
5. Persistent future-data exfiltration with `SubscriptionTopic` + full-resource FHIR `Subscription`.
6. SMART authorization takeover/persistence by replacing the token-validation Lambda and metadata.
