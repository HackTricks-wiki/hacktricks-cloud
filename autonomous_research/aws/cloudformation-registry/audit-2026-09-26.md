## Results

### Execution role and `iam:PassRole`

| Probe | Result |
| --- | --- |
| Activate AWS Guard Hook with only `cloudformation:ActivateType` and an execution role | Denied specifically for missing `iam:PassRole` on the role |
| Register a private resource type with only `cloudformation:RegisterType` and an execution role | Denied specifically for missing `iam:PassRole`; no registration token/type was created |
| Activate with the admin role and a role trusted by `resources.cloudformation.amazonaws.com` | Succeeded |

The CLI/API documentation says CloudFormation assumes an extension execution role and passes its credentials to the handler. The trust principal is deliberately different from the normal CloudFormation stack service principal. This confirms the expected private-handler privilege-escalation chain (`RegisterType` + `iam:PassRole` + a way to invoke the handler), but not an IAM bypass.

### Stored configuration disclosure

The activated Guard Hook was given a disabled, valid configuration with an S3 rule URI marker. A role with only:

```json
{"Effect":"Allow","Action":"cloudformation:BatchDescribeTypeConfigurations","Resource":"*"}
```

received the complete literal configuration, configuration ARN, alias, timestamp, and type ARN. `DescribeType` and `SetTypeConfiguration` were independently denied.

Resource-scoping probes with the exact type ARN and exact type-configuration ARN were both denied. The action required `Resource: "*"` in this test. This makes guessed/discovered type names sufficient for an account/Region-wide configuration-read oracle.

Sensitive literal values would be exposed. AWS's dynamic-reference recommendation is effective because it keeps the resolved value out of stored configuration.

### Hook defense-control mutation

A role with only `cloudformation:SetTypeConfiguration` on the exact activated type ARN changed the Guard Hook's S3 rules URI from the original marker to an attacker marker and kept `HookInvocationStatus: DISABLED`. It had no read, S3, or `iam:PassRole` permission. Admin verification showed the mutation.

Security uses include disabling the Hook, changing `TargetStacks`, target filters, stack-role filters, or `FailureMode`, and redirecting type-specific external policy/data. This is expected authorization and a strong defense-evasion technique, not a service defect.

### Cross-account-shaped type ARN behavior

With `BatchDescribeTypeConfigurations` allowed on `*`, passing:

`arn:aws:cloudformation:us-east-1:111111111111:type/hook/Ht-Cfnregistry-GuardHook`

returned the **local account's** configuration and local configuration ARN, while the response's `TypeArn` field echoed the caller-supplied foreign account ID. The API is documented to read configurations from the current account and Region, so this appears to be local name/path resolution plus an unvalidated echoed field. It did not access account `111111111111` and produced no cross-account disclosure. Record as a response-integrity oddity; no bug-bounty report was created because no security boundary or confidentiality impact was demonstrated.

No Registry `Put*TypePolicy`/`Get*TypePolicy` API exists. Private extensions are account/Region local; sharing code with other accounts requires registering it there or using the public publishing and destination-account activation model. No cross-account resource-policy persistence path was found.

### Cloud Control async request ownership

1. A creator role with only `cloudformation:CreateResource` submitted the invalid S3 bucket request and received request token `29415793-5dbf-4679-b54e-66e71b8250ab`.
2. The creator could not poll it without `cloudformation:GetResourceRequestStatus`.
3. A new session of a separate observer role with only `GetResourceRequestStatus` successfully read the creator's token and recovered type, identifier, operation, `FAILED` status, event time, status message, and error code.
4. A lister role with only `cloudformation:ListResourceRequests` enumerated the same token and fields.
5. A random UUID returned `RequestTokenNotFoundException`.

Request records are therefore account/Region scoped rather than creator scoped, matching the API's authorization model. AWS documents a seven-day lifetime. The returned metadata is useful operational recon, but `DesiredState` was not returned.

### Versions and modules

- `SetTypeDefaultVersion` was not mutated live because no private package/version pre-existed and registering persistent executable code was unnecessary for the authorization questions.
- Expected high-value paths retained for the book:
  - malicious resource/Hook version plus a passed execution role, then handler invocation;
  - malicious Hook enabled for future organic provisioning;
  - malicious module version made default so future unversioned module use expands attacker-selected resources under the future stack role.
- `SetTypeDefaultVersion` alone was not presented as a generic privilege escalation. It can select only an already registered version.
