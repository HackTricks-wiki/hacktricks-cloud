## Live fixture

Each successful run created:

- one stopped `FLINK-1_20` streaming application;
- one S3 bucket containing two harmless valid JARs already present on the test host;
- one application service role trusted by `kinesisanalytics.amazonaws.com`;
- one CloudWatch log group/stream for the logging-option test; and
- application properties containing synthetic marker values.

The role could read only the fixture bucket, write the fixture log stream and perform AWS's documented VPC/ENI actions. The app was never started, so those permissions did not create runtime infrastructure or perform downstream reads.

The first setup attempt deliberately/accidentally used a non-JAR object and `CreateApplication` rejected it with `No valid JAR file found in the zip file`; its trap removed the role, bucket and objects. This demonstrates that application creation validates at least the submitted ZIP/JAR container without starting compute.

## Tested authorization and attack matrix

| Hypothesis / action | Minimum-session result | Security conclusion |
| --- | --- | --- |
| Unsigned `ListApplications` | `MissingAuthenticationTokenException` | No unauthenticated inventory path; no unauth page warranted |
| `DescribeApplication` on exact application, with `s3:GetObject` and PassRole explicitly denied | Returned service role, S3 code location and cleartext property values | Treat describe as secret access; caller does not need artifact access |
| `ListApplicationVersions` + `DescribeApplicationVersion` on exact application | Version 1 returned the original marker after current config was changed | Historical versions retain rotated property values and old code pointers |
| `UpdateApplication` code pointer on exact application, with `s3:GetObject` and PassRole explicitly denied | Succeeded; version 1 → 2 and key changed from `original.jar` to `replacement.jar` | Update authority can select code for the already delegated role without caller S3 read/PassRole |
| `UpdateApplication` runtime properties under same scoped session | Succeeded; version 2 → 3 and returned replacement values | Property poisoning/redirect is a durable application configuration change |
| `UpdateApplication --service-execution-role-update` with PassRole denied | `AccessDeniedException` on `iam:PassRole`, even for the same ARN | Explicit role updates preserve the PassRole boundary |
| `AddApplicationCloudWatchLoggingOption` with `logs:*`, `ec2:*` and PassRole denied | Succeeded; version 3 → 4 and returned the selected stream ARN | API caller configures the destination; existing execution-role log access is the downstream boundary |
| `AddApplicationVpcConfiguration` under the same scoped caller | Succeeded after the existing role had all documented VPC/ENI actions; version 4 → 5 | Caller needs neither EC2 permissions nor PassRole; role permissions and selected network resources are the boundary |
| First VPC attempt without `ec2:DescribeDhcpOptions` in the execution role | Rejected: service lacked necessary VPC privileges | AWS enforces the documented execution-role permission set |
| `RollbackApplication` on a `READY` application | `ResourceInUseException: Application cannot be rolled back in READY status` | Do not claim stopped-app rollback; testing a running rollback was excluded by the no-start rule |
| Start/update runtime code execution | Not invoked | AWS documentation establishes that running the configured JAR uses the application role; this audit proves only the stopped control-plane precursor |
| Studio presigned URL | Not invoked because no Studio app was started | Strong documentation-backed path only: a running interactive app is required and starting it costs money |
| Snapshot creation/restore | Not invoked because snapshots require a running application/state | Retained only as enumeration/recovery context, not a standalone persistence claim |

## Exact minimum-permission boundaries

The read-only session allowed only these actions on the exact application ARN and explicitly denied S3 object reads and PassRole:

```json
[
  "kinesisanalytics:DescribeApplication",
  "kinesisanalytics:ListApplicationVersions",
  "kinesisanalytics:DescribeApplicationVersion",
  "kinesisanalytics:ListApplicationOperations"
]
```

The update session allowed only:

```json
[
  "kinesisanalytics:UpdateApplication",
  "kinesisanalytics:DescribeApplication"
]
```

with explicit denies for `s3:GetObject` and `iam:PassRole`. Code-pointer and property updates succeeded; an explicit role update did not.

The auxiliary session allowed only:

```json
[
  "kinesisanalytics:AddApplicationCloudWatchLoggingOption",
  "kinesisanalytics:AddApplicationVpcConfiguration",
  "kinesisanalytics:DescribeApplication"
]
```

on the exact application, with explicit denies for `logs:*`, `ec2:*` and `iam:PassRole`. Both configuration changes succeeded because the pre-existing application role already had the necessary downstream permissions.

## Useful techniques accepted for the book

1. Complete application/configuration enumeration, including roles, code locations, properties, VPCs, logs, Glue and snapshot settings.
2. Current runtime property disclosure through `DescribeApplication`.
3. Historical secret recovery and code-location discovery through `DescribeApplicationVersion`.
4. Conditional S3 artifact retrieval and offline code/dependency review.
5. Exact-app `UpdateApplication` code replacement followed by update/start as execution under the existing application role, without PassRole when retaining it.
6. `CreateApplication` + exact `iam:PassRole` + attacker code + `StartApplication` as a fresh delegation path.
7. Studio `CreateApplicationPresignedUrl` as a documentation-backed interactive Zeppelin execution path on an already running notebook.
8. VPC attachment without caller EC2/PassRole permissions, combined with code control for private-network pivoting.
9. CloudWatch log destination addition/removal as log redirection or suppression, bounded by the existing role's write permission.
10. Durable code-pointer and application-consumed runtime-property implants as service-level persistence.

## Rejected, constrained or deferred ideas

- **Generic role credential theft:** MSF code executes with the role, but service APIs do not return reusable role credentials.
- **Code update alone equals execution:** false for the tested `READY` application; it remained stopped. Documentation distinguishes later start/update execution.
- **VPC configuration alone equals network access:** false. It only changes control-plane configuration; attacker code and a running app are required. No ENI existed after the stopped test.
- **CloudWatch option alone proves log exfiltration:** false. The config was accepted, but delivery also requires a running application and execution-role write permission.
- **Rollback as stopped-app persistence:** rejected live with `ResourceInUseException`; no running test was authorized under the strict cost rule.
- **Snapshots as code persistence:** snapshots preserve application state, not a downloadable JAR or independent code implant.
- **Unauthenticated APIs:** unsigned requests failed. Only leaked presigned extension URLs are bearer capabilities.
- **Cross-account application resource policy:** MSF exposes no general application resource-policy API. Cross-account administration uses an assumed role; downstream S3/KMS policies can still enable cross-account code/data access.
- **Starting a Studio notebook to test Zeppelin:** rejected because it creates billable compute. AWS documentation is sufficient to state the conditional path.
- **Destructive delete/stop denial of service:** real but obvious effects of destructive permissions and not a useful standalone book technique.
