# Systems Manager GUI Connect recording audit — 2026-09-27

## Scope and inventory

- Authorized account `228478051196`, Region `us-east-1`.
- Current public API surface: get, update and delete the account/Region connection-recording preference. Current IAM surface additionally has permission-only start/get/list/cancel connection actions.
- No resource type or service-specific condition key; all seven actions use `Resource: "*"`.
- Existing book coverage contained no GUI Connect/Fleet Manager RDP recording preference technique.

Initial and final `GetConnectionRecordingPreferences` returned `ResourceNotFoundException: ConnectionRecordingPreferences`. JIT node access is not enabled in the test account.

## High-value expected behavior

1. `DeleteConnectionRecordingPreferences` disables recording for future GUI Connect RDP sessions in the account/Region. It does not delete existing S3 objects.
2. `UpdateConnectionRecordingPreferences` selects one symmetric customer KMS key and one S3 bucket name/owner pair. This is a durable future-session video sink. The bucket policy grants the GUI Connect service principal write permission for the victim source account; an attacker-readable bucket can therefore become a recording exfiltration path when all prerequisites are satisfied.
3. A deliberately invalid/broken bucket or KMS boundary can cause the documented `ProcessingError` after a connection, creating a defense-evasion/blinding outcome.

## Minimum-permission live boundary

A disposable IAM role attempt was cleaned after the account's administrator role could not assume it. A disposable IAM user was then given only:

```json
{
  "Effect": "Allow",
  "Action": "ssm-guiconnect:UpdateConnectionRecordingPreferences",
  "Resource": "*"
}
```

After IAM credential propagation, the caller submitted a synthetic nonexistent KMS key and bucket. It passed IAM authorization and returned:

```text
AccessDeniedException: Just-in-time node access is not enabled. You must set up just-in-time node
access to record RDP connections.
```

The test proves the single update action reaches the service prerequisite. It does not prove that a real configured update can omit the documented `kms:CreateGrant`; public guidance retains that KMS permission and all JIT/bucket/key prerequisites from AWS's setup documentation.

The post-check still returned `ResourceNotFoundException`, proving no preference was stored. Both attempted disposable role/user paths, inline policies and access keys were deleted; final audit-prefix role and user counts were zero. No S3 bucket, object, KMS key/grant, managed node, JIT setting or RDP connection was created.

## Telemetry

`GetConnectionRecordingPreferences` appeared in CloudTrail Event History as a management read with `eventSource=ssm-guiconnect.amazonaws.com`. AWS documents Systems Manager control-plane operations as management events and GUI Connect events flowing to EventBridge through CloudTrail. Preference writes/deletes are therefore the primary signals. Recording delivery is an S3 object data event and is absent by default unless the bucket is selected.

## Exclusions

- No privilege escalation: preference writes do not start an RDP session or grant managed-node access.
- No IAM persistence page: the setting persists as evidence redirection/blinding but does not preserve attacker login or AWS credentials.
- No unauthenticated path: the API is SigV4/IAM protected and connections are permission-only service workflows.
- No end-to-end redirect in the lab: enabling JIT, provisioning a customer KMS key, and creating an actual Windows/RDP workflow solely for proof would add unnecessary state/cost. API/IAM, bucket owner, resource-policy and failure semantics are explicit in primary documentation.
- No unexpected AWS defect was found; no private report was created.
