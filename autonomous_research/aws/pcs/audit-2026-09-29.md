# AWS PCS audit — 2026-09-29

## Scope

Reviewed the current PCS API model, scheduler-authentication fields, Secrets Manager handoff, enumeration coverage and IAM boundaries for cluster-secret access.

## Findings

- `GetCluster` returns the ARN and version for the PCS-managed shared Slurm authentication secret.
- With Slurm REST enabled, the same response returns the JWT signing-key ARN/version and private endpoint. AWS's documented client procedure retrieves the signing key and constructs JWTs with POSIX identity claims.
- The secret value still requires the separate `secretsmanager:GetSecretValue` permission; PCS does not vend the plaintext key through `GetCluster`.
- A restricted caller holding only `pcs:GetCluster` reached a service-side `ResourceNotFoundException` for a nonexistent cluster while an exact canary-secret read returned `AccessDeniedException`. Adding `secretsmanager:GetSecretValue` on only that canary ARN produced a matching one-way hash. This verifies the independent IAM gates without creating a billed cluster.
- No PCS clusters existed in either allowed Region (`us-east-1`, `eu-west-1`), so no live scheduler or managed secret was touched.

## Telemetry

`GetCluster` and `GetSecretValue` are default CloudTrail management reads. Secret values are not stored in the CloudTrail record. Scheduler and Slurm REST traffic is outside CloudTrail and requires PCS/Slurm logs plus network telemetry.

## Cleanup

The canary secret was force-deleted and the access key, inline policy and IAM user were deleted. Prefix-filtered inventories returned no remaining test user or active canary secret. No PCS resource, VPC resource, instance or compute node was created.

## Disposition

This is expected AWS functionality with dangerous authorization consequences, not an AWS service defect. Public enumeration and post-exploitation coverage was added; no private report was created.
