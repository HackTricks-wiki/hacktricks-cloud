## Important role and authorization boundaries

### Original application invoker role

`CreateApp` and `UpdateApp` accept a permission model with `invokerRoleName` and optional `crossAccountRoleArns`. The primary role trusts `resiliencehub.amazonaws.com`. Documentation and live tests confirmed `iam:PassRole` is enforced when the role is stored.

Later import and assessment APIs do not accept a role and reuse the stored invoker role. This is a constrained deputy for resource discovery, not arbitrary role execution.

### Next-generation service invoker role

`CreateService`/`UpdateService` store `invokerRoleName` plus optional cross-account role/external-ID pairs. A restrictive session with only `resiliencehub:CreateService` received `AccessDenied` specifically for `iam:PassRole` on the supplied role. Exact-role PassRole to `resiliencehub.amazonaws.com` allowed service creation.

This is enforced even though the current Service Authorization Reference row observed during the audit omitted the dependent-action column for `CreateService`.

### Next-generation FIS execution role

`CreateTest` accepts a separate `roleName` trusted by `fis.amazonaws.com`. Live authorization checks established three gates:

1. Without `iam:PassRole`, `CreateTest` was denied on the exact execution-role ARN.
2. With PassRole but `resiliencehub:CreateTest` scoped only to the customer service ARN, the request was denied on the AWS-owned test-template ARN.
3. With `CreateTest` on both ARNs and exact-role PassRole, authorization passed and the request reached policy/template validation.

No test run was started. AWS documents the caller-side FIS orchestration set in `AWSResilienceHubResilienceTestingPolicy` and template-specific permissions for the FIS execution role.

Initial inventory returned zero applications, resiliency policies, recommendation templates and Resilience Hub roles.

The test fixture created:

| `CreateApp` with invoker role | `resiliencehub:CreateApp` only | `AccessDenied` on exact role `iam:PassRole` |

## Next-generation test templates

`ListTestTemplates` returned four AWS-owned templates:

1. `aws-az-recovery:rtaz001` — stop EC2, inject EC2/ASG capacity errors, disrupt subnet traffic, RDS failover, ElastiCache AZ-power interruption and ARC zonal autoshift.
2. `aws-dependency-validation:rtdep001` — predefined SSM/ECS/EKS dependency traffic loss.
3. `aws-multi-region-isolation:rtmr001` — disrupt TGW/routes/endpoints, pause S3/DynamoDB/MemoryDB replication and predefined workload traffic loss.
4. `aws-multi-region-recovery:rtmr002` — dependency traffic loss and optional ARC Region Switch execution.

`GetTestTemplate` was called for all four. Actions and parameter schemas matched the documentation. These are impactful, constrained templates; they do not permit arbitrary FIS action IDs or arbitrary SSM documents through `CreateTest` parameters.

`CreateTest` validation was exercised only through configuration creation. A compatible topology/policy was not assembled because doing so would add no authorization evidence and a live `StartTestRun` would create real FIS experiments. No `StartTestRun` call was made.

## Strong expected attacks accepted

1. Read concentrated original/v2 resource topology, dependency graphs, failure-mode reasoning, recommendations, test role/configuration/run history and report locations.
2. Trigger import/discovery/assessment through an existing stored invoker role without fresh PassRole or direct source-service permissions, then retrieve modeled topology.
3. Poison application/service topology, policies, recommendations and finding status to blind or mislead resilience reviews and alter later test targeting.
4. Combine `CreateTest`, exact-role PassRole, the AWS-owned template authorization and `StartTestRun`/FIS orchestration permissions to execute predefined high-impact faults as an FIS role.

## Rejected, narrowed or deferred ideas

- **Missing PassRole on next-generation `CreateService`:** rejected. The Service Authorization Reference omitted the dependency, but live authorization denied exactly on the supplied invoker role.
- **Missing PassRole on `CreateTest`:** rejected. Live authorization denied exactly on the supplied FIS execution role.
- **Service-only `CreateTest` resource policy:** rejected. The AWS-owned test-template ARN is also authorized.
- **Arbitrary code execution through the dependency template:** narrowed. The template includes `aws:ssm:send-command`, ECS and EKS actions, but the public request selects only documented dependency/duration/Region parameters, not an arbitrary command/document.
- **Raw Terraform state/secret output disclosure:** rejected in the live fixture. Import succeeded through the role, but the sensitive output canary was not returned by the application-template response.
- **Arbitrary role actions through assessments:** rejected. Invoker roles are used for fixed discovery/assessment behavior; they are not general credential vending or arbitrary API execution.
- **Cross-account S3 export solely by naming a foreign bucket:** deferred. `StartMetricsExport` and recommendation/test report outputs accept bucket names, but foreign-account acceptance, bucket policy, ownership and KMS boundaries require a second authorized account. No export task was launched because the API has no delete-task operation.
- **Unsigned API enumeration:** rejected. Signed authentication is required for both generations.
- **Delete/stop-only denial of service:** kept ledger-only as low-value and not published as standalone techniques.
- **Organizations delegated-admin data replication:** documentation reviewed, but no organization settings were changed in the training account.

## Candidate future defect tests

1. In two authorized accounts, validate foreign-account Terraform/report/log destinations, bucket-owner enforcement, KMS context and stale bucket-name reuse for both generations.
2. Build a disposable but non-production topology and execute each test template with minimal execution-role permissions, immediate stop conditions and independent observers; verify target scoping cannot escape the service.
3. Test parameter canonicalization for Regions, AZs, dependency domain names, ARC plan ARNs, duration boundaries and duplicate values.
4. Attempt cross-service/test ID substitution and mismatched service/template/test-run IDs under exact resource policies.
5. Verify whether stored execution roles are re-authorized after role replacement, trust removal, policy shrink and test update; test stale queued runs.
6. Validate multi-account FIS orchestrator/target-role name and external-ID binding, same-name role substitution and account targeting.
7. Test EKS cluster/user/service-account scoping and namespace confusion without touching production workloads.
8. Audit GenAI failure-mode inputs/outputs for prompt injection from tags, resource names, Terraform metadata, DNS names and CloudFormation fields; verify no cross-account context leakage.
9. Check dependency-discovery DNS log isolation, retention, redaction, third-party endpoint handling and data-residency/home-Region replication.
10. Capture a successful metrics/recommendation/test report lifecycle and determine exactly which caller, invoker role or service principal writes the destination.

## Harness issue and recovery

The first original-API harness accidentally allowed already-exported AWS credentials to take precedence over `AWS_PROFILE` during a nested `AssumeRole`. Its authorization output was discarded. The cleanup trap deleted the transient application, role, object and bucket; an independent inventory returned zero residue before the corrected test. Later harnesses explicitly unset credential variables before every profile-based assume.
