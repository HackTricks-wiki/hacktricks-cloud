## Current service model reviewed

AppFabric for security is regional and uses this hierarchy:

```text
appbundle/<uuid>
appbundle/<uuid>/appauthorization/<uuid>
appbundle/<uuid>/ingestion/<uuid>
appbundle/<uuid>/ingestion/<uuid>/ingestiondestination/<uuid>
```

The bundle contains encrypted authorization credentials. An ingestion pulls SaaS audit logs through a connected authorization, and up to five destinations deliver them to S3 or Firehose. The user-access APIs query connected SaaS directories for an email address.

Primary current references reviewed:

- AWS AppFabric API Reference and CLI models;
- AppFabric Administration Guide, including terminology, supported applications, user-access workflow, OCSF formats and destination setup;
- AWS Service Authorization Reference and the machine-readable AppFabric service reference;
- AWSAppFabricServiceRolePolicy;
- AppFabric endpoints and quotas.

## Attack and defect hypotheses

| Hypothesis | Class | Result |
| --- | --- | --- |
| Read APIs return stored SaaS API keys, OAuth client secrets or access/refresh tokens | Potential unexpected secret disclosure | Rejected; output schemas and live responses omit credentials |
| User-access tasks can enumerate identity/access data in connected SaaS tenants using only bundle-scoped AppFabric permissions | Expected post-exploitation | Confirmed at the AppFabric authorization and task layer; connected-tenant result schema confirmed from current API contract |
| Adding/updating an ingestion destination can copy SaaS audit logs to an attacker-readable same-account location | Expected post-exploitation | Confirmed by API/IAM validation and service-role policy; end-to-end delivery was not run because no disposable connected SaaS tenant was available |
| An arbitrary cross-account S3 bucket can receive AppFabric logs | Potential cross-account exfiltration | Rejected; service-linked role requires `s3:ResourceAccount` equal to its own account |
| A cross-account Firehose stream can trivially receive logs | Potential cross-account exfiltration | Rejected as a standalone primitive; SLR requires `AWSAppFabricManaged=true`, and no native AppFabric resource sharing exists |
| `UpdateAppAuthorization` reveals or returns the previous credential | Potential unexpected secret disclosure | Rejected; it accepts replacements but never returns the stored credential |
| Replacing an app authorization credential is persistence in AWS | Persistence hypothesis | Rejected; it can disrupt or repoint the SaaS connection but grants no durable AWS access |
| Creating an app bundle with a customer KMS key grants arbitrary KMS or IAM authority | Privilege-escalation hypothesis | Rejected; no generic role execution or caller-selected principal grant path was found |
| AppFabric objects are shareable through a resource policy | Cross-account hypothesis | Rejected; AppFabric has no resource-policy API |
| List or get APIs work unsigned | Unauthenticated-access hypothesis | Rejected; unsigned calls returned `MissingAuthenticationTokenException` |
| API credentials or target user email leak into CloudTrail | Potential unexpected telemetry leak | Rejected; API keys/client secrets and search email were redacted as `HIDDEN_DUE_TO_SECURITY_REASONS` |
| Failed AppFabric requests are misclassified in CloudTrail | Potential detection defect | Rejected in tested cases; `AccessDenied`, `ValidationException` and `ResourceNotFoundException` were represented accurately |

## Verified behavior

### 1. Inventory and unauthenticated boundary

Signed `ListAppBundles` returned an empty list in `us-east-1` and `eu-west-1` before fixture creation. The same call with `--no-sign-request` returned:

```text
MissingAuthenticationTokenException: Missing Authentication Token
```

Tokyo returned an explicit SCP denial for the assumed admin role and was not probed further.

### 2. Stored credentials remain write-only

Creating an API-key authorization returned:

- authorization ARN;
- bundle ARN;
- app and tenant metadata;
- `authType=apiKey`;
- `status=PendingConnect`;
- creation/update timestamps and `persona=admin`.

`GetAppAuthorization` and `ListAppAuthorizations` returned the same non-secret metadata and no credential member. `UpdateAppAuthorization` could replace tenant/credential input, but its response likewise contained no secret material.

CloudTrail recorded the credential field but replaced `apiKey` or `clientSecret` with `HIDDEN_DUE_TO_SECURITY_REASONS`. The OAuth client ID and tenant metadata were not treated as secrets, matching the service model.

### 3. User-access task authority

A probe with only these two actions on the exact bundle reached the service:

```json
{
  "Action": [
    "appfabric:StartUserAccessTasks",
    "appfabric:BatchGetUserAccessTasks"
  ],
  "Resource": "arn:aws:appfabric:us-east-1:228478051196:appbundle/eed2bead-4671-42fa-a130-b954a61337a0"
}
```

`StartUserAccessTasks` returned one item for ASANA. Because the authorization was deliberately unconnected, the item contained no task ID and reported that no authentication token was available. This proves action/resource authorization without contacting or modifying an external tenant.

`BatchGetUserAccessTasks` on a fabricated UUID returned a structured per-task 404 inside a successful API response, proving that the exact bundle permission is sufficient to query task results.

The current response contract for completed tasks includes app, tenant ID/display name, target email, vendor user ID, full/first/last name and vendor user status. This is a useful expected post-exploitation primitive when real connected authorizations exist.

CloudTrail behavior:

- `StartUserAccessTasks`: management event, `readOnly: false`, target email redacted;
- `BatchGetUserAccessTasks`: management event, `readOnly: true`, task UUIDs visible, result body omitted.

### 4. Hierarchical IAM evaluation is stricter than the high-level table suggests

Live policy evaluation found that several APIs authorize an implicit child resource in addition to their parent:

- `ListAppAuthorizations` with only the exact bundle ARN was denied on `<bundle-arn>/appauthorization/*`; adding both ARNs succeeded.
- `ListIngestions` succeeded with the bundle ARN plus `<bundle-arn>/ingestion/*`.
- `CreateIngestion` with only the bundle ARN was denied on `<bundle-arn>/ingestion/*` before business validation.
- Adding tags to `CreateIngestion` separately required `appfabric:TagResource` on the prospective ingestion wildcard.
- `GetAppAuthorization` and `UpdateAppAuthorization` required both the bundle ARN and exact authorization ARN. A child-only policy was denied on the bundle; both ARNs succeeded.

The service authorization reference describes the resource types but can be read as parent-only for some list/create calls. The enforced child wildcard should be documented for usable least privilege. This is not a security vulnerability because it narrows rather than broadens access.

### 5. Destination mutation permissions

No connected authorization was available, so a real ingestion could not be created. Admin `CreateIngestion` correctly returned:

```text
ValidationException: The app authorization for the specified application and tenant was not connected.
```

Permission evaluation was isolated using fabricated ingestion/destination UUIDs. A temporary user received:

- `CreateIngestionDestination` / `ListIngestionDestinations` on bundle, ingestion and prospective destination wildcard;
- `GetIngestionDestination` / `UpdateIngestionDestination` on bundle, ingestion and exact destination ARNs.

All four calls passed IAM and reached resource/business validation:

```text
ListIngestionDestinations: ResourceNotFoundException (ingestion does not exist)
CreateIngestionDestination: ValidationException (ingestion does not exist)
GetIngestionDestination: ResourceNotFoundException (destination does not exist)
UpdateIngestionDestination: ValidationException (ingestion does not exist)
```

The current API contract allows `CreateIngestionDestination` to add S3/Firehose output and `UpdateIngestionDestination` to replace the destination configuration. The expected attack is limited but real: point an existing connected ingestion at a same-account S3 bucket/prefix the attacker can read, or an appropriate same-account tagged Firehose stream, then optionally start the ingestion.

### 6. Service-linked-role constraints

The pre-existing AWS-managed `AWSAppFabricServiceRolePolicy` grants:

```text
cloudwatch:PutMetricData
  only for namespace AWS/AppFabric

s3:PutObject
  only arn:aws:s3:::*/AWSAppFabric/*
  with s3:ResourceAccount = ${aws:PrincipalAccount}

firehose:PutRecordBatch
  only when aws:ResourceTag/AWSAppFabricManaged = true
```

This rules out the simple claim that AppFabric alone writes to an arbitrary external-account bucket. The caller can configure AppFabric without direct S3 write permission, but later data recovery still requires independent read authority to the chosen same-account bucket or downstream destination.

## Classification decisions

Published as post-exploitation:

1. enumerate SaaS user membership and identity/status through `StartUserAccessTasks` plus `BatchGetUserAccessTasks`;
2. copy SaaS audit logs into an attacker-readable same-account destination with destination create/update authority.

Not published as standalone attacks:

- bundle/authorization/ingestion metadata enumeration: useful reconnaissance, documented in enum, but no raw secret extraction;
- `UpdateAppAuthorization` credential replacement: primarily disruption or telemetry poisoning and requires attacker-controlled/vendor credentials; it does not grant more AWS or victim-SaaS authority by itself;
- stop/delete operations: obvious availability actions without a distinct data, privilege or persistence consequence;
- cross-account S3 destination: contradicted by the service-linked-role resource-account condition;
- customer-managed KMS ARN discovery: ARN metadata is not decrypt authority;
- fake task-ID polling: results are scoped to the bundle and fabricated IDs return only a structured not-found result.

No AppFabric privilege-escalation, AWS persistence or useful unauthenticated-access page was created.
