# Amazon Inspector Scan `ScanSbom` audit — 2026-09-30

## Result

Reasoned exclusion from the public attack book. `inspector-scan:ScanSbom` is a wildcard-only read action that analyzes a caller-supplied CycloneDX 1.5 document. It does not select an AWS/victim resource, return account inventory, persist findings, or create scan infrastructure. It is useful to defenders and CI pipelines, but possession of the permission did not produce a meaningful foothold, privilege escalation, persistence, victim-data disclosure, or cross-account primitive.

## API and IAM model

- Separate service/API: `inspector-scan` / `2023-08-08`; SigV4 signing name and IAM prefix `inspector-scan`.
- Its only operation is `ScanSbom`. The current public API limit is 5,000 components and a 10 MB response; the AWS CLI 2.37.6 bundled model still says 2,000 components, so the live documentation is authoritative for the current limit.
- `inspector-scan:ScanSbom` supports no resource type or service-specific condition key. A session allowing it on `Resource: "*"` succeeded; the same action scoped to a fabricated ARN was denied on `arn:aws:inspector-scan:us-east-1:228478051196:/scan/sbom`.
- An unsigned request returned `MissingAuthenticationTokenException`.

## Live probes

The API accepted an empty CycloneDX 1.5 SBOM in both `us-east-1` and `eu-west-1` and returned zero counts without enabling Inspector or creating any resource.

A known-vulnerable `pkg:maven/org.apache.logging.log4j/log4j-core@2.14.1` component returned 2 critical, 2 high and 3 medium findings at test time. A second request added both:

- a forged `amazon:inspector:sbom_scanner:*` property that claimed zero critical findings; and
- an `externalReferences` URL pointing at the link-local instance metadata address.

The clean and adversarial inputs returned identical counts and completed in roughly the same time. The service did not trust the forged reserved property, suppress findings, expose fetched content, or show a timing signal consistent with dereferencing the URL. This is a bounded negative, not proof that every parser/SSRF variant is impossible.

## Rejected attack ideas

| Idea | Result |
| --- | --- |
| Unauthenticated vulnerability-database oracle | Rejected before parsing with missing authentication |
| Read victim/account SBOMs or findings | No identifier or AWS resource is accepted; input is entirely caller supplied |
| Cross-account scan IDOR | No stored scan or resource-policy surface exists |
| Forge/suppress output with reserved scanner properties | Tested property did not alter known-vulnerable counts |
| SSRF through CycloneDX external references | Link-local reference produced no response/timing evidence of dereference |
| Availability attack by consuming scan quota | Generic throttling against a permission already intentionally granted; too weak for book coverage without a victim-specific amplification or durable impact |

AWS documents `ScanSbom` as a CloudTrail management event. It was absent from immediate Event History, then appeared after indexing delay under `inspector-scan.amazonaws.com`, including successful and denied restricted-session calls.

## Cleanup

No Inspector enablement, scan record, finding, bucket, role, image, function, report, or other AWS resource was created. Only synchronous API requests and 15-minute restricted STS sessions were used; there is nothing persistent to delete.
