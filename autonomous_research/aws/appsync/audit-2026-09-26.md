## Verified useful techniques

### `ListApiKeys` is account-wide credential read

- An exact GraphQL API ARN allow was denied. `Resource: "*"` succeeded.
- `ListApiKeys` returned the literal `da2-...` bearer value in `apiKeys[].id`.
- The key successfully queried static data and the public introspection schema.
- CloudTrail logged the API ID but not the response/key value.

Result: added to enumeration and post-exploitation coverage.

### Environment values and schema are account-wide reads

- Exact-API allows for `GetGraphqlApiEnvironmentVariables` and `GetIntrospectionSchema` were denied; wildcard allows succeeded.
- Environment values were returned in plaintext.
- `GetIntrospectionSchema` returned the SDL even while public GraphQL introspection was disabled.
- CloudTrail used `responseElements: null` for both reads. Put operations redacted the entire environment map as `***`.

Result: added as credential/configuration discovery.

### Resolver mutation and delayed serving-plane convergence

- Exact API/field ARN policy did not authorize `UpdateResolver`; `Resource: "*"` did.
- Replacing a response mapping produced attacker-controlled output through the public endpoint.
- The control-plane `GetResolver` result reflected the restored template before the serving plane stopped returning the prior value. This was treated as ordinary eventual propagation, not a vulnerability.
- CloudTrail redacted request/response mapping-template bodies as `***` while retaining the target type, field, API and data-source name.

Result: added as post-exploitation/service persistence, with no zero-day claim.

### Data-source redirect and `iam:PassRole`

- Exact API/data-source ARN policy did not authorize `UpdateDataSource`; wildcard did.
- An unauthenticated HTTP endpoint change to an AWS-controlled STS endpoint succeeded without `iam:PassRole`.
- Adding a role-backed DynamoDB data source failed without `iam:PassRole` and succeeded with exact-role `iam:PassRole` conditioned on `iam:PassedToService = appsync.amazonaws.com`.
- CloudTrail recorded target type, role ARN, backend configuration and HTTP endpoint.

Result: added to post-exploitation and least-privilege guidance.

### IAM-signed HTTP data source is a passed-role AWS API proxy

- Low caller permissions: wildcard `UpdateDataSource`, wildcard `UpdateResolver`, exact-role `iam:PassRole` with the AppSync service condition.
- Configured `https://sts.us-east-1.amazonaws.com` as an HTTP data source with IAM signing service `sts` and the dedicated role.
- A VTL request invoked `GetCallerIdentity`; the GraphQL response contained:
  `arn:aws:sts::228478051196:assumed-role/ht-appsync-audit-ds-role-20260927/APPSYNC_ASSUME_ROLE`.
- This proves the resolver can issue AWS API requests under the passed role. The role's own policy and downstream service authorization still constrain impact; no raw STS credentials were disclosed.

Result: added as a high-value expected `PassRole` privilege-escalation technique.

### Auth-mode downgrade plus API-key creation

- `UpdateGraphqlApi` was successfully scoped to the exact IAM-primary API ARN.
- Adding `API_KEY` only as a secondary auth provider did not authorize an API-key client for a field inheriting the IAM primary mode.
- Changing the primary mode to `API_KEY` and keeping IAM secondary immediately authorized that same field.
- `CreateApiKey` succeeded under the wildcard-only permission documented by the service authorization reference. An exact-resource denial was not separately repeated for this action.
- CloudTrail clearly recorded primary/additional modes and key creation, while redacting the returned key value.

Result: added as application-level privilege escalation and persistence.

### API-key extension

- Exact-API `UpdateApiKey` was denied; wildcard succeeded.
- A low caller changed the key description and extended expiration. The administrator restored the original expiration and description.

Result: added as service-level persistence.

### Environment overwrite

- Exact-API `PutGraphqlApiEnvironmentVariables` was denied; wildcard succeeded.
- A call with one key replaced the complete two-key map, proving destructive overwrite semantics.
- Original fixture values were restored before API deletion.

Result: added as post-exploitation/service-level persistence.

### Merged-API authorization and association boundary

- An IAM-primary source was associated with an API-key-primary merged API whose execution role had exact `SourceGraphQL` access.
- Merge status reached `MERGE_SUCCESS`.
- The merged API key was denied on the source field; source IAM authorization was preserved.
- `AssociateSourceGraphqlApi` on the merged API alone was denied for missing `AssociateMergedGraphqlApi` on the source API. Granting both actions on their exact API ARNs succeeded.
- Cross-account was not attempted because no second authorized account/RAM fixture was available. Documentation confirms it additionally requires RAM/resource-policy sharing.

Result: documented the real boundary and `@canonical`/`@hidden` risk; no auth bypass found.

### WAF defense evasion

- Associated a temporary regional WAFv2 web ACL with the GraphQL API.
- A caller with only `wafv2:DisassociateWebACL` was denied for missing `appsync:SetWebACL` on the API ARN.
- Adding exact-API `appsync:SetWebACL` allowed disassociation.
- AWS documentation also describes newer `appsync:DisassociateWebACL`/`AssociateWebACL` actions; current live behavior still emitted the legacy dependent-action name.

Result: added WAF detachment as a defense-evasion technique and advised monitoring both permission forms.
