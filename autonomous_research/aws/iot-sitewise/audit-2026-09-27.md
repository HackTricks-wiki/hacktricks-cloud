## Tested permission and attack matrix

| Hypothesis / action | Minimum-permission result | Security conclusion |
| --- | --- | --- |
| `GetAssetPropertyValue` on one asset ARN | Succeeded for the selected asset; sibling asset was denied | Direct reads can be least-privilege scoped to an asset |
| Alias read with `GetAssetPropertyValue` on exact time-series ARN | Succeeded | Alias addressing authorizes against the time-series ARN |
| `BatchPutAssetPropertyValue` on one asset ARN | Changed selected asset's latest value from `21.5` to `999.0`; sibling entry returned `errorEntries[].AccessDeniedException` | Data poisoning is possible with only the exact asset write permission; batch callers must inspect partial errors |
| `ListTimeSeries` on an exact time-series ARN | Denied on resource `*` | The list action is wildcard-only |
| `ListTimeSeries` on `Resource: "*"` | Returned both aliases, associations, UUIDs and ARNs | High-value alias/time-series inventory |
| `ExecuteQuery` on `Resource: "*"`, with no list/describe/read action | Returned both test asset names and IDs after propagation | Independent account-wide metadata read path; SQL also supports SiteWise raw/latest/aggregate data views |
| Immediate `ExecuteQuery` after creating assets | First query returned no rows; later query returned both | SQL metadata view is eventually consistent |
| Alias-constrained `BatchPutAssetPropertyValue` on `time-series/*` | Created a new unassociated time series and stored value `666.0` | An attacker can pre-seed a guessed future alias when disassociated ingestion is enabled |
| Associate the pre-seeded stream to a victim property | Succeeded only when policy included both exact asset and exact time-series ARNs; victim history then returned `666.0` | Pre-onboarding history poisoning works; association has a two-resource authorization boundary |
| Associate with only exact asset ARN | Denied on the time-series ARN | The service checks both resources even though some summaries emphasize the asset |
| Associate with asset plus a `propertyAlias` condition | Denied | `iotsitewise:propertyAlias` is not a supported condition for this association action; use it on ingestion policies instead |
| Disassociate victim stream and associate it to a second asset | Succeeded with both asset/time-series ARNs | Alias rebinding can persistently reroute future producer data |
| Read after unchanged producer wrote value `77.7` to re-bound alias | Succeeded using only read permission on the second asset | Confirmed service-level telemetry exfiltration without victim read permission |
| Create SiteWise Monitor portal without `iam:PassRole` | Denied specifically on `iam:PassRole` for the supplied role | `CreatePortal` has a real PassRole boundary |
| Create portal with exact `iam:PassRole` and `iam:PassedToService=iotsitewise.amazonaws.com` | Passed IAM check, then returned `Forbidden` because SiteWise Monitor is closed to new customers | Portal/PassRole path remains relevant only to enrolled legacy customers in this account/Region |

## CloudTrail observations

CloudTrail Event history contained the following SiteWise management operations:

- `CreateAssetModel`
- `UpdateAssetProperty`
- `AssociateTimeSeriesToAssetProperty` (including the restricted test actor)
- `DisassociateTimeSeriesFromAssetProperty`
- `ExecuteQuery`

The raw `ExecuteQuery` event classified itself as `readOnly: true`, `managementEvent: true`, and `eventCategory: Management`, but redacted the SQL as `queryStatement: HIDDEN_DUE_TO_SECURITY_REASONS`. It retained `maxResults` and the client token. The association event retained the alias, asset ID and property ID.

It returned no events for:

- `BatchPutAssetPropertyValue`
- `GetAssetPropertyValue`

This matched AWS's data-event model. SiteWise asset/time-series data events were not selected because the account had no trail or event data store. Tests did not enable logging because doing so would mutate account-wide monitoring and could add cost.

## Useful book techniques accepted

1. Account-wide metadata and telemetry query via wildcard-only `ExecuteQuery`.
2. Exact asset/time-series data theft through direct property APIs.
3. Latest/history telemetry poisoning with `BatchPutAssetPropertyValue`, including partial-success response semantics.
4. Pre-seeding a guessed unassociated alias, then inheriting malicious history when it is associated.
5. Persistent alias/time-series rebinding to an attacker-readable asset while the producer continues writing to the unchanged alias.
6. Existing SiteWise Edge gateway capability replacement as a high-impact collector/publisher tampering path. This one is documentation-backed but not live-deployed because no gateway existed and creating Greengrass/edge infrastructure was disproportionate to the API behavior being documented.

## Rejected, constrained, or deferred ideas

### Not promoted as a new technique

- **Generic delete/update denial of service:** `DeleteAsset`, `DeleteAssetModel`, `DeleteTimeSeries`, and destructive model edits are real but obvious write/delete permissions, so no standalone low-value technique was added.
- **Unauthenticated API access:** `ListAssetModels --no-sign-request` returned `MissingAuthenticationTokenException`. Knowing an account ID, asset UUID or alias did not present a bearer/public access path. No unauthenticated page was added.
- **General resource-policy/RAM cross-account access:** SiteWise exposes no general resource-policy API and is not in AWS RAM's shareable resource list. Expected cross-account access uses an assumable IAM role in the owning account.
- **SiteWise Monitor privilege escalation in this account:** portal creation cannot be completed because this account was not enrolled before the 2025 new-customer cutoff. The PassRole boundary was verified, but no unverified escalation page was added.
- **Standalone alias collision as a zero-day:** unique aliases, association APIs, disassociated ingestion and historical attachment are documented behavior. The pre-seeding/rebinding consequences are expected-functionality attack techniques, not AWS defects.

### Candidates for a future account with existing infrastructure

- Snapshot and mutate a real gateway's OPC UA collector/publisher configuration using only exact-gateway `UpdateGatewayCapabilityConfiguration`; verify whether referenced Secrets Manager ARNs or endpoints receive any additional validation.
- Check whether a capability update can downgrade a deployed gateway from encrypted/authenticated OPC UA to `TrustAny`/`NONE`, and measure Greengrass audit/log signals.
- On a legacy Monitor-enabled account, test the complete `CreateAccessPolicy` self-grant and cross-account IAM-role portal-access chains, including the portal role's generated session-policy ceiling.
- Test datasets, export jobs and computation models with passed roles once a current CLI/SDK exposes the newer workspace/pipeline APIs in an account where those features are enabled.
- Revisit `ExecuteQuery` row visibility versus direct asset-level permissions if AWS later introduces resource-level query authorization.
