## Live least-privilege tests

### Connection credential return

- Created a harmless JDBC connection pointed at `127.0.0.1` with a random dummy password.
- `GetConnection` returned the exact stored password by default; `HidePassword=true` omitted it.
- Exact connection ARN alone was denied. `glue:GetConnection` on the catalog plus exact connection ARN succeeded.
- `GetConnections` on catalog plus `connection/*` also returned passwords by default and hid them with `HidePassword=true`.
- Deleted all fixtures. A subsequent exact lookup returned `EntityNotFoundException`.
- CloudTrail recorded `GetConnection` with a null response body. `CreateConnection` masked the username and omitted the password/JDBC URL from the observed request fields.

Result: publish as high-value post-exploitation.

### Record access through a connection

- With only `glue:GetEntityRecords`, the call was denied and named missing `glue:GetConnection` on the catalog.
- `glue:GetEntityRecords`, `glue:GetConnection` and permission-only `glue:PassConnection` on the catalog plus exact connection passed IAM evaluation.
- The deliberately unsupported dummy JDBC connection then returned a validation error before any outbound connection or record retrieval.
- Official API behavior confirms supported connectors return JSON record values, up to 1,000 per page.
- Deleted the dummy connection. CloudTrail captured connection/entity/limit and no response data.

Result: publish as high-confidence data exfiltration with the verified IAM boundary; do not claim unsupported JDBC works.

### Interactive-session boundaries

- `glue:CreateSession` on an exact new session ARN without `iam:PassRole` was denied and explicitly identified the missing PassRole permission. No session was created.
- `glue:RunStatement` on an exact nonexistent session ARN reached resource lookup and returned `EntityNotFoundException`, confirming that the existing-session code path does not require PassRole.
- No interactive compute or statement execution was launched.

Result: publish the distinct create-session and existing-session escalation paths.

### Current `UpdateJob` PassRole enforcement

- Created a no-permission Glue-trusted role and a non-runnable job pointing to a nonexistent S3 script.
- `glue:UpdateJob` on the exact job, repeating the same role but without `iam:PassRole`, was denied.
- Omitting the required role from the update returned `InvalidInput`; the role and script were unchanged.
- Deleted job and role.

Result: remove the stale claim that `UpdateJob` alone escalates. Current Glue requires PassRole even when the existing role value is repeated.

### Plaintext configuration reads

- Put unique dummy strings in a disposable job's `DefaultArguments` and a workflow's `DefaultRunProperties`.
- Exact-resource `glue:GetJob` and `glue:GetWorkflow` each returned the dummy value without execution permissions.
- Read response bodies were absent from CloudTrail. Create request parameters contained the dummy values unredacted.
- Deleted job, workflow and role.

Result: publish as post-exploitation and reinforce that arguments/properties are not secret stores.

### Catalog poisoning

- Created a disposable database/table with a nonexistent benign S3 URI.
- `glue:UpdateTable` on only the table ARN was denied.
- The catalog, exact database and exact table ARNs succeeded and changed the table to a second nonexistent URI.
- CloudTrail contained the table input and changed location.
- Deleted table and database.

Result: publish as high-value post-exploitation with downstream S3/KMS/Lake Formation caveats.

### Catalog resource-policy persistence

- Initial and final `GetResourcePolicy` returned `EntityNotFoundException`.
- Applied a minimal policy granting the already-administrative test role `GetDatabase` on a nonexistent database. No external principal received access.
- `glue:PutResourcePolicy` on the exact catalog ARN alone succeeded; `GetResourcePolicy` returned the policy and hash.
- CloudTrail included the full JSON policy string.
- Deleted the policy and verified absence.

Result: publish as service/account-level catalog persistence, while stating that grantee IAM and downstream controls are still required.

### Scheduled-trigger persistence

- Created a no-permission Glue role and a non-runnable job referencing a nonexistent S3 script.
- A principal with only `glue:CreateTrigger` on the exact new trigger ARN successfully created an activated scheduled trigger with a date in 2099 and `StartOnCreation=true`.
- It had no `iam:PassRole`, `glue:StartTrigger` or `glue:StartJobRun`. No job run occurred.
- `DeleteTrigger` transitioned asynchronously through `DELETING`; polling then confirmed the trigger absent. Deleted job and role.

Result: publish as Glue-service persistence dependent on an existing useful job.

## CloudTrail conclusions

All observed Glue calls were management events with `eventSource=glue.amazonaws.com`. Sensitive read responses (`GetConnection`, `GetJob`, `GetWorkflow`, `GetEntityRecords`) were null in CloudTrail. Mutations included useful request data: job/workflow configuration, table input/location, resource-policy JSON, trigger schedule/actions, and session/job role selections. Detection should alert on sensitive read event names and identities rather than depend on response fields.

## Considered but not promoted

- `UpdateJobFromSourceControl`: potentially valuable supply-chain overwrite path, but a controlled repository/S3 fixture was not available for a safe end-to-end minimum-permission test. Keep for a future audit.
- Blueprints: can provision workflows/jobs through a supplied role, but the full role/S3/template boundary was not safely exercised and overlaps the established PassRole execution pattern.
- Destructive delete/batch-delete operations: obvious availability impact without a distinct offensive primitive; not worth a dedicated HackTricks technique.
- Schema Registry, data-quality, optimizer, usage-profile and integration mutations: useful service abuse but no distinct escalation or data-access path was proven.
- Cross-account catalog policy without the grantee's own IAM allow: not a bypass; it is one half of the documented authorization model.
- Job `ExecutionRoleSessionPolicy`: only restricts a run role and cannot grant permissions absent from that role.
- No unauthenticated page: native Glue APIs require SigV4, and no bearer/public application endpoint is created by the tested control-plane features.
