# Amazon Connect Outbound Campaigns V2 audit — 2026-10-01

## Result

Published the missing `connectcampaignsv2` control-plane inventory and two material expected attack families:

1. exact-campaign `PutOutboundRequestBatch` can submit attacker-selected voice/SMS/email/WhatsApp recipients and parameters through approved business identities, flows and templates; and
2. exact updates against an `Initialized` campaign plus `StartCampaign` can persistently replace and lock recipient sources, flows, content, schedules and contact safeguards; wildcard-only instance integrations also support a documented cross-account Lambda custom action that receives future Customer Profiles `CustomerData` JSON.

These are expected capabilities of explicit Outbound Campaigns permissions. No AWS defect or private report was created.

## Current control plane

- SDK/CLI client: `connectcampaignsv2`; model version `2024-04-23`.
- Endpoint/signing name: `connect-campaigns`; IAM prefix: `connect-campaigns`.
- 37 V2 operations cover campaign CRUD/state, direct/profile outbound batches, channel/source/flow/schedule/guardrail updates, instance onboarding, integrations and tags.
- Campaign ARN: `arn:aws:connect-campaigns:<region>:<account>:campaign/<id>`.
- Instance configuration/integration/onboarding actions are wildcard-resource only in the current authorization reference.
- CloudTrail/EventBridge source documented by AWS: `connect-campaigns.amazonaws.com` / `aws.connect-campaigns`.

## Live inventory and authentication

All opted-in commercial Regions were checked in parallel. The account had no Amazon Connect instances and no V2 campaigns. Unsigned `ListCampaigns` returned `MissingAuthenticationTokenException`. No campaign, Connect instance, onboarding job, integration, contact flow, Customer Profiles domain/segment, Q Connect template, Lambda function, phone/email identity, message, call or delivery request was created.

## Exact campaign authorization

A disposable IAM user was allowed only `connect-campaigns:PutOutboundRequestBatch` on:

```text
arn:aws:connect-campaigns:us-east-1:228478051196:campaign/00000000-0000-0000-0000-000000000001
```

The user also had explicit denies for `connect:*`, `lambda:*`, `profile:*`, `wisdom:*` and `iam:*`. A valid-shape telephony batch against the allowed fake campaign reached the service and returned `ResourceNotFoundException: Campaign ... doesn't exist`. The identical call against a second ID was IAM-denied on its different campaign ARN. This confirms exact-campaign authorization without any adjacent service permission and without placing a contact.

## Wildcard instance-integration boundary

The same user received `connect-campaigns:PutConnectInstanceIntegration` on `*` and submitted a fake same-account Lambda ARN for a nonexistent Connect instance. The call reached `ConnectInstanceConfig not found` despite the explicit `lambda:*`, `connect:*`, IAM, Customer Profiles and Q Connect denies. This proves the initial Campaigns authorization is wildcard-only; it does not prove the later Lambda-policy mutation path on a real onboarded instance.

AWS's current documentation separately establishes that:

- the API automatically adds the required resource policy for same-account Lambda integrations;
- cross-account functions are supported when the external function already trusts `connect-campaigns.amazonaws.com` with victim SourceAccount/SourceArn conditions; and
- invoked custom actions receive batches containing `ProfileId`, complete `CustomerData` JSON and idempotency tokens.

The cross-account exfiltration path is therefore documented with its flow-version/update and runtime prerequisites, but deferred for live validation because no instance/campaign exists and creating one solely to deliver test customer data would expand scope and cleanup risk.

## Delivery and guardrail boundaries

- Direct batches still require an onboarded/runnable campaign, valid channel configuration, approved sending resources/templates, future expiration, quotas and any CMK access.
- Voice campaign concurrency defaults to zero until raised; mass emergency notifications require AWS pre-authorization.
- Campaign `instanceLimitsHandling: OPT_OUT` bypasses total instance communication limits, empty/replaced campaign limits can remove per-campaign caps, `maxEntryCount: 0` is unlimited, and deleting communication-time configuration removes campaign quiet-hour/restricted-period state.
- Source, flow, schedule, communication-time/limit and entry-limit mutations require `Initialized`. `StartCampaign` locks those fields; stopping later is terminal and defenders must recreate the campaign rather than edit it back.
- Provider/carrier anti-abuse, delivery receipts, complaint/spam metrics and customer-side evidence remain independent controls.

## Telemetry

AWS documents Campaigns API events as CloudTrail-originated EventBridge events with source `connect-campaigns.amazonaws.com`. The three failed restricted probes appeared after propagation as default `Management` writes with `readOnly:false`:

- both exact-resource and IAM-denied `PutOutboundRequestBatch` events retained campaign ID, client token and expiry while replacing the destination phone number and attributes with `***`;
- `PutConnectInstanceIntegration` retained the complete Connect instance ID and Lambda ARN; and
- failed events used `resources:null`, with error detail in `responseElements.message` rather than `errorMessage`.

Successful abuse additionally produces Connect contact/campaign state, service-linked-role calls, channel delivery records, recipient evidence, spend, performance metrics and optional outbound-campaign data-lake rows. These downstream signals make actual delivery low stealth even if its initiating API record is absent or delayed.

## Cleanup

The disposable IAM user, inline policy and access key were deleted. Final matching `ht-ccv2-*` IAM-user inventory was empty. The original zero-instance/zero-campaign inventory was unchanged, and no recipient or external system was contacted.
