## Record injection and theft

A session containing only `kinesis:PutRecord` on the exact stream wrote `restricted-injected-record`. Another restricted session with only `GetShardIterator` created a `TRIM_HORIZON` iterator. A different session containing only exact-stream `GetRecords` used that iterator and recovered both test payloads.

This split proves:

- knowing the ARN is enough for exact-stream write access; no list/describe action is needed;
- shard iterators are transferable between sessions;
- an iterator is not a bearer authorization artifact because `GetRecords` evaluates the second caller against the encoded target stream;
- authorization for a different stream did not work with the target iterator.

Useful expected attacks:

- read every retained record from open and closed shards with `ListShards` + `GetShardIterator` + `GetRecords`;
- poison downstream Lambda/Flink/analytics/business workflows with `PutRecord(s)` and a chosen partition key;
- register and use an enhanced fan-out consumer for dedicated continuous read throughput.

The installed AWS CLI did not expose the streaming `SubscribeToShard` operation, so that live event-stream call was not executed. Its consumer-ARN authorization and two-policy cross-account requirements were confirmed from the current API and IAM references and retained as an expected path.

## Resource-policy validation

A session with only `kinesis:PutResourcePolicy` on the exact stream successfully installed a policy granting the test role `PutRecord`. The same exact permission worked on the registered consumer for `DescribeStreamConsumer` and `SubscribeToShard`.

Two boundary probes were rejected as expected:

```text
kinesis:Put* -> InvalidArgumentException: resource policy cannot contain invalid actions
Principal:"*" -> InvalidArgumentException: resource policy cannot contain the wildcard principal
```

The policies were deleted with exact-resource `DeleteResourcePolicy`. A subsequent `GetResourcePolicy` returned `{"Policy":"{}"}` for each resource rather than a not-found error.

Useful expected attacks:

- persistent cross-account stream read/write by adding a specific attacker role;
- persistent enhanced fan-out access by placing one policy on the stream and another on the consumer;
- policy replacement can also remove legitimate principals and cause availability impact.

Boundaries retained in documentation:

- the external principal also needs an identity policy for cross-account use;
- resource policies allow only a documented action subset;
- an AWS-managed Kinesis KMS key cannot be shared cross-account, so an encrypted stream must use a compatible customer-managed key and key policy;
- service and federated principals are not accepted in KDS resource policies.

## Configuration and destructive controls

Live exact-resource mutations and restorations:

- retention `24 -> 48 -> 24` hours;
- all enhanced shard metrics enabled, then disabled;
- maximum record size `1024 -> 2048 -> 1024` KiB;
- encryption `NONE -> KMS (alias/aws/kinesis) -> NONE`;
- shard count `1 -> 2 -> 1` open shards;
- stream mode `PROVISIONED -> ON_DEMAND`, followed by deletion.

The mutations are asynchronous. A response does not mean `DescribeStreamSummary` immediately reflects the final value, and another update can return `ResourceInUseException` while status is `UPDATING`.

Security impact:

- lower retention deletes access to records outside the new window;
- shard/mode/warm-throughput/account-setting changes can cause cost or availability impact;
- maximum-record-size changes can break producers/consumers or permit much larger poison payloads;
- disabling enhanced monitoring removes shard-level visibility but not base stream metrics;
- encryption/key changes can weaken protection for future records or create KMS-dependent denial of service;
- stream deletion destroys all shards and retained data.

`UpdateAccountSettings` was deliberately not invoked. The account was verified `DISABLED` before and after because enabling minimum-throughput billing has a commitment window and would violate cleanup/cost discipline. It remains a high-confidence cost-abuse candidate from the public API contract.

## New channel / PassRole attack path

The latest KDS API adds channels for continuous S3 or S3 Tables delivery. The installed AWS CLI 2.34.45 lacked these operations, so a temporary current boto3/botocore environment was used.

The first least-privilege attempts established these boundaries:

1. adding tags caused an explicit `kinesis:TagResource` denial on `channel/*`;
2. granting `CreateChannel` only on the stream ARN caused an explicit denial on `arn:aws:kinesis:us-east-1:228478051196:channel/*`;
3. a freshness value of 60 passed IAM but was rejected by validation; the allowed range is 300-900 seconds;
4. this minimum caller policy created the channel:

```json
{
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "kinesis:CreateChannel",
      "Resource": "arn:aws:kinesis:us-east-1:228478051196:channel/*"
    },
    {
      "Effect": "Allow",
      "Action": "kinesis:AssociateStreamsWithChannel",
      "Resource": "arn:aws:kinesis:us-east-1:228478051196:stream/htx-kds-channel-20260927"
    },
    {
      "Effect": "Allow",
      "Action": "iam:PassRole",
      "Resource": "arn:aws:iam::228478051196:role/HTKDSChannelAuditRole20260927",
      "Condition": {
        "StringEquals": {"iam:PassedToService":"kinesis.amazonaws.com"}
      }
    }
  ]
}
```

The caller session had no `GetRecords` permission. The channel reached `ACTIVE` and used the passed role for S3 delivery. Three objects were created before deletion. Direct downloads confirmed the original `channel-exfil-secret-20260927` marker and a 100-record `channel-exfil-batch-*` set. The first small object appeared roughly 12 minutes after its record was written even though freshness was configured to 300 seconds, so operators should not treat the configured interval as an exact flush deadline during a newly created, tiny test workload.

This is an expected privilege-escalation and persistence path: channel control plus a passable destination role becomes access to all **future** source records. It does not backfill older records.

General-purpose S3 delivery supports a destination bucket in another account, making this a direct exfiltration primitive when the role and bucket policy allow the attacker bucket. The source stream and channel must be same-account/same-Region. S3 Tables destinations are same-account/same-Region.

## CloudTrail evidence

Event History contained management events for the control-plane tests, including:

```text
RegisterStreamConsumer
PutResourcePolicy / GetResourcePolicy / DeleteResourcePolicy
IncreaseStreamRetentionPeriod / DecreaseStreamRetentionPeriod
EnableEnhancedMonitoring / DisableEnhancedMonitoring
UpdateMaxRecordSize
StartStreamEncryption / StopStreamEncryption
UpdateShardCount
UpdateStreamMode
CreateChannel
```

Failed control requests were logged too. The rejected wildcard policy event had:

```json
{
  "eventName": "PutResourcePolicy",
  "eventType": "AwsApiCall",
  "managementEvent": true,
  "readOnly": false,
  "errorCode": "InvalidArgumentException",
  "errorMessage": "...resource policy cannot contain invalid actions: [kinesis:Put*]"
}
```

Event History returned zero matching events for the live `PutRecord`, `GetShardIterator`, and `GetRecords` operations. That is expected because those are Kinesis **data events**, which are disabled by default. Current CloudTrail selectors support:

- `AWS::Kinesis::Stream` for stream data-plane activity;
- `AWS::Kinesis::StreamConsumer` for registered-consumer activity.

This distinction is important: the KDS service guide broadly says CloudTrail captures the APIs, but an ordinary Event History view does not reveal record theft or injection.

## Rejected and deferred hypotheses

| Hypothesis | Result |
| --- | --- |
| Unsigned stream describe/recon | Rejected |
| Shard iterator alone is a bearer token | Rejected; caller still needs `GetRecords` on the encoded stream |
| Iterator can bypass resource scoping with permission on another stream | Rejected |
| Wildcard KDS resource-policy actions | Rejected by policy validation |
| Wildcard KDS resource-policy principal | Rejected by policy validation |
| Resource-policy write silently unlogged | Rejected; success and failure are management events |
| Registering a consumer alone grants read access | Rejected; `SubscribeToShard` is separately consumer-scoped |
