# AWS Resource Groups and Tagging API security audit — 2026-09-26

## Scope and result

Reviewed cross-service tag reads, generic tag writes, Resource Groups query behavior, organization-wide tag-policy reports, CloudTrail visibility, and the previously researched tag-sync role path.

Main results:

1. `tag:GetResources` alone is a cross-service resource-ARN and complete tag-value oracle; it does not require target-service enumeration access.
2. `tag:GetTagKeys`/`GetTagValues` independently disclose the Regional tag dictionary and values, but not resource ARNs.
3. `GetResources` CloudTrail events expose request filters but omit returned ARNs/tags.
4. `tag:StartReportCreation` is a high-confidence organization-wide metadata exfiltration path from a management account to a policy-enabled cross-account S3 bucket. The lab is not the organization primary account, so the safe probe reached and confirmed that boundary.
5. `tag:TagResources` is not a native-service authorization bypass: it additionally enforced `ssm:AddTagsToResource` in a live test.
6. The previously reviewed `StartTagSyncTask` role path remains excluded because `iam:PassRole` is enforced and the workflow can only maintain the AppRegistry membership tag.
7. No unexpected AWS malfunction or zero-day was found.

## Experiment A — `tag:GetResources` only

The role policy contained only:

```json
{
  "Effect": "Allow",
  "Action": "tag:GetResources",
  "Resource": "*"
}
```

Results:

- `ssm:DescribeParameters` failed with identity-policy `AccessDeniedException`.
- `GetResources` filtered on `HtTaggingAudit=unique-20260926` succeeded.
- It returned `arn:aws:ssm:us-east-1:228478051196:parameter/ht-tagging-audit-20260926` and both complete tags.
- `GetTagKeys` independently failed because the role did not have `tag:GetTagKeys`.

Conclusion: `GetResources` is independently sufficient and does not authorize through the target service.

## Experiment B — tag-dictionary actions only

The role policy was replaced with only `tag:GetTagKeys` and `tag:GetTagValues`. `GetTagValues --key HtTaggingAudit` returned `unique-20260926`, while `GetResources` was denied. These are weaker but useful discovery permissions when an organization uses descriptive or sensitive tag values.

## Experiment C — generic write dependency

With only `tag:TagResources`, the API returned a per-resource failure:

```text
AccessDeniedException: ... is not authorized to perform: ssm:AddTagsToResource
```

After adding `ssm:AddTagsToResource` on the exact parameter ARN, the same generic request returned an empty `FailedResourcesMap`, and native SSM tag listing confirmed `GenericPlusNative=works`.

Conclusion: do not document generic tagging permission as a universal tag-write or ABAC bypass. The target service's native tag authorization is still enforced.

## Experiment D — organization report boundary

An administrator safely called `StartReportCreation` in `us-east-1` with a unique nonexistent bucket. The request reached the service and failed:

```text
AccessDeniedException: The caller is not the primary account of the Organization.
```

Official API documentation establishes the remaining behavior and prerequisites:

- callable only by the management account in `us-east-1`;
- tag-policy service integration and an attached policy are required;
- report covers tagged resources across organization accounts;
- destination can be a different account's bucket when its policy grants delivery;
- output path is `AwsTagPolicies/<org-id>/<timestamp>/report.csv`.

This is an expected-feature exfiltration path, not a vulnerability. The lab lacks the required management-account context, so no report or bucket was created.
