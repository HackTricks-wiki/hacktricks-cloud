## Current API and IAM inventory

AWS CLI 2.34.45 and botocore 1.43.103 expose 25 API operations:

| Group | Operations | Resource authorization |
| --- | --- | --- |
| Scope control | `CreateScope`, `GetScope`, `UpdateScope`, `DeleteScope`, `ListScopes` | Create/list use `*`; get/update/delete use exact scope ARN |
| Monitor control | `CreateMonitor`, `GetMonitor`, `UpdateMonitor`, `DeleteMonitor`, `ListMonitors` | List uses `*`; other actions use exact monitor ARN, including the prospective ARN for create |
| Workload queries | `StartQueryWorkloadInsightsTopContributors`, `GetQueryStatusWorkloadInsightsTopContributors`, `GetQueryResultsWorkloadInsightsTopContributors`, and the corresponding `...Data` trio, plus both stop actions | Exact scope ARN |
| Monitor queries | `StartQueryMonitorTopContributors`, `GetQueryStatusMonitorTopContributors`, `GetQueryResultsMonitorTopContributors`, `StopQueryMonitorTopContributors` | Exact monitor ARN |
| Tags | `ListTagsForResource`, `TagResource`, `UntagResource` | Exact scope or monitor ARN as documented |
| Agent ingest | permission-only `networkflowmonitor:Publish` | `*`; no public CLI operation |

Resource ARNs:

```text
arn:aws:networkflowmonitor:REGION:ACCOUNT:scope/SCOPE_ID
arn:aws:networkflowmonitor:REGION:ACCOUNT:monitor/MONITOR_NAME
```

Network Flow Monitor supports identity policies, resource scoping and partial ABAC, but no resource-based policies or ACLs. The Service Authorization Reference documents only `aws:RequestTag/*`, `aws:ResourceTag/*` and `aws:TagKeys` service-relevant conditions.

### Query result sensitivity

Monitor top-contributor results can include:

- local/remote IP addresses, instance IDs and ARNs;
- local/remote VPC and subnet IDs/ARNs, Region and Availability Zone;
- SNAT and DNAT addresses, target port and destination category;
- traversed component IDs/types/ARNs and AWS service names;
- local/remote Kubernetes service, pod and namespace names;
- transferred bytes, timeouts, retransmissions or round-trip-time values.

Scope workload results can include account ID, local VPC/subnet/AZ/Region, remote identifier, resource ARNs and metric values. The related data query returns timestamp/value series and topology labels. Workload queries accept timeouts, retransmissions and transferred bytes; monitor queries additionally accept round-trip time.

## Official-source findings selected for public documentation

### 1. Topology and flow reconnaissance through query APIs

High value. Exact scope/monitor query permissions reveal infrastructure and communication metadata without corresponding direct EC2/VPC/EKS read permissions. Monitor results are especially sensitive because they include internal IPs, target ports, NAT translations, traversed constructs and Kubernetes names.

Logging nuance: start/status/result/stop query APIs are CloudTrail **data events**, not management events. They are absent from Event history and are not logged unless a trail explicitly includes `AWS::NetworkFlowMonitor::Scope` and/or `AWS::NetworkFlowMonitor::Monitor`. Discovery list/get operations remain normal management events. Public stealth rating: high by default, lower where data selectors exist.

### 2. Retarget an existing monitor / expand an Organizations scope

High value when combined with query permissions. `UpdateMonitor` can add sensitive resources already in the scope without EC2/EKS describe rights. `UpdateScope` in an Organizations management/delegated-administrator account can add organization member Region/account pairs; IAM permission alone is insufficient because CloudWatch trusted access and service-side Organizations checks apply. Both updates are logged management events.

### 3. Console-only `NetworkFlowMonitorAccountResourceAccess` cross-account role

Distinct service-specific lateral read path. AWS instructs each member account to create this role, trust the monitoring account and attach `AmazonEC2ReadOnlyAccess`; optional EKS console visibility adds broad EKS reads and `eks:AccessKubernetesApi`. A principal admitted by the trust policy and allowed `sts:AssumeRole` can use it independently of the Network Flow Monitor console. Kubernetes RBAC remains a separate boundary.

### Agent package and `Publish` validation

The official current x86_64 RPM was downloaded only to `/tmp` and inspected statically:

- Package SHA-256: `5823d03284f35ade883b922247e642fdcd3a5fe9ecb5d8c8488d951074265224`.
- Embedded agent version/build: `1.1.7`, `2026-07-22T08:42:08Z`.
- Default endpoint constructed by the start script: `https://networkflowmonitorreports.REGION.api.aws/publish`.
- Content type: `application/x-protobuf`; reports may be gzip-compressed.
- Agent reports contain network statistics, flow properties, host/usage statistics and optional Kubernetes metadata.

An unsigned empty POST returned HTTP 403. A SigV4-signed empty protobuf using the administrator role returned HTTP 200. To establish the exact permission boundary, a temporary role was then created with only:

```json
{
  "Effect": "Allow",
  "Action": "networkflowmonitor:Publish",
  "Resource": "*"
}
```

The same empty request returned HTTP 200 (`Request processed successfully`). The inline policy and temporary role `ht-nfm-publish-audit-20260927` were immediately deleted; `iam get-role` confirmed absence.

This confirms that `Publish` is not bound to EC2/EKS principal type and that the ingestion endpoint accepts an empty/default protobuf. It does **not** demonstrate visible metric injection, attribution spoofing or monitoring disruption. It is therefore retained as a future-test hypothesis rather than a public attack technique or private vulnerability report.

## Negative results and exclusions

- **No unauthenticated page:** SigV4 is required, no resource-based policies exist, and known identifiers do not cross the caller-account boundary.
- **No direct privilege-escalation page:** Network Flow Monitor has no user-selectable execution role or credential-vending API. Service-linked roles have fixed service-only trust.
- **No persistence page:** scopes and monitors persist observability configuration, not attacker access. Deleting or blinding a monitor is destructive post-exploitation, not credential/account persistence.
- **No generic delete technique:** `DeleteMonitor`/`DeleteScope` are obvious logged denial-of-observability actions and add little value beyond their names.
- **No public telemetry-injection technique:** acceptance of an empty protobuf proves only authorization/format behavior, not a useful integrity impact.
- **No cross-account resource policy technique:** the service explicitly does not support resource-based policies. Cross-account scope behavior is Organizations-controlled.
- **Plural query names:** current CloudTrail documentation lists `*MonitorsTopContributors` plural operations, but the current CLI, latest botocore model, API reference search and Service Authorization Reference expose only singular `*MonitorTopContributors`. Treated as documentation/internal-model drift, not a callable attack surface.
- **`Publish` CloudTrail:** AWS's Network Flow Monitor CloudTrail page lists control-plane management events and query data events but does not list `Publish`. This is unsurprising for a 30-second agent ingestion stream and was not treated as a defect.
