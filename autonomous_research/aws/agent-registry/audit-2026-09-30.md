# AWS Agent Registry audit — 2026-09-30

## Scope and current model

- Audited the GA `agent-registry-control` and `agent-registry` namespaces in AWS CLI 2.37.6, the current developer guide and the Service Authorization Reference.
- AWS Agent Registry is distinct from the broader AgentCore runtime/gateway surface already covered in the book. It catalogs MCP servers, agents, skills and custom resources, with registry-level authorization/approval and record-level revision state.
- The older public-preview registry namespace under `bedrock-agentcore` is scheduled for discontinuation on 2026-10-30.
- `CreateRegistryRecord` is scoped to the registry ARN. `Get/Update/Delete/Submit/UpdateStatus` are scoped to the exact registry-record ARN.
- URL-backed record creation/update can depend on AgentCore Identity workload/token actions or `iam:PassRole` to `agent-registry.amazonaws.com`. This was not generalized to ordinary inline custom descriptors.

## Live results

Account `228478051196`, `us-east-1`; all content was synthetic and inert.

1. Initial `ListRegistries` returned an empty inventory.
2. Created one IAM-authorized registry with manual approval (`autoApprovalRules: []`) and one `CUSTOM` record whose only endpoint used the non-routable `example.invalid` domain.
3. Submitted the record and confirmed it reached `PENDING_APPROVAL`.
4. Assumed the authorized administrator role with a session policy allowing only `agent-registry:UpdateRegistryRecordStatus` on the exact record ARN. That session successfully changed the record to `APPROVED`; it had no record create/update/read, registry update or discovery permission.
5. Discovery immediately listed the approved record.
6. Assumed a second session allowing only exact-record `agent-registry:UpdateRegistryRecord`. It changed the description and custom descriptor. The control plane returned a new `DRAFT`, while discovery correctly continued serving the previous approved description/revision. This is a secure negative result: update-only access did not bypass review.
7. Assumed a third session allowing only `agent-registry:UpdateRegistry` on the exact registry ARN. It replaced the approval configuration with `APPROVE_ALL`.
8. Assumed a fourth session allowing only `agent-registry:SubmitRegistryRecordForApproval` on the exact record ARN. Submitting the new draft immediately returned `APPROVED`; discovery then served the unreviewed replacement revision.

These results support two public techniques:

- exact-record status approval as a curation/supply-chain post-exploitation primitive; and
- exact-registry `APPROVE_ALL` as durable governance weakening that converts future publisher submissions into automatically discoverable revisions.

Neither action itself executes a tool, forces a consumer to use a record, or grants AWS IAM privileges.

## Telemetry

- `CreateRegistry`, `CreateRegistryRecord` and `UpdateRegistryRecord` appeared as default CloudTrail management writes.
- Events identified the registry/record resource, caller and state-changing structure.
- CloudTrail replaced record name, description and descriptor payload fields with `HIDDEN_DUE_TO_SECURITY_REASONS`; defenders cannot rely on CloudTrail to reconstruct the malicious descriptor.
- `UpdateRegistryRecord` identified the record resource by short record ID in the observed `resources` entry even though its response returned the full ARN.
- Event History later indexed the restricted calls exactly: `UpdateRegistryRecordStatus` retained the IDs and `APPROVED` target while redacting the reason; `UpdateRegistry` retained `APPROVE_ALL`; and the submit-only event returned `APPROVED`. Record events used the short record ID—not its full ARN—as the observed CloudTrail `resources[].ResourceName`.
- Discovery APIs are opt-in CloudTrail data events. EventBridge emits registry/record lifecycle events and is the better near-real-time approval signal.

## Follow-up hypotheses

Private candidates; do not publish as techniques unless verified:

- **Credential-provider replay / redirect:** determine whether an exact-record updater can replace a synchronized source URL, replay an existing OAuth provider ARN or IAM role from `GetRegistryRecord`, and trigger synchronization without the documented AgentCore Identity token permissions or `iam:PassRole`. Any OAuth test must use a wholly synthetic token and controlled endpoints that record only header presence/hash, never raw credentials.
- **Cross-registry identifier confusion:** attempt exact-record operations with mismatched registry and record identifiers, including ARN-versus-short-ID combinations.
- **Provenance/auto-detection boundary:** verify that non-service callers cannot create or refresh provenance, mutate source identity or convert an auto-detected record into a caller-controlled record.
- **Resource-policy account binding:** investigate the permission-only `Put/Get/DeleteResourcePolicy` actions used by organization workflows and the `RecordCreatorAccount` / `RecordSourceAccount` condition keys.
- **JWT configuration immutability:** verify that update operations cannot replace the documented immutable discovery URL or silently broaden authorizer semantics beyond the allowed patch model.
- **Search-ranking and content poisoning:** assess whether approved records can dominate semantic search or inject instructions into consumers. Treat this as consumer/application behavior, not an AWS vulnerability, unless the service violates a documented isolation guarantee.

No unexpected AWS vulnerability was established in this pass, so no private report was created.
