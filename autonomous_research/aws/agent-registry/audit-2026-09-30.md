# AWS Agent Registry audit — 2026-09-30

## Scope and current model

- Audited the GA `agent-registry-control` and `agent-registry` namespaces in AWS CLI 2.37.6, the current developer guide and the Service Authorization Reference.
- AWS Agent Registry is distinct from the broader AgentCore runtime/gateway surface already covered in the book. It catalogs MCP servers, agents, skills and custom resources, with registry-level authorization/approval and record-level revision state.
- The older public-preview registry namespace under `bedrock-agentcore` is scheduled for discontinuation on 2026-10-30.
- `CreateRegistryRecord` is scoped to the registry ARN. `Get/Update/Delete/Submit/UpdateStatus` are scoped to the exact registry-record ARN.
- URL-backed record creation/update can depend on AgentCore Identity workload/token actions or `iam:PassRole` to `agent-registry.amazonaws.com`. This was not generalized to ordinary inline custom descriptors.

## Live results

Account `228478051196`, `us-east-1`; all content was synthetic and inert.

1. Initial `ListRegistries` returned an empty inventory.
2. Created one IAM-authorized registry with manual approval (`autoApprovalRules: []`) and one `CUSTOM` record whose only endpoint used the non-routable `example.invalid` domain.
3. Submitted the record and confirmed it reached `PENDING_APPROVAL`.
4. Assumed the authorized administrator role with a session policy allowing only `agent-registry:UpdateRegistryRecordStatus` on the exact record ARN. That session successfully changed the record to `APPROVED`; it had no record create/update/read, registry update or discovery permission.
5. Discovery immediately listed the approved record.
6. Assumed a second session allowing only exact-record `agent-registry:UpdateRegistryRecord`. It changed the description and custom descriptor. The control plane returned a new `DRAFT`, while discovery correctly continued serving the previous approved description/revision. This is a secure negative result: update-only access did not bypass review.
7. Assumed a third session allowing only `agent-registry:UpdateRegistry` on the exact registry ARN. It replaced the approval configuration with `APPROVE_ALL`.
8. Assumed a fourth session allowing only `agent-registry:SubmitRegistryRecordForApproval` on the exact record ARN. Submitting the new draft immediately returned `APPROVED`; discovery then served the unreviewed replacement revision.

These results support two public techniques:

- exact-record status approval as a curation/supply-chain post-exploitation primitive; and
- exact-registry `APPROVE_ALL` as durable governance weakening that converts future publisher submissions into automatically discoverable revisions.

Neither action itself executes a tool, forces a consumer to use a record, or grants AWS IAM privileges.

## Telemetry

- `CreateRegistry`, `CreateRegistryRecord` and `UpdateRegistryRecord` appeared as default CloudTrail management writes.
- Events identified the registry/record resource, caller and state-changing structure.
- CloudTrail replaced record name, description and descriptor payload fields with `HIDDEN_DUE_TO_SECURITY_REASONS`; defenders cannot rely on CloudTrail to reconstruct the malicious descriptor.
- `UpdateRegistryRecord` identified the record resource by short record ID in the observed `resources` entry even though its response returned the full ARN.
- Event History later indexed the restricted calls exactly: `UpdateRegistryRecordStatus` retained the IDs and `APPROVED` target while redacting the reason; `UpdateRegistry` retained `APPROVE_ALL`; and the submit-only event returned `APPROVED`. Record events used the short record ID—not its full ARN—as the observed CloudTrail `resources[].ResourceName`.
- Discovery APIs are opt-in CloudTrail data events. EventBridge emits registry/record lifecycle events and is the better near-real-time approval signal.

## Controlled synchronization credential-replay test

The highest-priority private hypothesis was that an exact-record updater might redirect a previously configured outbound credential without the dependent permission that originally authorized it.

The controlled harness used:

- one synthetic MCP responder behind an `AWS_IAM` Lambda Function URL and one role trusted only by `agent-registry.amazonaws.com`;
- one public synthetic OAuth endpoint that returned a non-production bearer token and logged only the authorization scheme plus a SHA-256 prefix;
- one external Secrets Manager secret containing a synthetic OAuth client secret; and
- separate `/a` baseline and `/b` redirect paths. No raw authorization header, access token or client secret was logged.

Results:

1. The administrator baseline successfully synchronized through `/a`. The OAuth endpoint observed one client-credentials token request and MCP requests carrying the same synthetic Bearer-header hash, proving the harness.
2. A session with only exact-record `UpdateRegistryRecord` could not reuse the existing IAM signing role. The API synchronously returned `AccessDeniedException` for `iam:PassRole`, left the `/a` source unchanged and made no `/b` request.
3. An OAuth update behaves differently: exact-record `UpdateRegistryRecord` accepted a replacement `/b` URL/provider ARN and returned `UPDATING`, but asynchronous synchronization changed to `UPDATE_FAILED` because the caller lacked `bedrock-agentcore:GetWorkloadAccessToken`. No token endpoint or `/b` request occurred.
4. Adding only the observed workload-token resources advanced authorization to an exact `bedrock-agentcore:GetResourceOauth2Token` denial. The current service evaluated the registry workload identity/directory and provider/token-vault resources; omission of any evaluated resource produced an explicit asynchronous denial.
5. With an externally managed provider secret, the caller context additionally required `secretsmanager:GetSecretValue` on that exact secret. The restricted session lacked it, synchronization failed, and `/b` again received nothing.

Conclusion: credential redirect/replay is **closed as a secure negative**. The URL/source configuration itself can change before asynchronous OAuth authorization fails, which can cause a failed draft/synchronization state, but the service did not send a bearer token or make a credentialed request without every downstream permission. The public enum page now warns that an accepted `UPDATING` response is not proof of credential use.

## Cross-registry identifier confusion test

Two isolated registries each held one inert custom DRAFT record. Record A was addressed through registry B, and record B through registry A, using both short record IDs and complete record ARNs.

- An administrator using a mismatched short ID received `ResourceNotFoundException`; no record was resolved globally outside the supplied registry.
- A complete record ARN whose embedded registry disagreed with the path received `ValidationException: Registry ID mismatch between path and record ARN`.
- A restricted session allowed only `GetRegistryRecord` and `UpdateRegistryRecord` on record A's exact ARN. With registry B plus record A's short ID, authorization evaluated the synthetic B/record-A ARN and denied both actions. With record A's complete ARN, the service rejected the registry mismatch.
- Record A retained its original descriptor, null description and `DRAFT` status after all read/write attempts.

Cross-registry IDOR/identifier confusion is therefore **closed as a secure negative** for current `GetRegistryRecord` and `UpdateRegistryRecord`, across short-ID and full-ARN forms.

## JWT discovery-authorization mutation

A controlled Lambda Function URL served two inert OpenID Connect discovery documents (`/oidc-a` and `/oidc-b`). A registry was created with `CUSTOM_JWT`, the `/oidc-a` discovery URL and `allowedClients: ["trusted-client"]`.

- The SDK model accepts a complete replacement authorizer object, but an exact-registry `UpdateRegistry` session attempting to replace `/oidc-a` with `/oidc-b` received `ValidationException: Changing discoveryUrl is not allowed`. The `/oidc-b` endpoint was never contacted. Issuer replacement is closed as a secure negative.
- A second session with only `agent-registry:UpdateRegistry` on the exact registry ARN retained `/oidc-a` and replaced `allowedClients` with `["attacker-client"]`. The registry reached `READY` with that configuration.
- `authorizerType` is absent from the update shape, so the same API cannot switch an IAM registry to JWT or vice versa.
- CloudTrail retained both outcomes: the failed request recorded the replacement URL/client and `ValidationException`; the successful management write recorded the exact client allowlist in request and response, the short registry ID in `resources`, and `UPDATING` state.

This supports a bounded public persistence technique: a controlled client registered at the **existing** IdP can be made trusted for registry discovery after the AWS session is lost. It does not substitute an attacker issuer, grant control-plane permissions or prove access without a valid IdP-signed JWT.

## Follow-up hypotheses

Private candidates; do not publish as techniques unless verified:

- **Provenance/auto-detection boundary:** verify that non-service callers cannot create or refresh provenance, mutate source identity or convert an auto-detected record into a caller-controlled record.
- **Resource-policy account binding:** investigate the permission-only `Put/Get/DeleteResourcePolicy` actions used by organization workflows and the `RecordCreatorAccount` / `RecordSourceAccount` condition keys.
- **Search-ranking and content poisoning:** assess whether approved records can dominate semantic search or inject instructions into consumers. Treat this as consumer/application behavior, not an AWS vulnerability, unless the service violates a documented isolation guarantee.

No unexpected AWS vulnerability was established in this pass, so no private report was created.
