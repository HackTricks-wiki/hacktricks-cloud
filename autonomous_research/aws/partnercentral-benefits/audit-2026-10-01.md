# Partner Central Benefits API audit — 2026-10-01

## Result

Published the missing `partnercentral-benefits` inventory and three material expected paths:

1. `GetBenefitAllocation` returns literal AWS promotional credit codes plus account/value/status/expiry, or cash/consumable/access fulfillment details.
2. `GetBenefitApplication` returns benefit-specific JSON, workflow reasons, Partner contact PII, related resource ARNs and supporting-file metadata.
3. Exact-application writes can amend a credit destination, replace a draft, recall/update/resubmit an early-review request, or permanently cancel an application. AWS's guide explicitly uses `$.CreditDisbursementDetails.AwsAccountIdForCredits` as an amendment example.

These are expected Partner-benefit read/write capabilities, not AWS defects. No private report was created for this service.

## Current control plane

- CLI/SDK client: `partnercentral-benefits`; API model version `2018-05-10`.
- IAM prefix: `partnercentral`.
- Live endpoint: `partnercentral-benefits.us-east-1.api.aws`; no reachable `eu-west-1` endpoint.
- CloudTrail source: `partnercentral-benefits.amazonaws.com` in `us-east-1`.
- 17 operations cover catalog discovery, application lifecycle/resource association, allocation reads and tags.
- Primary resource families: accountless catalog Benefit definitions and account-owned Benefit Application/Allocation ARNs.

## Live result and enrollment boundary

Unsigned `ListBenefits` returned `MissingAuthenticationTokenException`. Signed administrator calls for Benefits, Applications and Allocations in both `AWS` and `Sandbox` reached the endpoint but returned the service-side active-benefit gate:

```text
AccessDeniedException: This action requires an active AWS partner benefit.
Register as an AWS partner if you haven't already, or contact AWS partner central support.
```

A disposable principal was granted `GetBenefitAllocation` on exactly one synthetic allocation ARN. Both that identifier and a different identifier returned the same enrollment error, so the service checks active-benefit state before the lab can observe resource-level authorization. Public text does not claim a live exact-ARN success/denial; it uses the current Service Authorization Reference and AWS-managed policy patterns for that boundary.

A correctly shaped `AmendBenefitApplication` against a synthetic application ID, including client token, revision, reason and the documented credit-account field path, stopped at the same enrollment gate. No application or mutation was created.

## Security-relevant response contract

Current AWS documentation/model explicitly defines:

- `CreditDetails.Codes[].AwsCreditCode` as the actual credit-code string redeemable in the AWS billing console, alongside `AwsAccountId`, amount/currency, status, issue time and expiry;
- cash disbursement amounts and issuance IDs/timestamps;
- consumable allocated/remaining/utilized amounts;
- application details as arbitrary benefit-specific JSON;
- contact email/name/phone/title, file URI/name/status/uploader, associated AWS resource ARNs, workflow stage/reasons and revision; and
- draft-only full updates, early-review recall, JSON-path amendments, final cancellation and comprehensive validation on submission.

The managed `PartnerCentralIncentiveBenefitManagement` policy v4 grants the complete Benefits lifecycle over `benefit/*`, `benefit-application/*`, and `benefit-allocation/*`, conditioned on `Catalog` being `AWS` or `Sandbox`. It also grants narrowly scoped ephemeral-file S3 writes and the Marketplace/Opportunity reads needed by the workflow.

## Telemetry

Enrollment-gate failures were default management reads under `partnercentral-benefits.amazonaws.com`, `readOnly:true`, with `requestParameters:null`. `ListBenefits` still populated the `resources` list with the catalog-specific accountless `benefit/*` ARN and hid the resource account ID. This means failure detections should not require request parameters.

The correctly shaped amendment call appeared as a management write with `readOnly:false`; the enrollment failure again used `requestParameters:null`. No successful write/response telemetry is claimed because the account is not enrolled.

## Deferred validation

Retest in a reversible enrolled Partner sandbox when available:

- successful exact/allocation-family resource scoping and the `Catalog`, `FulfillmentTypes`, `Programs`, and tag conditions;
- whether active credit codes are account-bound at redemption and whether code reads trigger any additional notification;
- whether file URIs are bare S3 locations or time-limited capabilities and what independent authorization they require;
- the permitted amendment stages/paths for each benefit schema and reviewer visibility;
- contact/file/destination replacement through draft update and recall/update/resubmit; and
- permanent cancellation recovery/support behavior.

Do not create a production application solely for testing: submissions can trigger external review, funding workflows and records that cannot be deleted.
