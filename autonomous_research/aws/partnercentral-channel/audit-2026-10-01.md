# Partner Central Channel API audit — 2026-10-01

## Result

Published the missing `partnercentral-channel` inventory and four material expected paths:

1. PMA, relationship and handshake reads map reseller/customer AWS account topology and billing-transfer terms.
2. A compromised enrolled Partner can attempt to add an attacker-controlled management/customer account and complete the target-side PMA handshake to divert program benefits or discounts.
3. Exact-handshake decisions can activate, reject or cancel PMA/service-period agreements; service-period handshakes govern minimum-notice or fixed billing-transfer commitments.
4. Exact relationship/PMA writes can change requested support configuration or remove accounts/relationships from resale programs.

These are expected Channel control-plane capabilities with explicit mutual-consent and business-state boundaries, not AWS defects. No private report was created for this service.

## Current control plane

- CLI/SDK client: `partnercentral-channel`; API model version `2024-03-18`.
- IAM prefix: `partnercentral`.
- Commercial endpoint: `partnercentral-channel.global.amazonaws.com`; SigV4a preferred with SigV4 fallback to the partition implicit global Region.
- CloudTrail source: `partnercentral-channel.amazonaws.com`, indexed in `us-east-1`.
- 17 operations cover PMAs, relationships, three handshake types and tags.
- Resource families: Program Management Account, nested Relationship, and Channel Handshake ARNs.

## Live results

Unsigned PMA and relationship lists returned `MissingAuthenticationTokenException`.

With a confirmed assumed administrator session:

- all three handshake types listed successfully as both `SENDER` and `RECEIVER` in `AWS` and `Sandbox`, returning empty arrays;
- the same list worked with `us-east-1`, `eu-west-1` and `ap-southeast-2` Region input, confirming the global endpoint behavior;
- PMA and relationship lists in both catalogs returned the active-Partner-benefit gate; and
- correctly shaped PMA creation for this account in both catalogs returned `INCOMPATIBLE_BENEFIT_AWS_PARTNER_STATE` before creating a record.

The enrollment boundary is important: non-Partner target accounts still need handshake visibility so they can receive/decide invitations, whereas Partner-owned PMA/relationship state requires an active benefit.

## Least-privilege test

A disposable IAM user received only `partnercentral:ListChannelHandshakes`. With the documented concrete family ARN, even the intended list call was denied because no concrete resource existed to evaluate. Replacing it with `Resource: "*"` and both conditions:

```json
{
  "StringEquals": {
    "partnercentral:Catalog": "AWS",
    "partnercentral:ChannelHandshakeType": "PROGRAM_MANAGEMENT_ACCOUNT"
  }
}
```

allowed exactly `AWS` + `PROGRAM_MANAGEMENT_ACCOUNT`. The same principal was denied for `START_SERVICE_PERIOD` and for the `Sandbox` catalog. This is recorded as practical least-privilege guidance, not a vulnerability: list/discovery has no known resource identifier, so conditions are the meaningful boundary.

## Security-relevant contracts

- PMA activation and every service-period start/revocation require acceptance from the target AWS management account.
- An active PMA applies program benefits/discounts to invoices delivered to its associated management account.
- A relationship covers end-customer, downstream-seller or internal organization usage and carries AWS Partner Network metadata used for Channel discount qualification.
- Handshake summaries expose owner/sender/receiver account IDs, sender display name, resource ID, status and type-specific program or service-period details.
- Relationship create/update supports requested Resold Enterprise, Partner-Led Support or Resold Unified Operations configuration. The resold variants include optional charge-account IDs; coverage/provider/TAM fields are type-specific.
- Create relationship/handshake operations have dependent read permissions in the current service authorization table. Tags add a separate `TagResource` dependency.

## Telemetry

A successful empty `ListChannelHandshakes` appeared as a default management read with `requestParameters` containing handshake type, catalog, participant side and max results. CloudTrail stored `responseElements:null`, so absence of response data does not distinguish empty results. IAM-denied list calls were also management reads but used `requestParameters:null` and included the denial text.

Both valid PMA-create probes appeared as management writes with `readOnly:false`, `requestParameters:null`, `responseElements:null` and `AccessDenied`. No successful write event exists because enrollment stopped both requests. This means detections for enrollment-gate failures must not depend on request parameters or a resource list.

## Deferred validation

Retest in a reversible enrolled Partner sandbox when available:

- successful PMA creation, target-side `PROGRAM_MANAGEMENT_ACCOUNT` acceptance, activation timing and complete deletion dependency order;
- relationship creation for a lab-owned organization and whether discount qualification changes immediately or only after AWS validation;
- successful exact-resource list/get/update/delete authorization for PMAs and relationships;
- support-plan update review/application, charge-account constraints and rollback behavior;
- both service-period types, exact minimum/end-date rules, counterparty notifications and early-revocation recovery; and
- successful CloudTrail request/response redaction for every write.

Do not target an unrelated account or use a production Partner relationship. All live writes must use lab-owned accounts and be removed in dependency order after the observation.

## Cleanup

Both PMA creation attempts failed before resource creation. The three disposable IAM users, inline policies and access keys were deleted, and final `ht-pcc-*` matching user/role inventories were empty. Every final AWS/Sandbox handshake list also remained empty. No PMA, relationship, handshake, tag, billing transfer, support-plan change, invitation, discount, invoice or Partner Central record was created or changed.
