# AWS AppFlow security audit — 2026-09-26

## Scope and result

Reviewed current AppFlow book coverage, AWS API models, service-authorization metadata, official connector documentation, CloudTrail behavior, and low-cost live S3-to-S3 flows in `us-east-1`.

Main results:

1. `StartFlow` remains a real stored-authority execution primitive with only exact-flow `appflow:StartFlow` required at call time.
2. `CreateFlow` is stronger but its minimum-permission requirements were understated: S3 validation reads, KMS key enumeration/grant actions, and `UseConnectorProfile` for profile-backed connectors are important prerequisites.
3. `UpdateFlow` cannot repoint S3 buckets or prefixes, but it can change tasks/filters/mappings and triggers. This can remove field/record suppression or establish scheduled execution after a separate `StartFlow` activation.
4. `UpdateConnectorProfile` is the high-confidence connector-boundary persistence primitive: replace source or destination tenant credentials/properties while flows retain the same profile name.
5. AppFlow does not support cross-account S3 access. EventBridge support is partner-event-specific rather than an arbitrary cross-account bus destination.
6. No unexpected AWS vulnerability or zero-day was found. The changes are expected-feature abuse and defensive boundary corrections.

## Official authorization model

Current service-authorization metadata records these dependent actions:

| AppFlow operation | Resource scope | Documented dependent actions / boundary |
| --- | --- | --- |
| `CreateFlow` | `*` | `appflow:TagResource`, `appflow:UseConnectorProfile`, `iam:PassRole` when those request features are used |
| `UpdateFlow` | Exact flow ARN | `appflow:UseConnectorProfile`, `iam:PassRole` when applicable |
| `StartFlow` | Exact flow ARN | No dependent action listed |
| `CreateConnectorProfile` | `*` | `appflow:DescribeConnector`, `iam:PassRole` for role-bearing profiles |
| `UpdateConnectorProfile` | Exact profile ARN | `iam:PassRole` for role-bearing profiles |
| `UseConnectorProfile` | Exact profile ARN | Permission-only action used when a flow references a profile |

AppFlow does not support resource-based cross-account delegation for flows/profiles. Official IAM integration documentation reports no AppFlow service role or service-linked role. Individual connector configurations can still embed roles.

## Experiment A — S3 source/destination immutability under `UpdateFlow`

### Setup

Created one disposable S3-to-S3 flow and four disposable buckets so both prefix-only and bucket changes could be attempted. The low-privilege actor initially had only `appflow:UpdateFlow` on the exact flow.

### Results

Changing the destination prefix or bucket returned:

```text
ValidationException: Destination object for the destination connector can not be updated
```

Changing the source prefix or bucket returned:

```text
ValidationException: Do not update the object for the flow.
```

### Conclusion

The source and destination `bucketName`/`bucketPrefix` object is immutable for an existing S3 flow. Do not document `UpdateFlow` as an S3 endpoint-redirection primitive.

## Experiment B — task and trigger changes under `UpdateFlow`

### First attempt

`appflow:UpdateFlow` on the exact flow alone failed during AppFlow validation. The service error identified missing S3 list, location, and bucket-policy reads.

### Successful minimum tested policy shape

```json
{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "appflow:UpdateFlow",
      "Resource": "arn:aws:appflow:us-east-1:228478051196:flow/<test-flow>"
    },
    {
      "Effect": "Allow",
      "Action": "s3:ListAllMyBuckets",
      "Resource": "*"
    },
    {
      "Effect": "Allow",
      "Action": ["s3:ListBucket", "s3:GetBucketLocation", "s3:GetBucketPolicy"],
      "Resource": [
        "arn:aws:s3:::<source-bucket>",
        "arn:aws:s3:::<destination-bucket>"
      ]
    }
  ]
}
```

With those grants:

- Changing a `Map_all` task to add `EXCLUDE_SOURCE_FIELDS_LIST=secret` succeeded.
- `DescribeFlow` showed the changed task plus AppFlow-derived mapping/filter tasks.
- The flow remained `Active` after the task-only update.
- Changing the trigger from `OnDemand` to `Scheduled` with `rate(1days)` succeeded but moved the flow to `Draft`.
- It did not become recurring automatically. A caller needs `appflow:StartFlow` to activate the scheduled flow.

### Security interpretation

`UpdateFlow` can remove an existing exclusion/filter and send a broader dataset to the existing destination. This is meaningful only if that destination is attacker-readable or creates a useful downstream effect. Task/mapping changes can also poison downstream interpretation. Trigger mutation plus `StartFlow` provides flow-level persistence.

## Experiment C — `CreateFlow` validation and KMS dependencies

### Attempt 1

The actor had:

- `appflow:CreateFlow` on `*`
- `appflow:StartFlow` on the known future flow ARN

S3-to-S3 creation failed, identifying the same direct S3 validation read family used by `UpdateFlow`.

### Attempt 2

After granting `s3:ListAllMyBuckets` and exact-bucket `ListBucket` / `GetBucketLocation` / `GetBucketPolicy`, creation failed again and explicitly listed:

```text
kms:ListKeys
kms:DescribeKey
kms:ListAliases
kms:CreateGrant
kms:ListGrants
```

### Successful policy addition

```json
[
  {
    "Effect": "Allow",
    "Action": ["kms:ListKeys", "kms:ListAliases"],
    "Resource": "*"
  },
  {
    "Effect": "Allow",
    "Action": ["kms:DescribeKey", "kms:ListGrants"],
    "Resource": "arn:aws:kms:us-east-1:228478051196:key/<appflow-key-id>",
    "Condition": {
      "StringLike": {"kms:ViaService": "appflow.*.amazonaws.com"}
    }
  },
  {
    "Effect": "Allow",
    "Action": "kms:CreateGrant",
    "Resource": "arn:aws:kms:us-east-1:228478051196:key/<appflow-key-id>",
    "Condition": {
      "StringLike": {"kms:ViaService": "appflow.*.amazonaws.com"},
      "Bool": {"kms:GrantIsForAWSResource": "true"}
    }
  }
]
```

Creation then succeeded. The request omitted `kmsArn`; AppFlow used the account's default `alias/aws/appflow` key. This corrects the older conclusion that plain `CreateFlow` + `StartFlow` alone was the S3 minimum.

## Experiment D — CloudTrail telemetry

Live event inspection produced:

| API | Request visibility | Response visibility |
| --- | --- | --- |
| `CreateFlow` | `flowName` and trigger visible; source config, destination list, and tasks each replaced by `"***"` | Service response not useful for endpoint review |
| `UpdateFlow` | `flowName`/trigger visible; source config, destination list, and tasks each replaced by `"***"`; error messages visible | Limited |
| `StartFlow` | `flowName` visible | Live response contained `executionId`, `flowStatus`, and `flowArn` |
| `DescribeConnectorProfiles` | No identifying request parameters | Response omitted |

This means CloudTrail detects mutation/execution but cannot by itself explain the exact endpoint/task change. Defenders need `DescribeFlow` snapshots/diffs and profile inventory history. AppFlow also places flow execution/status reports on the default EventBridge bus; a rule/archive/consumer is required to retain/action them.

## Connector-profile boundary analysis

### Secret boundary

`DescribeConnectorProfiles` returns profile metadata and a `credentialsArn`, but not stored secret values. AWS documents that AppFlow stores connector credentials in a Secrets Manager secret with an `appflow` prefix and protects them with KMS. No claim is made that direct `GetSecretValue` yields a reusable plaintext SaaS credential; this was not tested and may include AppFlow-managed encoding/encryption.

### Metadata authority

`ListConnectorEntities` and `DescribeConnectorEntity` accept a connector profile name. With exact profile authorization, they can make AppFlow enumerate remote object names and schema using stored authority. This is a useful recon boundary, but generally weaker than the transfer/mutation techniques and was retained as enumeration rather than promoted to a standalone attack.

### Profile replacement

The `UpdateConnectorProfile` API accepts complete replacement connector properties and credentials. Because flows retain a profile-name reference:

- Replacing a destination profile can route later flow records to the attacker's valid SaaS tenant.
- Replacing a source profile can feed attacker-controlled data to existing destinations.

This is high-confidence from the API contract and connector model, but was not live-fired because the lab did not provide a disposable external SaaS tenant. The technique requires valid replacement credentials and passes connector validation. Redshift profiles add `iam:PassRole` constraints.

## Connector-specific and cross-account conclusions

### S3

- AppFlow and S3 bucket must be in the same account and Region.
- Source access is granted to `appflow.amazonaws.com` with bucket listing/object reads.
- Destination access is granted to the service principal for put/multipart/ACL-related operations.
- A direct attacker-owned external-account S3 bucket is not supported. An in-account bucket readable by an attacker is still a viable destination.

### Redshift

- Destination-only.
- Current Data API setup can include an AppFlow role, intermediate S3 bucket, and a Redshift role used to read staged content.
- Creating/updating such a profile can require `iam:PassRole` for AppFlow and Redshift service paths.
- Reusing an already stored profile in a flow requires `UseConnectorProfile`, not passing the roles again unless the flow request embeds another role such as Glue catalog metadata.

### Snowflake

- Destination-only.
- Uses an intermediate S3 stage and Snowflake `COPY`; the Snowflake integration needs stage access and KMS decryption when encrypted with a customer-managed key.
- The stored profile remains the main remote-account trust boundary.

### EventBridge

- AppFlow supports EventBridge as a destination for supported partner-event integrations such as Salesforce events.
- The partner source must be associated with an EventBridge event bus before activation.
- This is not a generic arbitrary cross-account bus selector.
- Payloads over 256 KB can be stored in S3 with an event pointer, introducing a separate bucket authorization boundary worth future testing.

## Candidate matrix

| Candidate | Expected permission/prerequisite | Result / disposition |
| --- | --- | --- |
| Execute existing flow | Exact `appflow:StartFlow` | Verified useful, fixed endpoints only |
| Create attacker-defined S3 flow | `CreateFlow`, future `StartFlow`, exact S3 validation reads, KMS list/describe/grant actions, valid bucket policies | Verified control-plane minimum shape; prior end-to-end transfer verified |
| Reuse stored SaaS profile | Add exact `UseConnectorProfile`; valid existing profile | High-confidence, external tenant precondition |
| Repoint existing S3 flow | `UpdateFlow` plus S3 validation reads | Blocked for bucket and prefix |
| Remove filter/exclusion task | `UpdateFlow` plus validation dependencies | Verified |
| Convert to scheduled persistence | `UpdateFlow` + `StartFlow` | Trigger update verified; requires separate activation |
| Replace connector profile tenant | Exact `UpdateConnectorProfile`; valid replacement credentials; connector-specific `PassRole` | High-confidence, not live-fired |
| Cross-account S3 exfiltration | External bucket | Not supported; excluded |
| Arbitrary EventBridge bus exfiltration | EventBridge destination | Hypothesis rejected; integration is partner-source-specific |
| Directly recover profile secret | Secret/KMS access | Not established; do not publish as credential exfiltration |
| Custom connector capture | Register/create profile/Lambda prerequisites | Deferred; needs separate safe custom-connector test |
