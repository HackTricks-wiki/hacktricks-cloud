# Amazon AppFlow security audit — 2026-09-27

## Scope and starting state

- Region/account: `us-east-1`, authorized account `228478051196`.
- Admin role: `arn:aws:iam::228478051196:role/ChackBotAdministratorRole`.
- Initial AppFlow state: no flows, no connector profiles and no account-owned custom connectors.
- Cost controls: only three general-purpose S3 buckets, tiny CSV objects, one AppFlow flow, four IAM roles and one Glue database were created. No SaaS subscription, Redshift/Snowflake resource, KMS customer key, VPC endpoint, gateway or paid long-lived infrastructure was used.
- Existing book coverage: none was found for AppFlow.

## Attack hypotheses

| Hypothesis | Expected class | Result |
| --- | --- | --- |
| `StartFlow` can exercise stored connector/S3 authority without direct data-plane permission | Expected post-exploitation | Confirmed |
| Exact-flow `UpdateFlow` can redirect the immutable destination to a different bucket/profile | Potential expected attack / defect if contrary to contract | Rejected; API and documentation enforce immutable source/destination |
| `UpdateFlow` can broaden mappings/filters and change an on-demand trigger into a recurring schedule | Expected post-exploitation/persistence | Confirmed |
| A blind S3 source writer can inject records that AppFlow propagates | Expected post-exploitation | Confirmed |
| Glue catalog role can be attached without `iam:PassRole` | Potential security defect | Rejected; explicit PassRole denial |
| With exact `iam:PassRole`, AppFlow can exercise Glue catalog authority the caller lacks directly | Expected bounded privilege escalation | Confirmed |
| Connector profile describe returns raw SaaS credentials | Potential security defect | Rejected by API schema/documentation; only profile properties and `credentialsArn` are returned |
| AppFlow exposes an unauthenticated native data/control endpoint | Unauthenticated-access hypothesis | Rejected; AppFlow APIs require SigV4, and SaaS/custom endpoints belong to their respective applications/functions |
| AppFlow flows/profiles have cross-account resource policies | Cross-account hypothesis | Rejected; no AppFlow resource-policy API. Underlying service/SaaS policies are the boundary, and AppFlow documents no cross-account S3 flow access |

## Verified results

### 1. On-demand service-principal transfer

The initial successful execution processed one record and wrote one S3 object. The first run intentionally failed because the task list omitted the required S3 `Filter` task with `connectorOperator.S3 = PROJECTION`; adding it produced:

```text
executionStatus: Successful
bytesProcessed: 896
bytesWritten: 66
recordsProcessed: 1
```

A principal with only `appflow:StartFlow` on the exact flow could start it. That principal's direct S3 list/read calls were denied, but AppFlow read and wrote through the service-principal bucket policies. This confirms that `StartFlow` is delegated data-plane authority, not a harmless scheduler action.

### 2. Destination redirect was rejected

An exact-flow updater tried to replace the destination bucket with the alternate bucket while preserving the connector type and tasks. AppFlow returned:

```text
ValidationException: Destination object for the destination connector can not be updated
```

AWS documentation also states that an existing flow's name, source and destination cannot be changed. Do not publish arbitrary redirect as an AppFlow `UpdateFlow` technique. A new flow is required.

### 3. S3 metadata validation dependency

For an S3 flow, `UpdateFlow` validated both buckets using the calling identity. The initial exact-bucket policy allowed direct calls to `ListBucket`, `GetBucketLocation` and `GetBucketPolicy`, plus global `ListAllMyBuckets`, but AppFlow still returned its generic bucket-validation denial.

Matching the AWS-managed `AmazonAppFlowFullAccess` shape—`s3:ListAllMyBuckets`, `s3:ListBucket`, `s3:GetBucketLocation`, `s3:GetBucketPolicy` with `Resource: "*"`—allowed the update. `s3:GetObject` remained denied. This is an important real least-privilege constraint and should be rechecked if AWS changes validation.

### 4. Recurring schedule persistence

The exact-flow updater changed the trigger to:

```json
{
  "triggerType": "Scheduled",
  "triggerProperties": {
    "Scheduled": {
      "scheduleExpression": "rate(1minutes)",
      "dataPullMode": "Complete",
      "flowErrorDeactivationThreshold": 100
    }
  }
}
```

The flow became `Draft`. A different role with only exact-flow `StartFlow` activated it. A new scheduled execution later appeared and processed records without the caller retaining credentials. The schedule was stopped immediately after confirmation.

### 5. Blind S3 source injection

The injector role had only:

```json
{
  "Effect": "Allow",
  "Action": "s3:PutObject",
  "Resource": "arn:aws:s3:::ht-appflow-audit-src-228478051196/input/*"
}
```

It uploaded `input/injected.csv`; its own `GetObject` was denied. The next flow execution reported `recordsProcessed: 2`, proving that the legitimate and attacker-written files were both ingested. The destination is fixed, but a production destination could be a SaaS application, warehouse, custom connector or downstream data lake.

### 6. Glue role PassRole enforcement and use

The updater attempted to add:

```json
{
  "glueDataCatalog": {
    "roleArn": "arn:aws:iam::228478051196:role/ht-appflow-audit-glue",
    "databaseName": "ht_appflow_audit_db",
    "tablePrefix": "ht_"
  }
}
```

Without `iam:PassRole`, `UpdateFlow` returned an explicit `AccessDenied` naming the role. After adding exact-role `PassRole` conditioned on `iam:PassedToService = appflow.amazonaws.com`, the update succeeded.

Catalog-enabled S3 output required `SCHEMA_VERSION` in `pathPrefixHierarchy`, and `EXECUTION_ID` was also required when a timestamp path format was present. Starting the flow from the exact-start role succeeded. Execution metadata reported:

```text
catalogType: GLUE
status: Successful
result: Created: 2, Updated: 0
```

Two generated Glue tables pointed at the versioned S3 output. Their `CreatedBy` values were AppFlow-assumed sessions of `ht-appflow-audit-glue`. The updater/starter had no direct Glue authority and never received role credentials.

This is bounded role-backed catalog access, not generic execution. Publish the precise impact (catalog creation/update/poisoning), not arbitrary role takeover.

## CloudTrail observations

All tested AppFlow calls appeared as management events in Event History:

| API | Logged request details |
| --- | --- |
| `CreateFlow` | Flow name, description and trigger visible; `sourceFlowConfig`, `destinationFlowConfigList` and `tasks` replaced with `***` |
| `UpdateFlow` | Flow name and trigger visible; source/destination/tasks `***`; Glue role/database/table prefix visible |
| `StartFlow` / `StopFlow` | Flow name, client token and resulting status/ARN visible |
| `DescribeFlow` / `DescribeFlowExecutionRecords` | Caller and flow name visible; successful response omitted |
| Failed `UpdateFlow` | Error class/message visible, including missing `iam:PassRole` target role and validation failures |

This redaction creates a detection gap for exact changed fields/tasks. Defenders should snapshot/diff `DescribeFlow`; CloudTrail alone cannot reconstruct the mapping/filter mutation.

S3 source/destination object activity is a separate data-event class and is not guaranteed in Event History. Flow execution records provided aggregate byte/record/error information and successful Glue catalog results.

## Connector-profile and custom-connector review

- `DescribeConnectorProfiles` output includes `credentialsArn` and connector-specific properties but not credential structures.
- `CreateConnectorProfile` is unscoped (`Resource: "*"`) and can require `DescribeConnector` plus `iam:PassRole` for AppFlow/Redshift role-backed profiles.
- `UpdateConnectorProfile` is exact-profile scoped and can replace properties/credentials, making it a strong profile-hijack/persistence action across referencing flows.
- `UseConnectorProfile` is a permission-only exact-profile action checked when a flow uses stored credentials.
- `RegisterConnector` is unscoped and registers a Lambda ARN. There is no passed role; the Lambda resource policy and connector handler authorization remain the security boundaries.
- No external SaaS account was available, so credential replacement, SaaS object reads/writes, OAuth token behavior and vendor audit logging were documented from current AWS API/service-authorization references rather than live-tested.

## Ideas rejected or not published as standalone attacks

- **Raw connector credential theft through AppFlow describe:** API does not return it. The credentials ARN alone is reconnaissance and requires independent Secrets Manager access that service-owned policies should deny.
- **UpdateFlow arbitrary source/destination redirect:** explicitly rejected and documented immutable.
- **Cross-account S3 destination:** AWS explicitly documents it as unsupported. Do not claim direct S3 exfil to an attacker account; use same-account readable buckets or an external SaaS/custom-connector profile when actually available.
- **Custom connector = automatic Lambda privilege escalation:** too broad. Registration/invocation depends on the Lambda resource policy and a protocol-compliant connector; useful impact depends on what the function implements.
- **KMS key disclosure:** `DescribeFlow` reveals the key ARN, not plaintext or decrypt authority.
- **Execution records as data theft:** they expose counts/errors/catalog metadata, not record contents.
