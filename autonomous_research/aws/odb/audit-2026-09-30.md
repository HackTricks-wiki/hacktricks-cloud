# Oracle Database@AWS (`odb`) audit — 2026-09-30

## Scope and live-account boundary

- The book had no Oracle Database@AWS coverage before this pass.
- `hacktricks-training` via `ChackBotAdministratorRole` returned `NOT_STARTED` from `GetOciOnboardingStatus` in `us-east-1`.
- Resource list calls in `us-east-1` were rejected because the account is not onboarded; `us-west-2` is denied by an organization SCP.
- No Marketplace registration was accepted and `InitializeService` was not called. Those operations create subscription/legal/billing state and were unnecessary for validating the public API and authorization model.
- No ODB, OCI, RAM, License Manager, IAM, KMS, Secrets Manager, VPC, compute, or database resource was created. Cleanup inventory was therefore empty by construction.

## Published expected techniques

### #103 — `CreateAutonomousDatabaseWallet`

The current API returns `autonomousDatabaseWalletFile` as a compressed binary archive and lets the caller choose its encryption password. This is high-confidence credential-material export for an existing Autonomous Database. The archive supplies database connection and mTLS client material but not an Oracle username/password, so practical database access also requires a database credential and network reach.

Authorization model:

- `odb:CreateAutonomousDatabaseWallet` supports the exact `autonomous-database` ARN.
- The direct `API_REQUEST_PARAMETER` password path contains no role or secret reference.
- The `CUSTOMER_MANAGED_AWS_SECRET` path supplies a secret ID, IAM role ARN, and OCID-derived external-ID type. The Service Authorization Reference publishes `iam:PassRole` with `iam:PassedToService=odb.amazonaws.com` as a dependent action.
- Because the account has no target database, conditional versus unconditional PassRole enforcement could not be measured. The public page tells readers to validate that boundary rather than claiming a live least-privilege result.

Telemetry model:

- AWS documents every ODB control-plane call as a CloudTrail management event.
- Exact password/archive request and response serialization could not be observed without an onboarded database; the public table deliberately avoids claiming that secret contents are logged.
- The customer-managed-secret branch additionally creates OCI role-assumption and secret-read evidence.

### #104 — `UpdateAutonomousDatabase` administrator takeover

The current API accepts a replacement `ADMIN` password, IP allowlist, and `isMtlsConnectionRequired` flag in one exact-database update. This converts configuration authority into Oracle database-administrator access when the attacker can also reach the endpoint. The impact is database/service-level, not AWS IAM or full OCI-tenancy escalation.

Important constraints:

- The endpoint is private; an allowlist change does not create Internet routing.
- `ADMIN` capabilities remain bounded by Oracle's managed Autonomous Database privileges.
- Direct password input avoids an explicit secret/role field, but the SAR lists PassRole as a dependent action for the API and live conditional enforcement is unmeasured here.
- Changing the password is durable service-level persistence but was classified as privilege escalation because its primary outcome is new database-admin privilege.

## Cross-account and integration review

- AWS RAM shares Exadata infrastructure, ODB networks, and Exascale storage vaults only to account IDs in the same organization. Managed permissions cannot be customized.
- Recipients can create and own child database resources. Those children continue operating after unsharing, and the owner cannot delete some parents until recipient children are removed. This is operationally important, but it is intended sharing behavior and not a standalone attack without RAM authority.
- License Manager entitlement grants also remain limited to accounts in the same organization and require recipient acceptance/activation.
- `AssociateIamRoleToResource` supports KMS TDE integration and requires PassRole. No evidence supports describing it as an arbitrary role-execution primitive.
- Permission-only ODB actions for resource policies, grant shares, and outbound zero-ETL integrations are invoked through their owning integrations rather than direct ODB API operations.

## Rejected or deferred ideas

- VM-cluster `sshPublicKeys` are a strong access primitive at creation time, but no current update API was found that injects a new key into an existing Cloud VM cluster. Creating Exadata infrastructure solely to demonstrate the expected creation-time key would be costly and low value.
- `GetAutonomousDatabaseWalletDetails` returns only status, rotation time, and password-source summary, not wallet bytes.
- Start/stop/reboot/failover/delete and capacity mutations are availability or cost effects and were not promoted as primary book techniques.
- Onboarding-status discovery alone is low-value account metadata.
- No unexpected AWS behavior was observed, so no file was created under the private vulnerability-report directory.
