## Live-tested permission and attack matrix

| Hypothesis / action | Minimum-permission result | Security conclusion |
| --- | --- | --- |
| `CreateAttendee` on exact meeting ARN | Succeeded and returned a 98-character `JoinToken` | Meeting-scoped write permission creates a credential that can enter the meeting |
| `GetAttendee` on exact meeting ARN | Returned the same token originally minted for the attendee | This is a sensitive credential-read action, not only metadata enumeration |
| `ListAttendees` on exact meeting ARN | Returned both attendees and both non-null join tokens | A single list call can steal every active attendee identity/token for that meeting |
| `GetMeeting --no-sign-request` | `MissingAuthenticationTokenException` | Meeting ID alone does not expose placement unauthenticated |
| `UpdateAttendeeCapabilities` on exact meeting ARN | Changed `Audio`, `Video` and `Content` from `Receive` to `SendReceive`; response also returned the join token | Exact-meeting permission can enable/suppress media and recover the attendee credential |
| `ListChannelMessages` on exact private channel + victim user ARN, using victim as Chime bearer | Returned persisted message content, sensitive metadata and victim sender ARN | Backend IAM credentials allowed for a logical user can read all channels that user may read |
| `SendChannelMessage` on exact private channel + victim user ARN | Created a persistent message that was later listed as sent by the victim | The bearer ARN is the logical author; overbroad backend roles enable user impersonation |
| Same read with an attacker user that was not a member | `ForbiddenException` | Chime's service-level membership layer remains effective in addition to IAM |
| `CreateChannelMembership` on exact channel, target attacker and AppInstanceAdmin bearer ARNs | Added the attacker to the private unrestricted channel | Exact-resource administrative permission can install persistent access |
| Read after adding attacker membership | Attacker bearer returned both victim and spoofed messages | Confirmed end-to-end durable channel data access |
| `CreateVoiceConnector` with administrative credentials | `AccessDeniedException: Service is restricted for AWSAccountId 228478051196` | Voice/SIP techniques could not be live-tested in this account; no resource was created |

## Meeting token details

`CreateAttendee` returned default capabilities `SendReceive` for audio, video and content when omitted. The test token length was 98 characters. `GetAttendee` returned a byte-for-byte identical token, and `ListAttendees` included token fields for every entry.

AWS documentation explicitly states that the signed join token lets the attendee access the meeting for its duration or until `DeleteAttendee`. The audit did not establish a real WebRTC media session because the sensitive authorization result was already proven by the API and official client contract; generating browser/media traffic would not clarify the IAM boundary.

The separate capability test began with a receive-only attendee. `UpdateAttendeeCapabilities` promoted all three media types to `SendReceive` and returned the same attendee object, including the join token. AWS documents that an audio capability upgrade can allow audio to flow when a client left its microphone unmuted; video/content changes require renegotiation.

## Messaging bearer and membership details

The test topology was:

```text
AppInstance
├── admin (AppInstanceAdmin)
├── victim (initial private-channel member)
└── attacker (initially not a member)
    └── added later using CreateChannelMembership
```

The channel used `Privacy=PRIVATE` and `Mode=UNRESTRICTED`. A victim-authored marker contained both message content and metadata. Restrictive sessions had only the tested action and exact channel/user ARNs.

This confirmed that `--chime-bearer` is not an independent bearer credential. Requests remain SigV4 authenticated and IAM must authorize the logical user/bot ARN; Chime then applies membership/admin/moderator rules. The dangerous pattern is an IAM role that permits one AWS workload to act for many or wildcarded AppInstanceUser ARNs.

The private channel correctly denied an authorized API call when the supplied logical identity was not a member. AppInstance administrative membership creation then converted that denied identity into a durable reader. This is expected authorization behavior and not an AWS defect.

## Authoritative pipeline and streaming boundary review

### Meeting capture and live connector pipelines

- `CreateMediaCapturePipeline` is a wildcard creation action and takes a meeting source ARN plus same-account S3 sink ARN.
- Normal capture depends on `AWSServiceRoleForAmazonChimeSDKMediaPipelines`, and the S3 bucket must trust `mediapipelines.chime.amazonaws.com` for object writes. AWS also documents `s3:GetBucketPolicy` for the caller.
- Optional `SinkIamRoleArn` in the KMS parameters introduces `iam:PassRole` with `iam:PassedToService=mediapipelines.chime.amazonaws.com`.
- Capture artifacts can include audio, video, content share, data-channel messages, transcription and meeting events.
- A media live connector can relay meeting media to RTMP/RTMPS, including an external platform/stream key. Ending the remote stream does not stop the AWS pipeline; `DeleteMediaPipeline` does.

No live pipeline was created because the account had no Chime media-pipeline service-linked role, S3 sink or Lambda/Kinesis fixture. Creating that cross-service infrastructure would provide little extra evidence beyond the documented authorization contract and would mutate account-wide IAM state.

### Media insights PassRole proxy

`CreateMediaInsightsPipelineConfiguration` and `UpdateMediaInsightsPipelineConfiguration` accept `ResourceAccessRoleArn` and have an authoritative `iam:PassRole` dependency. The configuration can include Transcribe/voice analytics processors and Lambda, Kinesis, S3, SQS or SNS sinks. `CreateMediaInsightsPipeline` later operates on the exact configuration ARN without a second PassRole decision.

This is a constrained privilege proxy, not arbitrary IAM role assumption. Impact is limited to the configured pipeline processors/sources/sinks and their resource-policy/runtime validation.

### Messaging streaming

`PutMessagingStreamingConfigurations` can continuously export future `ChannelMessage` and `Channel` events. AWS prerequisites are:

- same account and Region as the AppInstance;
- Kinesis stream name begins `chime-messaging-`;
- at least two shards;
- server-side encryption enabled;
- relevant caller Kinesis permissions.

First use can create `AWSServiceRoleForChimeSDKMessaging`, whose stream permissions are prefix-constrained. No configuration was installed because neither that role nor a test stream existed and creating a two-shard encrypted stream solely to reconfirm the documented contract was unnecessary.

### Channel flows

A channel flow's Lambda processor must be in the same account/Region, its resource policy must allow `messaging.chime.amazonaws.com`, and the Lambda role needs `chime:ChannelFlowCallback`. An AppInstance admin or channel moderator can associate the flow. The processor receives standard persistent and non-persistent message content/metadata and can modify, deny or delay delivery. This was accepted as a strong expected-functionality technique without provisioning a Lambda.

## Voice/SIP authoritative review

The account-wide service restriction prevented even an empty Voice Connector from being created. No phone-number or call action was attempted.

Strong expected techniques retained from the public API/IAM contract:

1. Add termination SIP credentials and an attacker source CIDR/calling Region.
2. Replace origination SIP hosts or phone-number associations.
3. Enable Kinesis Video call-media streaming.
4. Repoint a SIP media application to a malicious same-account Lambda and attach/update SIP rules.

These are durable, logged configuration attacks with toll-fraud/privacy consequences. Existing termination passwords are not readable: the list API returns usernames only. The account restriction is documented in the research ledger and the public pages do not imply live validation.

## Accepted book techniques

1. Exact-meeting attendee token theft using `GetAttendee`/`ListAttendees` and token minting with `CreateAttendee`.
2. Attendee capability promotion/suppression, including the token in the update response.
3. Exact channel+logical-user history theft and sender impersonation through overbroad bearer authorization.
4. Persistent private-channel membership and AppInstance administrator promotion.
5. Lambda channel-flow interception/tampering.
6. Continuous AppInstance Kinesis message/channel export.
7. Capture and RTMP relay of meeting media, plus the narrow media-pipeline PassRole proxies.
8. Voice Connector/SIP credential, streaming, route and Lambda backdoors for enabled accounts.

## Rejected, constrained or deferred ideas

- **Unauthenticated meeting enumeration:** `GetMeeting --no-sign-request` returned `MissingAuthenticationTokenException`; no public/account-ID-only endpoint was found.
- **Treating `x-amz-chime-bearer` as a standalone secret:** it is an ARN header plus SigV4/IAM and service-level role checks, not a replacement for AWS authentication.
- **Membership IDOR/authorization bypass:** the nonmember private-channel read was correctly denied. Administrative membership creation is intended behavior.
- **Cross-account AppInstance policy:** the current service exposes no general AppInstance resource-policy API. Cross-account application access normally uses an IAM role/Cognito credentials in the owning account; no unverified cross-account bypass was published.
- **Generic delete/update denial of service:** deleting meetings, attendees, channels, users or pipelines and redacting/deleting messages are real but obvious granted destructive permissions, so they were not split into low-value standalone techniques.
- **Legacy `CreateApiKey` as a modern SDK escalation:** it is a permission-only action for legacy Chime Enterprise SCIM/Okta. The collaboration service is past end of support and new accounts cannot enroll; the old TODO was replaced with a constrained legacy warning rather than an executable technique.
- **Media-pipeline generic admin escalation:** passed roles are usable only through supported pipeline sources/processors/sinks. No credentials are returned, so claims were limited to a constrained authorization proxy.
- **PSTN/SIP execution:** not attempted due account restriction, monetary impact and third-party risk.
