# AWS Resource Explorer 2 security audit — 2026-09-27

## Scope and result

Audited the current Resource Explorer 2 control plane, with emphasis on APIs and resource classes added after the prior page was written:

- `CreateResourceExplorerSetup`, `GetResourceExplorerSetup`, and `DeleteResourceExplorerSetup`
- account-level Organizations configuration and member-index enumeration
- Resource Explorer-owned service indexes and service views
- AWS managed views and their embedded resource policies
- service streaming access
- resource-policy and streaming permission-only actions
- cross-account and AWS RAM boundaries
- default-view persistence and deletion behavior
- CloudTrail redaction

The existing tested `GetView` + `Search` metadata-oracle and `UpdateView` filter-widening coverage was preserved. The public page was expanded at:

`src/pentesting-cloud/aws-security/aws-services/aws-resource-explorer-enum.md`

No unexpected AWS security defect was found. The new findings are expected authorization, service-integration, and configuration behavior, so no report was created under `/home/tester/cloud_bb/aws`.

## Primary conclusions

1. Resource Explorer now has two index/view planes even before customer setup: user-owned objects returned by `ListIndexes` / `ListViews`, and AWS-owned objects returned by the new service-index/service-view APIs. An empty user inventory does not mean the service has no index or fallback view.
2. The bulk setup actions are standalone, wildcard-scoped IAM capabilities. `CreateResourceExplorerSetup` can create user indexes/views across multiple Regions and select one aggregator; `DeleteResourceExplorerSetup` can remove user indexes/views from a Region list or every configured Region.
3. `GetResourceExplorerSetup` is task-oriented, not a general configuration-list API. It requires the UUID returned by a create/delete setup call and paginates per-Region index/view status and errors.
4. Service views are immutable global definitions. `GetServiceView` discloses their filter, included properties, scope type, and streaming principal. Resource Explorer-defined service views provide fallback discovery; service-defined views support AWS integrations.
5. Managed views are created with FAS or an SLR and controlled by the integrating service. `GetManagedView` returns the trusted service and attached resource policy; customers cannot directly update or delete the view and must disable the owning integration.
6. `CreateStreamingAccessForService`, `DeleteStreamingAccessForService`, `CreateManagedView`, and Resource Explorer `Get`/`Put`/`DeleteResourcePolicy` are permission-only IAM actions. They are not customer-callable operations in the current Resource Explorer public API/CLI. AWS services or AWS RAM invoke the relevant integration.
7. `ListStreamingAccessForServices` is the customer-visible audit surface for effective streaming grants and returns the service principal and creation time.
8. Multi-account search requires Organizations trusted access, the Resource Explorer service-linked role, a management/delegated administrator, consistent aggregator placement, active member user indexes, an organization/OU/account-scoped view, and an AWS RAM share.
9. RAM documents `resource-explorer-2:View` as shareable only to accounts in the same organization. It cannot be shared to external accounts, IAM users/roles directly, service principals, or with customer-managed RAM permissions. Consumer identity permission is still required in addition to the owner-side share/resource policy.
10. A default-view association is Region-level and persists across `UpdateView` because the ARN does not change. Deleting the view/index automatically disassociates it. Recreating the same view name produces a new UUID/ARN, so the deleted association and old IAM policy do not attach to the replacement.
11. `GetDefaultView` reports the persisted customer association and can return `{}` while the Resource Explorer-owned fallback service view exists. Current immediate-discovery documentation describes service-view fallback, while the explicit API contract still says an omitted `ViewArn` needs a default. Explicit view ARNs are the predictable API behavior.
12. CloudTrail intentionally redacts every `Tags`, `Filters`, and `QueryString` value. Search results are not logged. A configuration baseline is required to determine what a caller searched or whether a view filter was widened.

## Setup API analysis

### Create

Request:

```json
{
  "RegionList": ["us-east-1", "us-west-2"],
  "AggregatorRegions": ["us-east-1"],
  "ViewName": "example-view"
}
```

- `RegionList` requires at least one Region.
- `AggregatorRegions` accepts zero or one Region.
- `ViewName` is 1-64 alphanumeric/hyphen characters.
- The call returns only `TaskId`.
- The action is `resource-explorer-2:CreateResourceExplorerSetup` with no resource type in the Service Authorization Reference, so IAM uses `Resource: "*"`.
- The operation creates user-owned indexes and views across the requested Regions and can establish the aggregator Region.

### Get status

`GetResourceExplorerSetup` requires a task UUID returned by a create/delete call. It accepts `MaxResults` 1-100 and a pagination token. Each Region entry can include:

- Region
- index status, index ARN/Region/type, or error code/message
- view status, view definition, or error code/message

It is not a general “show current setup” operation; use the various list/get index and view APIs for steady-state inventory.

### Delete

The request accepts either:

- an exact `RegionList`; or
- `DeleteInAllRegions: true`, with no Region list.

It removes user-owned indexes and views and returns a task ID. `resource-explorer-2:DeleteResourceExplorerSetup` also has no resource-level ARN constraint. This is a high-impact availability/visibility permission even though immediate partial service-owned discovery can remain.

Deleting an index asynchronously deletes its customer views. If a deleted view was the default, Resource Explorer emits a service-generated `DisassociateDefaultView` event. Managed views can block turning off Resource Explorer until the managing integration removes them.

## Live validation

### Safety controls

- Used the authorized administrator profile only for read-only APIs.
- Did not call `Search`, because current Resource Explorer can automatically create a user index/view after the account service-linked role exists.
- Did not invoke create/update/delete/default/RAM/resource-policy/setup actions.
- Did not create any test index, view, policy, setup task, streaming grant, managed view, or organization configuration.
- Consequently, cleanup had no test resources to remove.

### Initial and final state

Read-only checks in `us-east-1` returned:

| API | Sanitized result |
| --- | --- |
| `ListIndexes` | `Indexes: []` |
| `ListViews` | `Views: []` |
| `GetDefaultView` | Empty JSON response, exit status 0 |
| `GetServiceIndex` | AWS-owned local index with the account-less `default-resource-explorer-2-index` ARN |
| `ListServiceIndexes` | The same AWS-owned local index |
| `ListServiceViews` | Three AWS-defined views, including the Resource Explorer fallback and two integration views |
| `GetServiceView` | Filters, included-property names, scope type, and (where configured) a streaming service principal |
| `ListManagedViews` | `ManagedViews: []` |
| `ListStreamingAccessForServices` | `StreamingAccessForServices: []` |
| `GetAccountLevelServiceConfiguration` | `ResourceNotFoundException`: organization information not configured for Resource Explorer |
| `ListIndexesForMembers` | `ValidationException`: Resource Explorer service access not enabled for the organization |

The organization was present, but Resource Explorer trusted/service access was disabled. This cleanly demonstrated that Organizations membership alone is insufficient for account-level configuration and member-index enumeration.

Because all live calls were read-only, the final state was identical to the initial state: no user index, user view, default association, managed view, or streaming access was created.

### Service-view observations

The available service views illustrated all important fields:

- Resource Explorer's own service view had an empty filter, account scope, and no optional properties.
- An observability integration view included tags and named a streaming service principal.
- Another integration view included tags, relationships, and configuration.

The exact set is AWS-controlled and can change, so the public page documents enumeration rather than treating the observed names as a stable allowlist.

### CloudTrail validation

Existing authorized test history was inspected read-only:

- Resource Explorer `Search` events exposed the view ARN and replaced `QueryString` with `"***"`; `responseElements` was null.
- `UpdateView` exposed the view ARN and included-property names but replaced both request and response filters with `"***"`.
- `CreateView` similarly redacted filters.
- An existing index/view cleanup sequence contained AWS-service-generated `DeleteView` and `DisassociateDefaultView` events, confirming that deletion removes the persisted default association rather than leaving a dangling ARN.

These observations match the current official CloudTrail documentation, which states that all Tags, Filters, and QueryString values are redacted.

## Default view and fallback nuance

The following statements are simultaneously true in the current documentation and live behavior:

- `AssociateDefaultView` persists one customer view ARN per Region.
- Search/List calls that omit `ViewArn` traditionally require that association.
- Updating the view leaves the association intact because the ARN is stable.
- Deleting the view removes the association asynchronously.
- Resource Explorer's immediate-discovery documentation now describes an immutable Resource Explorer-owned view as the fallback when no user-owned view is available.
- `GetDefaultView` returned an empty result even though `ListServiceViews` showed the fallback service view.

Therefore, the fallback is not equivalent to a persisted default association. Security reviews should inventory both planes, and deterministic API clients should specify an explicit view.

## Managed views, streaming, and resource policies

### Managed views

An AWS service creates a managed view using FAS or an SLR. Resource Explorer attaches a policy that allows the trusted service to get/search/delete the managed view and generally denies non-service principals except for view-owner inspection. `GetManagedView` returns the policy as a string alongside the trusted service, scope, filter, optional properties, owner, and version.

The customer-facing controls are `ListManagedViews` and `GetManagedView`. Update/delete are reserved to the service that created the view. Removal is service-specific; the documented Systems Manager example requires disabling the unified console.

### Streaming

Service views can support real-time resource-update streaming. Customers inspect effective access with `ListStreamingAccessForServices`, which returns service principals and creation times. Official documentation says customer opt-in is represented by `CreateStreamingAccessForService`, but the current authorization reference classifies create/delete as permission-only and current SDK/CLI service models do not expose public operations for them. The integrated, allowlisted service invokes the action through its setup path.

Search/List access through an integration's SLR is distinct from streaming access. AWS documentation says removing that search/list access can require disabling the entire integration.

### Resource policies and RAM

The Resource Explorer user guide still tells sharing administrators to have `GetResourcePolicy`, `PutResourcePolicy`, and `DeleteResourcePolicy`. The authorization reference resolves the apparent API gap: those are permission-only actions used by AWS RAM, not public Resource Explorer endpoints.

Security consequence: possessing `resource-explorer-2:PutResourcePolicy` is sensitive, but it is not by itself a direct arbitrary JSON-policy write primitive. The principal must also control the supported RAM workflow and satisfy the Resource Explorer organization constraints.

## Multi-account boundary

Required chain:

1. Enable Organizations trusted access for Resource Explorer.
2. Create/validate `AWSServiceRoleForResourceExplorer` in the management/delegated account.
3. Optionally register the one supported delegated administrator.
4. Enable user indexes in the participating accounts.
5. Use the same aggregator Region across the organization.
6. Create an organization-, OU-, or account-scoped view in the management/delegated administrator aggregator Region.
7. Share it through AWS RAM.
8. Grant consumer principals identity permission for `GetView` and `Search` on the owner view ARN.

Important boundaries:

- `GetAccountLevelServiceConfiguration` is management-account-only.
- `ListIndexesForMembers` is management/delegated-administrator-only and accepts 1-10 account IDs per call.
- Removing/changing the delegated administrator removes its multi-account views.
- Member accounts that leave the organization lose organization/OU shares; member indexes removed or disabled disappear from multi-account results.
- RAM marks Resource Explorer views as same-organization only, account principals only, AWS-managed permission only, and not shareable to service principals.
- Across accounts, owner resource policy/share plus consumer identity policy are both required.

No arbitrary external-account/public-view path was identified.

## Candidate matrix

| Candidate | Required authority / prerequisite | Result and disposition |
| --- | --- | --- |
| Cross-service inventory through a user view | Exact `GetView` + `Search` | Previously verified; preserved |
| Expand existing consumers/default by clearing a filter | Exact `UpdateView` | Previously verified; preserved and extended with default persistence |
| Bulk create complete multi-Region inventory | `CreateResourceExplorerSetup` on `*`; SLR prerequisites as applicable | Expected high-impact configuration behavior; documented |
| Bulk destroy account search topology | `DeleteResourceExplorerSetup` on `*` | Expected availability/visibility impact; documented, not live-tested |
| Enumerate service-owned discovery when `ListIndexes` is empty | `GetServiceIndex` / `ListServiceIndexes` / service-view reads | Verified read-only; documented |
| Arbitrarily modify a service view | Customer IAM permission | Rejected; service views are immutable AWS definitions |
| Directly delete/update a managed view | Customer Resource Explorer API | Rejected; managing AWS service controls lifecycle |
| Grant streaming to an arbitrary principal with the CLI | `CreateStreamingAccessForService` string | Rejected; permission-only, allowlisted service integration path |
| Directly attach a Resource Explorer view policy | `PutResourcePolicy` string | Rejected as a standalone API primitive; permission-only and mediated by RAM |
| Share a view outside the organization | Resource Explorer view + RAM | Rejected; RAM resource-type matrix explicitly disallows external accounts |
| Search shared view with only owner RAM policy | Share only | Rejected; consumer identity policy also required |
| Default association survives `UpdateView` | `UpdateView` on current default | Confirmed by ARN semantics; documented |
| Dangling default survives view deletion/recreation | Delete/recreate same name | Rejected; delete auto-disassociates and UUID changes |
| Determine query/filter contents from CloudTrail | CloudTrail history | Rejected; intentional redaction; configuration snapshots required |

## Cleanup and residue verification

No write operation was performed during this audit, so there were no newly created indexes, views, setup tasks, policies, defaults, shares, managed views, streaming grants, IAM roles, or service integrations to clean up.

Final read-only inventory remained:

- user indexes: 0
- user views: 0
- persisted default: none
- managed views: 0
- streaming access grants: 0
- Resource Explorer Organizations service access: disabled
- AWS-owned service index/views: unchanged

Pre-existing service-linked roles and all unrelated resources were left untouched.
