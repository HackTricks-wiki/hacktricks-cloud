## Application Discovery data-exfiltration reasoning

`StartExportTask` with no agent filter creates a summary of all servers, applications, tags and performance. A single-agent filter exports up to 72 hours of detailed process, network and performance data. The response is only an export ID. `DescribeExportTasks` returns `configurationsDownloadUrl` once complete.

The API reference explicitly says the report is written to an **AWS-managed S3 bucket**. The documented successful response says the URL expires in 24 hours and exported data expires in 10 days. Therefore the exact useful minimum is:

1. `discovery:StartExportTask` on `*`.
2. `discovery:DescribeExportTasks` on `*`.

No customer-account `s3:GetObject`, bucket discovery or bucket-policy change is required. This is expected product behavior, not a vulnerability, but it invalidates policies that classify those two permissions as harmless reporting metadata.

## Migration Hub Automation privilege escalation

The preview feature is limited to `us-east-1` and requires that Region as the Migration Hub home Region. A custom automation unit accepts the ARN of:

- an AWS-owned SSM Automation document;
- a customer SSM Automation document; or
- a Lambda function.

An IAM role is associated with the unit and assumed for its execution. AWS's own IAM page contains this explicit warning: a user with `mgh:CreateAutomationUnit`, `mgh:AssociateAutomationUnitRole`, `mgh:CreateAutomationRun`, and `iam:PassRole` can perform any actions in the account. The service role permissions can exceed those of the user.

Current public CLI/SDK models available locally do not expose the preview operations, and the authorized account has no home Region. This prevented a clean end-to-end run without changing durable account-wide state. Under the research testing limit, official documentation and the current Service Authorization reference were used as the authoritative expected-behavior confirmation. No public page claims an `iam:PassRole` bypass.
