# Amazon Redshift and Redshift Serverless security audit - 2026-09-27

## Scope and safety

- Services: provisioned Redshift (`redshift`), Redshift Serverless (`redshift-serverless`) and Redshift Data API (`redshift-data`).
- Focus: persistence, enumeration, namespace/workgroup and role repointing, resource policies/cross-account access, credentials, snapshots/datashares and current APIs.
- Authorized identity: `hacktricks-training` assuming `arn:aws:iam::228478051196:role/ChackBotAdministratorRole` in `us-east-1`.
- No provisioned cluster or Serverless workgroup/capacity was created. The only Redshift resource created was an empty Serverless namespace, which incurs no RPU compute and was deleted in the same test.
- Every disposable IAM role and the namespace were deleted. Passwords, STS credentials and tokens were never printed or written to the repository.

## Baseline coverage and API review

The pre-audit enum page covered only basic provisioned cluster discovery. - Data API: statement execution/result lifecycle, role-level statement listing, retained sessions, metadata listing and current owner condition keys.

## Live tests

### 1. Serverless administrator reset and role repointing

Fixture:

- Empty namespace `ht-rs-audit-927`; no workgroup or compute capacity.
- Namespace ARN: `arn:aws:redshift-serverless:us-east-1:228478051196:namespace/57b54e88-5563-4d7f-b6ad-5915719ed212`.
- Probe role `ht-rs-update-namespace-probe-927`.
- Service role `ht-rs-namespace-service-role-927`.

Results:

1. A role with only `redshift-serverless:UpdateNamespace` on the exact namespace ARN changed `adminUsername`/`adminUserPassword` without the old password. No `iam:PassRole` was present.
2. The same role could not set `iamRoles`/`defaultIamRoleArn`; the denial explicitly named missing `iam:PassRole` on the service role.
3. Adding only `iam:PassRole` on that exact role, conditioned by `iam:PassedToService = redshift-serverless.amazonaws.com`, allowed association and default-role selection.
4. CloudTrail event `2026-09-27T04:22:23Z` recorded `UpdateNamespace` with request keys `adminUsername`, `adminUserPassword`, and `namespaceName`. The password was correctly replaced by `HIDDEN_DUE_TO_SECURITY_REASONS`.
5. CloudTrail event `2026-09-27T04:22:56Z` recorded the role association, including `iamRoles` and `defaultIamRoleArn`.

Conclusion: administrator reset is a valuable expected persistence primitive. IAM-role repointing is valuable privilege escalation but correctly enforces exact service-conditioned `iam:PassRole`; no bypass was found.

Cleanup: namespace and both IAM roles deleted. Follow-up inventory showed zero namespaces/workgroups/snapshots and zero `ht-rs-*` roles.

### 2. Provisioned `ModifyClusterIamRoles` and `ModifyCluster`

Disposable roles: `ht-rs-provisioned-probe-927` and `ht-rs-provisioned-service-role-927`.

Against a synthetic exact cluster ARN:

- `ModifyClusterIamRoles` without pass permission returned `AccessDenied` explicitly naming `iam:PassRole`.
- Adding only exact-role `iam:PassRole` conditioned for `redshift.amazonaws.com` moved the call to `ClusterNotFound`.
- `ModifyCluster` password reset plus `--publicly-accessible` reached `ClusterNotFound` with only `redshift:ModifyCluster` on the exact cluster ARN.
- `ModifyCluster` with a VPC security-group ID and a password reset also reached `ClusterNotFound`; the role contained no `ec2:*` action.

Conclusion: no pass-role bypass. `ModifyCluster` is a database-master persistence primitive, and it can select existing network resources without EC2 API permission.

Cleanup: both roles deleted; no cluster existed or was changed.

### 3. Serverless `UpdateWorkgroup` network boundary

A disposable role had only `redshift-serverless:UpdateWorkgroup` with `Resource: "*"` and no EC2 permissions. Separate requests against a synthetic workgroup changed:

- `publiclyAccessible`;
- `securityGroupIds`; and
- `subnetIds`.

Every request passed IAM authorization and returned `ResourceNotFoundException`. This confirms `UpdateWorkgroup` alone selects already-existing VPC resources and changes public exposure; it does not require `ec2:*`. It does not bypass SQL authentication.

Cleanup: role deleted; no workgroup was created.

### 4. Provisioned cross-account sharing boundaries

One disposable role used exact synthetic ARNs and only the action under test:

| Action | Resource authorization | Safe result |
| --- | --- | --- |
| `redshift:AuthorizeSnapshotAccess` | Exact cluster and snapshot ARNs | `ClusterSnapshotNotFound` |
| `redshift:AuthorizeEndpointAccess` | Exact cluster ARN | `ClusterNotFound` |
| `redshift:AuthorizeDataShare` | Exact datashare ARN | `InvalidDataShareFault` |

The post-authorization resource errors confirm no extra Redshift/EC2 permission is needed for the producer-side call. Snapshot sharing exfiltrates a durable full copy; endpoint authorization provides network reach only; datashare authorization provides only objects already placed in the share by SQL.

Cleanup: role deleted; no authorization or resource was created.

### 5. Serverless snapshot resource policy

A disposable role had only `redshift-serverless:PutResourcePolicy`, `Resource: "*"`. Putting a cross-account restore policy on a synthetic snapshot ARN reached `ResourceNotFoundException`, confirming that no auxiliary API permission was required. The Service Authorization Reference currently exposes no resource type for this action, so wildcard resource authorization is required.

CloudTrail recorded the expected failed management event at `2026-09-27T04:30:11Z`, including the synthetic snapshot ARN.

Cleanup: role deleted; no policy or snapshot existed.

## Retained high-value techniques

| Technique | Classification | Why retained |
| --- | --- | --- |
| Data API SQL through HTTPS | Post-exploitation | Removes the VPC route requirement and preserves database-user privilege impact |
| Same-role statement result theft | Post-exploitation | AWS documents shared role ownership; cached results can disclose another workload's rows |
| Retained Data API session reuse | Post-exploitation | Same-role callers can reuse an authenticated `SessionId` unless owner conditions isolate it |
| Provisioned snapshot authorization | Post-exploitation | Durable complete database copy across accounts |
| Serverless snapshot resource policy | Post-exploitation | Durable complete namespace snapshot sharing; wildcard-scoped policy action |
| Datashare authorization | Post-exploitation | Live cross-account access to already-shared objects, optionally writes |
| Serverless admin reset | Persistence | Database administrator credential independent of attacker's IAM principal |
| Provisioned master reset | Persistence | Same service-level persistence for a cluster |
| Workgroup public/SG/subnet replacement | Persistence enablement | Makes a planted credential reachable without EC2 API permissions |
| Cross-account endpoint authorization | Persistence enablement | Durable external private route; SQL credential remains separately necessary |
| Attach/default an attacker-selected service role | Privilege escalation | Redshift SQL features can exercise the passed role's AWS permissions |
| Predictable Serverless endpoint | Unauthenticated recon | Workgroup + account + Region deterministically identify the standard hostname |

## Rejected or ledger-only ideas

- **Namespace resource policy as direct victim-data sharing:** current namespace policies primarily authorize zero-ETL integration into a target. They do not independently grant a reader SQL access to existing victim databases; not published as an exfiltration technique.
- **Zero-ETL integration as a new Redshift source-exfil primitive:** source-service authorization and integrations are useful, but this audit found no distinct Redshift-only bypass beyond documented source/target policy controls. Existing source-service coverage is the better location.
- **Authentication profiles as password disclosure:** profiles contain connection/plugin properties and impersonation settings, not database passwords. Enumeration retained; no standalone attack.
- **`UpdateWorkgroup` alone:** network exposure without a credential is not a foothold. Published only as a composition with admin reset or existing SQL credentials.
- **Scheduled actions / resize / pause / capacity changes:** availability and cost attacks, not a quality privilege/persistence/data-access technique for this update.
- **HSM and certificate configuration:** no private-key retrieval path identified.
- **IAM Identity Center auth token:** still requires an authorized IdC assignment/identity path; no standalone escalation identified.
- **Disabling log exports:** valid defense evasion but insufficient as a separate foothold technique. The changed `logExports`/activity-logging settings remain a useful detection signal.
- **Public endpoint DNS:** endpoint prediction supplies reconnaissance only. It does not bypass VPC policy or database authentication.

## Unexpected-defect assessment

No unexpected AWS security defect was confirmed. In particular:

- both provisioned and Serverless IAM-role association correctly enforced `iam:PassRole`;
- Serverless admin passwords were redacted in CloudTrail;
- network configuration accepted existing VPC identifiers without EC2 API calls, which is expected service behavior rather than an authorization bypass;
- all cross-account tests stopped at missing synthetic resource lookup and created no share/policy.

No private bug-bounty report was created.
