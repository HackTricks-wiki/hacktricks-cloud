# Amazon EVS audit — 2026-09-29

## Scope and environment

Reviewed all current EVS API operations, environment/connector credential references, IAM resource
scoping, topology exposure and the possible connector credential-relay chain. `ListEnvironments`
returned empty in both allowed Regions, so no four-host bare-metal environment was created.

## Verified authorization boundary

- `evs:GetEnvironment` with no Secrets Manager permission reached service-side
  `ResourceNotFoundException` for a synthetic environment ID.
- The same restricted caller was denied `GetSecretValue` on an existing canary secret.
- Adding only `secretsmanager:GetSecretValue` on that exact canary ARN produced the expected one-way
  hash. This verifies that EVS metadata access and credential-value access are independent IAM gates.
- Official response models show that `GetEnvironment` returns EVS-managed credential secret ARNs and
  `ListEnvironmentConnectors` returns each connector's credential ARN and appliance FQDN.

## Connector relay hypothesis

`UpdateEnvironmentConnector` can update the appliance FQDN without changing the stored secret, and
EVS performs periodic connector checks using the secret. However, AWS requires the new FQDN to match
the environment's configured domain. TLS validation, exact request behavior and whether credentials
would reach an operator-controlled same-domain endpoint were not testable without an existing EVS
environment and management network. Keep this as a candidate requiring controlled DNS, TLS and a
canary credential; do not publish it as confirmed.

## Cleanup and disposition

The access key, inline policy and IAM user were deleted, and the canary secret was force-deleted.
Prefix-filtered inventories returned empty. No EVS, EC2, VPC, KMS or VMware resource was created.
The direct credential-reference techniques are expected functionality and were published; no private
report was created.
