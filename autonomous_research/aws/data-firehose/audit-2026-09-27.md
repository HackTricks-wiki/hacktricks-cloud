# Amazon Data Firehose security audit — 2026-09-27

## Scope and safety

- Account `228478051196`, Region `us-east-1`.
- Administrator session assumed `ChackBotAdministratorRole` from profile `hacktricks-training`.
- One DirectPut delivery stream, two empty S3 buckets, one Firehose delivery role, and one exact-action caller role were created.
- The stream used a 1 MiB / 60 second S3 buffer and received two tiny marker records. Total cost was negligible.
- A shell exit trap deleted the stream, emptied/deleted both buckets, and removed both roles/policies on success or failure.

## Existing documentation review

The existing service page already identified S3 and HTTP endpoint destination replacement, deletion, and record injection. It lacked:

- a dedicated post-exploitation/persistence split;
- per-technique impact, stealth, and expandable log tables;
- a live proof that omitting `RoleARN` avoids `iam:PassRole` while retaining the role;
- proof that exact-stream `PutRecord` reaches the destination without destination permissions; and
- the current Firehose CloudTrail data-event resource type.

The prior conditional warnings were preserved: S3 redirection is not an arbitrary cross-account write, and an HTTP endpoint key must not be assumed reusable against its original vendor.

The delivery role trusted `firehose.amazonaws.com`, constrained by the account and exact delivery-stream source ARN. Its inline policy allowed only the required S3 bucket/object actions on the two test buckets.

The caller role allowed only these actions on the exact stream ARN:

No S3, IAM, KMS, Lambda, CloudWatch Logs, or other destination permission was granted to the caller.

## Live results

### Exact-resource reads and ingestion

- `DescribeDeliveryStream` succeeded with the exact delivery-stream ARN.
- `PutRecord` succeeded with the exact delivery-stream ARN.
- The original marker was written to the first S3 bucket by the Firehose delivery role.
- The caller had no direct S3 access in its test boundary.

This is an expected data-poisoning primitive: Firehose is the authorization boundary, and the configured role performs delivery.

### Destination redirection without PassRole

The caller supplied the current version and destination ID plus a partial `ExtendedS3DestinationUpdate` containing the second bucket, prefix, error prefix, and buffering values. It intentionally omitted `RoleARN`.

Results:

1. `UpdateDestination` succeeded using only the exact Firehose action.
2. `DescribeDeliveryStream` showed the new bucket and retained delivery role.
3. A second exact-stream `PutRecord` succeeded.
4. The second marker was delivered to the replacement bucket by the retained role.

The delivery role was deliberately authorized for both buckets. This proves the authorization behavior, not a bucket-policy bypass.

### Explicit role triggers PassRole

A second update supplied the same existing role ARN. The caller still had the exact-stream Firehose permission but no `iam:PassRole`. AWS denied it:

```text
AccessDeniedException: ... is not authorized to perform: iam:PassRole on resource:
arn:aws:iam::228478051196:role/ht-firehose-audit-20260927
```

Therefore omission is security-relevant: it retains the existing role without a new PassRole authorization, while providing any role value triggers PassRole.

### HTTP destination retention

No external HTTP collector was created. Current API shapes and AWS documentation establish that the URL may be supplied while the access key and other optional endpoint fields are omitted. The public page keeps this as a conditional expected technique and requires an HTTPS server that implements Firehose's protocol.

### Lower-value and rejected ideas

- Creating a stream with a powerful role is not general role escalation. Firehose exposes only its configured source/processor/destination workflows and does not return credentials or provide an arbitrary AWS API proxy.
- S3 redirection cannot bypass the retained role's identity policy, bucket policy, ownership controls, or KMS policy.
- An HTTP access key may be only a Firehose ingestion token; broader reuse depends on the third-party service.
- Guessing destination/version IDs against live streams is state changing when correct and is not unauthenticated enumeration.
- No unsigned Firehose control/data API accepted requests.

## CloudTrail observations

The successful destination update was a default management event. Its request recorded:

```text
deliveryStreamName
currentDeliveryStreamVersionId
destinationId
extendedS3DestinationUpdate.bucketARN
prefix / errorOutputPrefix
bufferingHints
```

`responseElements` was `null`. The denied explicit-role update recorded `errorCode=AccessDenied` and the missing `iam:PassRole` in `errorMessage`, but `requestParameters` was `null`.

`CreateDeliveryStream`, `DescribeDeliveryStream`, `UpdateDestination`, and `DeleteDeliveryStream` appeared in Event History. `PutRecord` did not, as expected without Firehose data-event logging. CloudTrail supports selecting:

```text
AWS::KinesisFirehose::DeliveryStream
```

S3 object delivery is likewise a data-plane write attributed to the Firehose role and requires S3 data-event logging for object-level CloudTrail evidence.

## Cleanup proof

After both markers were read back successfully:

```text
matching delivery streams: []
ht-firehose-audit-20260927 role: absent
ht-firehose-caller-20260927 role: absent
original bucket: absent
redirect bucket: absent
```

The first client-side creation attempt used the outdated field spelling `SizeInMB`; parameter validation failed before stream creation. Its cleanup trap removed the two empty buckets and roles, and a separate inventory confirmed no residual before the corrected test began.

Only immutable CloudTrail management-event history remains. No AWS security defect or zero-day was confirmed, so no private report was created.
