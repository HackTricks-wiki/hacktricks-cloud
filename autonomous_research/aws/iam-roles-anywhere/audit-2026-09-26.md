# IAM Roles Anywhere attack-surface audit — 2026-09-26

## Scope and primary sources

Reviewed the regional IAM Roles Anywhere control plane, X.509 `CreateSession` flow, IAM role trust boundary, profiles/session policies, certificate attribute mappings, CRLs, subject history, telemetry, and cross-account behavior.

Primary sources checked:

- IAM Roles Anywhere API model and AWS CLI 2.34.45 command model
- AWS Service Authorization Reference for `rolesanywhere`
- IAM Roles Anywhere trust model, certificate attribute mapping, CreateSession, monitoring, and CRL documentation
- API references for every control-plane operation

## Existing coverage found

- STS privilege-escalation page already covered weak role trust policies and `UpdateTrustAnchor` CA replacement.
- IAM persistence already covered attacker-owned `CERTIFICATE_BUNDLE` trust anchors plus profiles.
- Cross-account documentation correctly stated that anchors/profiles/roles are same-account and same-Region; multi-account access is ordinary STS role chaining after the first Roles Anywhere session.
- There was no useful Roles Anywhere control-plane enumeration section and no coverage for profile-policy removal, attribute-mapping condition inversion, or CRL weakening.

## Live tests

All tests used the authorized account `228478051196`, Region `us-east-1`, explicit JSON output/Region variables, and disposable resources prefixed `htx-ra-`. Private keys stayed only in mode-0700 temporary directories, were never printed, and were deleted after each test. No `CreateSession` call was made because a successful call creates a Subject resource and the public API has no `DeleteSubject` operation.

### `UpdateProfile` without `iam:PassRole` — worked

Fixture:

- Disposable IAM role trusted `rolesanywhere.amazonaws.com`.
- Enabled profile containing that role and the restrictive AWS managed `ReadOnlyAccess` session policy.
- Disposable caller with only `rolesanywhere:UpdateProfile` and `rolesanywhere:DeleteAttributeMapping` on the exact profile ARN; it had no `iam:PassRole`.

Results:

- A patch that omitted `roleArns` successfully set `managedPolicyArns` to `[]`, changed `durationSeconds` from 3600 to 43200, and enabled `acceptRoleSessionName`.
- A separate fixture confirmed that the same exact-profile `UpdateProfile` permission, still without `iam:PassRole`, replaced a restrictive inline session policy with `Allow`, `Action: *`, `Resource: *`.
- The existing role list was retained in both responses. This establishes that the session-policy boundary can be removed without PassRole when `roleArns` is omitted. Supplying/changing `roleArns` remains the PassRole boundary documented by the Service Authorization Reference.
- CloudTrail recorded `UpdateProfile` as a default management write. Request parameters contained the empty managed-policy list, duration, role-session-name setting, and (for the other test) replacement inline policy; response elements contained the resulting profile and retained role ARN.

Book decision: added. This is a strong privilege-escalation boundary because a certificate holder can move from the profile's restricted intersection to the full effective permissions of an already-associated role. It does not exceed that role and still requires a valid certificate/private key and a role trust policy that accepts the session.

### Attribute-mapping deletion — worked

- The same minimum-permission caller successfully invoked `DeleteAttributeMapping` on the exact profile ARN with `certificateField=x509Issuer` and `specifiers=*`.
- The resulting profile no longer contained any issuer mapping.
- AWS's own trust-policy documentation states that if the referenced certificate principal tag is no longer mapped, `StringEquals` evaluates false while `StringNotEquals` evaluates true. This makes negative/missing-key-tolerant trust conditions fail open.
- CloudTrail recorded the profile ID, field, and removed specifier in request parameters and the remaining mappings in response elements.

Book decision: added with strict prerequisites. It needs a trusted certificate/private key and a role trust statement using a vulnerable negative or `...IfExists` condition. Positive `StringEquals`, `aws:SourceArn`, signature validation, and trust-anchor validation are not bypassed.

### CRL disable with exact-resource permission — worked

Fixture:

- Disposable external root CA and a CA-issued client certificate.
- Client certificate revoked through OpenSSL; a signed CRL containing that serial was generated.
- Disposable external-bundle trust anchor and enabled imported CRL.
- Disposable caller with only `rolesanywhere:DisableCrl` on the exact CRL ARN.

Results:

- `DisableCrl` succeeded and returned `enabled: false` with the associated trust-anchor ARN.
- CloudTrail recorded a default management write whose request named the CRL ID and whose response exposed the disabled state.
- Importing a CA-signed CRL containing no revoked certificate was rejected with `ValidationException: At least one of the included CRLs doesn't include a revoked certificate.` This prevents the simplest empty-CRL replacement but does not prevent disabling/deleting the CRL or updating it to another valid signed CRL that omits a chosen serial while retaining another revoked entry.

Book decision: added as regional service-level persistence. It only resurrects a certificate/private key the attacker still possesses and does not create new identity material.

## Enumeration conclusions

- Enumerate every Region. Anchors, profiles, CRLs, subjects, and their CloudTrail control-plane events are regional.
- `GetProfile` is the key correlation point: it exposes target role ARNs, managed/inline session policies, maximum duration, custom session-name acceptance, and certificate attribute mappings.
- Correlate the profile with each IAM role trust policy. The main conditions are `aws:SourceArn`, `aws:SourceAccount`, `sts:SourceIdentity`, and the mapped `aws:PrincipalTag/x509*` keys.
- `GetSubject` exposes certificate bodies, serials, issuer/subject activity, and recent authentication outcomes. Its `credentials` member contains `CredentialSummary` certificate records, not AWS access keys, secret keys, private keys, or reusable sessions.
- CRLs are optional. IAM Roles Anywhere does not use OCSP or fetch CRL Distribution Points, so imported enabled CRLs are the only service-side certificate-revocation input.

## Attack inventory and decisions

| Idea | Result | Book decision |
| --- | --- | --- |
| Weak role trust lets any certificate under an account anchor select a privileged profile role | Expected and already covered | Retained/corrected stealth metadata |
| Replace an external-bundle anchor CA with `UpdateTrustAnchor` | Expected and already covered | Retained/corrected stealth metadata |
| Create attacker CA anchor + profile | Expected and already covered | Retained |
| Remove managed/inline profile session boundaries with `UpdateProfile` but no PassRole | Live verified | Added to privesc |
| Enable 12-hour sessions / caller-chosen role session names with `UpdateProfile` | Live verified | Included as secondary impact, not a separate low-value technique |
| Delete/narrow certificate mappings to make `StringNotEquals` or `...IfExists` conditions pass on a missing tag | Mutation live verified; evaluation semantics explicitly documented by AWS | Added to privesc |
| Disable/delete/replace CRL to restore a revoked certificate | Disable path live verified; other APIs documented | Added to persistence |
| Delete/disable trust anchors or profiles | Ordinary denial of service | Not added |
| Manipulate certificate-expiry notification settings | Hides an operational warning but does not preserve an already-expired certificate or add access | Not added |
| Read Subject certificate history | Useful PKI/authentication reconnaissance but no private key or live credentials | Added only to enumeration |
| Direct cross-account profile/anchor use | Unsupported: all Roles Anywhere resources and directly assumed roles are same-account; chain with STS afterwards | Existing cross-account text sufficient |
| Add/change `roleArns` through `UpdateProfile` | Requires `iam:PassRole`; ordinary PassRole path | Not split into a separate technique |
| `TagResource` against tag-gated administration policy | Generic ABAC self-grant pattern and configuration-dependent | Tracked, not added as Roles Anywhere-specific technique |

## Further test queue

Expected-feature work:

- Validate `UpdateCrl` with two revoked certificates, replacing the CRL with a valid signed CRL that preserves one serial but removes the other.
- Confirm exact `EnableProfile` PassRole evaluation when the profile's role list is unchanged.
- Capture a sanctioned existing `CreateSession` event, if one becomes available, to settle whether this environment records a separate STS `AssumeRole` event in addition to the Roles Anywhere `CreateSession` event without creating an undeletable Subject.
- Test resource-tag authorization boundaries on profile, anchor, CRL, and Subject operations, including whether tag mutation can self-satisfy a poorly designed `aws:ResourceTag` policy.

Unexpected-behavior candidates (no finding yet):

- PKIX path-building ambiguity with same-subject intermediate CAs, alternate chains, name constraints, policy constraints, and chain order.
- CRL association/issuer-collision edge cases across multiple anchors and intermediate CAs.
- Duplicate/malformed critical extensions, repeated RDNs/SANs, Unicode/canonicalization differences, and multi-valued attribute-to-principal-tag condition semantics.
- RSA-PSS/ECDSA algorithm-declaration mismatches and required-header coverage already surfaced in `CreateSession.additionalEventData`.
- Stale trust-anchor validity caching for AWS Private CA anchors between PCA validity changes and `UpdateTrustAnchor` refresh.

No unexpected authorization or validation flaw was confirmed, so no private bug-bounty report was created.
