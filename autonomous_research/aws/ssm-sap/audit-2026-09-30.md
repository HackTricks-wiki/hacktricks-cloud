# AWS Systems Manager for SAP audit — 2026-09-30

## Result

Added the missing service inventory and two useful post-exploitation techniques:

1. `ssm-sap:GetDatabase` exposes the Secrets Manager identifier configured for each SAP HANA `ADMIN` credential. A separately authorized `secretsmanager:GetSecretValue` (and sometimes `kms:Decrypt`) recovers the credential value.
2. Exact-application `ssm-sap:StopApplication` can stop registered SAP processes, optionally a connected HANA DBMS. EC2 host shutdown is a separate branch that AWS validates against the caller's `ec2:StopInstances` permission.

These are expected AWS functions, not vulnerability candidates.

## Current API and IAM surface

AWS CLI 2.37.6 exposes 27 control-plane operations: resource-permission CRUD; application registration, deregistration, start, stop, refresh and settings updates; application/component/database getters and listers; operation/event getters and listers; configuration checks; and tags.

The Service Authorization Reference defines:

- application: `arn:${Partition}:ssm-sap:${Region}:${Account}:${ApplicationType}/${ApplicationId}`;
- component: the application ARN plus `/COMPONENT/${ComponentId}`;
- database: the application ARN plus `/DB/${DatabaseId}`.

`StopApplication`, `StartApplication`, refresh, settings update and deregistration advertise exact application resources. `GetComponent` supports a component resource. `GetDatabase`, `GetApplication`, operation/configuration reads, database lists and resource-permission operations are wildcard-only.

## Live account and authentication checks

Read-only inventory in both `us-east-1` and `eu-west-1` returned zero applications, databases and components. `us-east-1` advertised three configuration checks (instance type, EBS configuration and Pacemaker configuration). An unsigned `ListApplications` request failed with `MissingAuthenticationTokenException`.

The account has no `AWSServiceRoleForAWSSSMForSAP` role. No SAP application, EC2 instance, SSM managed node, secret, KMS key, role or AWS Backup fixture was created.

## Restricted-session authorization probes

All probes assumed `ChackBotAdministratorRole` from `hacktricks-training` with a restrictive inline session policy and used fabricated identifiers only.

| Probe | Result | Conclusion |
| --- | --- | --- |
| `GetDatabase` with `Resource: "*"` | Reached `ValidationException: No database found` | `ssm-sap:GetDatabase` wildcard grant authorizes the call |
| `GetDatabase` with only a fabricated database ARN | `AccessDenied`; evaluated against synthetic `arn:aws:ssm-sap:us-east-1:228478051196:/get-database` | Confirms no database resource type is supported for the action |
| `StopApplication` with `Resource: "*"` | Reached `ResourceNotFoundException` | Wildcard control authorized the request before existence validation |
| `StopApplication` with only the fabricated intended application ARN | `AccessDenied` on `resource: *` | A nonexistent ID is unresolved during authorization; this does **not** contradict documented exact scoping for a real application |

The exact-live `StopApplication` minimum could not be exercised without a registered SAP workload. AWS's current authorization table and troubleshooting examples explicitly show the application ARN, including the need for permission on the connected HANA application. Public coverage uses that documented live-resource boundary and does not claim the synthetic wildcard behavior applies to existing applications.

## Credential-recovery boundary

The `GetDatabase` response schema includes `Credentials[]` with `DatabaseName`, `CredentialType` and `SecretId`. Registration documentation requires an ADMIN secret containing `username` and `password`. The SSM for SAP read returns the identifier only. Secret value recovery remains independently authorized by Secrets Manager and, for a customer-managed key, KMS.

This is valuable because a principal that can read both planes need not guess which secret contains the SAP administrator account. Impact is database access allowed by that SAP credential, not AWS IAM or automatic EC2-host access.

## Stop boundary and downstream authority

The service-linked-role policy can send only AWS-managed SAP SSM documents to EC2 instances tagged `SSMForSAPManaged=True`. It can also start/stop tagged instances. There is no arbitrary command/document input in `StopApplication`.

AWS separately validates the caller:

- `ssm-sap:StopApplication` on the target application;
- the same action on a connected HANA application when the DBMS is included;
- `ec2:StopInstances` on associated hosts when EC2 shutdown is requested.

Without the EC2 grant, the documented result is `ValidationException: Caller lacks permissions to stop Amazon EC2 instances`. Therefore public coverage does not overclaim that `StopApplication` alone shuts down EC2.

## Restore permission and settings hypotheses

- `PutResourcePermission` accepts only action type `RESTORE` and connects a source database ARN to a target database ARN. AWS Backup documentation uses it as preparation for a destructive system-copy restore. It is not sufficient by itself: a recovery point, AWS Backup restore job, restore role/pass-role and relevant restore authorization are still needed. Recorded for enumeration, not promoted as a standalone attack.
- `UpdateApplicationSettings` can add/update/remove credential SecretIds and replace an ABAP application's connected HANA database ARN. Credential-reference poisoning and connection sabotage are plausible, but no registered workload was available to validate refresh/runtime effects, so no book technique was added.
- `RegisterApplication` triggers fixed discovery through the service-linked role rather than accepting an arbitrary SSM document or command. No `iam:PassRole` execution path was found.

## Telemetry

AWS documents every SSM for SAP API call as CloudTrail-captured control-plane activity under `ssm-sap.amazonaws.com`. The service also emits best-effort direct EventBridge `SSM for SAP Operation State Change` events and `AWS/SSMForSAP` operation metrics.

Event History indexed every restricted probe. `GetDatabase` appeared as `readOnly: true`; `StopApplication` appeared as `readOnly: false`. Both retained the supplied database ARN/application ID and the restricted STS session name, including denied and nonexistent-resource attempts. Existing records also confirmed failed `PutResourcePermission` and `UpdateApplicationSettings` requests as default management writes with request fields retained. A successful stop would additionally produce SSM service-role activity and, when requested, an EC2 `StopInstances` event.

## Cleanup

Only read calls, nonexistent-resource probes and expiring STS sessions were used. Final inventories remained empty and the SSM for SAP service-linked role remained absent. Cleanup was empty by construction.
