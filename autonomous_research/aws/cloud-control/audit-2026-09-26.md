## Documentation and authorization audit

AWS's current Service Authorization Reference assigns Cloud Control API actions to the `cloudformation` service prefix:

- `cloudformation:CreateResource`
- `cloudformation:DeleteResource`
- `cloudformation:GetResource`
- `cloudformation:ListResources`
- `cloudformation:UpdateResource`

The API/CLI namespace and CloudTrail source remain `cloudcontrol` / `cloudcontrolapi.amazonaws.com`. The existing HackTricks page incorrectly used `cloudcontrolapi:*` in its heading, prose and policy example.

The generic operations have no resource-level ARN type or service-specific condition key in the authorization reference. `Resource: "*"` is therefore required for the Cloud Control front-door action. Handler-defined permissions and `iam:PassRole` remain separate authorization layers.

## Live tests

### Unknown IAM namespace grants nothing

1. Created `ht-cloudcontrol-audit-20260926` trusted only by the administrative setup role.
2. IAM accepted an inline statement allowing `cloudcontrolapi:GetResource`; policy creation did not reject the unknown service/action string.
3. With `iam:GetRole` separately allowed, direct `GetRole` succeeded but Cloud Control failed at its front door:

```text
not authorized to perform: cloudformation:GetResource on resource:
arn:aws:cloudformation:us-east-1:228478051196:resource/*
```

Conclusion: `cloudcontrolapi:GetResource` is a silent no-op. The correct permission is `cloudformation:GetResource`.

### Generic action alone does not bypass the target service

With only `cloudformation:GetResource`, the Cloud Control front door accepted the request, but the `AWS::IAM::Role` handler failed on `iam:GetRole`. After granting `iam:GetRole`, the handler next required `iam:ListAttachedRolePolicies`. A successful read required the handler's modeled IAM reads, including role and policy-listing/policy-read operations.

The successful response for `AWSServiceRoleForServiceQuotas` contained:

- role name, ARN, ID, path, description and maximum session duration;
- the complete assume-role policy;
- the attached AWS managed policy ARN.

Conclusion: without `RoleArn`, Cloud Control runs the handler with the caller's credentials. No target-service authorization bypass was found.

### Passed-role read proxy

Created `ht-cloudcontrol-handler-20260926`, trusted by `cloudformation.amazonaws.com`, with the IAM read operations needed by the `AWS::IAM::Role` handler. Reduced the caller role to:

- `cloudformation:GetResource`
- `cloudformation:ListResources`
- `iam:PassRole` on the exact handler role

Results:

| Probe | Result |
| --- | --- |
| Direct `iam:GetRole` | Denied |
| Direct `iam:ListRoles` | Denied |
| Cloud Control `GetResource` without `RoleArn` | Denied by the IAM handler |
| Cloud Control `GetResource` with the passed handler role | Succeeded; full modeled role properties returned |
| Cloud Control `ListResources` with the passed handler role | Succeeded; IAM role identifiers returned |

This is expected stored-authority behavior, not an AWS defect. It is useful for post-exploitation when the caller can pass but cannot directly assume an inventory/deployment role.

### CloudTrail

Observed successful `GetResource` event:

- `eventSource`: `cloudcontrolapi.amazonaws.com`
- `eventName`: `GetResource`
- `readOnly`: `true`
- `requestParameters`: `typeName` and `identifier`
- `responseElements`: `null`

The handler-level `iam:GetRole` denial retained the requested type and identifier in the outer event but CloudTrail reduced the error message to `An unknown error occurred`. Front-door denials sometimes had `requestParameters: null` and preserved the missing `cloudformation:GetResource` error.

After normal lookup latency, the passed-role events were visible. Both successful `GetResource` and `ListResources` recorded the complete handler `roleArn`, resource `typeName`, and supplied identifier or `maxResults`; their `responseElements` were `null`. The adjacent `GetResource` without a role recorded the type and identifier but reported only `AccessDenied` / `An unknown error occurred`.

## Publication decisions

- Correct the privilege-escalation page from the ineffective `cloudcontrolapi:*` namespace to `cloudformation:*`.
- Add a service enumeration page explaining the three authorization layers and the passed-role read proxy.
- Do not publish the direct generic-action-only path as an attack: the target-service handler permissions are enforced, so it provides no extra authority.
- Do not create a private AWS report. No unexpected authorization bypass or malfunction was found.

## Future tests / backlog

- Compare read-handler permissions and returned properties for high-value supported types: Secrets Manager secrets, SSM parameters, Lambda functions, API Gateway resources, Cognito pools, Glue connections and CloudFormation registry extensions.
- Determine whether a type exposes a modeled sensitive property that its native read API redacts or protects with an additional action. Any difference must be tested with least privilege before publication and treated as a potential AWS report.
- Test whether provider handler errors leak existence across identifiers when the caller has the generic action but lacks target-service reads.
- Compare `ListResourceRequests` and `GetResourceRequestStatus` ownership boundaries across principals and passed roles; look for request-token IDOR or disclosure of desired-state/error data.
- Test private third-party resource types for unsafe logging, overly broad execution-role use, mutable type configuration and confused-deputy paths.
- Audit Cloud Control operations invoked by AWS service-linked roles (for example Resource Explorer) to understand indirect visibility and attribution.
