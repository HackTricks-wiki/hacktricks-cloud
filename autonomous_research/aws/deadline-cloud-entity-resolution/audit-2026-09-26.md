# Deadline Cloud and Entity Resolution audit — 2026-09-26

## Inventory and scope

- Reviewed both enum pages against the current API references and Service Authorization Reference.
- Read-only lab inventory in `us-east-1`: zero Deadline farms and zero Entity Resolution schema
  mappings, matching workflows, or ID-mapping workflows before testing. Other tested regions were
  blocked by the lab SCP and were not mutated.
- No public unauthenticated surface was identified for either service.

## Entity Resolution results

### `AddPolicyStatement` append-only resource-policy persistence — verified

`AddPolicyStatement` is a distinct, useful companion to the existing `PutPolicy` technique. It needs
only `entityresolution:AddPolicyStatement` on `*`, takes a known resource ARN, and appends a named
statement without a revision token or `GetPolicy`. The request accepts an AWS account ID or service
principal. A cross-account attacker still needs an identity-policy allow in that account.

Live validation used a disposable matching workflow backed by a disposable Glue table, S3 bucket,
schema mapping, and minimally scoped Entity Resolution role. A caller constrained to the single
`AddPolicyStatement` action reached service-side policy validation rather than an authorization denial.
In a separate successful append using the real lab account ID as principal, the service accepted both
`GetMatchingWorkflow` and `StartMatchingJob`, expanded the principal to
`arn:aws:iam::<account>:root`, and returned the updated policy. A fake 12-digit account ID was rejected
as `Invalid Policy`.

Observed implementation/documentation mismatch: a schema-mapping ARN passed the published client-side
pattern but the service rejected it and stated that only `idmappingworkflow`, `idnamespace`, and
`matchingworkflow` targets are supported. Do not advertise schema mappings for this path without
revalidation.

Disposition: integrated into the public resource-policy technique with exact permissions, principal
constraints, impact, stealth, and CloudTrail details.

### Per-run `StartIdMappingJob` output override — documented contract

The start request can override the output S3 path and output role for that run. This allows a principal
with `StartIdMappingJob` plus `iam:PassRole` on an Entity Resolution-trusting output role to write the
fresh ID map to an attacker-readable S3 destination without changing the stored workflow. The result is
an identifier mapping table, not arbitrary raw input columns, so the impact is deliberately bounded.

The API contract and Service Authorization Reference establish the output fields, PassRole dependency,
and namespace-use dependency. No job was launched because the empty lab had no genuine ID namespaces or
datasets and manufacturing a synthetic mapping run would add no authorization evidence beyond the
contract.

Disposition: added as post-exploitation because the per-run destination override is operationally
different from the generic create-workflow PassRole catalog and has direct confidentiality impact.

## Deadline Cloud results and rejected candidates

- Existing coverage already contains the two high-value no-compute chains: queue-role credentials via
  `AssumeQueueRoleForUser`, and fleet-role credentials via a logical customer-managed-fleet worker and
  `AssumeFleetRoleForWorker`. Both already have live validation and complete technique metadata.
- `AssumeQueueRoleForWorker` was considered as a separate escalation. It is intended for a fleet-role
  session processing an assigned queue job, requires both queue and worker context, and gives the same
  queue role used by the already documented job/queue paths. Without evidence that an unassigned logical
  worker can bypass scheduling, presenting it as a new technique would overstate the boundary. Retain as
  a future test only when a real worker/job fixture is available.
- `CreateJob` arbitrary command execution remains real but compute-gated: attacker-supplied Open Job
  Description commands execute only when an associated live worker accepts the task. It is not a
  zero-cost control-plane escalation and is already tracked in the Deadline checklist; no duplicate
  public technique was added.
- Queue environments can inject variables into jobs, but those values only affect scheduled worker
  sessions. Without worker execution or a demonstrated credential/log exfiltration primitive, this is a
  job-tampering subcase rather than a separate high-value technique.
- Monitor creation and Identity Center wiring require an Identity Center instance/application not
  present in this member account. No unsupported claim was made.

## Cleanup and telemetry

All disposable Entity Resolution workflows/schema mappings, Glue tables/databases, S3 buckets, IAM
roles/policies, and policy statements were deleted. Independent prefix inventory returned zero matching
workflows, schema mappings, Glue databases, buckets, and roles. No job or compute resource was launched.

CloudTrail confirmed `AddPolicyStatement`, `DeletePolicyStatement`, `CreateMatchingWorkflow`, and
`DeleteMatchingWorkflow` as default management events. The successful policy event records the resource
ARN, statement ID, principal, effect, and requested actions; `iam:PassRole` has no standalone event.
