# AWS Proton attack-surface audit — 2026-09-26

## Lifecycle result

AWS stopped accepting new Proton customers on October 7, 2025 and will end support on October 7, 2026. Existing deployed infrastructure remains after shutdown. This sharply limits the remaining testing and operational window and must be shown on the public technique page.

The authorized account could call Proton inventory APIs and had no environments, components, templates, services, repositories, connections, or account roles configured. `CreateEnvironmentTemplate` from the assumed administrator returned `AccessDeniedException`. Because the account had no pre-existing Proton use and AWS blocks new customers, no Proton template/environment fixture could be created for an end-to-end component test.

## Candidate matrix

| Candidate | Boundary and disposition |
| --- | --- |
| `CreateEnvironment` plus `iam:PassRole` and template control | Existing valid technique. The caller passes the environment role at create time and Proton provisions attacker-controlled IaC with it. |
| `CreateComponent` against an environment with `componentRoleArn` | Strong missing technique. AWS explicitly documents that a directly defined component takes caller-supplied IaC inline and Proton assumes the environment's component role. Service authorization lists no `iam:PassRole` dependency for `CreateComponent`. Added to the book as high-confidence documented delegated execution. |
| `UpdateComponent` template replacement | Same stored-role primitive on an existing component, resource-scoped to its component ARN. Included with the create path. |
| Attacker-controlled service template plus `CreateService` | Plausible stored environment-role execution, but it needs several template registration/publication/service actions and is dominated by one-action `CreateComponent`; not promoted separately. |
| `UpdateAccountSettings` pipeline-role replacement | Requires `iam:PassRole` and a subsequent service-pipeline provisioning path. Not a standalone escalation and was previously overgeneralized as equivalent to environment creation. Retained only as a related logged entry point. |
| Environment account connection | Explicit cross-account deployment design. Creation/update requires PassRole in the environment account and acceptance in the management account; no authorization bypass was found. |

## Component permission boundary

- Direct components have no Proton template resource or S3 bundle; `CreateComponent` receives the manifest and IaC template directly.
- The target environment must have a `componentRoleArn`, and AWS-managed provisioning assumes it for every directly defined component in that environment.
- The Service Authorization Reference lists only `proton:CreateComponent` (and `proton:TagResource` when tagging), not `iam:PassRole`, for the API.
- `CreateComponent` supports the component resource type, whose ARN contains a generated ID. A wildcard over that type is therefore the practical create policy; `UpdateComponent` can use the exact ARN after creation.
- Impact is exactly the stored role's CloudFormation/Terraform authority. A narrowly scoped component role limits the primitive; a broad role can turn it into account privilege escalation.

## Live setup attempt and cleanup

A no-cost fixture was prepared locally: an environment template would create one SSM parameter, and a directly defined component would create a second parameter under a component role. Before the denied Proton registration, the setup created one private S3 bucket and three narrowly named IAM roles. The failed registration created no Proton resource and no CloudFormation/SSM resource.

All setup resources were then deleted. Independent final inventory returned:

```text
Proton test templates: 0
Proton test environments: 0
Proton test components: 0
IAM roles beginning ht-proton-: 0
S3 buckets beginning ht-proton-: 0
SSM parameters under /ht/proton/20260926: 0
```

No unexpected AWS flaw was found and no private vulnerability report was created.
