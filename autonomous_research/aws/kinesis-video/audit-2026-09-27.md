# Amazon Kinesis Video Streams security audit — 2026-09-27

## Scope and safety

- Service: Amazon Kinesis Video Streams, archived media, media ingestion, WebRTC signaling, TURN/ICE and WebRTC storage mapping.
- Region: `us-east-1`.
- Authorized base profile: `hacktricks-training`.
- Test role: `arn:aws:iam::228478051196:role/ChackBotAdministratorRole`.
- Least privilege was tested with inline STS session policies, so no IAM users, roles, policies, or access keys were created.
- Live media consisted of a generated three-second, 160x120 H.264 test pattern only. No real customer media was accessed.
- Costs were limited to several short-lived empty/three-fragment streams, signaling channels, and one SNS topic. All delete requests were issued immediately after each test.

## Documentation baseline

Before this audit, the repository had no Kinesis Video Streams service-enumeration, post-exploitation, privilege-escalation, or persistence page. The only page was an unauthenticated-access placeholder containing a generic opaque endpoint format, which could be misread as implying that an endpoint hostname was a public stream.

## API and IAM attack-surface inventory

### Stream resources

- Control/inventory: `ListStreams`, `DescribeStream`, tag APIs, storage tier, image generation, notifications, edge agent.
- Endpoint discovery: `GetDataEndpoint` for `PUT_MEDIA`, `GET_MEDIA`, `LIST_FRAGMENTS`, `GET_MEDIA_FOR_FRAGMENT_LIST`, `GET_HLS_STREAMING_SESSION_URL`, `GET_DASH_STREAMING_SESSION_URL`, `GET_CLIP`, and `GET_IMAGES`.
- Data plane: `PutMedia`, `GetMedia`, archived fragments/clips/images, HLS and DASH sessions.
- Integrity/destructive: media injection, retention decrease, tier changes and stream deletion.

### Signaling-channel resources

- Control/inventory: `ListSignalingChannels`, `DescribeSignalingChannel`, tags and endpoint discovery.
- WebRTC: `ConnectAsMaster`, `ConnectAsViewer`, `GetIceServerConfig`, `SendAlexaOfferToMaster`.
- Storage: `UpdateMediaStorageConfiguration`, `DescribeMediaStorageConfiguration`, `DescribeMappedResourceConfiguration`, `JoinStorageSession`, `JoinStorageSessionAsViewer`.

### Important IAM boundaries

- `ListStreams`, `ListSignalingChannels`, and `ListEdgeAgentConfigurations` have no resource type in the service authorization reference and require `Resource: "*"`.
- Media and channel actions support their exact stream/channel ARN.
- `GetDataEndpoint` is necessary but not sufficient: the eventual media API has its own action.
- `UpdateMediaStorageConfiguration` has only `channel` as its supported resource type. The destination stream is not a dependent authorization resource.
- KVS has no resource-policy management API. AWS's cross-account access pattern requires a role in the resource-owning account.

## Live test results

### 1. Exact-channel ICE/TURN credential vending — confirmed

Created one `SINGLE_MASTER` signaling channel and assumed a session restricted to:

```json
{
  "Effect": "Allow",
  "Action": [
    "kinesisvideo:GetSignalingChannelEndpoint",
    "kinesisvideo:GetIceServerConfig"
  ],
  "Resource": "<exact-channel-arn>"
}
```

Results:

- HTTPS endpoint discovery succeeded.
- `GetIceServerConfig` succeeded.
- Response contained two credential sets.
- Observed TTL: 300 seconds.
- URI schemes: `turn` and `turns`.
- Observed password length: 44; username length: 135.
- Credential values were never printed or written to disk.

Conclusion: expected sensitive-token behavior. These are short-lived TURN bearer credentials, not AWS credentials and not a substitute for signaling authorization.

### 2. HLS/DASH bearer playback — confirmed

Created one 1-hour-retention stream and uploaded a generated 31,968-byte H.264 MKV using a session restricted to the exact stream and these actions:

- `GetDataEndpoint`
- `PutMedia`
- `GetHLSStreamingSessionURL`
- `GetDASHStreamingSessionURL`

The custom SigV4 request received HTTP 200 and three `PERSISTED` acknowledgements. HLS and DASH `LIVE` session creation each returned an authenticated URL with a 165-character query component.

Unauthenticated fetch comparison:

| Request | HLS | DASH |
| --- | --- | --- |
| Complete session URL, no AWS credentials | HTTP 200 | HTTP 200 |
| Same path with query token removed | HTTP 400 | HTTP 400 |

AWS accepts requested expiration from 300 to 43,200 seconds. Conclusion: expected bearer-capability behavior suitable for a temporary persistence technique. No token was retained.

### 3. Exact-stream `PutMedia` evidence injection — confirmed

The same exact-stream session uploaded three MKV clusters and received `BUFFERING`, `RECEIVED`, and `PERSISTED` acknowledgements for each fragment. `ListFragments` observed all three archived fragments in an earlier run.

Conclusion: a principal with only endpoint discovery and `PutMedia` can inject evidence/analytics input into one stream. This is expected functionality, not privilege escalation.

### 4. WebRTC storage remap without destination-stream permission — confirmed

Created one retained stream and one signaling channel. Assumed a session whose entire KVS allow was:

```json
{
  "Effect": "Allow",
  "Action": "kinesisvideo:UpdateMediaStorageConfiguration",
  "Resource": "<exact-channel-arn>"
}
```

The session successfully enabled storage to the stream ARN despite having no KVS permission on that stream. An administrator then confirmed the mapping with `DescribeMediaStorageConfiguration`.

Conclusion: expected documented resource model, but an important authorization edge. Protect the channel action as authority to select the storage destination.

### 5. Notification destination replacement with only KVS permission — confirmed

Created one stream and SNS standard topic. A session restricted to `kinesisvideo:UpdateNotificationConfiguration` on the exact stream successfully installed that topic ARN without any SNS action in the session policy.

The configuration call is separate from delivery authorization. Official AWS documentation says cross-account publishing additionally requires `sns:Publish` on the producer calling `PutMedia` and an SNS topic policy that trusts the source account.

Conclusion: persistent metadata redirection is practical when the producer/topic permissions already allow the chosen destination; the KVS update action alone does not bypass SNS authorization.

### 6. Endpoint hostname behavior — confirmed, rejected as a book attack

Previously allocated `b-...` and `s-...` endpoint hosts resolved and returned an HTTP response at `/`; invented opaque IDs did not resolve. The hostname still contained no account/stream/channel mapping and did not authorize any request.

Conclusion: the DNS distinction is mostly useless, expensive to search over opaque IDs, and not a foothold. It is recorded here but deliberately not promoted as an attack technique.

### 7. Empty-stream playback behavior — confirmed negative

HLS and DASH session creation on a retained stream with zero fragments returned `ResourceNotFoundException: No fragments found in the stream for the streaming request.` This prevents token-generation testing without actual media but is not a security boundary.

## CloudTrail and stealth findings

The account had no trails or event data stores during this test. Event history showed the management actions promptly:

- `CreateStream`, `DescribeStream`, `DeleteStream`
- `GetDataEndpoint` with stream ARN and requested API name
- `GetSignalingChannelEndpoint` with channel ARN, protocol and role
- list operations and configuration updates

The following endpoint/data-plane operations did not appear in default Event history:

- `PutMedia`
- `GetHLSStreamingSessionURL` / `GetDASHStreamingSessionURL`
- bearer playlist fetches
- `GetIceServerConfig`

CloudTrail supports optional KVS data-event resource types:

- `AWS::KinesisVideo::Stream`, including activity such as `GetMedia` and `PutMedia`.
- `AWS::KinesisVideo::SignalingChannel` for signaling-channel activity.

Therefore, techniques using endpoint-specific APIs are high stealth when those data events are disabled, while endpoint discovery and persistent configuration changes remain normal management events. CloudWatch KVS/WebRTC metrics provide separate behavioral evidence.

## Cross-account conclusions

- KVS media streams/channels expose no resource-policy API. Direct identity policies in another account are not the documented authorization model.
- AWS documents assuming a role in the KVS resource-owning account for cross-account stream use.
- SNS fragment notifications can cross accounts, but only when both the producer identity and destination topic policy authorize publishing.
- HLS/DASH tokens and TURN credentials cross account/network boundaries as bearer capabilities without an AWS role, but are narrowly scoped and expire.

## Zero-day assessment

No AWS security malfunction was found. The channel-only authorization model for WebRTC storage mapping is reflected in the public service-authorization reference and behaved consistently. Playback URLs and TURN credentials are documented bearer capabilities. No private bug-bounty report was created.
