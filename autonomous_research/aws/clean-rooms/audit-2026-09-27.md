### Authentication boundary

Unsigned `ListCollaborations` and `ListConfiguredAudienceModels` requests both returned
`MissingAuthenticationTokenException`. An account ID, collaboration UUID or resource ARN is not
sufficient for unauthenticated enumeration.

Disposition: no unauthenticated technique.

### Newly published intermediate-table and analysis-log-export APIs

The current Service Authorization Reference/API model includes:

- `Create/Get/List/Update/Delete/PopulateIntermediateTable` and analysis-rule/version operations;
- `DisallowIntermediateTable`; and
- `Start/Get/ListAnalysisLogExport`.

AWS CLI `2.34.45` did not yet expose these commands. A current boto3 model exposed 103 Clean Rooms
operations, including all 16 intermediate-table/analysis-log operations. Signed calls using a fake
membership UUID reached the Clean Rooms service and returned `ResourceNotFoundException` naming the
target account for:

- `ListIntermediateTables`;
- `GetIntermediateTable`;
- `ListAnalysisLogExports`; and
- `GetAnalysisLogExport`.

This confirms that the endpoints are active and authenticated. It is SDK/CLI model lag, not an AWS
security defect. The enum uses current boto3 examples and warns operators not to mistake missing CLI
subcommands for absent resources.

The analysis-log export is deliberately constrained:

- only a member with `CAN_EXPORT_QUERY_ANALYSIS_LOG` that was the query runner or payer can export;
- only terminal, executed protected SQL queries are supported (not differential-privacy queries or
  PySpark jobs);
- AWS writes to same-Region S3 using the caller's existing authority rather than a passed role; and
- the exported Spark event log retains source-column names, physical-plan structure, timing and
  rounded scale information, while redacting values, query text, table/storage identifiers, account/
  role/KMS identifiers, stack traces and exact small counts.

Disposition: documented as an enumeration/recon surface. It was not promoted as a standalone attack
because the caller is already the runner or payer, must have an explicit collaboration ability, and
the intentionally preserved information is much weaker than raw data or query-result access.

### Intermediate-table controls

Reviewed the current documented controls:

- materialization consumes all referenced base-table access budgets, including transitive inputs;
- multi-party tables inherit a point-in-time snapshot of base constraints and may only make those
  controls more restrictive;
- repopulation refreshes the inherited snapshot and creates a new version;
- a contributing provider can disallow the table, optionally cascading to descendants; and
- removal of a base association makes dependent tables unusable and deletes their stored data.

No privacy bypass was claimed. A real test requires at least two collaboration members and paid query
execution; neither was necessary to document the expected controls and both would exceed this pass's
safe scope.

### Collaboration change requests

The current API can request member additions, member/ML ability changes, payer changes and
auto-approval changes. Only the collaboration creator can submit them. All members normally approve;
an enabled auto-approved change type can remove that approval round for exactly the configured
abilities. The invited account must still create its own membership and explicitly accept any payer
responsibility.

Disposition: added as conditional cross-account service persistence, not as an authorization bypass.
No external invitation was sent.

### ML/container and role boundary

Rechecked the custom-model chain: ECR model provider, configured algorithm association, data-provider
approval, ML input channel, trained model/inference, privacy configuration, and output/log recipients.
`iam:PassRole` is required on several create/update actions, but the customer container runs in an
isolated user space and does not thereby obtain the service role's AWS credentials or arbitrary direct
S3/Glue access. Data-provider approvals and collaboration abilities remain additional gates.

Disposition: do not publish a speculative PassRole-to-container privilege-escalation technique.

Potential unexpected-security tests, kept as hypotheses until reproduced:

1. Search for a stale inherited-constraint window in intermediate tables after a base-table rule is
   tightened but before repopulation; expected behavior is the documented snapshot, so report only if
   it violates the provider-visible contract or disallow behavior.
2. Fuzz change-request replacement semantics for ability omission, simultaneous auto-approval edits
   and stale approval races; expected behavior is atomic validation by all required members.
3. Test analysis-log redaction with adversarial column names, Spark error classes, unusual file
   formats and plan/operator strings for value/path/account leakage.
4. Test configured-audience-model policy canonicalization and concurrency hashes for principal or

5. Verify that custom container logs/metric names cannot disclose provider data beyond the selected

6. Probe KMS encryption-context/source-ARN enforcement for intermediate tables using owned keys and

## Telemetry

- Account and resource list/get operations are read-only CloudTrail management events under
  `cleanrooms.amazonaws.com` or `cleanrooms-ml.amazonaws.com`; responses are normally omitted.
- Write operations record resource identifiers, configuration and role ARNs. `iam:PassRole` has no
  standalone CloudTrail event.
- Protected-query SQL parameters are redacted in CloudTrail; analysis logs provide query-level audit.
- Analysis-log export adds a Clean Rooms management event, a native export record delivered to
  relevant members' log groups, and S3/KMS evidence where configured.
- S3 source/result reads and writes need data-event coverage. Cross-account audience-generation starts
  are documented in the starting account but not the configured-model owner's CloudTrail.
