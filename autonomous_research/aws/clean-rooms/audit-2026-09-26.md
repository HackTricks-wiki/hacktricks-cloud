  Reference, user guide, API models, CloudTrail behavior, and the existing 60-line post-exploitation
  page from commit `b040f6c4b` on the AWS research branch.

## Existing-page corrections

The old page overstated `UpdateConfiguredTableAnalysisRule` in three important ways:

1. The update operation cannot switch an existing `AGGREGATION` rule to `LIST`. Rules are addressed
   by configured-table ID **and type**. A live update with type `LIST` returned
   `ResourceNotFoundException` for the nonexistent list rule. A switch requires
   `DeleteConfiguredTableAnalysisRule` plus `CreateConfiguredTableAnalysisRule`.
2. `listColumns:["*"]` was not retained. The API expects configured column names, not a wildcard.
3. Rewriting a rule weakens the compromised table owner's controls; it does not give an ordinary
   query runner IAM control over another member's account or rules.

The original configured-table-association `PassRole` paragraph also lacked a concrete authority
path. A broad role is useful only for the source referenced by the configured table. The expanded
coverage pairs the stored association role with the newly documented configured-table source
retargeting path.

## Live validation

### Configured-table source substitution — verified

Created two disposable Glue catalog tables, `benign` and `sensitive`, then one Clean Rooms configured
table initially pointing to `benign`. No S3 bucket or objects were created; the Glue locations were
nonexistent fixture URIs and no data read occurred.

The configured-table update has conditional authorization checks that are easy to omit from IAM
reviews:

- A principal with only `cleanrooms:UpdateConfiguredTable` was denied specifically for missing
  `cleanrooms:UpdateConfiguredTableReference` when `tableReference` was supplied.
- After adding that permission-only action, the caller reached source validation but was denied
  because it lacked access to the Glue table.
- Adding resource-scoped `glue:GetDatabase` and `glue:GetTable` succeeded and changed the reference
  from `benign` to `sensitive`.
- A caller without `cleanrooms:UpdateConfiguredTableAllowedColumns` was denied specifically for that
  action. Adding it successfully widened the configured table to include a new `secret_note` column.

All Clean Rooms actions were scoped to the exact configured-table ARN. This establishes the minimum
control-plane permissions and the otherwise-undocumented-in-the-request Glue metadata prerequisite.
The configured table was not associated because safely producing an association would require a
collaboration with another account.

Disposition: added as the highest-value technique. An already-associated configured-table resource
can be retargeted while retaining its trusted identity and associations. Actual query access still
requires the stored association role to read the replacement source; `UpdateConfiguredTableAssociation`
plus `iam:PassRole` can replace that role when the attacker has those additional permissions.

### Analysis-rule weakening and type replacement — verified

Created an aggregation rule with minimum distinct-user threshold `10` and dimension `segment`. A
resource-scoped principal holding only `cleanrooms:UpdateConfiguredTableAnalysisRule` successfully:

- reduced the threshold to `2`; and
- added `email` as a dimension.

The same principal's attempt to submit `analysisRuleType=LIST` reached the service but failed because
no LIST rule existed. As administrator, deleting the aggregation rule and creating a LIST rule with
`email`, `revenue`, `segment`, and `secret_note` succeeded. This confirms both the useful same-type
attack and the correct two-action type-switch boundary.

CloudTrail recorded the complete replacement policy for create/update and the type on delete.

Disposition: rewrote the existing technique with exact minimum permissions, ownership boundary,
impact, stealth, and telemetry.

### Configured-audience-model policy authorization — verified to resource boundary

A least-privilege caller with only
`cleanrooms-ml:PutConfiguredAudienceModelPolicy` on a fake configured-audience-model ARN submitted a
valid same-account policy granting `StartAudienceGenerationJob`. The service returned
`ResourceNotFoundException`, not an IAM denial. No policy or model was created.

AWS documents the complete cross-account model:

- the configured-model owner policy grants `StartAudienceGenerationJob` on both the configured model
  and the owner's audience-generation-job wildcard;
- the starting account needs an identity allow on its own audience-generation-job ARN;
- only `StartAudienceGenerationJob` works cross-account;
- a `cleanrooms-ml:CollaborationId` condition forces active-collaborator validation; and
- the start is logged in the starting account but **not** the configured-model owner's CloudTrail.

Disposition: added as durable cross-account resource-policy persistence. Omission of the documented
collaboration condition is clearly identified as the removal of that validation binding, not as a
platform vulnerability. The public impact is bounded: the external caller can use/probe the model and
view configured shared metrics, but an export is written to the configured model owner's stored S3
destination, so object theft needs separate S3 access or output-configuration control. No external
principal or real job was used.

## Strong documented paths integrated without paid execution

### Privacy and data-access budget weakening

- `UpdatePrivacyBudgetTemplate` is resource-scoped to the template.
- Differential privacy accepts epsilon `1..20` and users-noise-per-query `10..100`. AWS explicitly
  documents that increasing epsilon permits more aggregate answers and that lower per-query noise
  yields more accurate answers.
- An access-budget edit replaces the configuration and resets the current balance. A period or
  lifetime budget can be raised to `1,000,000`.
- This does not grant query ability, so the technique requires an existing querying member.

Disposition: added with the precise parameter effects. The old vague statement that a "widened DP
budget weakens noise" was replaced with the actual epsilon/noise/balance behavior.

### Stored result and ML output redirection

- `UpdateMembership` can replace `defaultResultConfiguration` and
  `defaultJobResultConfiguration`, including the S3 destination and role. The Service Authorization
  Reference lists `iam:PassRole` when a role is supplied.
- `PutMLConfiguration` stores a membership's default S3 output location and role for trained-model
  artifacts and inference results. It is authorized on `*` and also depends on `iam:PassRole`.
- `UpdateConfiguredTableAssociation` can persistently replace the service role used to read a
  configured table.
- Passed roles remain same-account roles under normal `PassRole` semantics. Cross-account S3 output
  additionally needs a bucket policy. Role trust should bind the applicable Clean Rooms service,
  source account, and narrow source ARN.

Disposition: added as stored-authority persistence. No membership existed in the lab, so no role was
passed and no output was produced.

## Other surfaces reviewed and not promoted as attacks

### Collaborations and memberships

- Collaboration change requests can add members or update abilities. Auto-approved change types can
  reduce the approval cycle, while other changes require member approval. This is a sensitive
  administration surface but not a demonstrated authorization bypass; the invited account must still
  create a membership. It was not tested because inviting or affecting another account was prohibited.
- `DeleteMember`, `DeleteMembership`, and result-role deletion are straightforward destructive or
  denial-of-service actions and did not merit separate post-exploitation techniques.
- `UpdateMembership` can turn query/job logging off for the compromised membership. It does not turn
  off independently enabled logs delivered to other collaboration members, and the update remains in
  CloudTrail.

### Analysis templates, queries, jobs, and intermediate tables

- SQL analysis-template source is immutable; `UpdateAnalysisTemplate` changes only description.
- PySpark artifacts are pinned to the specific S3 object version and SHA-256 hash. AWS validates both
  at job time, so overwriting the key makes the job fail instead of replacing approved code.
- `StartProtectedQuery` and `StartProtectedJob` remain subject to configured-table and association
  rules. Results can go only to permitted receivers. `GetProtectedQuery` reveals SQL/metadata and an
  S3 location, not S3 object permission.
- Intermediate tables store materialized derived data, but inherit base-table constraints. Providers
  can call `DisallowIntermediateTable`, and base-table removal/retention state is tracked. No privacy
  bypass was claimed without a failing inherited-control test.
- Query/job starts and lifecycle state are CloudTrail/native EventBridge signals. CloudTrail redacts
  protected-query `sqlParameters` as `***`; analysis logs contain query text, rules, parameters, and
  result receivers when enabled.

### ID mapping

- `CreateIdMappingTable` and `CreateIdNamespaceAssociation` can manage underlying Entity Resolution
  resource policies when `manageResourcePolicies=true`, but this is the documented association flow
  and still requires ownership/authorization of the referenced resource.
- `PopulateIdMappingTable` creates mapping results but does not grant query permission.
- The ID mapping table analysis rule is AWS-managed and immutable. No credible rule-rewrite path was
  found.
- `allowUseAsDimensionColumn` on an ID namespace association is privacy-sensitive but not sufficient
  alone to extract data; query rules, membership abilities, and result-receiver controls remain.

### Clean Rooms ML models and audiences

- Creating a custom model algorithm does not alone expose collaboration data. Data providers must
  allow the configured algorithm association, and its privacy configuration controls container logs,
  metrics, artifact size, and inference output.
- Clean Rooms ML executes customer containers in an isolated user space; direct S3/Glue calls from
  the container are blocked by the documented architecture. No speculative arbitrary-role credential
  theft was added.
- `CreateMLInputChannel`, `CreateTrainedModel`, inference, model exports, audience generation, and
  audience exports all require additional collaboration/model/input/output controls and can incur
  compute cost. None were run.
- Delete/cancel APIs are destructive/availability paths, not confidentiality or privilege escalation
  by themselves.

## Telemetry

- Live CloudTrail events confirmed that `CreateConfiguredTable`, `UpdateConfiguredTable`,
  `CreateConfiguredTableAnalysisRule`, `UpdateConfiguredTableAnalysisRule`, and
  `DeleteConfiguredTableAnalysisRule` are default management events.
- Successful `UpdateConfiguredTable` recorded the new Glue database/table, and the analysis-rule
  calls recorded the complete policies. Failed conditional-authorization calls named the missing
  permission-only action.
- `iam:PassRole` produces no standalone event; the Clean Rooms API event carries the role ARN.
- Protected-query CloudTrail events redact SQL, so analysis logging is needed for query-level audit.
- Native EventBridge events cover collaboration/membership changes and protected query/job lifecycle;
  API calls are also delivered through CloudTrail/EventBridge on a best-effort basis.
- S3 reads/writes require S3 data-event coverage. Cross-account audience job starts are a documented
  blind spot in the configured-model owner's CloudTrail.

## Cleanup and residue verification

Deleted the configured table and LIST analysis rule, both Glue tables and database, the temporary IAM
user and access keys, and the unused temporary IAM role/policy. No S3 bucket, object, collaboration,
membership, query/job, model, audience, or output was created.

Independent post-cleanup inventory returned:

- zero Clean Rooms collaborations, memberships, and configured tables;
- zero Clean Rooms ML audience models, configured audience models, configured model algorithms, and
  training datasets;
- no IAM users or roles matching the `ht-cr-audit` prefix; and
- `EntityNotFoundException` for the disposable Glue database.

No unexpected AWS security defect was observed, so no report was written under
