# Amazon Braket audit — 2026-09-27

## Scope and result

Reviewed the current Braket API/IAM model, Hybrid Jobs execution semantics, device/task/job
enumeration, spending limits, unauthenticated access, telemetry and the existing generic
ML/data-access PassRole catalog.

One high-value expected-feature technique was retained as a dedicated page:
`braket:CreateJob` plus `iam:PassRole` executes attacker-controlled Python or a custom container as
the passed execution role. The previous catalog row was accurate but did not explain exact
prerequisites, impact, API shape, logs, stealth or defensive separation.

## Least-privilege evidence

CloudTrail retained two 2026-09-23 requests from the prior disposable role
`ht-audit-pr-braket`. The request specified a deliberately nonexistent role, device and output path
and could not create a valid job. The caller had `braket:CreateJob` but no `iam:PassRole`; Braket
returned:

`not authorized to perform: iam:PassRole on resource: arn:aws:iam::228478051196:role/htnonexistentzzz`

Both events were `Management`, `readOnly:false`, under `braket.amazonaws.com`. Request parameters
included job/device/role/instance/output configuration. Current IAM inventory confirms that the
disposable role is absent, and current Braket inventory confirms that no job resulted.

An end-to-end Hybrid Job was intentionally not launched: jobs consume billable managed compute and
their control-plane history has no delete API. AWS's current API/developer documentation explicitly
defines the caller-controlled code/container, execution role and result directory, so the execution
semantics are expected service functionality rather than an unverified exploit claim.

## Other ideas reviewed

| Candidate | Decision |
| --- | --- |
| `GetJob` steals credentials/results | Rejected. It returns configuration/paths, not role credentials or S3 objects. Useful role/code/data-path recon remains on the enum page. |
| `GetQuantumTask` returns result data | Rejected. It returns result S3 location and program metadata; S3 access remains separate. |
| Mutable script object/ECR tag poisons a later legitimate job | Real generic S3/ECR supply-chain pattern, but requires separate write permission and an external scheduler/pipeline. Not presented as a distinct Braket primitive. |
| `CreateQuantumTask` as code execution | Rejected for IAM escalation. It runs a supported quantum program on the selected device and has no caller-selected execution role. |
| Delete/update a spending limit | Cost-control weakening or availability only; it does not grant task/device/IAM access. Kept as defensive inventory, not a standalone book attack. |
| Cancel jobs/tasks | Availability-only; excluded. |
| Customer resource-policy/RAM persistence | Rejected; no job/task resource-policy or share API exists. |
| Unauthenticated device/job/task access | Job search was auth-required. Public AWS device marketing/specification data is not victim-account reconnaissance. |

## Telemetry

- All Braket API calls are documented CloudTrail management events.
- `CreateJob` exposes the selected role and execution configuration; `iam:PassRole` has no separate
  CloudTrail event.
- Hybrid Job stdout/stderr is stored under `/aws/braket/jobs` in CloudWatch Logs.
- Script/input/result/checkpoint object access needs S3 data events; image retrieval needs ECR
  telemetry.
- Attacker code's AWS calls use the execution role and should be correlated to the job start and
  role session.
