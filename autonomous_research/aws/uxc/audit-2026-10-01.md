# AWS User Experience Customization audit — 2026-10-01

## Result

Published the missing UXC service inventory and one bounded post-exploitation technique. A principal with only wildcard `uxc:UpdateAccountCustomizations` can replace the account-wide visible-service and visible-Region lists and set the account color, manipulating AWS Management Console navigation for every account user.

This is expected functionality and not an authorization bypass. It is useful defense evasion/operator confusion, but it does not modify IAM, suppress telemetry, block direct console URLs or affect CLI/SDK/API access. No AWS vulnerability report was created.

## Service and authorization surface

- Service/IAM/signing prefix: `uxc`.
- Operations: `GetAccountCustomizations`, `ListServices`, and `UpdateAccountCustomizations`.
- Fields: `accountColor`, `visibleServices`, and `visibleRegions`.
- Settings are account-level. Immediate reads from `us-east-1` and `eu-west-1` returned the same color and visibility state during a dedicated propagation check.
- UXC supports no resource ARN and no service-specific IAM condition key. Current actions therefore require `Resource: "*"`.
- The current full-setting actions are `uxc:GetAccountCustomizations`, `uxc:ListServices`, and `uxc:UpdateAccountCustomizations`.
- The Service Authorization Reference also maps the get/update operations to legacy field-specific color actions: `GetAccountColor`, `PutAccountColor`, and `DeleteAccountColor`.
- Both unsigned `GetAccountCustomizations` and the signed APIs require AWS credentials; no resource policy, public token or cross-account share exists.

## Verified minimum and effect

A disposable IAM user was given only:

```json
{
  "Effect": "Allow",
  "Action": "uxc:UpdateAccountCustomizations",
  "Resource": "*"
}
```

Without any UXC read, list, IAM, target-service or other permission it successfully set:

```json
{
  "accountColor": "red",
  "visibleServices": ["ec2", "cloudtrail"],
  "visibleRegions": ["us-east-1"]
}
```

An administrator read the same account-wide lists from another Region. A separate bounded check set `lightBlue`; both allowed Regions returned it immediately and continued to agree at later reads. The earlier one-off color disagreement is therefore recorded as likely short propagation rather than a regional security boundary.

Official documentation confirms the UI effect:

- a hidden service is unavailable in the Services menu and greyed out in Unified Search, Recently Visited, and Favorites;
- a hidden Region leaves the Region selector;
- direct navigation shows an overlay explaining that the service/Region is hidden;
- Unified Settings remains available; and
- CLI, SDK, and other API access is unchanged.

The result is public as console-only defense evasion, not privilege escalation or persistence. The durable setting outlives the caller's session, but it does not preserve attacker access.

## Telemetry

CloudTrail Event History contained the successful restricted-user writes under `uxc.amazonaws.com`:

| Event | Category | Observed content |
| --- | --- | --- |
| `UpdateAccountCustomizations` | Default management write | IAM user identity, source/user agent, exact supplied lists/color, resulting fields, `readOnly:false`, and `AWS::UXC::AccountCustomization` resource |
| `ListServices` | Management read in live Event History | Pagination input; successful `responseElements:null` |
| `GetAccountCustomizations` | Optional data event per AWS documentation | Not present in default Event History; requires an advanced selector for `AWS::UXC::AccountCustomization` |

This makes the mutation Low stealth. UXC does not suppress later target-service logs.

## Reset and API inconsistencies

The API documentation says to reset list fields by supplying JSON `null`. Two implementation details were recorded:

1. AWS CLI 2.37.6 omitted explicit null list fields from the serialized request, so a CLI request containing null did not reset the existing values.
2. A correctly SigV4-signed raw `PATCH` with explicit null fields reached the live `uxc.us-east-1.api.aws` endpoint but returned HTTP 400 `Invalid request body`.

Submitting empty lists succeeded and restored the live API state to empty arrays; the CloudFormation documentation also defines an omitted property or empty array as the reset representation. This is a documentation/client compatibility issue without demonstrated security impact, so it was not treated as a vulnerability.

The API reference examples use the `uxc.us-east-1.amazonaws.com` host while the current CLI resolves the `.api.aws` endpoint. This did not create an authorization difference.

## Negative and bounded candidates

| Candidate | Result | Disposition |
| --- | --- | --- |
| Hide a service to prevent access | Direct URL and CLI/SDK/API access remain available | Cosmetic navigation control only |
| Hide a Region to conceal resources from APIs | Region is removed only from the console selector | No API or IAM effect |
| Suppress security telemetry | Target-service logging is unchanged; the UXC write itself is a management event | Negative |
| Anonymous enumeration or mutation | Unsigned request failed authentication | Negative |
| Resource-scoped grant | No UXC resource ARN exists | Wildcard-only IAM boundary documented |
| Cross-account customization | No resource policy/share mechanism exists | Requires a target-account principal |
| JSON-null reset | Current raw endpoint rejected it | Low-impact compatibility/docs issue only |

## Cleanup

The account color was restored to `none`; visible services and Regions were restored to empty/default arrays. Independent reads in `us-east-1` and `eu-west-1` returned:

```json
{
  "accountColor": "none",
  "visibleServices": [],
  "visibleRegions": []
}
```

The disposable access key, inline policy and IAM user were deleted. A final IAM inventory found no `ht-uxc-*` user. No compute, storage, logging or paid service resource was created.

## Follow-up ideas

- Recheck raw JSON-null reset behavior after service/SDK updates.
- Verify whether legacy `PutAccountColor`/`DeleteAccountColor` grants are treated as field-specific alternatives to the current update action under explicit-deny combinations.
- Monitor for future UXC fields that may affect more than console appearance.
- Test organization-policy interactions if AWS later adds organization-wide customization or delegated administration.
