## Current surface reviewed

The current action model includes cluster, user, ACL, snapshot, parameter-group, subnet-group and Multi-Region CRUD; `BatchUpdateCluster`, `FailoverShard`, `PurchaseReservedNodesOffering`, service-update and node-update discovery, tagging, and the permission-only `Connect` and `PauseMultiRegionClusterReplication` actions. MemoryDB publishes resource ARNs for ACLs, clusters, Multi-Region clusters/parameter groups, parameter groups, reserved nodes, snapshots, subnet groups and users. It supports resource/request tag conditions plus `memorydb:TLSEnabled` and `memorydb:UserAuthenticationMode` on the documented actions.

Important authorization relationships rechecked:

- `memorydb:Connect` requires both cluster and user resources.
- `memorydb:UpdateACL` requires the ACL and each referenced user.
- `memorydb:CreateCluster` can depend on ACL, parameter-group, snapshot, subnet-group and Multi-Region resources.
- `memorydb:UpdateCluster` has a required cluster resource and optional ACL and parameter-group resources. Security-group IDs are request values, not EC2 resources evaluated by IAM for this action.
- MemoryDB exposes no resource-based IAM policy that directly grants a foreign account data-plane access.

## New valuable technique retained

### `UpdateCluster` can cross the ACL and security-group controls

`UpdateCluster` can replace either or both of these existing cluster controls:

1. `ACLName=open-access` associates the immutable passwordless `default` user and its unrestricted access string with a TLS-enabled cluster.
2. `SecurityGroupIds=[...]` replaces the cluster's security-group set with existing groups in the same VPC. This requires no `ec2:*` permission.

This is materially different from creating or modifying a user: an attacker with `UpdateCluster` but no user-management permission can remove authentication by selecting the account's pre-existing immutable `open-access` ACL. It is also materially different from modifying an EC2 security group: cluster-only MemoryDB authorization can move the service behind another existing network policy without `ec2:AuthorizeSecurityGroupIngress` or `ec2:ModifyNetworkInterfaceAttribute`.

Boundaries:

- ACL swap minimum: `memorydb:UpdateCluster` on the exact cluster ARN and exact destination ACL ARN.
- Security-group replacement minimum: `memorydb:UpdateCluster` on the exact cluster ARN only.
- Combined update: both the cluster and destination ACL ARNs.
- The account service-linked role `AWSServiceRoleForMemoryDB` must exist.
- A suitable security group must already exist in the cluster VPC, and the attacker still needs a route to the VPC. The action does not create an IPv4 public endpoint.
- Cluster updates are asynchronous and persistent. Replacing the entire group list or ACL can disrupt the application.

Public action: added `src/pentesting-cloud/aws-security/aws-post-exploitation/aws-memorydb-post-exploitation/README.md` with impact, exact minimum resources, commands, logs and stealth.

## Least-privilege live evidence

Two disposable roles (`ht-memorydb-updatecluster-probe-927` and `ht-memorydb-updatecluster-probe-928`) were used for authorization-boundary tests. Policies contained no `ec2:*` action and scoped `memorydb:UpdateCluster` to synthetic target resources in this account.

| Probe | Policy resources | Request | Result and interpretation |
| --- | --- | --- | --- |
| A | Synthetic cluster ARN only | `UpdateCluster --acl-name open-access` | `AccessDenied` named the exact `acl/open-access` ARN. The destination ACL is an independently required resource. |
| B | Synthetic cluster ARN only | `UpdateCluster --security-group-ids sg-0123456789abcdef0` | `ClusterNotFoundFault`. IAM authorization passed without any EC2 permission; service logic attempted cluster lookup. |
| C | Synthetic cluster ARN plus `acl/open-access` ARN | `UpdateCluster --acl-name open-access` | `ClusterNotFoundFault`. Adding the destination ACL resource satisfied the additional authorization check. |

Before the service-linked role existed, otherwise-authorized calls returned `ServiceLinkedRoleNotFoundFault`; this was used as another non-mutating service-logic boundary. A temporary `AWSServiceRoleForMemoryDB` was then created to disambiguate the deeper checks and deleted immediately after the probes. No real cluster existed or was named, so no cluster setting changed.

CloudTrail Event History confirmed:

- denied ACL call: `UpdateCluster` from `memorydb.amazonaws.com`, error naming the missing ACL authorization;
- authorized security-group call: request contained the synthetic cluster name and `securityGroupIds`, followed by `ClusterNotFoundFault`;
- authorized ACL call: request contained the synthetic cluster name and `aCLName: open-access`, followed by `ClusterNotFoundFault`;
- pre-role calls: `UpdateCluster` with `ServiceLinkedRoleNotFoundFault`.

This validates the IAM/resource boundary and logging shape without paying for or changing a data cluster. It is not represented as an end-to-end passwordless engine connection; the ACL behavior and supported cluster modification are documented AWS functionality.

## Existing valuable coverage revalidated

| Technique | Current finding |
| --- | --- |
| `memorydb:Connect` | Still requires cluster and user ARNs; token creation is local, token lifetime is 15 minutes, a successful connection can last up to 12 hours, and the user's engine access string remains the final boundary. |
| `UpdateUser` | Still replaces passwords without the old password and can widen the access string. Existing post-exploitation/persistence coverage remains accurate. |
| `CreateUser` + `CreateACL`/`UpdateACL` | Still the direct durable password-user plant. Existing persistence coverage remains accurate. |
| `CopySnapshot --target-bucket` | Still a high-value full-dataset RDB export without cluster network access. AWS explicitly warns that anyone with `CopySnapshot` can create a bucket and export a snapshot. The snapshot and bucket must initially be in the same Region. Export is not supported for clusters using data tiering. |
| `open-access` | Still an immutable ACL containing the unrestricted passwordless `default` user. It is exploitable only when associated with a cluster and when the endpoint is network-reachable. |

The same-Region and data-tiering boundaries should be added when the pending MemoryDB enum page is next integrated; they do not justify duplicating that already-pending page in this shared checkout.

## Rejected, bounded, or queued ideas

| Idea | Finding | Decision |
| --- | --- | --- |
| IPv6 creates an Internet-facing MemoryDB endpoint | Current MemoryDB supports dual-stack and IPv6-only clusters and engine/DNS discovery of IPv6 node addresses. However, AWS still documents MemoryDB nodes as VPC-attached with private subnet addresses and provides no public-access flag. Whether a globally routable IPv6 address plus an IGW route and `::/0` security group accepts unsolicited Internet traffic was not proved. | Credible future live-test lead only. Do not publish or report as a defect without an isolated low-cost cluster and an external IPv6 vantage point. |
| Change `IpDiscovery` on a dual-stack cluster | Chooses whether engine discovery returns IPv4 or IPv6. It does not change the immutable cluster `NetworkType` or independently create reachability. | Recon/network-composition detail, not a standalone attack. |
| Parameter-group `slowlog-log-slower-than=0` | Could make SLOWLOG record all executed commands if a caller already has engine access and the relevant engine command is supported. It may expose arguments, but needs a live cluster and command authorization; no AWS control-plane API retrieves the log. | Research lead only; not high-confidence enough for the book. |
| Keyspace notifications | Can reveal key names/events to a subscriber who already has data-plane access, but does not expose values or cross an ACL by itself. | Too weak/duplicative. |
| Vector-search ACL bypass | Current documentation requires a user's key permissions to cover all possible vector-index prefix keys; no concrete prefix/filter bypass or cross-index leakage was identified. | Fuzzing lead only. |
| Crafted RDB import/parser fault | External RDB seeding reaches an AWS-managed parser and remains a plausible vulnerability surface. No safe evidence of a defect exists, and meaningful fuzzing requires repeated paid cluster launches. | Private research queue only; no report created. |
| Cross-account cluster/snapshot policy | MemoryDB has no resource-based policy and no snapshot-sharing attribute API. Snapshot export to a suitably configured S3 bucket remains the practical cross-account path. | No new technique. |
| Multi-Region cross-account copy | Multi-Region members remain owned by one account; this is regional replication, not direct cross-account exfiltration. Minimum node sizes also make speculative testing wasteful. | Rejected. |
| `PauseMultiRegionClusterReplication` | Permission-only action with availability/replication impact, not a new privilege, persistence, or sensitive-information primitive. | Below book quality bar. |
| Generic delete/failover/scaling/reservation abuse | Real sabotage or cost impact, but not privilege escalation, persistence, unauthenticated access, or sensitive-data post-exploitation. | Track as defensive risk, do not promote as a technique. |
| Mutable tag/ABAC self-tagging | Matters only when another flawed victim policy already trusts mutable resource tags for authorization. | Generic conditional-policy composition, not MemoryDB-specific. |

## Telemetry and stealth conclusions

- `UpdateCluster`, user/ACL writes, snapshots, exports, parameter changes, failovers and deletion are CloudTrail management events.
- `UpdateCluster` request parameters expose the requested ACL and security-group IDs; this is the primary signal for the new technique.
- `memorydb:Connect` token creation is local SigV4 signing. Successful engine authentication and Valkey/Redis commands are not per-command CloudTrail events.
- `AuthenticationFailures` and `CommandAuthorizationFailures` are aggregate CloudWatch metrics, with failure details in `ACL LOG`; they do not audit successful commands.
- VPC Flow Logs expose connection metadata only when enabled on the relevant interface/subnet/VPC. Ordinary MemoryDB metrics expose aggregate volume and latency, not exact keys or commands.
