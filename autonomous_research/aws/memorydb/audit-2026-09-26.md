## Scope and environment

## Useful techniques retained

| Idea | Result / boundary | Book action |
| --- | --- | --- |
| Use `memorydb:Connect` with an IAM-enabled database user | High-value post-exploitation path. `Connect` is permission-only and must cover both the cluster and user ARNs. The SigV4 token is generated locally, is valid for 15 minutes, and can back a connection lasting up to 12 hours. It still requires an engine version >= 7, an IAM-authenticated user in the attached ACL, network reachability and permissions in that user's access string. | Added a post-exploitation section to `aws-memorydb-enum.md`. |
| Connect without credentials to a cluster using `open-access` | High-value misconfiguration path. The immutable `default` user is passwordless and broadly privileged, but is usable only on clusters explicitly attached to the immutable `open-access` ACL. MemoryDB has private VPC IPs, so network reachability and security-group access remain prerequisites. | Added a dedicated unauthenticated-access page and linked it from the enum page and `SUMMARY.md`. |
| Reset/widen an existing user with `UpdateUser` | Already covered. The password-reset post-exploitation and access-string persistence variants accurately distinguish existing rights from privilege expansion. | Retained existing coverage. |
| Plant a password user with `CreateUser` plus `CreateACL`/`UpdateACL` | Already covered and previously live-validated. | Retained existing persistence coverage. |
| Export an RDB with `CopySnapshot --target-bucket` | Already covered. This is the cleanest no-network full-dataset exfiltration path; creating a fresh snapshot additionally needs `CreateSnapshot`. | Retained existing coverage. |

## Rejected, bounded or duplicate ideas

| Idea | Finding | Decision |
| --- | --- | --- |
| Direct cross-account MemoryDB resource policy | MemoryDB explicitly reports no support for resource-based IAM policies. Direct cross-account `Connect` therefore lacks the resource-side grant; the external principal must first assume an authorized identity in the owning account. | Rejected as a direct cross-account technique. |
| Public or account-shared MemoryDB snapshot | The current API exposes no `ModifySnapshotAttribute`/share operation. Snapshot export can target a suitably configured S3 bucket, including cross-account, and that useful boundary is already documented. | Rejected duplicate/nonexistent sharing primitive. |
| Abuse Multi-Region membership for cross-account exfiltration | A Multi-Region cluster and all regional clusters are owned by one AWS account. Adding a regional member can duplicate data to another Region, not another account, and requires an expensive `db.r7g.xlarge`-or-larger fixture. | Rejected as cross-account; no paid test. |
| Restore a victim snapshot into an attacker-accessible cluster | Feasible with `CreateCluster` plus access to the snapshot, ACL, subnet/security-group configuration and KMS/S3 dependencies. It is slower, costlier and permission-heavier than `CopySnapshot` export. | Not promoted; mostly inferior duplicate. |
| `UpdateCluster --acl-name` / `--security-group-ids` as standalone access | Can attach a permissive ACL or attacker-reachable security group, but each solves only one layer. It still needs a usable user/ACL and network path; creating a password user or resetting one is already documented more directly. | Recorded as a composition step, not a separate technique. |
| `TagResource` against tag-based IAM | Could matter only when a victim policy independently trusts mutable MemoryDB resource tags. This is generic ABAC self-tagging and no concrete default privilege boundary exists. | Not promoted. |
| Parameter-group command execution / module loading | MemoryDB blocks `CONFIG`, `DEBUG`, `MODULE`, `REPLICAOF`, `SAVE`, `SHUTDOWN` and related managed-service escape commands. The published parameter surface does not provide an OS code-loading primitive. | Rejected expected attack; retain as a future parser/configuration review lead. |
| RDB parser attack via `CreateCluster --snapshot-arns` | Importing a crafted external RDB reaches AWS-managed parsing and is a plausible fuzzing/zero-day surface, but no safe evidence of a vulnerability exists. A meaningful test needs corpus generation and paid cluster launches. | Research lead only; not a book technique or zero-day report. |
| `iam:CreateServiceLinkedRole` for MemoryDB | Creates the fixed `AWSServiceRoleForMemoryDB` service-linked role; it does not let the caller select an arbitrary execution role or gain its credentials. | Rejected as privilege escalation. |
| `PauseMultiRegionClusterReplication` | Permission-only control with availability/replication impact, not a new information, privilege or persistence primitive; Multi-Region fixtures are costly. | Not promoted. |
| Destructive `DeleteCluster`, snapshot deletion, failover and parameter changes | Valid sabotage/ransomware actions, but not privilege escalation, persistence or sensitive-information post-exploitation under the book's technique quality bar. | Tracked but not promoted. |
| Read APIs leaking passwords | `DescribeUsers` returns authentication type/count and access string, never the password. `DescribeClusters` exposes topology/endpoint but does not bypass VPC or ACL controls. | Recon only; existing enumeration is sufficient. |
| Public Internet endpoint | MemoryDB nodes have private VPC IPs. Even a security group permitting `0.0.0.0/0` does not give a node a public IP. VPN, peering, Direct Connect, Transit Gateway, a proxy or a compromised workload is still required. | Correctly bounded unauthenticated coverage to reachable private networks. |

## Telemetry conclusions

- MemoryDB management API calls such as `CreateUser`, `UpdateUser`, `UpdateACL`, `CreateSnapshot` and `CopySnapshot` are CloudTrail management events.
- IAM token generation for `memorydb:Connect` is local SigV4 signing; successful engine `AUTH`/`HELLO` and Valkey/Redis commands are not per-command CloudTrail events.
- `AuthenticationFailures` and `CommandAuthorizationFailures` provide aggregate CloudWatch signals, with details available through `ACL LOG`; they describe failures, not a successful-command audit trail.
- VPC Flow Logs can expose connection metadata only when enabled on the relevant network scope. Ordinary MemoryDB metrics may reveal volume/latency changes but not the exact keys or commands.

## Cleanup

No AWS resources were created or modified during this audit. A final read-only inventory still showed zero clusters, snapshots and Multi-Region clusters; the only user/ACL were the service-created immutable `default` and `open-access` objects. There is therefore no test infrastructure to delete.
