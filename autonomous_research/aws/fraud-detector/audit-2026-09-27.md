# AWS Fraud Detector audit - 2026-09-27

## Scope and lifecycle

- Authorized account: `228478051196`; tested Region: `us-east-1`.
- AWS stopped accepting new Fraud Detector customers on November 7, 2025; existing customers can continue using it.
- `us-east-1` accepted live APIs and began with no event types. Sampled unused Regions returned customer-availability or SCP access denials, so no multi-Region fixtures were created.
- Testing used only zero-compute control-plane objects, synthetic stored events and rules/detector versions. No model training, prediction, batch job, SageMaker endpoint or paid compute was started.

## Surfaces reviewed

- Stored-event/event-type enumeration, exact resource authorization, blind ingestion/replacement, relabeling and deletion.
- Variables, labels, entity types, lists, outcomes and KMS configuration.
- Rules, detector versions, activation/default behavior, internal models and external-model delegation.
- Batch import/prediction `iam:PassRole` paths.
- CloudTrail request/response visibility, unauthenticated access and current service availability.

## Verified results

### Exact `GetEvent` discloses a known event without list access

A session allowed only `frauddetector:GetEvent` on the exact event-type ARN and explicitly denied `GetEventTypes` and `GetVariables`. With the known event type and event ID it returned:

- every stored variable/value;
- entity type and entity ID;
- event timestamp;
- current label and label timestamp.

Events do not have separate IAM ARNs; the event-type ARN is the authorization boundary. This is expected sensitive-data access, not a defect.

### Exact `SendEvent` blindly replaced existing data

Initial synthetic event:

```text
event timestamp: fixed T0
variable: original@example.test
label: legit at T0
```

A session allowed only `frauddetector:SendEvent` on the exact event-type ARN and explicitly denied `GetEvent`, `GetEventTypes` and `UpdateEventLabel`. It submitted the same event ID and immutable event timestamp with a later label timestamp, replacing the variable with `replaced@example.test` and the current label with `fraud`. An administrator read confirmed both changes.

Submitting the repeated event ID with a different event timestamp was rejected with `ConflictException`. Reusing T0 but an equal label timestamp was rejected because a replacement label timestamp must be later. The successful path matches AWS's documented event validation rules.

Security value: ingestion-only identities can poison historical event features and labels without read permission, influencing investigations and later training/retraining.

### Exact `UpdateEventLabel` blindly relabeled the event

A second session allowed only `frauddetector:UpdateEventLabel` on the exact event-type ARN and explicitly denied `GetEvent`, `GetEventTypes` and `SendEvent`. It changed the current label back from `fraud` to `legit` with a later label timestamp. The variable replacement remained.

This is expected feedback-loop authority and should be isolated to adjudication roles.

### Exact detector-version status permission changed the default logic

The fixture contained:

```text
version 1: ACTIVE, original rule/outcome
version 2: DRAFT, replacement rule/outcome
```

A session allowed only `frauddetector:UpdateDetectorVersionStatus` on the exact version-2 ARN and explicitly denied `GetDetectorVersion`, `DescribeDetector`, `CreateDetectorVersion` and `UpdateDetectorVersion`. It promoted version 2 to `ACTIVE`; version 1 automatically became `INACTIVE`.

Only one version can be active and predictions omitting a version use it. Therefore status-only access to a known staged version is sufficient to switch the application's default fraud-decision logic. This is expected service-level persistence, not an authorization bypass.

## CloudTrail observations

All tested operations appeared as CloudTrail management events with `eventSource=frauddetector.amazonaws.com`.

- `GetEvent` included event type and event ID, was `readOnly=true`, and omitted returned event content from `responseElements`.
- Successful `SendEvent` was `readOnly=false` and included event ID/type/timestamps and assigned label. Event variable keys were visible but each value was `HIDDEN_DUE_TO_SECURITY_REASONS`; entities were also replaced with that marker.
- `UpdateEventLabel` included the event ID/type, assigned label and label timestamp.
- `UpdateDetectorVersionStatus` included detector ID, version ID and status.
- Explicitly denied `GetEvent` appeared with `errorCode=AccessDenied` and null request parameters.

## Candidate vulnerabilities tested and rejected

- **Read without list permission:** works by documented exact-resource authorization; it is a useful known-ID technique, not an AWS defect.
- **Blind event overwrite:** works when the immutable event timestamp matches and the new label timestamp is later; AWS documents repeated-event timestamp validation and `SendEvent` storage semantics.
- **Status-only version activation:** works on the exact staged version and is the intended purpose of `UpdateDetectorVersionStatus`.
- **Timestamp mutation:** rejected with `ConflictException`.
- **Stale/equal label timestamp:** rejected with `ValidationException`.
- **Unsigned account inventory:** no unauthenticated inventory path was found; control-plane APIs require SigV4.
- **Cross-Region customer availability as an IAM bypass:** rejected. Availability/SCP denials are account lifecycle and organization controls.
- **Batch-role arbitrary execution:** not claimed. Batch import/prediction are constrained S3 data jobs, already covered by the shared ML/analytics PassRole page.

No unexpected AWS security defect or zero-day was confirmed, so no private report was created.


Rules and detector versions were deleted before their parent detector. The synthetic event and audit history were deleted before the event type; labels, entity type and variable were then removed. No S3 bucket, IAM role/policy, model, external model, list, endpoint, process or background cleanup job was created.
