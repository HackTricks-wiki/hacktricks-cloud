## Cross-account export boundary

AWS documents that a Data Export bucket may be in a designated destination account. That account grants `s3:PutObject` to `bcm-data-exports.amazonaws.com`, constrained by the victim `aws:SourceAccount` and source export ARN pattern. This is intended cross-account delivery, not a resource-policy bypass.

CUR 2.0 can include linked-account names/IDs, resource identifiers, resource/account/cost-category tags, product details, discounts and—where supported—Bedrock caller IAM principal attribution. The schedule refreshes as source data changes, up to three times daily. Reading delivered objects is authorized by the destination bucket, not by Data Exports.

Decision: retain as both post-exploitation and cross-account service-level persistence. It provides materially more detailed and recurring intelligence than a one-time Cost Explorer aggregate query.

## Live minimum-permission matrix

Two isolated IAM-user cycles used a syntactically valid CUR 2.0 query and a deliberately nonexistent S3 bucket, so no export could deliver data.

| Policy state | Result |
| --- | --- |
| `CreateExport` only on the exact `COST_AND_USAGE_REPORT` table ARN | Denied specifically for `bcm-data-exports:CreateExport` on `arn:aws:bcm-data-exports:us-east-1:228478051196:export/*`. |
| Add the prospective `export/*` ARN | Passed the Data Exports resource checks and was denied specifically for `cur:putReportDefinition`. |
| Add `cur:PutReportDefinition` on `*` | Reached service validation: `ValidationException: S3 bucket permission validation failed`. |

The live service therefore requires `CreateExport` on both the source table and prospective export pattern. The current service-authorization action row shows the table (and optional billing view) but does not list the prospective export resource. Public technique prerequisites use the empirical requirement so a least-privilege proof works.

No `iam:PassRole` is involved. `UpdateExport` can retarget stored export configuration when the caller holds its export/table/billing-view permissions and the destination passes the same policy validation.

## Telemetry

- `ListExports`, `ListTables`, and `GetTable` appeared as `readOnly:true` CloudTrail management events from `bcm-data-exports.amazonaws.com` in `us-east-1`.
- `CreateExport`, `UpdateExport`, and `DeleteExport` are management writes. The creation request contains the stored query, table properties, bucket owner/name/prefix and output configuration.
- Scheduled S3 delivery is service-principal `PutObject` activity. Object-level evidence and later reads depend on S3 data/access logging in the destination account.
- `ListExports` plus `GetExport` is the essential defensive reconciliation because it recovers the destination and complete stored query.

## Rejected or bounded ideas

| Idea | Result |
| --- | --- |
| Unsigned export/table inventory | Rejected; authentication required. |
| `GetTable` directly leaks cost rows | Rejected; it returns table metadata only. |
| `GetExecution` returns report objects without S3 access | Rejected; it provides export execution/status context, not an S3 authorization bypass. |
| `CreateExport` alone is sufficient | Rejected for CUR 2.0; actual service checks the table, prospective export, and `cur:PutReportDefinition`. |
| `iam:PassRole` escalation | Rejected; Data Exports uses its service integration/service-linked role and no caller-selected role ARN. |
| Immediate end-to-end delivery test | Not justified: delivery can take hours and requires an external bucket fixture. The API authorization and S3 policy boundary were isolated without persistent infrastructure. |
