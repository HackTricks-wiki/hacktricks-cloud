## Live tests

### Metadata fixtures

Created a disposable schema mapping with dummy `customer_id`/`email` fields and an ID namespace referencing a deliberately nonexistent Glue table. Entity Resolution accepted the metadata without reading data. The source namespace required exactly one mapping-property object, input-source configuration and a `roleArn`.

`GetSchemaMapping` returned field names, PII types, match key and cleartext/hash flag. `GetIdNamespace` returned the Glue table ARN, schema, rules and job role. This validates the reconnaissance value of exact-resource reads.

### Resource-policy round trip

`AddPolicyStatement` accepted an alphanumeric statement ID, the owning 12-digit account principal and `entityresolution:UseIdNamespace`. `GetPolicy` returned a standard JSON policy granting the account-root principal and a revision token. The API principal shape permits a 12-digit account or service principal, not an arbitrary IAM role ARN.

The statement was deleted before the namespace. Result: documented cross-account persistence/sharing behavior, not a public endpoint or arbitrary role-principal self-escalation.

The preceding 2026-09-26 disposable-workflow test also established that
`AddPolicyStatement` accepts supported matching-workflow actions such as
`GetMatchingWorkflow` and `StartMatchingJob` for an account principal. The same earlier audit found
that a schema-mapping ARN is rejected for policy attachment and documented the per-run
`StartIdMappingJob.outputSourceConfig` redirect. Those stronger results remain in the reorganized
public pages.

### PassRole boundary

Created a no-permission job role trusting `entityresolution.amazonaws.com` and a separate test caller whose only service permission was `entityresolution:CreateIdNamespace` on `*`. Creating a role-bearing namespace failed with an explicit missing `iam:PassRole` on the exact job role; no resource was created.

Result: the role-bearing namespace path enforces PassRole. Official workflow APIs similarly accept a caller-selected job role and the documented console policy constrains role names/PassRole. Published role pivot is bounded to supported Glue/S3/KMS data movement, not arbitrary code execution or raw credential theft.

### Authentication and CloudTrail

Native operations require SigV4; an unsigned `ListSchemaMappings` call returned `MissingAuthenticationTokenException`. Resource policies support account/service principals for authenticated cross-account workflows. No unauthenticated or bearer endpoint exists.

AWS documents every Entity Resolution API as a CloudTrail event with `eventSource=entityresolution.amazonaws.com`. Control-plane requests expose resource/configuration changes; downstream job access must also be detected in Glue, S3 data events and KMS. Match-ID requests can place supplied PII attributes in request logging.

## Published techniques

- Enum: complete current inventory, IAM/resource boundaries, providers, policy and Match-ID surfaces.
- Post-exploitation: metadata/data-lake reconnaissance; `GetMatchId` membership/linkage oracle; schema/workflow poisoning.
- Privilege escalation: pass a service role to supported matching/ID-mapping workflows to read/export role-authorized data.
- Persistence: authenticated cross-account `UseIdNamespace`/`UseWorkflow` resource-policy grant.

## Exclusions and failed ideas

- No general role credential theft/RCE: Entity Resolution executes fixed matching operations, not attacker code.
- No policy self-escalation to an IAM role: `AddPolicyStatement` only accepts account IDs or service principals. Account delegation still requires recipient IAM authorization.
- No public/anonymous policy technique: the sharing model is authenticated AWS account/service use.
- No live matching/ID-mapping job: the account had no real Glue input and jobs may incur cost. Role/data behavior is documented and PassRole was live-verified without starting a job.
- No `GenerateMatchId`: AWS states it incurs charges and persists/updates records. `GetMatchId` requires a previously successful workflow, so it was documented from the official API rather than artificially creating PII/job state.
- Delete/batch-delete and destructive retention effects are obvious availability operations, not distinct high-value techniques.
- Provider-service workflows require subscriptions and provider permissions; no safe/provider-neutral exploit path was identified.
- Updating a schema/workflow is valuable poisoning only when a later job runs; it does not by itself bypass Glue/S3/KMS.
- No unexpected AWS defect was confirmed; no private report was created.
