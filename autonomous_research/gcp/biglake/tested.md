# BigLake / Lakehouse — tested and reviewed

## 2026-09-28 — end-to-end documentation and local CLI audit

- No project resource API was called and no resource, IAM policy, object, query job, or billable workload was created. The review used current official Google Cloud documentation, public REST contracts, read-only predefined-role metadata, and local `gcloud`/`bq` help.
- Separated three previously conflated products: BigQuery Cloud Storage BigLake tables, the current Lakehouse runtime catalog Iceberg REST surface, and BigLake metastore (classic). Their resource paths, identities, permissions, and audit namespaces are materially different.
- Confirmed from local stable CLI help that current Iceberg catalog commands are `gcloud biglake iceberg ...`, not alpha-only, and that catalog/namespace/table resources are project-scoped without `--location`. Confirmed `get-iam-policy` and `set-iam-policy` subcommands for Iceberg catalogs and tables.
- Confirmed the BigQuery access-delegation boundary: creating a Cloud Storage BigLake table needs `bigquery.tables.create` and `bigquery.connections.delegate`; SQL also needs `bigquery.jobs.create`. Querying needs `bigquery.jobs.create`, `bigquery.tables.get`, and `bigquery.tables.getData`, plus `bigquery.readsessions.create` only for Storage Read API use. The connection service account, not the caller, reads Cloud Storage.
- Retained connection delegation as privilege escalation only when a caller can create a table pointing to a path the connection service account can read but the caller cannot. Existing table access deliberately granted through `tables.getData` is ordinary data access, not escalation.
- Confirmed current Iceberg REST catalog, namespace, and table IAM policy support and exact v1 audit methods:
  `IcebergCatalogIamService.SetIcebergCatalogIamPolicy`, `SetIcebergNamespaceIamPolicy`, and `SetIcebergTableIamPolicy`. Each is non-LRO Admin Activity. The old page's regional resource path and guessed `MetastoreService.SetIamPolicy` method were false for these current IAM resources.
- Confirmed credential vending returns one or more `StorageCredential` objects containing a storage `prefix`, `gcs.oauth2.token`, and expiration. The per-catalog service account needs explicit Storage access; viewer permits reads and editor permits data writes and commits.
- Recorded a telemetry uncertainty precisely: the current audit-method catalog does not list a v1 `LoadIcebergTableCredentials` method. It explicitly identifies the older v1alpha/v1beta variants as no-audit methods, but omits v1 from both its audited and explicit no-audit tables. The book now says “not documented” rather than claiming an impossible-to-detect v1 operation.
- Confirmed current Iceberg `CommitTable` maps to `google.cloud.biglake.v1.IcebergCatalogService.UpdateIcebergTable`, checks `biglake.tables.update`, is non-LRO, and is always-on Admin Activity. Storage writes performed with vended credentials remain Cloud Storage Data Access and are disabled by default.
- Confirmed classic regional `Table.hiveOptions.storageDescriptor.locationUri` remains mutable by `biglake.tables.update`. Its exact audit method is `google.cloud.bigquery.biglake.v1.MetastoreService.UpdateTable`, non-LRO Admin Activity. The technique is bounded to classic metastore consumers, needs a compatible replacement path that those engine identities can read, and is not a universal BigLake MITM.
- Removed/folded catalog recon as a standalone post-exploitation technique, permission-name-only partition tampering without an executable boundary, and destructive catalog/table deletion. Removed classic location repointing from persistence because it poisons data resolution but does not preserve attacker access.
- Corrected logging defaults: BigQuery job/table Data Access logs cannot be disabled; BigLake metadata reads and Cloud Storage object Data Access logs are disabled by default; control-plane IAM, classic updates, and current Iceberg commits are Admin Activity and always on.

## Rejected hypotheses

- **`biglake.tables.getData` directly downloads arbitrary `gs://` objects:** rejected. On the current runtime catalog it authorizes table data access and, in credential-vending mode, produces temporary prefix-scoped credentials. It is not unscoped raw bucket access.
- **BigQuery BigLake tables are governed by `biglake.*`:** rejected. They are BigQuery table and connection resources; the backing Storage access is exercised by the connection service account.
- **Current Iceberg REST tables accept the classic regional PATCH body:** rejected. Current Iceberg tables use the Iceberg REST CommitTable protocol and project/catalog/namespace/table path.
- **A current Iceberg table can be repointed to any attacker bucket:** rejected as a documented general technique. Current table paths must be nested beneath the namespace path and receive a randomized suffix. Arbitrary `locationUri` PATCH applies to the classic Hive-compatible API.
- **Delete-only metadata DoS belongs in the post-exploitation page:** rejected as destructive-only, low-value duplication of obvious CRUD.
- **A resource-level IAM binding is invisible:** rejected. It can evade project-IAM-only inventory, but the set-policy operation is always-on Admin Activity and the resource policy is directly enumerable.

## Open evidence questions

Official role and workflow documentation establishes the read/write boundary, but the v1 REST reference currently omits per-method IAM permission sections for credential loading.

## 2026-09-28 — independent cross-review corrections

- No cloud resource or policy was read or changed. Rechecked the stable SDK 586 command source, generated v1 client, current predefined role metadata, and current official API/audit contracts.
- Replaced the IAM examples' unsafe role-only merge. It previously added the controlled member to every matching role binding, including conditional bindings. The helper now requests policy version 3, retains `etag`, `version`, conditions, unrelated bindings, and audit configuration, and amends only an unconditional binding (or creates one).
- Used the raw v1 IAM read in the safe helper because the current stable SDK 586 generated `get-iam-policy` command does not populate `options.requestedPolicyVersion`; the explicit REST query avoids representing a conditional policy as a lower policy version. The stable table IAM CLI names and positional/flag syntax remain correct.
- Made scope inheritance exact: a catalog binding reaches its namespaces and tables, a namespace binding reaches its tables, and a table binding stays local. A child policy cannot remove a parent grant.
- Confirmed that the stable credential RPC is `google.cloud.biglake.v1.IcebergCatalogService.LoadIcebergTableCredentials`, not `GetTableCredentials`. The stable v1 REST surface, generated SDK client, and current official Go client agree. The current audit page omits that stable v1 method, but explicitly marks only the v1alpha and v1beta `LoadIcebergTableCredentials` methods as producing no audit log; stable v1 telemetry therefore remains undocumented, not proven absent.
- Split SQL DDL telemetry into the Data Access LRO `JobService.InsertJob`/`JobService.Query` event and the separate Admin Activity `BigQueryAuditMetadata.tableCreation` side effect with reason `QUERY`. A direct `TableService.InsertTable` is non-LRO Admin Activity with `TABLE_INSERT_REQUEST` and no SQL job.
- Added the credential-vending header to the raw CommitTable request. Reconfirmed the bounded write chain: `tables.updateData` controls writable delegated storage, `tables.update` authorizes the non-LRO Admin Activity commit, and the catalog service account's Storage Object User grant plus returned prefixes constrain object access.
- Reconfirmed the classic boundary: `tables.update` can patch only the targeted classic table; keeping its server `etag` provides optimistic concurrency, affected engines still need access to the replacement path, and the mutation neither reveals the original objects nor changes current Iceberg REST table locations.
