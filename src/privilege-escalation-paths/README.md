# Шляхи підвищення привілеїв

{{#include ../banners/hacktricks-training.md}}

HackTricks Cloud підтримує машиночитаний каталог підвищення привілеїв, який використовує [Blue-CloudPEASS](https://github.com/peass-ng/Blue-CloudPEASS). Кожна техніка вказує, якими дозволами має фактично володіти суб’єкт і на яких ресурсах, щоб отримати привілеї цільових суб’єктів. Blue-CloudPEASS офлайн оцінює ці записи за знімком інвентаризації, доступним лише для читання, і будує шляхи атак від одного суб’єкта до іншого, зазначаючи як доказ політику або прив’язку, що надає дозвіл, і спосіб усунення шляху. Редагуйте тут канонічні файли, а не їхні копії у споживачі.

Записи описують лише передумови, доступні цілі та спосіб усунення. Вони не містять команд, payloads чи кроків виконання; техніку пояснює пов’язана сторінка HackTricks.

## Структура

Для кожної платформи (`aws`, `gcp`, `azure`, `k8s`) є окремий каталог, а для кожного сервісу — окремий файл `<service>.yaml`, що містить список технік у форматі YAML. У файлах із назвою `_excluded*.yaml` перелічено перевірені техніки HackTricks, для яких навмисно немає записів, наприклад post-exploitation, persistence або технік, які неможливо змоделювати на основі конфігурації; також зазначено причину. `privesc-technique.schema.json` — це експортована JSON Schema для автодоповнення та перевірки в редакторі.

## Поля техніки

- `id`: глобально унікальний ідентифікатор у нижньому регістрі та kebab-case із префіксом платформи.
- `provider`, `service`, `title` і `summary`: одне речення з описом того, що отримує джерело.
- `source`: сторінка HackTricks і якір, де описано техніку, відносно цієї книги. `source_revision` — коміт книги, який було прочитано.
- `requires`: дозволи, якими має володіти джерело. `all_of` містить усі обов’язкові елементи, а `any_of` — альтернативи. Елементи AWS і GCP використовують `action` і `resource`, елементи Azure — `action` (або `data_action`) і `scope`, елементи Entra ID — `entra_permission` або `entra_role`, а елементи Kubernetes — `verb`, `resource`, `subresource`, `api_group` і `namespace`. Заповнювачі на кшталт `{target.arn}` прив’язують вимогу до цілі.
- `target`: цільовий `kind`, `selector` з умовами, які мають виконуватися всі, щоб суб’єкт був досяжним, і його `scope`.
- `conditions` і `blockers`: те, що може завадити реалізації шляху, наприклад ключі умов, SCP, межі або політики admission.
- `confidence`, `severity`, `mitigation`, `references` і необов’язкові `notes`.

Невідомі поля, типи цілей, ключі селектора та заповнювачі відхиляються, а не ігноруються, тож запис не може непомітно розширити чи звузити набір цілей. Спершу додайте підтримку нового селектора в оцінювачі споживача.

## Перевірка та синхронізація

Перед надсиланням змін запустіть `python scripts/validate_privesc_paths.py --book-root .`, попередньо встановивши PyYAML. Скрипт перевіряє структуру каталогів, кожен запис за допомогою суворого завантажувача оцінювача (`scripts/privesc_paths_schema.py`, копії модуля схеми Blue-CloudPEASS), унікальність ідентифікаторів, наявність кожної сторінки `source` у цій книзі та актуальність JSON Schema. Той самий процес перевірки запускається в робочому процесі pull request книги.

Щопонеділка Blue-CloudPEASS отримує поточну версію `master` цієї книги, перевіряє ці файли та порівнює SHA-256 хеш кожного файла з хешами, записаними під час попередньої синхронізації. Додані, оновлені й видалені в upstream файли замінюють незмінені копії у споживачі. Якщо файл змінено з обох боків, про це повідомляється як про конфлікт; ідентифікатори технік ніколи не вилучаються без явного перевіреного реєстру. Некоректний вміст або невдала перевірка залишають гілку за замовчуванням споживача без змін. Не пов’язані з цим зміни книги не призводять до коміту у споживачі.
