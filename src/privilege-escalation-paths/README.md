# Шляхи підвищення привілеїв

{{#include ../banners/hacktricks-training.md}}

HackTricks Cloud підтримує каталог підвищення привілеїв у машинозчитуваному форматі, який використовує [Blue-CloudPEASS](https://github.com/peass-ng/Blue-CloudPEASS). У кожній техніці вказано, які дозволи фактично має мати суб’єкт і на яких ресурсах, щоб отримати привілеї цільових суб’єктів. Blue-CloudPEASS офлайн оцінює ці записи на основі знімка інвентаризації лише для читання та будує шляхи атак між суб’єктами, наводячи політику або прив’язку, що надає доступ, як доказ, а також спосіб усунути цей шлях. Редагуйте тут канонічні файли, а не їхні копії у проєкті-споживачі.

Записи описують лише передумови, доступні цілі та спосіб усунення. Вони не містять команд, payload-ів чи кроків виконання; техніку пояснює пов’язана сторінка HackTricks.

## Структура

Для кожної платформи (`aws`, `gcp`, `azure`, `k8s`) є окрема директорія, а для кожного сервісу — файл `<service>.yaml`, що містить список технік у форматі YAML. У файлах `_excluded*.yaml` перелічено перевірені техніки HackTricks, для яких навмисно немає запису, наприклад post-exploitation, persistence або техніки, які неможливо змоделювати за конфігурацією; також указано причину. `privesc-technique.schema.json` — це експортована JSON Schema для автодоповнення та перевірки в редакторі.

## Поля техніки

- `id`: глобально унікальний ідентифікатор у нижньому регістрі, у форматі kebab-case, із префіксом платформи.
- `provider`, `service`, `title` і `summary`: одне речення з описом того, що отримує джерело.
- `source`: сторінка HackTricks і якір, де описано техніку, відносно кореня цієї книги. `source_revision` — коміт книги, який було прочитано.
- `requires`: дозволи, які має мати джерело. `all_of` перелічує всі обов’язкові елементи, а `any_of` — альтернативи. Для AWS і GCP використовуються поля `action` і `resource`, для Azure — `action` (або `data_action`) і `scope`, для Entra ID — `entra_permission` або `entra_role`, а для Kubernetes — `verb`, `resource`, `subresource`, `api_group` і `namespace`. Заповнювачі на кшталт `{target.arn}` прив’язують вимогу до цілі.
- `target`: цільовий `kind`, `selector` з умовами, які всі мають виконуватися, щоб суб’єкт був доступний, і його `scope`.
- `conditions` і `blockers`: умови, які можуть завадити реалізації шляху, наприклад ключі умов, SCP, межі або політики admission.
- `confidence`, `severity`, `mitigation`, `references` і необов’язкові `notes`.

Невідомі поля, типи цілей, ключі селекторів і заповнювачі відхиляються, а не ігноруються, тож запис не може непомітно розширити чи звузити набір цілей. Спершу додайте підтримку нового селектора в evaluator проєкту-споживача.

### Об’єднання у Schema v2

У завантажувачі v2 додано два заповнювачі та один селектор AWS, а на цілях GCP дозволено використовувати наявний селектор K8s для pod-ів, що працюють. Для цих полів потрібне точне зіставлення зі зібраними даними інвентаризації; якщо дані інвентаризації відсутні, охоплення невідоме, а не доступний шлях.

| Поле | Використання та обов’язкова структура |
| --- | --- |
| `{source.assumable_role_attached_policy_arn}` і `target.selector.via_assumable_role_attached_policy_covered_by: iam:CreatePolicyVersion` | Використовуйте разом для цілі AWS `aws_account_admin`. Кожна альтернатива вимог має містити `iam:CreatePolicyVersion` для цього заповнювача. Політика має бути приєднана до ролі, яку джерело може припустити в тому самому акаунті; evaluator перевіряє доступність версій політики та повторно обчислює ефективні дозволи ролі. `SetDefaultPolicyVersion` не підтримується. |
| `target.selector.k8s_sa_used_by_running_pod: true` | Для цілі GCP `k8s_service_account` з `scope: cluster` вибирає KSA, які використовуються pod-ами, що працюють і мають доступний токен у зіставленому кластері GKE. Не поєднуйте з `k8s_sa_in_cluster` або `k8s_sa_has_token_secret`. Наявне використання K8s не змінюється. |
| `{source_rolebound_clusterrole}` | Використовуйте як `resource_name` у вимогах K8s до `clusterroles` з `api_group: rbac.authorization.k8s.io` і `namespace: "*"`. Кожна альтернатива має вимагати `escalate` і `update` або `patch` для того самого імені. Ціллю має бути `k8s_service_account` з `scope: same_namespace` і `selector.k8s_sa_in_namespace: "{target.namespace}"`; RoleBinding має прив’язувати джерело в цьому namespace. |

## Перевірка та синхронізація

Перед надсиланням змін запустіть `python scripts/validate_privesc_paths.py --book-root .`, попередньо встановивши PyYAML. Скрипт перевіряє структуру директорій, кожен запис за допомогою суворого завантажувача evaluator-а (`scripts/privesc_paths_schema.py`, копії модуля схеми Blue-CloudPEASS), унікальність ідентифікаторів, сторінки джерел і якорі заголовків, а також актуальність JSON Schema. Додайте `--peaso-root /path/to/Blue-CloudPEASS`, щоб також побайтово порівняти обидва файли схеми з версією проєкту-споживача. Та сама перевірка запускається в pull request workflow книги.

Щопонеділка Blue-CloudPEASS отримує поточну версію `master` цієї книги, перевіряє ці файли й порівнює SHA-256-хеш кожного файла з хешами, зафіксованими під час попередньої синхронізації. Нові, оновлені та видалені у вихідному проєкті записи замінюють незмінені копії у проєкті-споживачі. Якщо файл змінено з обох боків, про це повідомляється як про конфлікт, а ідентифікатори технік ніколи не видаляються без явно перевіреного реєстру. Некоректний вміст або невдалий тест залишає гілку за замовчуванням проєкту-споживача без змін. Не пов’язані з цим зміни книги не створюють коміту в проєкті-споживачі.
