# Категоризація ризиків дозволів

HackTricks Cloud підтримує спільні дані про рівень критичності дозволів, які використовують [CloudPEASS](https://github.com/peass-ng/CloudPEASS) і [Blue-CloudPEASS](https://github.com/peass-ng/Blue-CloudPEASS). Редагуйте тут канонічний файл платформи, а не згенеровані копії в будь-якому зі споживачів.

- **Критичний**: дозволи, які безпосередньо або майже незалежно надають потужні привілеї, створюють identity або уможливлюють привілейоване виконання.
- **Високий**: доступ до конфіденційної інформації, облікових даних або умовного шляху підвищення привілеїв.
- **Середній**: DoS/Break, операційні збої, звичайні зміни або умовні можливості без підтвердженого шляху до конфіденційних даних чи привілеїв.
- **Низький**: звичайне виявлення та доступ до метаданих.

Для кожної платформи існує один канонічний YAML-файл: [AWS](aws.yaml), [GCP](gcp.yaml), [Azure](azure.yaml) і [Kubernetes](k8s.yaml). Це машиночитані файли; сторінки платформ пояснюють, як їх редагувати.

## Файли cloud-провайдерів

`version` і `provider` визначають схему. `permission_categories` містить чотири окремі списки дозволів. Перемістіть дозвіл між списками, щоб змінити його оцінку. AWS і Azure під час зіставлення ігнорують регістр; GCP зберігає регістр. Псевдоніми регістру можуть повторюватися в межах одного рівня критичності, але конфліктні оцінки відхиляються.

`severity_overrides` містить перевірені винятки із загальних правил. Якщо виняток також присутній у каталозі, обидва записи мають збігатися. `severity_caps` не дозволяє комбінації підвищувати рівень критичності вибраних дозволів. `non_permission_identifiers` виключає задокументовані назви API-методів, ключі умов та інші рядки, які не є фактичними дозволами авторизації.

`combinations.critical` і `combinations.high` — це списки списків дозволів: кожен елемент внутрішнього списку має бути наданий, щоб комбінація застосовувалася. Не розділяйте комбінації; поділ на окремі дозволи завищить ризик. Наявні поля exact і regular-expression залишаються резервним варіантом для дозволів, відсутніх у каталозі. Повне переписування класифікатора або додавання нової поведінки зіставлення все одно потребує змін у коді споживачів.

## Файл Kubernetes

`rules` упорядкований: застосовується перше відповідне правило. Кожне правило має унікальний `id`, `match`, `severity` і `description` звичайною мовою. Додайте більш специфічне правило перед ширшим або змініть рівень критичності наявного правила. Збережіть фінальний безумовний fallback.

Для композиції зіставлення використовуються `all`, `any` і `not`, або порівняння `field`, `op` і `value`. Доступні поля: `group`, `resource`, `subresource`, `full` (resource/subresource), `verb`, `namespace`, `name`, `path` (URL non-resource у нижньому регістрі), `non_resource_url`, `mode` і `delegated_verb`. Доступні операції: `eq`, `ne`, `in`, `not_in`, `contains`, `prefix`, `suffix` і `truthy` (значення не потрібне). `always: true` відповідає всьому. Значення group, resource, subresource і verb записуються в нижньому регістрі. Літеральний wildcard записується як `'*'`; зіставлення дозволу з wildcard явно вказується в правилах, а не розгортається як шаблон shell.

`severity_when` за потреби вибирає інший рівень критичності для умови зіставлення. `severity: delegated` зарезервовано для обмеженого impersonation: його мапа `delegated_severities` перетворює класифікацію делегованої дії на умовний рівень. Плейсхолдери опису можуть посилатися на доступні поля, наприклад `{full}` і `{verb}`. Правила є даними й ніколи не виконуються як код Python або shell.

## Перевірка та синхронізація

Перед надсиланням змін запустіть `python scripts/sync_hacktricks_permissions.py --book-root . --validate-only` із встановленим PyYAML. Workflow pull request цього book виконує таку саму перевірку.

Щопонеділка обидва репозиторії-споживачі отримують поточний `master` цього book, перевіряють усі чотири файли, порівнюють SHA-256-хеші та оновлюють свої вбудовані YAML-файли й згенеровані legacy-списки. Маніфест джерела містить revision book і хеш кожного файлу. Незв’язані зміни в book не створюють комітів у споживачах. Кожен workflow також підтримує ручний запуск. Тести виконуються до того, як workflow закомітить змінені дані у default branch споживача; у разі помилок ця гілка залишається без змін. Між оновленнями споживачі продовжують використовувати свої вбудовані копії в offline-режимі.

Щоб локально оновити дані у споживачі, запустіть `python scripts/sync_hacktricks_permissions.py --book-root /path/to/hacktricks-cloud`. Додайте `--check`, щоб виявити застарілі копії без їх запису.
